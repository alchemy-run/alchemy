# alchemy-org

A software factory that manages a GitHub repository end to end,
expressed almost entirely as prose: agents whose charters splice the
tools they hire and the skills that teach craft. Code appears only at
the edges — event routing, tool physics, and the entrypoint composition
that decides where the prose runs.

The folder structure is the architecture — `src/` is organized by
DOMAIN, not by kind (there is no `tools/`, `agents/`, or `skills/`
folder; a tool lives with the domain it acts on):

```
src/
  coding/    the Engineer: charter, the toolbox (read/run/edit tools), publishing a PR
  review/    the Reviewer: charter, event router, review tools
  sandbox/   where code runs: sessions' sandboxes, checkouts, output spill
  github/    the connected repositories, proposals, board projection
  alchemy/   what the org knows about the repository it maintains:
             the PR standard, provider doctrine, verification
  platform/  Cloudflare seams: D1, model, driver
  Routes.ts  the HTTP API the UI speaks
  Worker.ts  entrypoint — composition of the above onto Cloudflare
  OrgGuidance.ts     the entry to the org's own doctrine — names the
                     domain skills beside the code they govern
  CharterGuidance.ts how agents, skills, fragments are written (cross-domain)
```

Doctrine is PLUGGABLE: each domain keeps its own guidance as a small
`AI.Skill` beside the code it governs (`coding/ToolGuidance.ts`,
`CharterGuidance.ts`, `sandbox/SandboxGuidance.ts`,
`github/ProposalsGuidance.ts`, `process/ProviderEngineering.ts`), an agent
activates the ones its change touches, and shared standards every stance
must hold are fragments (`process/PullRequests.ts`). The conventions for
working on this folder live in [AGENTS.md](./AGENTS.md) — generated by
`bun scripts/agents-md.ts` from `src/OrgGuidance.ts` and the domain
skills it names, the same text the Engineer and Reviewer activate.

## Agents

Bare `AI.Agent` tags; behavior lives on the `*Live` Layer as a charter
(init → stance). One session per world entity, keyed by it.

- `coding/Engineer.ts` — the coding agent: the toolbox
  (`coding/Toolbox.ts` — `Bash`, `ReadFile`, `Grep`, `Glob`,
  `ListDirectory`, `ReadOutput`, grouped as Read + Run) plus the
  editor (`coding/Editor.ts` — the ONLY layer that grants
  `EditFile`/`WriteFile`), and `coding/PushBranch.ts` +
  `coding/OpenPullRequest.ts` to publish work as a proposed pull
  request. Its stance splices `process/PullRequests.ts` so it builds
  what the Reviewer will judge, and names `process/Verification.ts`,
  `process/ProviderEngineering.ts`, and `OrgGuidance.ts` for what a
  change may touch.
- `review/Reviewer.ts` — the review agent: reads and RUNS in the PR's
  checkout, never edits. It drafts a review as a PROPOSAL and keeps it
  a living draft: every new commit revises it in place, and the
  operator accepts, declines, or asks for changes from the UI until
  the review posts or the PR closes.

Authority lives in reference topology, not configuration: the Engineer
never reviews, the Reviewer holds no editor, and nothing reaches
GitHub without a proposal the operator accepted. A capability no
charter mentions cannot be granted by any Layer.

## The review pipeline (`src/review/`)

- `ReviewerEvents.ts` — the router. `PullRequestOpened` starts the
  review; `PullRequestSynchronized` (a new head commit) wakes the
  same session to revise it; PR comments (not the bot's own) are
  forwarded; close/merge settles the session, withdraws its pending
  proposals, and releases its checkout. Deliveries are deduped through
  the Ledger and verified with `GITHUB_WEBHOOK_SECRET` when set.
- `Companions.ts` — `findCompanions`: the companion pull requests
  (same branch name) in `distilled`/`floci`, and the submodule path
  whose pin to compare.
- `ReadDiff.ts` / `ReadIssue.ts` — the PR and issue read surfaces.
- `Ledger.ts` (+ `LedgerD1` / `LedgerMemory`) — dedupe, liveness, and
  metadata.

## The process (`src/process/`)

How the unit the org maintains is built and judged. Alchemy is one
unit with two repositories it moves with: `distilled`, the SDK factory
pinned as a submodule, and `floci`, the AWS emulator `alchemy dev`
runs against. A provider change usually crosses into both, so the
folder holds the standard for the whole unit and a skill for working
in each part — the same idea as the root repository's `processes/`,
written as skills the org's agents activate. Repositories are named by
reference (`nameOf(distilled)` from `github/Repos.ts`), never by
string.

- `PullRequests.ts` — the standard (an `AI.fragment`, spliced into both
  charters): behavior ships with its tests, tests are end-to-end
  fixtures (no mocks, idempotent, cover the variants), DX-first
  descriptions with a verification report, a companion PR in
  `distilled` with the submodule pin checked, an emulation in `floci`
  for AWS providers.
- `Verification.ts` — the read-and-run skill: search, read, RUN with
  the repository's own commands; what counts as evidence. Grants no
  editor.
- `ProviderEngineering.ts` — building, maintaining, and testing a
  provider: one file per resource, the reconciler doctrine, typed
  errors handled only through the SDK's union, Effect-only code, the
  test shape. Activated when a diff touches
  `packages/alchemy/src/{Cloud}/`.
- `Distillation.ts` — the flywheel that produces cloud coverage: build
  a resource or binding, test it live, feed every SDK mismatch the test
  surfaces back into `distilled` as a model patch, regenerate, test
  again — plus how distilled is built (Smithy + JSON Patch, never edit
  generated modules, the regenerate commands and the AWS dialect) and
  the two-pull-request convention with the pin.
- `AwsEmulation.ts` — building an AWS resource's emulation in floci so
  the same reconciler runs locally: the fork's protocol-fidelity rules
  and layered service pattern, the JDK-less session image, the
  `{Resource}.local.test.ts` proof, and the companion PR.
- `CloudflareEmulation.ts` — building a Cloudflare resource's local
  physics: a binding as a plugin in `packages/cloudflare-runtime`
  (`Plugin.Service` + `*.worker.ts` inside workerd), the second
  provider in alchemy (`ProviderLayer.dual`, `LocalProvider.make`,
  `Local*Gateway`, `localRuntimeServices()`), and the
  `{Resource}.local.test.ts` proof over the RPC sidecar.

## Proposals (`src/github/`)

Agents never act on GitHub directly. `Proposals.ts` is the
human-in-the-loop gate: a review, a comment, a merge, or a new pull
request is recorded as a pending proposal (`ProposalsDO` — one Durable
Object per pull request — in the Worker, `ProposalsD1` as the one-table
variant, `ProposalsMemory` in tests) and `ProposalActions.ts` replays it
verbatim once the operator accepts. `revise` lets the proposing agent
update a pending proposal in place; `POST /api/proposals/:id/revise`
carries the operator's "ask for changes" back to it.

`Repos.ts` names the connected repositories (`primary`, the companions
`distilled` and `floci` with their submodule paths, publish targets);
`Board.ts` and `PullRequest.ts` project sessions and pull requests for
the UI. `SessionRepo.ts` resolves a session key (`owner/repo/name`,
`owner/repo#N`) to the connected repository and ref its tree should
hold — the sandbox converges on that answer, it doesn't decide it.

## Sandboxes (`src/sandbox/`)

Every session's tools run in a sandbox that holds a checkout of the
repository it works on:

- `SandboxSession.ts` picks the sandbox for a session; `SandboxCheckout.ts`
  converges its tree on what `github/SessionRepo.ts` resolved.
- `SandboxMicrovm.ts` — a Firecracker microVM per machine, the org
  image baked by `SandboxBake.ts`; `SandboxContainer.ts` — the
  Cloudflare Container variant; `SandboxWorktree.ts` — `alchemy dev`,
  a git worktree under `.alchemy/worktrees` on the host.
- `CheckoutsSandbox.ts` / `CheckoutsWorktree.ts` — `Git.Checkouts`
  implementations for each.

## Artifacts (`src/artifacts/`)

What tools print, kept out of the transcript:

- `Artifacts.ts` — the store: opaque IDs, never host paths. Two
  physics: `ArtifactsLocal.ts` (an OS temp dir, `alchemy dev` and
  tests) and `ArtifactsSandbox.ts` (files under `.tool-output/` on the
  session's own machine) — the sandbox is one implementation, not the
  store's home.
- `Output.ts` — head/tail truncation and the bounded streaming
  collectors every tool's policy is built from.
- `SpillingTools.ts` — the spill net over every tool: an oversized
  result lands in `Artifacts` with a preview + id inline, and
  `ReadOutput.ts` pages it back.

## Platform (`src/platform/`)

`DriverCloudflare.ts` binds sessions to Durable Objects,
`Database.ts` / `SessionIndexD1.ts` keep the board and session index
on D1, `Model.ts` selects the model.

## Running

```sh
bun alchemy dev      # local: sessions in worktrees, GitHub by polling
bun alchemy deploy   # Cloudflare: microVMs, D1, GitHub by webhook
```

The deploy output prints the site URL; the UI is a coding-agent chat —
each new session gets its own sandbox, streams its transcript live over
the session socket, and pending proposals show in the inbox and on
their pull request.
