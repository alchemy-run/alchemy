# FunctionTrigger, event sources and CustomDomain

Initial status: **missing** for FunctionTrigger, CronEventSource, BucketEventSource and CustomDomain. Required gates G0–G5 and G9–G10; domain HTTPS and real cron delivery have separate explicit availability gates, not broad lifecycle skips.

## FunctionTrigger contract

Files: `packages/alchemy/src/Neon/FunctionTrigger.ts`, suite `packages/alchemy/test/Neon/FunctionTrigger.test.ts`, generated event types/internal dispatcher; minimal Providers/index additions. Shared scope is inferred from required target `function`. Optional name defaults to deterministic trigger label; name length 1–256 and unique among all visible triggers, including inherited ones. `path` defaults `/`, is a path without query, length 1–2048. `enabled` defaults true for newly managed local triggers, not for unowned inherited ones.

Discriminated props:

- `type: "schedule"`, `schedule: { cron }`; numeric five-field UTC cron, string length 1–1024. No invented timezone prop or scheduled export.
- `type: "storage_object_created"`, `storageObjectCreated: { bucket, prefix? }`; same-branch Bucket required; exact bucket name 3–63 characters. Prefix is case-sensitive literal UTF-8 bytes (≤1024), no path normalization/boundary semantics; omit for match-all, do not send empty prefix.

Outputs: projectId/branchId, triggerId, name/type, target slug/path, config, enabled, configuration version, inherited and schedule-only `nextRunAt: string | null`. Storage triggers do not require a nextRunAt field. Payload schema version and trigger configuration version are different values.

Immutable: project/branch scope and type replace. Target Function **within same branch**, name, path, schedule or storage selector, and enabled are mutable PATCH fields. A cross-branch target change replaces through scope change; bucket/Function branch mismatch fails before mutation. Keep old/new dependencies during replacement; no engine deadlock by removing an old dependency simultaneously.

### Verified public operation mapping

These exact IDs were observed in public OpenAPI 3.0.3 on 2026-09-17 but are **absent from the initial checked-in SDK**. They must be generated by the sole SDK owner; consumers do not create raw management HTTP workarounds.

| Phase | Operation ID | Wire |
| --- | --- | --- |
| List/recover | `listProjectBranchTriggers` | GET `/projects/{project_id}/branches/{branch_id}/triggers` |
| Read | `getProjectBranchTrigger` | GET same collection `/{trigger_id}` |
| Ensure | `createProjectBranchTrigger` | POST collection; discriminator + function_slug + name + schedule or storage_object_created; optional function_path/enabled |
| Sync | `updateProjectBranchTrigger` | PATCH `/{trigger_id}`; requires type plus at least one changed property; cannot change type |
| Delete | `deleteProjectBranchTrigger` | DELETE `/{trigger_id}`; typed absent handling and fresh read verification |

Public response is `{ trigger }`, list `{ triggers }`; inspected list schema has no pagination field. Avoid inventing one; if refreshed API adds it, follow its generated schema. `trigger_id` is opaque/project-wide; never reconstruct it from a UUID assumption. Match stored ID then unique name with ownership verification. Unchanged config must not PATCH or increment version.

Inherited triggers retain parent's trigger_id but are disabled with next_run_at null. Explicit child PATCH creates a branch-local copy; child DELETE hides it permanently there, leaving parent untouched. Do not automatically enable or delete inherited triggers merely because a resource with the same name exists. Require Unowned/adoption and explicit child ownership. No documented exactly-once/retry guarantees are invented.

## CronEventSource and BucketEventSource bindings

Files: `packages/alchemy/src/Neon/{CronEventSource,CronEventSourceBinding,BucketEventSource,BucketEventSourceBinding}.ts`, shared internal typed HTTP dispatcher, suite-owned fixtures under `test/Neon/fixtures/`.

`CronEventSource(name, { cron }, Effect handler)` and `BucketEventSource(bucket, { name, prefix? }, Effect handler)` register an event listener and a trigger declaration on the Function host during init. Use the callable Binding.Service convention and `host.bind` only at deploy time; runtime handler requires RuntimeContext and fresh request scope. Provide Binding layers on the Function once. Function host bindings materialize the same FunctionTrigger lifecycle after Function readiness, avoiding a Function↔Trigger resource cycle. No direct binding-specific trigger CRUD or separate competing ownership.

Neon sends POST to configured path with version 1 envelope: `invocation_id`, `trigger: { type, id, name }`, and data of `scheduled_at` or `{ bucket_name, object_key }`. Export validated native and Effect event types, mapping to consistent camel-case application fields where appropriate. Verify `X-Neon-Trigger-Invocation-Id` header at Neon edge; provider strips client-supplied X-Neon-* headers. Header/body ID equality is only consistency, not a secret/auth proof. Local dispatcher cannot claim that an arbitrary caller header is edge-attested. Reject malformed discriminator/version/method/route and untrusted calls; propagate handler failure as non-success HTTP response. Handlers use stable invocation_id for idempotency. Preserve trace context and observable failures.

### Trigger/event acceptance

- Both discriminated create/read/update/remove/replacement/delete paths with exact SDK operations, no-op version stability and wrong-variant compile/wire rejection.
- Inherited-disabled read, explicit child enable/update/delete, stable trigger ID but increased child version, parent schedule/config unchanged; no child delivery before enable.
- Native Function route plus Effect event source run against real trigger delivery; prefix-matching upload invokes, nonmatching upload does not, malformed event returns error, spoofed external X-Neon header is stripped/rejected at public URL.
- Cron registration/update always active in lifecycle suite. Real bounded cron invocation is separate: if it cannot fit ≤90–120 seconds/platform eligibility, gate only delivery and record exact timing/rejection; no fake manual POST counts as cron success.
- Upload fixture persists invocation marker/status in owned SQL/object state; read it with bounded Effect repeat, not Date.now polling. Duplicate delivery is idempotent and failed processing does not ACK success.
- Trigger deletion/credential cleanup is ordered before parents; verify no owned triggers leak and no inherited parent is removed.

## CustomDomain contract and lifecycle

Files: `packages/alchemy/src/Neon/CustomDomain.ts`, `packages/alchemy/test/Neon/CustomDomain.test.ts`; Websites compose this resource plus existing DNS resources. Required props `function` and `hostname`; target scope is inferred. Normalize hostname case and trailing root dot before identity comparison, reject managed/internal names and invalid hostnames. Outputs include hostname/projectId/branchId/Function slug, cnameTarget, status, dnsStatus, bindingStatus/statusReason, native Function URL and custom HTTPS URL. Empty CNAME target is a reported serving-region limitation, not active readiness.

Identity is scope + normalized hostname + target Function binding. No update operation exists. Hostname/scope changes replace. Target change for the same hostname is a conflicting-identity replacement: remove old owned registration before registering new target (do not create-first collide), preserve dependencies and keep ordinary no-op stable. Domain lifecycle never deletes supplied Function/Project.

Actual checked-in SDK:

- Read/recover: `listProjectBranchCustomDomains({ project_id, branch_id, cursor?, limit? })`; exact normalized hostname filter, `pagination.next` progress checks.
- Ensure: `registerProjectBranchCustomDomain({ project_id, branch_id, domain, entity_type: "function", entity_id: function.slug })`; POST branch `/custom-domains`. Target Function must already exist; typed conflict → observe and refuse foreign binding rather than take over implicitly.
- Delete: `deleteProjectBranchCustomDomain({ project_id, branch_id, domain })`; DELETE `/projects/{project_id}/branches/{branch_id}/custom-domains/{domain}`, typed absence and re-list verification.
- No domain PATCH or certificate-creation SDK operation. Read final published routing fields from list.

Domains are branch-specific and not inherited into previews. Registration must return CNAME records before DNS propagation so DNS resources can be created without a cycle. Use DNS-only CNAME and documented trusted forwarded-host handling, not unconditional trust of client headers. API `active` is not proof of working TLS; exercise actual HTTPS hostname/cert, redirects/cookies and framework reconstruction separately.

### Domain acceptance

Live lifecycle with deterministic authorized test hostname; no-op, normalization, host/target replacement, adoption refusal/acceptance, out-of-band deletion, repeated delete, fresh absence. Fork branch and prove domain does not migrate/inherit. DNS authority and actual HTTPS are unverified in preflight; keep registration/record-output test separate from DNS/TLS. An unavailable DNS credential/zone remains an explicit blocker, not a passed custom-domain feature. Test pending/misconfigured/CAA-blocked/missing-binding diagnostics with sanitized owned-fixture evidence where safely available, never mutate customer DNS to synthesize errors.
