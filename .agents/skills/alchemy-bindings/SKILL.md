# Generating bindings from distilled

A binding is a distilled operation, bound to one resource, with the
least grant that lets a host call it. Thousands of them follow one shape,
so they are produced in two halves:

- **A deterministic generator** (`scripts/generate-<cloud>-bindings.ts`)
  reads the distilled SDK and a JSON config per service
  (`packages/<cloud>/bindings/<Service>.json`) and writes every binding,
  the service's `generated.ts` barrel, and a live probe suite. It is
  pure: same inputs, same bytes.
- **An AI loop** (this skill) decides what the generator can't derive:
  which resource an operation targets, what it is checked against, which
  role covers it, what it is called, and which operations aren't
  bindings at all. It writes those decisions into the config, reruns the
  generator, and proves them with the probes.

```
 distilled SDK ─┐
                ├─> generator ─> <Op>.ts · generated.ts · Generated.test.ts
 <Service>.json ┘        │
       ^                 v
       └── AI edits ── --report · --changes · probes · tsrs
```

GCP is the reference: 199 services, every one generated
(`scripts/generate-gcp-bindings.ts`). AWS and Cloudflare bindings are
still hand-written; [porting.md](porting.md) is the contract for giving
them, or any provider, a generator.

## Rules

- **Generated files are output.** Every one starts with
  `// @generated by scripts/generate-<cloud>-bindings.ts … Do not edit.`
  Change the config, the generator, or replace the binding with a
  hand-written one. An edit to a generated file is lost on the next run
  and fails `--check` in CI.
- **One file per binding.** `<Op>.ts` holds the `Binding.Service`
  contract and its `<Op>Http` layer (and `<Op>Binding` where the cloud
  has a native binding). Layers are pure, so a module holding both tree
  shakes to what a host provides. Shared scaffolding (`HttpBinding.ts`,
  `BindingHttp.ts`) stays unexported.
- **Hand-written wins.** A hand-written binding (a file with an
  `@provides` layer, or `*Http.ts` scaffolding) that calls an operation
  marks it `covered`, and the generator skips it. A hand-written file
  with a generated binding's name stops the generator: add a `names`
  override.
- **Every exclusion has a reason.** `skip`, `projectGrant`, probe
  `skip`/`untestable` all take a sentence. It lands in the generated
  JSDoc or test, so the reason is reviewable where the binding would be.
- **Regenerating is a no-op.** The generator formats what it writes.
  Commit, then `--check`: any diff means a stale file or a
  nondeterministic generator, and both are bugs.
- **Probes never write.** A probe calls each binding on the testing
  project with placeholder arguments. The generator poisons the body of
  every non-GET probe and skips body-less writes against the project
  itself. Read every write probe before running a new service: a
  placeholder `UpdateProjectBillingInfo` once unlinked the testing
  project's billing account.
- **Patch distilled, not the binding.** A wrong error, missing operation,
  or wrong request shape found by a probe is a distilled patch (the
  Typed Error Doctrine in `AGENTS.md`), followed by a regenerate.

## Commands

GCP; every provider's generator takes the same flags (see
[porting.md](porting.md)).

| Command | Does |
| --- | --- |
| `node scripts/generate-gcp-bindings.ts --report <Svc>` | classifies every method and prints it; writes nothing |
| `node scripts/generate-gcp-bindings.ts <Svc> [<Svc>…]` | regenerates those services |
| `node scripts/generate-gcp-bindings.ts` | regenerates every service |
| `node scripts/generate-gcp-bindings.ts --changes [<Svc>…]` | regenerates, then lists bindings added, removed, and changed (and what changed), plus methods that need a config decision |
| `node scripts/generate-gcp-bindings.ts --check` (`pnpm gcp:bindings:check`) | regenerates everything and fails if git sees a change |
| `node scripts/generate-gcp-bindings.ts --refresh-roles` | rebuilds `roles.json` (permission → smallest predefined role) from `gcloud iam roles list`; run when Google adds roles |
| `pnpm test:integration test/GCP/<Svc>/Generated.test.ts --profile testing --concurrency 8` | runs the service's probes live |

`--report` sorts each method into one kind:

| Kind | Meaning | What to do |
| --- | --- | --- |
| `binding` | generated | review it (loop B) |
| `lifecycle` | create/update/delete of a configured resource | nothing: its provider owns it |
| `covered` | a hand-written binding calls it | nothing |
| `internal` | operation polling, IAM policy methods, location metadata | nothing |
| `skip` | listed in `skip` | nothing; the reason is recorded |
| `project` | runs on the project, not a configured resource | a binding on the project, or add the resource it really targets |
| `needs-permission` | no IAM permission derivable | add a `permissions` override (or `defaultPermission`) |

`--changes` and `--check` read git, so run them on a clean tree.

## Loop A: bring a service up

1. Find the discovery doc and module
   (`submodules/distilled/packages/gcp/specs/spec-mirror-gcp/specs/<api>-<version>.json`,
   `src/services/<module>.ts`) and write `packages/gcp/bindings/<Svc>.json`
   with `discovery`, `module`, and one `resources` entry per resource the
   service has an Alchemy provider for (or should). Patterns come from
   the methods' `name` parameter patterns.
2. `--report <Svc>`. Work the list until every method lands somewhere on
   purpose: `needs-permission` gets a `permissions` entry, a
   `project` method that really targets a resource gets that resource
   configured, infrastructure calls get a `skip` with a reason.
3. Generate. Then loop B over each binding.
4. Add `probes`: deploy one of each resource in
   `test/GCP/<Svc>/fixtures/generated-resources.ts`, map it in
   `probes.resources`, list APIs in `enable`. Audit the write probes
   (Rules), then run the suite. A `PermissionDenied` means the role is
   too small; an unexpected success on a write means a probe is unsafe.
5. Re-export `generated.ts` from the service `index.ts` (the generator
   appends it) and, for a new service, from `packages/gcp/src/index.ts`.
6. `pnpm exec tsrs -b`, `pnpm docs:gen`, commit, `--check`.

[config.md](config.md) has every config key, grouped by the decision it
records.

## Loop B: refine what was generated

The generator's guesses are usually right; this loop catches the rest.
For each new or changed binding, read the generated `<Op>.ts` and check:

1. **The target.** The binding takes the Alchemy resource the operation
   acts on, never a name string: `SendMessage(queue)`, `GetObject(bucket)`.
   If it binds to the project, or to a parent, ask which resource the
   request's name or path really points at, and add it to `resources`
   (with `attributes` / `nameAttribute` when the API takes split path
   parameters). An operation that names a second resource in its body
   (a subscription's topic, a copy's source bucket) grants there too:
   `grantOn`.
2. **The grant.** Read the role in the JSDoc and the `variants`. It must
   be the smallest predefined role covering the checked permission, on
   the bound resource. Fix a wrong permission with `permissions`, a poor
   role with `roles`; a grant that can only be honoured on the project
   goes in `projectGrant` with the reason.
3. **The request.** Fields the bound resource determines (a location, a
   parent) belong to the binding, not the caller: `fields`, `append`,
   `suffix`.
4. **The name.** `<Verb><Noun>` from the method, read aloud. Rename with
   `names` when the derived one is redundant or collides.
5. **Is it runtime at all?** Something a deploy sets up (creating
   caches, relocating a bucket, enabling a feature) is infrastructure:
   `skip` it with the resource that owns it as the reason.

When the config can't express what a binding needs — a Read/Write/ReadWrite
service over several operations, a stream, a client-side composite —
write it by hand next to the generated ones (`AGENTS.md`, Read/Write/ReadWrite
binding convention). The generator then marks its operations `covered`.
When the same fix recurs across two services, add a config key to the
generator instead of repeating hand-written code.

## Loop C: upgrade distilled

The upgrade PR moves the distilled pin and brings every binding with it.

1. Branch from main. Move `submodules/distilled` to the target commit
   (`git -C submodules/distilled checkout <sha>`) and run a root
   `pnpm install`. Check that `readlink -f submodules/distilled/packages/gcp/node_modules/effect`
   points into the root `node_modules/.pnpm`, not a store nested inside
   `submodules/distilled`. A nested copy of `effect` makes live tests
   fail with `Unable to get redacted value`. Never run `pnpm` inside the
   submodule. Commit the bump alone, so the next step's diff is only the
   generator's.
2. `node scripts/generate-gcp-bindings.ts --changes`. The report is the
   worklist:

   ```
   StorageInsights
     added      ListReports
     removed    ListReportConfigs
     changed    GetReportConfig  [role]
     unresolved storageinsights.projects.locations.datasetConfigs.linkDataset  (needs-permission: …)
     probes     Generated.test.ts, fixtures/generated-host.ts
   ```

3. Work each line:

   | Line | Action |
   | --- | --- |
   | `added` | loop B on it |
   | `removed` | an added + removed pair in one service is a rename (a new method id or a changed `name` pattern): keep the old name with `names` unless the new one is better. A method gone from the spec: `grep` for uses across `packages/`, `examples/`, and `website/`, and remove them |
   | `changed [role]` | the permission or `roles.json` moved: confirm the new role is still the smallest, and that it isn't broader than before without reason |
   | `changed [operation]` | the variants (resource types, operations, path parameter) changed: confirm the target is still right |
   | `changed [request]` / `[response]` | distilled's types moved: `pnpm exec tsrs -b` finds the callers that break; fix them |
   | `changed [docs]` / `[format]` | read once, accept |
   | `unresolved` | a config decision (Loop A step 2) |

   `unresolved` lists only methods that are new since `HEAD`; methods
   the committed probe suite already skips are a standing backlog the
   report counts on its last line. Clearing that backlog is loop A
   step 2 per service, not part of an upgrade.

4. Rerun `--changes` after each config edit until the report holds only
   the lines you mean to ship.
5. `pnpm exec tsrs -b`, `pnpm docs:gen`, commit, `--check`.
6. Run the `Generated.test.ts` of every service in the report, one suite
   at a time with `--concurrency 8`. Fix failures as in loop A step 4.
7. Open the PR: `chore(gcp): upgrade distilled bindings` (or
   `feat(gcp)!:` when a binding was removed or renamed). The body is the
   final `--changes` report, trimmed to the lines a reviewer needs, plus
   one snippet per renamed or removed binding showing the new call.
