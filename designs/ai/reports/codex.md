# OpenAI Codex CLI (openai/codex) — study for Alchemy AI

Studied at `main` (release 0.143.0, Jul 8 2026), shallow clone in `.vendor/codex`. All file:line references are into `.vendor/codex/`. Codex is ~96% Rust; the brain is the `codex-rs` workspace (~100 crates).

---

## Architecture overview

```
codex-rs/
  protocol/            ← the wire vocabulary: Submission(Op) / Event(EventMsg), approvals,
                          sandbox policies, RolloutItem, ThreadGoal, permissions, items
  core/                ← the engine: Session, TurnContext, tasks, tools, compaction,
                          rollout recording, safety, guardian, multi-agent control
    session/           ← Session + the turn loop (turn.rs), input queue (steering),
                          turn_context, rollout reconstruction, context_window
    tasks/             ← SessionTask trait + RegularTask / CompactTask / ReviewTask /
                          UserShellCommandTask
    tools/             ← registry, router, orchestrator, parallel gate, handlers/ (shell,
                          unified_exec, apply_patch, plan, multi_agents_v2, request_user_input,
                          request_permissions, view_image, ...)
    agent/             ← multi-agent control plane: AgentControl, AgentRegistry, roles
    context_manager/   ← model-visible history + normalization (tool-pairing repair)
    guardian/          ← model-based approval reviewer (auto-approve/deny gate)
  ext/                 ← extensions: goal (the /goal loop!), guardian, memories, skills,
                          connectors, mcp, web-search, items
  rollout/             ← JSONL session persistence (RolloutRecorder) + SQLite state db
  sandboxing/          ← seatbelt (macOS), landlock (Linux), bwrap, windows
  exec/                ← `codex exec` non-interactive CI mode (JSONL event output)
  mcp-server/          ← Codex exposed AS an MCP server (tool = run a codex session)
  app-server/          ← JSON-RPC server for IDE/desktop clients (protocol v2, threads API)
  cloud-tasks/         ← client/UI for Codex Web cloud task management
  hooks/               ← lifecycle hook engine (pre/post tool use, compact, stop, subagent)
  tui/                 ← the terminal UI (drives core via app-server session)
  thread-store, state/ ← thread persistence + SQLite state runtime (goals, memories)
  model-provider-info/ ← provider registry; wire_api is Responses-only now
codex-cli/             ← npm wrapper; sdk/ ← TS + Python SDKs; docs/ ← stubs → openai docs site
```

Where the brain lives: `core/src/session/turn.rs` (`run_turn`) is the act–observe loop; `core/src/tasks/mod.rs` (`SessionTask`) is the task lifecycle around it; `protocol/src/protocol.rs` is the SQ/EQ contract; `ext/goal/` is the outer (Ralph-style) loop; `core/src/agent/` + `core/src/tools/handlers/multi_agents_v2/` is the orchestration layer.

Naming note: what protocol_v1.md called `Task`/`Turn` was renamed — today a **Turn** is one user request (a `SessionTask` run) and a **sampling request** is one model round-trip. `ConversationManager`/`CodexConversation` are deprecated aliases for `ThreadManager`/`CodexThread` (core/src/lib.rs:128–133).

## 1. The loop

**Three nested loops**, each with its own driver:

- **Sampling loop** (innermost): `run_turn` at core/src/session/turn.rs:142 — the doc comment (turn.rs:128–141) is the whole model: each iteration builds input from history, makes one sampling request, executes returned tool calls, and repeats. Exit condition: `needs_follow_up = model_needs_follow_up || has_pending_input` (turn.rs:318) — i.e. **"model returned no tool calls and no user input is queued" ends the turn**. Auto-compaction is checked *inside* this loop after every sampling request (turn.rs:346–370). Stop hooks may veto the exit and inject a continuation prompt (turn.rs:372–404, `stop_outcome.should_block`).
- **Task loop**: `RegularTask::run` at core/src/tasks/regular.rs:73–88 — loops `run_turn` while `input_queue.has_pending_input()`, so user messages queued mid-turn become the next turn without ending the task. Tasks are typed (`TaskKind`: Regular/Compact/Review/UserShell) behind the `SessionTask` trait (tasks/mod.rs:214–251), each owning a `CancellationToken` and an abort hook. A session runs at most one task at a time.
- **Goal loop** (outermost, the Ralph-style `/goal`): `ext/goal/src/runtime.rs`. `continue_if_idle` (runtime.rs:359–415) is the restart driver: when a turn ends and the thread goal is still `Active`, it calls `thread.try_start_turn_if_idle(vec![continuation_steering_item])` — injecting a fresh synthetic "continue working toward the goal" turn. Exit is **not** the model saying done: the model must call the `update_goal` tool with `status: "complete"` (ext/goal/src/tool.rs:56–59), and the continuation template (ext/goal/templates/goals/continuation.md) demands a requirement-by-requirement **completion audit** ("The audit must prove completion, not merely fail to find obvious remaining work") and a strict **blocked audit** (only after the same blocker repeats for ≥3 consecutive goal turns).

**Interrupt/steering semantics**: `Op::Interrupt` aborts the current task (`TurnAbortReason::Interrupted`, protocol.rs:4120) and — configurably — records a model-visible "turn interrupted" marker in history (tasks/mod.rs:95–120, developer-role message under multi-agent V2). Steering *without* interrupting is first-class: `SteerInputError` (session/mod.rs:246–283) shows steering targets a specific turn id (`ExpectedTurnMismatch`) and is rejected for non-steerable turn kinds (review, compact). Queued input is drained at the top of each sampling iteration (turn.rs:229–233) — but deferred right after auto-compact so the model resumes its continuation before seeing the steer (turn.rs:219–222). The goal extension injects steering into a *running* turn via `inject_if_running` (ext/goal/src/runtime.rs:417–429) when the user edits the objective mid-flight.

## 2. Memory & compaction

- **Auto-compact trigger**: token accounting after every sampling request; `token_limit_reached` computed by `context_window_token_status` (turn.rs:304–319) against a per-model auto-compact limit with two scopes — `Total` vs `BodyAfterPrefix` (turn.rs:908–920), the latter measuring only tokens after the stable prefix (prompt-cache-aware). Compaction is **mid-turn capable**: `run_auto_compact(..., CompactionPhase::MidTurn)` (turn.rs:349–357) and pre-turn (`run_pre_sampling_compact`, turn.rs:156).
- **Compaction = a model turn**: `run_inline_auto_compact_task` (core/src/compact.rs:91–121) sends `SUMMARIZATION_PROMPT` (overridable via `compact_prompt` config) and replaces history with the summary. The subtle part is **initial-context injection placement** (compact.rs:55–68): mid-turn compaction must place the summary *last* ("the model is trained to see the compaction summary as the last item in history") with initial context re-injected just above the last real user message; pre-turn/manual compaction clears the reference context so the next turn fully re-injects. There is also **remote/server-side compaction** (compact_remote_v2.rs) when the provider supports it, with model fallback (compact_model_fallback.rs).
- **Context windows are chained entities**: `CompactedItem` (protocol.rs:3166–3182) persists `window_number`, `first_window_id`, `previous_window_id`, `window_id` (UUIDv7) — the thread is a linked list of context windows, and compaction events are durable items in the rollout, not in-memory-only.
- **Tool-pairing invariant, empirically**: `ensure_call_outputs_present` (core/src/context_manager/normalize.rs:17–116) scans history for `FunctionCall`/`ToolSearchCall`/`CustomToolCall`/`LocalShellCall` without a matching output and inserts synthetic `"aborted"` outputs *immediately after the call*, with **deterministic synthetic IDs** derived from a fixed UUID namespace because "Changing this value would change model-visible IDs and invalidate prompt caches" (normalize.rs:14–15). This is repair-on-read, run every time history is materialized.
- **World state diffing**: `WorldStateItem` (protocol.rs:3149–3163) persists full-vs-patch snapshots of the model-visible environment state so resume can rebuild the diff baseline; `record_step_world_state_if_changed` (turn.rs:265–268) emits patches per step.
- **Memories** (ext/memories, `Op::SetThreadMemoryMode` protocol.rs:658) — cross-thread memory generation with citations (`MemoryCitation`), gated per-thread. I did not trace its internals deeply; it is config- and feature-gated.

**What survives resume**: everything in the rollout file (below) — including compaction summaries with replacement history, turn contexts, world-state baselines. Resume reconstructs model-visible history via `session/rollout_reconstruction.rs`.

## 3. Tool system

- **Registry/router/orchestrator**: `ToolRegistry` (core/src/tools/registry.rs:322) holds handlers keyed by `ToolName`; each handler exposes `spec()` (JSON schema) and `supports_parallel_tool_calls()` (registry.rs:267). Built-ins live under core/src/tools/handlers/: `shell`, `unified_exec`, `apply_patch` (with a lark grammar, handlers/apply_patch.lark), `plan` (update_plan), `request_user_input`, `request_permissions`, `view_image`, `get_context_remaining`, `new_context_window`, `tool_search`, `sleep`, MCP tools, and the multi-agent family. Extensions contribute tools through `codex_extension_api::ToolExecutor` (that's how goal's `create_goal`/`update_goal`/`get_goal` register — ext/goal/src/tool.rs).
- **Parallelism is a read/write lock, not a scheduler**: core/src/tools/parallel.rs:133–137 — parallel-safe tools take a *read* lock, serial tools take the *write* lock. Brutally simple and correct.
- **Cancellation is two-phase**: parallel.rs:158–199 — on cancel, tools that "wait for runtime cancellation" (processes needing teardown) get an ownership handoff of the terminal outcome; others are hard-aborted and a synthesized "aborted after Xs" response is recorded, keeping the pairing invariant.
- **Exec sessions**: unified_exec (core/src/unified_exec/mod.rs:1–23) manages long-lived PTY processes the model can reuse across calls (`write_stdin`), with head/tail output buffering, yield-time floors/caps (250ms–30s, mod.rs:64–73), 1 MiB output cap, and max 64 concurrent processes. Approval/sandbox/retry policy is centralized in a shared `ToolOrchestrator` "so policy logic and user interaction stay centralized while PTY concerns remain isolated" — on sandbox denial it retries unsandboxed *if policy allows*, without re-prompting (approval caching).
- **Errors**: `FunctionCallError::Fatal` kills the turn; everything else becomes a failure `FunctionCallOutput` returned to the model (parallel.rs:84–88).

## 4. Subagents: how they're built and MANAGED

This is Codex's newest layer (multi-agent V2, feature-gated).

- **A subagent is a full thread**, not a scoped context: `spawn_agent` (core/src/tools/handlers/multi_agents_v2/spawn.rs:40–130) builds a child config from the parent's base instructions, applies a **role**, and spawns through `AgentControl`. The tool family is `spawn_agent`, `send_message`, `wait`, `list_agents`, `interrupt_agent`, `followup_task` (handlers/multi_agents_v2/).
- **Roles are config layers, not prompts-in-code**: agent/role.rs:1–30 — a role is a TOML file loaded "with the same config machinery as config.toml", inserted as a high-precedence config layer at spawn time. Built-ins: `explorer.toml` and `awaiter.toml` (core/src/agent/builtins/) — the awaiter is a delightful micro-role whose whole job is polling a long command with exponentially increasing timeouts. Roles can change model, reasoning effort, tool availability, `developer_instructions` — anything config can.
- **Control plane**: `AgentControl` (core/src/agent/control.rs:88–108) is created once per root thread and shared by every descendant — "keeps the registry scoped to that root thread". `AgentRegistry` (agent/registry.rs) enforces a **max thread count** (`AgentLimitReached`, registry.rs:84–87) and a **spawn depth limit** (registry.rs:71–77, depth carried in `SessionSource::SubAgent(ThreadSpawn { depth })`). Agents get human-friendly **nicknames** with collision suffixes ("Fred the 2nd", registry.rs:44–61).
- **Fork-mode spawning**: `SpawnAgentForkMode::FullHistory | LastNTurns(n)` (agent/control.rs:60–64) — a subagent can be born with a fork of the parent's conversation (full-history forks reject model/role overrides, spawn.rs:67–72). This is context-inheritance-by-fork rather than by summary.
- **Inter-agent communication is typed protocol, rendered as model items**: `InterAgentCommunication` (protocol.rs:736–860) carries author/recipient `AgentPath`s, optional `encrypted_content`, and `trigger_turn: bool` — a message may merely deposit into history or start a turn ("NEW_TASK" vs "MESSAGE" rendering, protocol.rs:816–826). Delivery goes through the normal submission queue (`Op::InterAgentCommunication`, protocol.rs:580) so ordering is preserved.
- **Result return**: completion is a formatted inter-agent message back to the parent (`format_inter_agent_completion_message`, session/mod.rs:44); parents `wait` on a watch-channel of agent activity with a deadline (multi_agents_v2/wait.rs:96).
- **Mode is model-derived**: `effective_multi_agent_mode` (session/multi_agents.rs:39–68) — `ReasoningEffort::Ultra` ⇒ `Proactive` spawning, everything else ⇒ `ExplicitRequestOnly`, overridable by a config hint. Autonomy of orchestration is a dial on reasoning effort.
- **Review mode is a separate, simpler mechanism**: `ReviewTask` (tasks/review.rs) runs a one-shot **in-process** child codex thread via `run_codex_thread_one_shot` (codex_delegate.rs:196) with the review prompt, isolated from the parent's history, returning structured findings (`ReviewOutputEvent`). The reviewer does not inherit the maker's context — deliberate maker/checker separation.
- **Collaboration modes** (crate collaboration-mode-templates) are in-thread positional stances, not subagents: `plan.md` is a strict read-only planning mode ("You are in Plan Mode until a developer message explicitly ends it... treat a request for execution as a request to plan the execution"), plus default/execute/pair_programming templates injected via `<collaboration_mode>` tags (protocol.rs:111–112).

## 5. Sessions / state / durability

- **The rollout file is the journal**: `RolloutRecorder` (rollout/src/recorder.rs:69–78) writes JSONL to `~/.codex/sessions/rollout-<ts>-<uuid>.jsonl`. `RolloutItem` (protocol.rs:3132–3145) = SessionMeta | ResponseItem | InterAgentCommunication(+Metadata) | Compacted | TurnContext | WorldState | EventMsg. Writes go through a background writer task with pending-queue retry semantics — items leave the pending queue only after a successful write; I/O failure drops the file handle but keeps the unwritten suffix for retry (recorder.rs:1545–1549). File creation is deferred until first persist (recorder.rs:744–748).
- **`TurnContextItem` is persisted per turn** (protocol.rs:3204–3219: "Persist once per real user turn... so resume/fork replay can recover the latest durable baseline") — cwd, permission profile, model, workspace roots. The environment config travels with the history.
- **Resume and fork**: `ThreadManager::resume_thread_from_rollout` (core/src/thread_manager.rs:760), `fork_thread` (:953) with `ForkSnapshot` (:138) = `TruncateBeforeNthUserMessage(n) | Interrupted` — fork is implemented as *truncate the rollout item list and replay*. There is also a SQLite state DB (`codex-rollout::state_db`, `core/src/state_db_bridge.rs`) and a thread-store crate for indexed listing/search; goals live in SQLite (`codex_state::StateRuntime`, ext/goal/src/runtime.rs:41), not in the rollout.
- **Crash recovery**: on resume, history is reconstructed from rollout items (session/rollout_reconstruction.rs) and `ensure_call_outputs_present` repairs any orphaned tool calls from the crash. Goals recover via `restore_after_resume` (ext/goal/src/runtime.rs:335–357): an `Active` goal on a resumed thread re-arms the continuation loop; the TUI explicitly prompts about paused goals after startup resume (tui/src/app/thread_routing.rs:1372).
- **`response_id` bookmarks**: each turn stores the Responses API `response_id` enabling server-side thread continuation/forking (docs/protocol_v1.md:45, 101).

## 6. Async vs sync (SQ/EQ)

- The contract: `Submission { id, op, .. }` in, `Event { sub_id-correlated, EventMsg }` out (protocol.rs:1–4, 168–179). Both enums are `#[non_exhaustive]`; `Op` at protocol.rs:527, `EventMsg` at :1279 (100+ variants: lifecycle, deltas, approvals, MCP, realtime audio, ...). A single `submission_loop` (session/handlers.rs) dispatches ops; turns run as spawned Tokio tasks so the SQ stays responsive for `Interrupt`/approvals.
- Submissions carry a **W3C trace context** (protocol.rs:177–189) — tracing is propagated across async handoffs, not reconstructed.
- **The SQ is also the ordering mechanism for settings**: `Op::ThreadSettings` "uses the same submission queue as turn starts so app-server can preserve caller order between both kinds of mutation" (protocol.rs:569–576). One queue, total order, no settings races.
- Events serialize to newline-delimited JSON for any transport; `Op` payloads are deliberately *not* a stable wire contract (protocol_v1.md:57, 103–107) — the stable external surface is the app-server JSON-RPC protocol (app-server-protocol, v2 threads API) and the exec JSONL event stream.
- Background exec: `unified_exec` processes outlive turns (`Op::CleanBackgroundTerminals`, protocol.rs:532–534); notifications via legacy `notify` hook (hooks/src/legacy_notify.rs) and the hooks engine.

## 7. Pluggability

- **Config layering** is the master mechanism: `ConfigLayerStack` with precedence-ordered `ConfigLayerSource`s (managed/system → user config.toml → profile → project → session flags). Agent roles (§4) and collaboration modes ride this. `config.md` at codex-rs/config.md is the reference.
- **MCP both directions**: client — `McpConnectionManager` (codex-mcp crate; core/src/mcp.rs) with OAuth credential store, elicitation requests surfaced as approvals (`Op::ResolveElicitation`, protocol.rs:602–614), tool exposure filtering (mcp_tool_exposure.rs), and skill dependencies (mcp_skill_dependencies.rs). Server — `mcp-server/` exposes *Codex itself* as an MCP tool ("codex" tool = run a session; exec_approval.rs/patch_approval.rs bridge approvals over MCP elicitation).
- **Hooks**: a full lifecycle engine (hooks/ crate). `HookEventName` (protocol.rs:1483–1494): PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, SessionStart, UserPromptSubmit, SubagentStart, SubagentStop, Stop. `HookHandlerType` = **Command | Prompt | Agent** (protocol.rs:1498–1502) — a hook can be a shell command, an injected prompt, or a whole agent. Stop hooks can block turn completion and force continuation (turn.rs:372–401) — a user-programmable exit condition.
- **Skills** (core/src/skills.rs, docs/skills.md): SKILL.md files injected under `<skills_instructions>`, with a metadata token budget (`default_skill_metadata_budget`) and explicit `skill` user-input items; **extensions** (codex-extension-api) contribute prompt fragments in typed `PromptSlot`s, tools, and turn-context contributions; **plugins** + **connectors** (apps) sit on top of MCP; **dynamic tools** let the *client* register tools whose calls round-trip over the SQ/EQ (`Op::DynamicToolResponse`, protocol.rs:632–638).
- **What's hardcoded**: the turn loop, compaction placement strategy, approval lattice, sandbox mechanisms, the tool-pairing repair, base instructions per model family (`BaseInstructions`), and — as of now — the wire protocol (Responses only).

## 8. Human-in-the-loop

- **The approval policy lattice**: `AskForApproval` (protocol.rs:913–937) = `UnlessTrusted` (everything but known-safe read-only asks) | `OnRequest` (default; **the model decides when to ask** — note `on-failure` is now a serde alias of OnRequest, the old distinct mode was folded in) | `Granular(GranularApprovalConfig)` (per-category booleans: sandbox_approval, execpolicy rules, skill approval, request_permissions, MCP elicitations — false ⇒ auto-*reject*, protocol.rs:939–954) | `Never`.
- **Approval decisions are amendments, not booleans**: `ReviewDecision` (protocol.rs:4025–4057) = Approved | ApprovedExecpolicyAmendment (persist a rule so future matching commands skip approval) | ApprovedForSession (session-scope cache) | NetworkPolicyAmendment (allow/deny a host going forward) | Denied | TimedOut | Abort. Every approval is an opportunity to *narrow future approvals* — the policy ratchets via use.
- **Safety assessment is a pure function**: `assess_patch_safety` (core/src/safety.rs:32–110) returns `SafetyCheck::AutoApprove { sandbox_type } | AskUser | Reject { reason }` from (policy × permission profile × sandbox capability × writable-roots analysis). Notably: a patch constrained to writable paths still runs sandboxed because paths may be **hard links** out of the workspace (safety.rs:63–66); auto-approve only happens when a sandbox can actually be enforced (safety.rs:78–100).
- **Sandbox**: `SandboxPolicy` (protocol.rs:1000–1048) = DangerFullAccess | ReadOnly | ExternalSandbox | WorkspaceWrite (writable_roots + network flag + tmpdir options). `WritableRoot` carves out read-only subpaths *inside* writable roots — `.git`, `.codex`, `.git/hooks` — "files that could be modified to escalate the privileges of the agent" (protocol.rs:1050–1066). Enforcement: seatbelt SBPL on macOS, Landlock on Linux, bwrap, a Windows sandbox (sandboxing/src/).
- **The Guardian — a model judges the approval gate**: core/src/guardian/mod.rs:1–12 — "Guardian review decides whether an `on-request` approval should be granted automatically instead of shown to the user": reconstruct a compact transcript (token-capped, guardian/mod.rs:52–58), ask a dedicated review session for strict JSON, **fail closed** on timeout (90s)/malformed output, apply allow/deny. Circuit breakers: max 3 consecutive guardian denials per turn, denial history window, and `Op::ApproveGuardianDeniedAction` for the human to override a specific denial (protocol.rs:670). This is an LLM-judge inserted *at the capability boundary*, with the human as appellate court.
- **The model can ask**: `request_user_input` tool (structured questions with options), `request_permissions` tool (ask for a permission-profile upgrade with `PermissionGrantScope`), MCP elicitations — all resolved via SQ ops, all timeout-capable.

## 9. Provider abstraction

- **Chat Completions is dead**: `WireApi` now has exactly one variant, `Responses` (model-provider-info/src/lib.rs:57–61), and `wire_api = "chat"` produces a hard migration error (`CHAT_WIRE_API_REMOVED_ERROR`, lib.rs:50 → discussion #7782). Even Ollama/LMStudio go through Responses-compatible endpoints (lib.rs:446–450). They deleted the abstraction rather than maintain two prompt/stream mappings.
- `ModelProviderInfo` (lib.rs:111+) carries base URL, auth mode (API key vs ChatGPT tokens), retry/backoff, WebSocket support (Responses-over-WebSocket for sticky, resumable streams — `ModelClientSession` in core/src/client.rs caches "WebSocket + sticky routing state" per turn, turn.rs:217–218). Models are described by `ModelInfo`/`ModelPreset` (context window, auto-compact limit, input modalities, reasoning support) from a models-manager with refresh strategies; reasoning effort (Minimal→Ultra) is per-turn config that even gates orchestration behavior (§4).
- Turn metadata rides HTTP headers (`X-Codex-Turn-Metadata`, client.rs) and `responsesapi_client_metadata` per turn (protocol.rs:560–561).

## 10. Integration

- **`codex exec`** (exec/): non-interactive CI mode; `--json` streams a *stable* simplified event schema (exec/src/exec_events.rs) distinct from internal EventMsg; human/JSONL processors are separate (event_processor_with_*). Resumable (`codex exec resume`), supports `--output-schema` for typed final answers (`final_output_json_schema` on `Op::UserInput`, protocol.rs:558–559).
- **IDE/desktop**: app-server (JSON-RPC over stdio/UDS; app-server-protocol has TS bindings generated via ts_rs) — the TUI itself is an app-server client now (tui/src/app_server_session.rs), eating the same dogfood as VS Code.
- **Cloud tasks**: cloud-tasks/ is a client for Codex Web tasks (list/apply/diff); `environment_selection.rs` + exec-server `EnvironmentManager` abstract local vs remote execution environments per turn (`TurnEnvironmentSelection`, protocol.rs:133–143 — multiple cwds/environments per turn).
- **Notify hooks** (legacy) + hooks engine for automation; otel crate exports turn-level spans/metrics (TURN_E2E_DURATION, TOKEN_USAGE, TOOL_CALL — tasks/mod.rs:42–46).

## Judgments

**What they got right**

1. **The SQ/EQ split with sub_id correlation** — one totally-ordered command queue in, one event stream out, non-exhaustive enums both ways. It survived a UI rewrite (TUI → app-server client), an IDE extension, an MCP server wrapping, and a realtime-audio addition without changing shape.
2. **Repair-on-read tool pairing with deterministic synthetic IDs** (normalize.rs) — they treat orphaned tool calls as a *permanent background hazard* (crashes, aborts, truncations, forks) rather than something to prevent at every call site, and the fix is cache-stable.
3. **Approval decisions as policy amendments** (`ApprovedExecpolicyAmendment`, `NetworkPolicyAmendment`) — the approval dialog is the policy editor. Human bandwidth is spent once per *pattern*, not once per command.
4. **Guardian** — recognizing that `on-request` approvals are themselves a judgment task a model can do, with fail-closed semantics, hard timeout, denial circuit-breakers, and human override. A positional judge at the capability boundary.
5. **Goal completion audit prompt** — the continuation template's "completion is unproven until evidenced" and the 3-consecutive-turn blocked audit are the most operationally mature loop-exit criteria I've seen shipped. Exit = judged claim + budget + explicit blocked path, all separate statuses (`ThreadGoalStatus`: Active/Paused/Blocked/UsageLimited/BudgetLimited/Complete).
6. **Roles as config layers** — subagent differentiation reuses the config system rather than inventing an agent-definition format. The awaiter/explorer built-ins show how cheap a "role" becomes.
7. **Deleting Chat Completions** — a working deprecation: hard error + migration text + discussion link, not a compatibility shim.
8. **Read/write-lock tool parallelism** — the simplest possible correct model for "some tools are parallel-safe".

**What's weak / regretted (evidence in-tree)**

1. **Vocabulary churn**: Session/Task/Turn → Thread/Turn/SamplingRequest, with deprecated aliases (lib.rs:128–133), legacy event names (`TurnStarted` serializes as `task_started`, protocol_v1.md:99), `Op::UserInput` legacy vs `UserTurn` — protocol docs admit "the code might not completely match this spec" (protocol_v1.md:5). Naming the loop levels wrong initially cost them years of aliases.
4. **`Session` is a god object**: session/mod.rs is 4,081 lines with 200 imports; session/tests.rs is 11,045 lines. The seams (tasks, tools, hooks, extensions) came late and the core never got re-cut. The extension API (`ext/`, goal as an extension) looks like the escape hatch being built after the fact.
2. **Compaction is a zoo**: compact.rs, compact_remote.rs, compact_remote_v2.rs, compact_model_fallback.rs, compact_token_budget.rs, plus phase/reason/trigger/implementation enums and a TODO admitting pre-turn compaction estimates wrong (turn.rs:152–155). Model-behavior coupling (summary must be last item mid-turn) is documented lore, not a mechanism.
3. **Approval surface fragmentation**: exec approvals, patch approvals, MCP elicitations, request_permissions, request_user_input, skill approvals, network approvals, guardian — seven-plus ask-the-human channels each with its own Op/Event pair and its own granular flag. The `Granular` policy config is the tell: the lattice grew ad-hoc and now needs per-category toggles.
5. **State is split three ways** (JSONL rollout, SQLite state db, thread-store) with a bridge module (state_db_bridge.rs) — durability of *history* and durability of *state* (goals) evolved separately and now must be reconciled on resume.
6. **Multi-agent V1 vs V2 both live** (`MultiAgentVersion`, tools/handlers/multi_agents.rs vs multi_agents_v2/) with behavior forks sprinkled through core (e.g. interrupted-turn marker role, tasks/mod.rs:84–92).

## Insights for Alchemy

1. **Codex's SQ/EQ ≠ our step machine; it's our LoopService/Kernel-events boundary — and it argues for command IDs.** Codex correlates every event to the submission that caused it (`sub_id`), and steering targets a specific turn id (`ExpectedTurnMismatch`, session/mod.rs:261). Our design (§2.3) gives events `{ring, term, session, workItem}` provenance but the `Command`s of the step machine (§2.4) carry no identity except `CallTool.callId`. Give **every command** a deterministic id (derived from state, not random — replay!) so feedback, interrupts, and Trace events can be correlated exactly. Codex needed this for steering, approvals, *and* the tool-pairing repair; we will need it for the same three.

2. **The tool-pairing invariant should be repair-on-read with deterministic synthetic fills, not prevent-on-write.** Codex's `ensure_call_outputs_present` (normalize.rs:17) runs every time history is materialized and inserts `"aborted"` outputs with **content-addressed synthetic IDs** to protect the prompt cache (normalize.rs:14–15). For our Kernel obligation (design §2.4 "no orphaned tool results after any trimming/recovery"), implement it as a pure normalization pass over the Trace-derived message list inside `step` — it composes with *any* fold/trim, including user-provided ones, instead of trusting each fold to preserve pairing. Property-test exactly what Codex tests: arbitrary truncation ⇒ normalized history is always well-paired and deterministic.

3. **Mid-iteration compaction placement is model-trained lore — keep it inside ContextPolicy, never in the Kernel.** Codex hard-codes "the model is trained to see the compaction summary as the last item after mid-turn compaction" (compact.rs:61–63) and re-injects world context *above the last user message*. This is provider-coupled behavior that changed across their own versions (v1→v2, remote compaction). Validates our design decision (§2.6) that `ContextPolicy` is a seam of the implementation, absent from the Kernel interface — but add a note: the seam's contract must include *placement* (where summaries and re-injected context go), not just *what to drop*.

4. **The /goal loop is trigger-and-steering, not a bespoke runtime — and its restart driver is `try_start_turn_if_idle`.** Codex's outer loop is: goal state in SQLite + "when idle and goal Active, inject a synthetic continuation turn" (ext/goal/src/runtime.rs:359–415) + templates that steer. Structurally identical to our ring: trigger (idle+active), fold (goal record + usage counters), halt (update_goal(complete) — *a tool call is the halt signal*), budget (token_budget → BudgetLimited status; `TurnAbortReason::BudgetLimited`). Two things to steal for the Cloudflare Ring DO: (a) **idempotent wake** — `try_start_turn_if_idle` makes duplicate stimuli harmless, exactly what a DO alarm handler wants; (b) **the goal-state semaphore** (runtime.rs:126–132, 364–366) — external mutations and idle continuation race, and they serialize through one lock. Our Ring DO gets this for free from DO single-threading; the design should say so explicitly.

5. **Exit-condition prompts are load-bearing kernel assets — version them like code.** The continuation.md completion-audit and 3-strikes blocked-audit are *the* difference between a loop that Ralph-terminates honestly and one that declares victory. Our `AI.check(Judge)` (design §1.2.2) covers who judges; Codex shows the *default judge policy* (design §2.5: "default judge policy grades the halt condition itself") needs this level of prompt engineering — evidence-based, scope-preserving, anti-goalpost-moving. Ship a canonical rendered check policy with `promptHash` regression tests; don't leave the default judge as an afterthought.

6. **`update_goal(status)` shows halts arriving as tool calls, budgets as statuses — our `Err` channel should distinguish them the way `ThreadGoalStatus` does.** Codex separates Complete / Blocked / UsageLimited / BudgetLimited / Paused. Our `Out`/`Err` covers complete (halt) and BudgetExceeded, and §8.4 flags escalation vocabulary (`blocked`/`needs-info`/`park`) as undesigned. Codex's shipped semantics for `Blocked` — *repeat-observed blocker, N consecutive iterations, model-claimed but rule-gated* — is a concrete, tested design for our `stall` ceiling's sibling: `stall` = no fold-visible progress (kernel-detected); `blocked` = judged impasse (check-claimed, kernel-ratified). Both belong in `Err`, distinctly typed.

7. **Approval-as-amendment should shape our human-tool contracts.** Codex's `ReviewDecision` (protocol.rs:4025) lets one human answer create a durable rule (execpolicy amendment, network rule, session cache). Our `Approve`/`AskHuman` tools (design §0.9) currently return verdicts. Type the response as `verdict + optional amendment`, where the amendment is a fold-visible policy delta persisted in ring state — then the "autonomy dial" ratchets *by use*, per ring, with the ratchet history in the Trace (it doubles as Gavrilescu's provenance "recipe", §8.4).

8. **Guardian = a Check on the capability boundary, and it's Layer-expressible today.** Codex inserts an LLM reviewer between "model wants to run X" and "human sees a prompt", fail-closed, 90s timeout, 3-denial circuit breaker, human override op. In Alchemy this is *exactly* an alternative Layer for the `Approve` tool contract: `ApproveGuardian = Layer.effect(Approve, judge-backed impl with timeout → Escalated)`. No new term needed — write this as the flagship demo of "autonomy is a Layer choice", sitting between `ApproveAuto` and `ApproveHuman` (contra neither; it composes: guardian denies ⇒ escalate to human).

9. **Roles-as-config-layers validates per-agent Layer physics — and suggests spawn-time cheapness matters.** Codex differentiates subagents purely by stacking a TOML layer (agent/role.rs) — same engine, different config, resolved at spawn. Our per-agent `Layer.provide` graphs (design §1.4) are the statically-typed version of this and strictly stronger (capability denial by construction vs. config discipline). The lesson to import is the *granularity*: Codex roles override model, reasoning effort, timeouts, instructions per spawn. Our `AI.layer(term)` composition is static per deployment; consider whether `dispatch` needs a per-run override channel (model/effort/budget) — Codex needed it (`spawn_agent` args: model, reasoning_effort, service_tier — spawn.rs:64–92).

10. **Fork-mode context inheritance is a real alternative to summary-return isolation.** Codex subagents can be born with `FullHistory` or `LastNTurns(n)` forks of the parent thread (agent/control.rs:60–64) — cheaper than re-explaining, stronger than a summary, and implemented as rollout truncate-and-replay. Our design treats sub-agent isolation as summary-return (design §0.1 Claude-Code pattern; §2.4 "isolation and summary-return fall out of composition"). Since our Trace already supports replay, `ForkLoop`'s work-item could optionally carry a Trace-prefix reference — fork-of-trace as a *third* memory topology (alongside OM-fold and Ralph-fresh) with zero new machinery. Worth a design note even if deferred.

11. **One totally-ordered inbox per ring, including settings changes.** Codex routes settings mutations through the SQ "to preserve caller order" (protocol.rs:569–576). For the Ring DO: charter redeployments, budget adjustments, and work items must flow through the *same* ordered stimulus stream, otherwise a budget change can race a dispatch. DO message ordering gives us this — but only if we resist adding side-channel RPCs (consistent with design §2.5's "the harness must not offer a private cross-ring channel", extended to *control* traffic).

12. **Steering semantics need a typed rejection vocabulary.** Codex rejects steering with reasons: no active turn, turn mismatch, non-steerable turn kind (review/compact) (session/mod.rs:246–283). Our LoopService has `dispatch`/`run` only; Phase 2's richer handle (design §2.1 note) should type steering errors the same way — in particular "you may not steer a check/fold in progress" is our analogue of "cannot steer a review/compact turn": the positional roles are non-steerable by parties other than the kernel.

13. **World-state diffs as persisted baseline items.** Codex persists `WorldStateItem { full | patch }` in the rollout so resume can rebuild what the model currently believes about the environment (protocol.rs:3147–3163). Our Trace design covers events; it should also name a **baseline-snapshot event class** (fold snapshots referencing motivating events — design §8.4 provenance — plus environment baselines) so `ReplayKernel` doesn't have to re-derive environment context from the entire event history. Cheap now, painful to retrofit (Codex added window-chaining ids to `CompactedItem` late — all `Option`al fields, protocol.rs:3168–3181, the fossil record of a retrofit).

14. **Contradiction check, resolved in our favor — kernel component vocabulary.** Codex's kernel-equivalent (Session) knows the words memory, compaction, sandbox, review, goals, guardian, skills, plugins, connectors — and the 4,000-line session/mod.rs with 11,000 lines of tests is the price. The one place Codex approaches our inversion is `ext/` (goal is an extension contributing tools + steering via a generic extension API) — their newest, cleanest code. That the *goal loop* — the most Alchemy-like feature — was buildable as an extension without touching the turn loop is direct evidence for design §0 claim 4 (Kernel has no component vocabulary).

15. **Contradiction with design §2.4 worth stating: Codex's loop is not a pure step machine, and it costs them replay.** Codex has no `step(state, feedback) → commands`; the turn loop interleaves I/O and decisions, so "replay" means re-materializing history from the rollout and *re-running the model* — they cannot deterministically replay a session, only resume it. Their durability is journal-of-items + repair, not journal-of-commands + deterministic replay. This is weaker than our Workflows-based plan but *cheaper*, and it works at massive scale. Implication: our conformance suite should treat Codex-style "resume + normalize" as the *floor* every Kernel implementation must pass (memory harness included), with byte-exact replay (`ReplayKernel`, design Phase 2 exit) as the stretch tier only the step-machine path enables — don't gate the memory kernel on full determinism.

16. **Budget accounting is transactional and attributed.** Goal usage accounting uses expected-goal-id compare-and-swap (`account_thread_goal_usage(..., Some(expected_goal_id))`, runtime.rs:449–461) and per-turn snapshots with idle/turn attribution, under a dedicated accounting permit. Our `AI.budget` decrement in the Ring DO needs the same shape: budget rows keyed by (ring, workItem), decremented transactionally with the fold write (same DO storage transaction), never from event-stream aggregation after the fact — otherwise crash-between-events double-counts.

**Couldn't determine / didn't find**: internals of the memories extension (generation pipeline); the `code-mode`/`v8-poc` crates (looks like an experimental "tools as code execution" mode — worth a follow-up); realtime voice conversation details (out of scope); `agent-graph-store` internals (appears to back multi-agent V2 thread relationships). The docs/ folder in the repo root is stubs pointing at developers.openai.com — the in-repo authoritative docs are codex-rs/config.md and codex-rs/docs/protocol_v1.md (self-admittedly stale).
