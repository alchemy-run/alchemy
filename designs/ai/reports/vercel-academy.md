**One honesty note up front:** the study brief expected the course to explicitly name "the tool-pairing / orphaned-tool-result problem." The course never uses those words. It covers the bug class twice, obliquely: (1) `completing-the-toolbox` documents that an unhandled `needsApproval` makes the tool call *disappear* — "The model gets no result back, so it makes one up: 'Done! ## 1. Course map

**TeensyCode** is a from-scratch TypeScript coding-agent harness on AI SDK v6 (`ToolLoopAgent`, `tool()`, `stepCountIs`, `pruneMessages`), AI Gateway model strings, Zod v3 schemas. The course's framing: "Harness is the word for the system around the agent." Its method is causal — each lesson exists because the previous one broke something.

| Module | What it actually teaches |
|---|---|
| 1. The Agent Loop | One tool turns a chatbot into an agent (`(1 steps)` → tool loop); description = model-facing API; execute-level safety gate; the `needsApproval` confabulation trap; bounded output from the very first tool (500-line read cap). |
| 2. Tool Design | The 5-section description contract (incl. doubled negatives against "bash gravity"); factory + operations pattern (contract above the seam, execution below); approval evolution boolean → function → discriminated union (`interactive`/`background`/`delegated`). |
| 3. System Prompt | Sectioned prompt (Agency / Guardrails / Verification); `buildSystemPrompt(ctx)` as a **pure function**; verification-honesty contract; `AGENTS.md` injection. |
| 4. Sandbox Abstraction | Minimal `Sandbox` interface (`readFile`/`exec`/`stop` + identity + optional `expiresAt`/`snapshot?`); three backends: local (Node wrap), in-memory (just-bash copy-on-write overlay), cloud (concept); lifecycle hooks `afterStart`/`beforeStop`/`onTimeout`. |
| 5. Context Management | Measure first (token telemetry); `pruneMessages` in `prepareCall` (pairs older than last 3 messages); bounded tool output as *prevention over cleanup* (caps + visible truncation contract); cache control (mark stable prefix ephemeral-cacheable, prune **before** cache). |
| 6. Subagent Delegation | Three single-agent failure modes; explorer (read-only, Haiku, 5 steps) vs executor (delegated bash, Sonnet, 15 steps, no askUser); `task` tool as router; spawn-permission map; model-per-role. |
| 7. Sandbox Lifecycle | 4-state machine (provisioning→active→hibernating→hibernated) + two timeouts + activity tracker; snapshot/restore's three idempotency hazards; durable workflows with `sleep()`; the five production hard-won lessons. |
| 8. Human-in-the-Loop | `askUser` with 2–4 multiple-choice options; the ambiguity protocol (search → ask → act); the two-layer approval model (config = who decides; events = what policies apply). |
| 9. Planning & Verification | Todo tool with a single-active-item invariant enforced in code; grep-first context understanding; verification contract with **scoped claims** (caused vs pre-existing failures) discovered from `package.json`. |
| 10. Surfaces | The agent is headless; CLI/TUI/web are renderers of the same chunk stream; `parseArgs` + SIGINT + `finally sandbox.stop()`; SSE for web; resumable streams via persisted sessions. |
| 11. Extensibility | Skills = progressive disclosure (names in prompt, content on demand, capped); tool registry + `wrapTool` composition; event bus with pass/block/modify handlers and ordering rules — deliberately taught **last**. |

## 2. Per-topic findings

### Topic 1 — The loop (`from-chat-to-agent`, `your-first-tools`, `completing-the-toolbox`, `cli-entry-point`)

- The whole delta between chatbot and agent is **one tool + the loop**: `ToolLoopAgent({ model, instructions, tools, stopWhen: stepCountIs(10) })`. A no-tools run returns "(1 steps)": "The model talked, and that's all it can do."
- Step limits are the universal outer bound: 10 for the main loop early, 15 later, 5 for the explorer subagent, 15 for the executor. Termination is otherwise "no more tool calls."
- Safety is enforced **inside `execute`**, not via the SDK's `needsApproval`, because of the confabulation trap (`completing-the-toolbox`, verbatim):

  > "When `needsApproval` returns `true`, the SDK creates a `tool-approval-request` in the response and skips execution. If you don't have an approval handler wired up, the tool call disappears. The model gets no result back, so it makes one up: 'Done! I deleted the files.' … This is worse than running the command, because the user has no idea anything went wrong."

  The rule the course lands on: **a blocked tool call must still return a real string result** ("Blocked: … requires approval") so the model can report truthfully. "needsApproval is a signal, not a gate."
- Prefix allowlists are acknowledged as incomplete: "If you say 'delete node_modules,' the model might try `find . -name node_modules -exec rm -rf {} +` instead… We're keeping the prefix check because it's clear, not because it's complete."
- The CLI lesson's loop hygiene: `try/finally { await sandbox.stop() }` plus a duplicate SIGINT handler — "the `finally` covers normal exit, the handler covers the explicit interrupt." Leaked cloud sandboxes are the named cost.

### Topic 2 — Memory & compaction (`the-problem`, `pruning-old-results`, `tool-output-design`, `cache-control`)

- **Measure first.** `onStepFinish` logs per-step input/output tokens; the disease is linear input growth ("Every step sends the entire message history… Nothing leaves on its own"), 200k window hit in 30–50 busy steps; symptoms: "instructions at the top get pushed out of attention… tool selection degrades… the agent loops or hallucinates." Named non-fixes: hoping, fewer steps, bigger model ("delays the problem, doesn't solve it").
- **Pruning** (`pruning-old-results`): `pruneMessages({ messages, toolCalls: "before-last-3-messages" })` inside `prepareCall`, run before **every** model call. It drops old tool call/result **pairs**; the original user prompt always survives; the last 3 messages survive. Tunable (`before-last-1` aggressive … `before-last-5` gentle); "Three is a reasonable default." Two stated gotchas: spread `...options` first (or silently lose `model`/`tools`/`system`) and guard `messages === undefined` on the first call.
- **Bounded tool output** (`tool-output-design`) is the load-bearing lesson: "If a single tool result is 5,000 tokens, pruning the next one doesn't save you. The damage is already done… Pruning is the cleanup crew. Tool design is the prevention." Exact caps:

  | Tool | Cap | Rationale |
  |---|---|---|
  | `read` | 500 lines (+ offset/limit pagination) | enough to grasp structure |
  | `grep` | 50 matches (+ "(N total, showing first 50)") | "Five hundred would be a data dump" |
  | `bash` | 5,000 chars, **keep the tail** | "errors usually live at the end" (test failures, build errors) |

  The **truncation contract** (verbatim): "1. Cap the output… 2. Tell the model the output was truncated and how much got cut 3. Provide pagination parameters… A tool that silently truncates is worse than no truncation at all, because the model thinks it has the full picture and acts on incomplete data." Caps are "a tax the agent pays in pagination" — four bounded reads beat one context-polluting read.
- **Cache control** (`cache-control`): `addCacheControl(messages)` marks message 0 and all but the last 2 messages with `providerOptions.cacheControl: { type: "ephemeral" }` (Anthropic shape; "cache breakpoints work by prefix"). Composition order is normative: **prune first, then cache** ("Pruning happens first because it changes how many messages there are"). Claimed effect: ~$30 → ~$6 per long session. The durable habit even without provider support: "separate stable context from fresh context."

### Topic 3 — Tool system (`descriptions-that-work`, `shell-execution-with-safety`, `approval-gates`)

- **The 5-section description contract**: first-line summary + output format; WHEN TO USE (2–4 scenarios with prompt keywords); WHEN NOT TO USE (soft redirect, names the alternative tool); DO NOT USE FOR (hard boundary, deliberately repeats the negative); USAGE (constraints the schema can't carry — caps, defaults, encoding); EXAMPLES (2–3 concrete invocations).
- **Bash gravity** (verbatim): "Every model we've tested leans toward `bash` when descriptions are thin. We call this bash gravity, the universal pull toward the most general tool. Saying 'don't use this for searching' once isn't always enough. Saying it twice almost always is." Model-tier detail: "Haiku reads WHEN NOT TO USE but ignores it under ambiguity; Sonnet respects it but benefits from DO NOT USE FOR as reinforcement; Opus handles both."
- Long descriptions are cheap because "tool descriptions live in the system prompt, which the SDK caches between turns."
- **Factory + operations** (`shell-execution-with-safety`): `createBashTool(operations, safePrefixes)` — "Everything the model sees lives above the seam. Everything that actually runs commands lives below." `BashOperations.exec` never throws; failure is data (`{ stdout, exitCode }`).
- **Approval-gate evolution** (`approval-gates`): boolean (blocks everything — "useless, but it sets the shape") → function of input (one baked-in rule) → discriminated union:

  ```ts
  type ApprovalConfig =
    | { mode: "interactive" }                       // human approves off-safelist
    | { mode: "background" }                        // CI: auto-approve
    | { mode: "delegated"; trust: string[] };       // subagent inherits a trust slice
  ```

  Why a union and not three functions: "the config is data, not code. You can load it from AGENTS.md, validate it with Zod, **serialize it across a subagent boundary**." `delegated` is called out as "the interesting one": the parent hands a subagent exactly the commands its job needs.

### Topic 4 — Subagents (`why-delegate`, `explorer-subagent`, `executor-subagent`, `task-tool`)

- Three single-agent failure modes pruning can't fix: **context pollution** (twenty exploration reads bury the change-relevant files), **lost focus** (step-30 drift into fixing an unrelated CSS typo), **over-broad capabilities** ("Exploration shouldn't be allowed to modify anything, but a single agent with the full toolset doesn't know how to draw that line for itself").
- Role design:

  | | Explorer | Executor |
  |---|---|---|
  | Tools | `read`, `grep` only | `read`, `grep`, `bash` in `delegated` mode, trust `["npm test","npm run build","npx tsc"]` |
  | Model | claude-haiku-4-5 | claude-sonnet-4-6 |
  | Steps | 5 | 15 |
  | Can modify | No | Within trust list |
  | Can `askUser` | **No** | **No** — "That responsibility stays with the parent, which is the role that has the human in the loop." |

- Mechanics: **fresh agent per call** ("Each delegation gets its own context window, which is the whole point"); subagent tools are the parent's tool instances closed over the same sandbox; **errors return as strings** ("An uncaught exception breaks the tool loop"); result comes back as `[Explorer: N steps]\n{text}` — the parent gets "the answer back, not the journey."
- Executor instruction discipline: "The executor follows instructions literally. A vague description gets you a vague (and possibly destructive) result… The parent's job is to provide goal, procedure, constraints, and verification steps." `Do NOT ask questions` in the executor prompt "forces the executor to either act on what it has or fail, instead of stalling."
- `task-tool` reframes the tool as a **router**: description names both roles + when to use each; role construction in per-role helpers; **spawn permissions** as a table (`orchestrator: [explorer, executor, reviewer]; executor: [explorer]; explorer: []`) checked at the top of `execute`, returning an error string when denied. **Model per role, not per session**: "Different roles, different models… the failure modes are different too." Anti-overbuild note: "Two roles is the right starting point… Each role is a new place for instructions to drift and a new model bill to track."
- When *not* to delegate: "If the parent could do the task in three steps, delegation isn't paying for itself"; decisions aren't delegable — "the decision is the work."

### Topic 5 — Sandbox abstraction & lifecycle (`designing-the-interface`, `local-implementation`, `in-memory-implementation`, `cloud-implementation`, `lifecycle-hooks`, `state-machine`, `snapshot-and-restore`, `durable-workflows`, `hard-won-lessons`)

- **The interface** (verbatim shape):

  ```ts
  export interface Sandbox {
    type: string;                 // identity, for logging
    workingDirectory: string;     // identity, base path
    readFile(path: string): Promise<string>;
    exec(command: string): Promise<{ stdout: string; exitCode: number }>;
    stop(): Promise<void>;        // required, no-op is fine
    expiresAt?: number;           // optional: cloud only
    snapshot?(): Promise<{ snapshotId: string }>;  // optional: cloud only
  }
  ```

  Design rules stated: everything async even when sync underneath ("inconsistent signatures across implementations are a mess"); optional methods for capabilities that don't apply everywhere ("A local sandbox doesn't expire. A just-bash sandbox doesn't snapshot… without forcing stubs"); and the minimalism warning: **"Make the interface as small as you can get away with. Anything you add now will be the thing every implementation has to support forever."** The lesson's open challenge is telling: adding `writeFile` forces a choice for read-only sandboxes — optional method vs separate write-capable interface vs runtime error — "Pick one and notice what it forces everywhere else."
- **Three implementations**: local = ~15-line wrap of `readFileSync`/`execSync` ("Boring is the point… the baseline every other backend is compared to"); in-memory = `just-bash` **copy-on-write overlay** ("Reads come from the real disk. Writes go to memory. The real filesystem is never modified") — "Ideal for exploration, testing, and any time you'd rather not let an agent loose on your actual files"; cloud = same shape, network under it, plus per-minute cost, per-call latency, 30-min hard expiry. Portability is empirically imperfect: "Some tools will quietly fail because they assumed something about the host… Plan to fix one or two tools after this swap" (the just-bash mount point `/home/user/project` "trips everyone up").
- **Lifecycle hooks**: `afterStart` (git config, `npm install`, `.env`), `beforeStop` (check `git status --porcelain`, WIP-commit, snapshot — inside `finally` so it fires on crash), `onTimeout` (harness-invoked at expiry, usually delegates to `beforeStop`). "For the cloud backend, skipping `beforeStop` means losing uncommitted work when the VM dies." Challenge pairing: `afterStart` restores from a found snapshot + `beforeStop` auto-snapshots = crash-resume with no call-site code.
- **State machine** (`state-machine`): `provisioning → active → hibernating → hibernated (→ restore → active)`. Two clocks: **hard expiry** (provider-set, non-negotiable: "You can't extend it. You can't argue with it") and **inactivity window** (you set it; 5 min default, 2 aggressive, 20 loose). **The activity tracker is the whole trick**: user message / tool call / fs change count; status polling, reconnect probes, health checks do NOT. "If your status polling counts as activity, the sandbox never hibernates and you pay for hours of idle time. If your tool calls don't count, the sandbox hibernates mid-task." Rule of thumb: auto-snapshot at ~80% of hard expiry.
- **Snapshot/restore** (`snapshot-and-restore`): snapshots capture filesystem only — "running processes, in-flight network connections, in-memory state" are lost; "if it was in the middle of running tests when the snapshot fired, the tests have to run again." Three idempotency hazards, each with a guard: (1) snapshot-in-progress → cache the in-flight promise and return it; (2) restore-onto-running → `attachOrRestore` looks for an active sandbox before creating ("Now you have two VMs"); (3) double-stop → a `stopped` boolean so call two is a no-op. Plus the fossil problem: "Restoring from a snapshot from yesterday still gives you yesterday's code… Production lifecycles handle this by invalidating snapshots when the project changes, or by re-running `afterStart` after a restore. Neither is automatic."
- **Durable workflows** (`durable-workflows`): `setTimeout` dies with the serverless process and with every redeploy. Vercel Workflow's `sleep()` "checkpoints the workflow to durable storage and returns… resumes from exactly where it left off, in whatever function instance happens to be available. Across deploys." Side effects live in `"use step"` functions — "retried on transient failures and cached on success." Cost math: no lifecycle = run to hard expiry ($4.80/session) vs hibernate-after-5-idle ($0.50). "The pattern survives the runtime" — Temporal/Step Functions equivalents named.
- **Hard-won lessons** — see §3 below (items 1–5).

### Topic 6 — Async vs sync, surfaces (`cli-entry-point`, `streaming-and-tool-rendering`, `web-surface`)

- `agent.stream()` over `generate()`: iterate `result.fullStream`, switch on `chunk.type` — `text-delta` → stdout, `tool-call`/`tool-result` → **stderr** ("They're meta. They go alongside the response, not inside it"). Redirecting stderr yields the clean answer — the split is the renderer contract.
- The web surface is the same chunk stream over SSE; persistence (`db.saveMessages(sessionId, …)`) and resumable streams belong to the surface: "The session is the unit of work. The stream is one render of that session."
- The boundary rule (verbatim): "**The agent does not know there is a web.** … If you find yourself adding 'is this web?' branches to the agent, that's the seam slipping."
- Streaming complicates inline approval: "you might want to pause the stream, ask the user, then resume. That's an interaction loop, not a chunk handler."

### Topic 7 — Pluggability (`skills-system`, `custom-tools`, `extension-points`)

- **Skills = progressive disclosure**: `skills/<name>/SKILL.md` with frontmatter; **names + one-line descriptions live in the system prompt forever (≈100 tokens); full content loads on demand via a `loadSkill` tool, capped at 4,000 chars** with a truncation message. Discovery scans multiple dirs; "The first directory wins, so project-local skills can override globals." "This is the same prevention-over-cleanup discipline from Module 5, applied at the knowledge layer." Caveat: "The model has to ask… Treat this as a retrieval path, not a guarantee."
- **Tool registry**: `register/get/list/entries`, `Object.fromEntries(registry.entries())` feeds the agent; registration **order matters** (`task` needs `read`/`grep` registered first). `wrapTool(base, { beforeExecute, afterExecute })` composes hooks without changing the base — the example rewrites `bun test` to add `--reporter=spec`. Extension-surface table: tools (registry+wrap), skills (dir+loadSkill), sandbox (factory), approval (config+events), system prompt (`PromptContext`), model (subagent defs).
- **Event bus** (`extension-points`): five events (`session_start`, `tool_call`, `tool_result`, `session_before_compact`, `session_shutdown`); handlers return `{ block?, reason?, modify? } | void`; run in registration order; any `block: true` stops the call and **feeds the reason back to the model as the tool result**; `modify` is visible to subsequent handlers. Ordering doctrine: "Logging before safety checks captures the call attempt even when it gets blocked. Telemetry after the result captures what actually ran." Notable example: a `session_before_compact` handler injecting "Preserve all safety constraints and approval rules across compaction" — "Compaction is a moment where instructions can leak."
- Why it's the **last** lesson: "The event bus is the most flexible extension surface and the most dangerous one… Building it last means you understand what you're plugging into before you plug. If you wired this earlier, the temptation would be to handle every problem with an event hook."

### Topic 8 — Human-in-the-loop (`structured-questions`, `approval-config`)

- The core empirical fact: "The agent will not ask you questions. Not on its own… Asking feels weak to them. They'd rather guess." The fix is two-part: a small tool and a system-prompt section that does most of the work.
- `askUser` schema: `question: string`, `options: string[]` **min 2, max 4**. `execute` prints to stdout for the human and returns the same content (ending "(Awaiting user response.)") so "The model knows the question is in flight and won't try to act on the assumption it's been answered." In a real harness the surface pauses, collects, and injects the answer as the next user message.
- **The ambiguity protocol** (`# Handling Ambiguity`): "1. Search the code or docs to gather context first 2. Use askUser to let the user choose. Do NOT guess. 3. [examples: 'add auth' → ask OAuth or JWT]… Specific tasks (with file paths, line numbers, or precise instructions) do not need askUser. Act directly." The ordering matters: "Without it, the agent either asks too early (before it has enough context to make the question useful) or too late (after it's already started building the wrong thing)."
- Named architectural friction: "If `bash` is blocked by approval, the agent can't run the commands it needs to gather that context. It might never reach step 2. The approval system and `askUser` are in tension, and that tension is real architectural friction, not a bug to fix."
- **Approval two-layer model** (`approval-config`): the config union answers *who decides* (session-scoped, set by who runs the harness); the event layer answers *what policies apply* (fine-grained, project-scoped, can block or **modify inputs**, e.g. wrap a command in `sandbox-exec -p '(deny default)'`). "The event fires after the config but before the tool runs. Defense in depth." "One config knob can't carry both kinds of decisions without getting tangled." Challenge idea worth keeping: risk-scored auto-approval (numeric score per command trait, threshold-gated, audited).

### Topic 9 — Planning & verification (`todo-tool`, `fast-context-understanding`, `verification-contract`, `verification-gates`)

- **Todo tool**: `add/start/complete/list` over an in-memory array with **one rule enforced in code, not prose**: `start` rejects while any item is `in_progress` ("one rule the agent can't argue with… Without it, the agent will start every item up front and then race through them in parallel"). In-memory on purpose: "A long-lived list across sessions tends to grow into a junk drawer of stale items… Don't carry stale `in_progress` items into a new session, since the agent has no memory of why they were started." Plan for 3+ steps/multiple files/dependencies; skip for one-file fixes.
- **Fast context understanding**: two prompt bullets — "Search before reading. Use grep first, then read only what you'll change" and "Don't read files 'just in case.'" — turn a 30-step read-everything crawl into ~5 steps. It's *agent policy, not tool description*: "It belongs at the agent's policy level, not the tool's." Dependency: "This policy is only as good as the grep tool's results… The 50-match cap from Module 5 is doing real work here."
- **Verification contract** (`verification-gates` + `verification-contract`): gates run in order **typecheck → lint → test → build** ("Typecheck first because it fails fastest"); gates are **discovered from the project** (`discoverGates` reads `package.json` scripts, falls back to `npx tsc --noEmit` if TS is a dep) rather than assumed. The contract is about honesty, not coverage — **scoped claims**:

  > "Distinguish failures you caused from failures that were already there: 'Ran npm test: 47 passed, 3 failed. The 3 failures are pre-existing in user.test.ts and unrelated to my changes.' … Do NOT claim 'tests pass' without running them. Do NOT inflate partial verification into a blanket success claim."

  And the tell for confabulation: "A model that ran the check uses past tense and a specific result. A model that didn't uses hedged future tense" ("should be fine," "looks good to me"). "The hardest gate is the agent's honesty… The protective force is the system prompt section, not the discovery code."

### Topic 10 — Prompting (`structuring-agent-instructions`, `dynamic-prompt-construction`, `project-context`)

- Structure: role line → `# Agency` ("USE your tools… Do NOT explain what you WOULD do. Actually do it." + tool list + routing preferences) → `# Guardrails` (minimal changes, search-before-create/reuse, no new deps without asking) → later `# Verification`, `# Handling Ambiguity`, `# Skills`. "Be explicit with negative instructions… Models default to explaining." Deliberate redundancy: "The tool preferences live in the prompt as well as the descriptions… We're saying it in two places because models miss it in one."
- **`buildSystemPrompt(ctx: PromptContext): string` is pure**: "Same context in, same prompt out, no side effects. That makes it unit-testable… composable… replaceable… deterministic." No template engine — sections array + join. The suggested unit test asserts presence/absence of the `gitBranch` line.
- **`AGENTS.md` injection**: existence check at startup, contents injected as a `# Project Instructions` section. "This is the same trick Cursor uses with `.cursorrules`, Codex with `AGENTS.md`, Claude Code with `CLAUDE.md`… The file name varies. The pattern doesn't." Content is project facts the harness can't infer: commands, architecture, style, **"Lessons learned"** (e.g. "Auth middleware must run before rate limiting"). Monorepo merging strategies differ per harness (pi merges all, Cursor deepest-only, Codex concatenates root+cwd) and are left as an exercise.

## 3. The hard-won lessons list

Every production gotcha the course names, flattened. Items 1–5 are the `hard-won-lessons` lesson proper ("Each caused a real outage, a real cost spike, or real lost work"); the rest are named gotchas from other lessons.

1. **Stale handles after reconnect** (`hard-won-lessons`) — "The handle survives the disconnect. The session inside it doesn't." Commands hang or return garbage. Fix: probe every reconnected handle (`echo probe`) before use; recreate from the last snapshot on failure.
2. **Stale expiry data** (`hard-won-lessons`) — cached `expiresAt` is "already old by the time you stored it"; a derived `remainingTimeout` passed to a provider API can "create a sandbox that's already expired." Fix: fetch fresh expiry before every lifecycle decision; "Cache expiry information for display, not for control flow."
3. **Polling resets inactivity** (`hard-won-lessons`, `state-machine`) — status checks counted as activity mean the sandbox never hibernates and runs to hard expiry. "A clean pure-function bug masquerading as an integration issue." Fix: activity = user message / tool call / fs change only; never status pings, health checks, probes, billing reads.
4. **Auto-resume loops** (`hard-won-lessons`) — auto-resume triggers a lifecycle check → snapshot → hibernate → next auto-resume: "an infinite loop out of two pieces of code that look correct in isolation." Fix: auto-resume only on initial entry; subsequent reconnects attach to the active sandbox; "Don't chain transitions automatically."
5. **State divergence** (`hard-won-lessons`) — sandbox state lives in provider API, your DB, and the client cache; "They will diverge." Fix: **provider API is the source of truth**; "Your database is a cache. The client cache is a cache… When in doubt, fetch." And the combination warning: "The combinations are worse than the individuals… Fix all five, even when one or two seem unlikely."
6. **The needsApproval confabulation trap** (`completing-the-toolbox`) — a tool call skipped without a result makes the model invent success. Blocked calls must return a real result string. (The course's version of the orphaned-tool-result bug class.)
7. **Bash gravity** (`your-first-tools`, `descriptions-that-work`) — all models drift to the most general tool under weak descriptions; the doubled negative (WHEN NOT TO USE + DO NOT USE FOR) is the counterforce, verified per model tier.
8. **Creative rewrites bypass allowlists** (`completing-the-toolbox`) — prefix check catches `rm` but `find -exec rm -rf {} +` slips through; prefix allowlists are legibility, not security.
9. **Unbounded tool output is unrecoverable damage** (`tool-output-design`) — once 5,000 tokens of grep output are in context, pruning later doesn't help; prevention (caps) over cleanup.
10. **Silent truncation is worse than none** (`tool-output-design`) — the model "thinks it has the full picture and acts on incomplete data"; every cap must announce itself and offer pagination.
11. **`prepareCall` spread/undefined gotchas** (`pruning-old-results`) — forget `...options` and you silently drop model/tools/system; the first call has `messages: undefined` and `pruneMessages` throws.
12. **Prune before cache** (`cache-control`) — caching messages that pruning is about to remove wastes the cache prefix; the pipeline order is normative.
13. **Recent messages must stay uncached** (`cache-control`) — "They're about to be replaced."
14. **Snapshot captures files, not work-in-progress** (`snapshot-and-restore`) — running processes and in-memory state die; in-flight tests must re-run after restore; the agent's mental model must account for it.
15. **Snapshot-in-progress reentrancy** (`snapshot-and-restore`) — two concurrent snapshots fight for the VM or produce "a partial snapshot that looks valid but isn't"; cache the in-flight promise.
16. **Restore-onto-running duplicates VMs** (`snapshot-and-restore`) — always attach-or-restore, checking for an active sandbox first.
17. **Double stop** (`snapshot-and-restore`) — inactivity timer + user, or hibernate + hard expiry, both call stop; the second call "either fails loudly or corrupts state silently"; guard with a boolean.
18. **Restored snapshots are fossils** (`snapshot-and-restore`) — yesterday's code/deps/env; invalidate on project change or re-run `afterStart` after restore; "Neither is automatic. Both have to be wired in deliberately."
19. **`setTimeout`/`setInterval` lifecycle code dies in serverless** (`durable-workflows`) — the timer is GC'd with the function instance and lost on every deploy; only a durable `sleep()` (Workflow/Temporal/Step Functions) survives.
20. **Subagent exceptions break the parent loop** (`explorer-subagent`) — wrap `generate` in try/catch and return `"Subagent error: …"` as a string; "The parent expects a string back from any tool."
21. **Subagent opacity** (`explorer-subagent`) — without logging step count and text length from inside the task tool, "you'll be staring at confused parent output with no idea whether the subagent ran for one step or five."
22. **Vague executor instructions are destructive** (`executor-subagent`) — the executor follows literally; parent must pass goal, procedure, constraints, verification.
23. **Registration order in the tool registry** (`custom-tools`) — `task` registered before `read`/`grep` exists captures undefined references.
24. **Models don't ask questions unprompted** (`structured-questions`) — the tool alone is ignored; the prompt protocol does the work.
25. **Approval and askUser are in tension** (`structured-questions`) — blocked `bash` can starve the context-gathering step of the ambiguity protocol; a real architectural friction.
26. **Compaction can eat safety instructions** (`extension-points`) — hence the `session_before_compact` hook injecting "preserve all safety constraints"; instructions leak at compaction boundaries.
27. **Event handler ordering determines trace quality** (`extension-points`) — log before safety gates (capture blocked attempts), telemetry after results (capture what ran); "Get it wrong and you log half the story."
28. **The agent confabulates verification** (`verification-gates`) — "all tests pass" without running them; hedged future tense is the tell; the scoped-claims contract is the counter.
29. **Stale todos poison new sessions** (`todo-tool`) — never carry `in_progress` items across sessions.
30. **Zod v4 breaks AI SDK v6 types** (index page tech-stack table) — a pinned-dependency gotcha named by the course.
31. **`stopWhen`/`instructions` naming drift** (`from-chat-to-agent`) — wrong SDK-version names "silently compile but the agent does not behave the way you'd expect."

## 4. Insights for Alchemy

Numbered; each maps course material to a concrete implication for our Kernel interface, step machine, fold, Cloudflare Ring DO, sandbox seam, tool layers, or Ask command. Contradictions/tensions with `alchemy-ai-design.md` are flagged inline.

1. **Blocked-tool feedback extends the tool-pairing invariant** (`completing-the-toolbox` → step machine §2.4). The course's worst bug — a skipped tool call with no result producing "Done! I deleted the files." — shows the invariant is not just about trimming/recovery. Any policy denial (approval gate, capability refusal, budget stop mid-turn) must synthesize a `ToolResult` feedback for the pending `CallTool` command. Make it structural: in our step machine, a `CallTool` command may only be answered by a `ToolResult` feedback — the command interpreter has no path that drops one. The design doc scopes the invariant to "trimming/recovery" (§2.4); broaden the wording to include policy blocks and interruption.

2. **`ContextPolicy.truncate` must be pair-atomic and prompt-preserving** (`pruning-old-results` → memory seam §2.6). The SDK's `pruneMessages` semantics are a good spec for our default policy: drop tool call/result *pairs* older than the last N messages, always keep the originating work-item message. Property test: for arbitrary trims, no orphaned `ToolRequested`/`ToolCompleted` in the rendered context, and the head of the transcript is stable (for cache).

3. **Bounded tool output is a tool-Layer convention, plus a kernel safety net** (`tool-output-design` → tool layers). The caps (read 500 lines, grep 50 matches, bash 5,000 chars tail-keep) and the three-part truncation contract (cap / announce / paginate) belong in the tool *implementations* — i.e., in `BashDevBox`, `GrepLive`, etc., and in the prose of the Tool terms (USAGE section documenting the cap so the model can plan pagination). Separately, the kernel step machine should enforce a hard per-tool-result byte budget as layer-1 defense (this is Claude Code's first compaction tier, already cited in §0.1) — the course's "the damage is already done" argument is precisely why the cap must run *before* the result enters `StepState`.

4. **Prune-then-cache is an ordering law for the fold/render pipeline** (`cache-control` → renderer §1.6 + ContextPolicy). Any compaction/fold must run before cache-boundary marking, and the most recent messages stay unmarked. Our renderer's cache-stability rules (tool contracts render into the schema section, not prose; `promptHash` content addressing) are corroborated: the course's "separate stable context from fresh context" is exactly the discipline; our term system makes the stable prefix *provably* stable (the rendered term is deterministic). Encode the ordering in the harness: `fold → render → markCacheBoundaries → CallModel`.

5. **The course's `Sandbox` interface validates our seam, and our Layer split answers its open question** (`designing-the-interface` → `Cloudflare.AI.Sandbox`). Their minimal interface (readFile/exec/stop + identity + optional capabilities) matches our seam's intended shape; keep it that small. Their unresolved challenge — how to add `writeFile` without forcing it on "a read-only review sandbox" (optional method? separate interface? runtime error?) — is exactly what our per-agent tool physics already solves at the type level: `Bash`/`ReadFile`/`EditFile` are separate contracts, and the Judge's Layer simply never provides `EditFile`. Where they choose between three bad options, we deny by absence-of-ref. Carry their one structural trick we lack: **optional capability members** (`snapshot?`, `expiresAt?`) — model these as separate optional seam services (`Cloudflare.AI.SandboxSnapshot`) rather than widening the core `Sandbox` tag, so `Effect.serviceOption` is the capability probe.

6. **Verifier physics should be copy-on-write, not command refusal** (`in-memory-implementation` → sandbox seam + the fixture's `BashReadOnly`). The fixture (`test/AI/fixtures/org/cloudflare/tools.ts`) mocks the Judge's Bash as a regex mutation-refuser. just-bash's COW overlay is the better physics: **reads hit real state, writes land in a discardable overlay**. A Judge whose `Bash` refuses `rm`/`mv` cannot actually run a test suite (tests write temp files, build artifacts); a COW-overlay Bash lets the verifier *execute anything* while guaranteeing its effects don't persist — write-scope isolation (§8.4's kernel obligation) satisfied by construction rather than by pattern-matching commands. Recommend: ship `Sandbox.overlay` (COW over the DevBox) as the canonical verifier Layer in Phase 3, and note in the design doc that "verifier-outside-write-scope" means *effects don't escape*, not *mutating commands are refused*. This is a mild contradiction with the current fixture's demonstration (not the doc's principle).

7. **Their three backends are our three Layers — keep local/in-memory in the conformance story** (`local-implementation`, `cloud-implementation` → Phase 2/3). Local ↔ `AI.Kernel.memory` + local exec for `alchemy dev`; just-bash ↔ an in-memory sandbox Layer for tests (fast, free, deterministic); cloud ↔ Containers. Their observation that "not every tool is portable on the first try" (simulated shell differs) argues for running our Phase 2 conformance suite against *all* sandbox Layers, not just the kernel Layers — tool-physics portability is a separately testable contract.

8. **Lifecycle hooks are Scope finalizers — we get their `try/finally` discipline for free, but must design `beforeStop`'s content** (`lifecycle-hooks` → sandbox seam). Their `afterStart`/`beforeStop`/`onTimeout` map to Effect `acquireRelease` on a Scoped `Sandbox` Layer (design §3.2 already says "Scoped acquire/release"). The part we haven't designed is the *content* of `beforeStop`: escape uncommitted work (WIP commit / snapshot) before teardown. For the Ring DO harness this is a fold-adjacent operation — "checkpoint at the sandbox boundary" — and should be wired as a finalizer that runs the same code path as `onTimeout` (their `onTimeout` delegates to `beforeStop`; ours should too, so eviction and graceful stop converge).

9. **The sandbox state machine + activity tracker must live inside the Sandbox seam as its own durable loop** (`state-machine`, `durable-workflows` → Ring DO / Containers). Their 4-state machine with hard expiry + inactivity window is directly the lifecycle of our `DevBox` Container. Two implications: (a) the hibernation watchdog is itself a durable loop — on Cloudflare that's a DO alarm owned by the Sandbox Layer, not by the ring's charter (the course's `sleep()` workflow is our alarm; their `"use step"` retry/cache semantics are our Activities rule from §3.2's replay constraint); (b) **the activity-tracker bug transfers to our Trace**: if kernel-internal events (status reads, `AI.observe` trace reads, health polling) count as ring/sandbox activity, perpetual rings and their sandboxes never sleep. Concretely: `AI.observe(Flywheel)` reading a ring's Trace must be a pure storage read that neither wakes the ring's reducer nor resets any keepalive — the design doc says observe contributes nothing to `Req` (§1.2.2) but says nothing about the *runtime* non-effect; add it as a harness obligation.

10. **Snapshot/restore hazards map onto our Durability seam — and checkpoint validity should be tied to `promptHash`** (`snapshot-and-restore` → Durability §3.2). Their three guards translate directly: in-flight dedup = memoized Effect (or a `Deferred` in the DO); attach-or-restore = observe-before-create (this is literally our IaC reconciler doctrine — "observation > assumption", output-as-cache — appearing at the runtime layer; pleasing convergence); double-stop = idempotent delete (already alchemy doctrine). The one genuinely new item is the **fossil problem**: a recovered `StepState`/fold checkpoint from *before a redeploy* may reference a term that has since changed. Our `Resume` policy `(cp) => Continue | Retry | Terminal` should compare the checkpoint's `term` promptHash against the currently deployed term and route mismatches to policy (default: `Retry` with fresh render, never blind `Continue`). Every event already carries `term: promptHash` (§2.3) — use it as the snapshot-invalidation key. The design doc doesn't currently state this; add to §3.2.

11. **State divergence: the provider is truth, the DO is a cache** (`hard-won-lessons` → Ring DO / sandbox seam). Ring DO storage will hold the sandbox handle, the Workflow instance id, the Container state. The course's rule — provider API is the source of truth, DB and client are caches, "when in doubt, fetch" — plus the stale-handle probe (cheap read-only exec before trusting a reconnected handle) should be standing policy in the Cloudflare harness: after any recovery/eviction, probe the Container before resuming a turn that will call `Bash`. Add "stale sandbox handle after DO eviction" to §6's risk table; it's the same class as their #1 outage.

12. **Subagent role design corroborates agent-as-tool and adds the model axis** (`why-delegate`, `task-tool` → Kernel §2.4 + Layer composition). "Sub-agents are not a Kernel feature" (§2.4) matches the course exactly: their task tool is an ordinary tool whose execute runs a fresh inner loop and returns a string — isolation and summary-return fall out of composition, as we claim. Their spawn-permission table (`executor: ["explorer"], explorer: []`) is our capability-by-interpolation, statically: an agent can only delegate to agents its template mentions, and the Layer graph fixes what each gets. **But the model-per-role table exposes a design tension**: in `alchemy-ai-design.md` §2.6/§3.1, `AiLanguageModel` sits in the *kernel/harness* requirements, implying one model per kernel instance, while the course argues "Model per role, not model per session… the failure modes are different too" (Haiku-explorer/Sonnet-executor/Opus-reviewer). Recommendation: the kernel should resolve the model like it resolves tool refs — `Effect.serviceOption(AiLanguageModel)` at *term interpretation time*, so `AI.layer(Judge).pipe(Layer.provide(OpusModel))` overrides the kernel default exactly like `BashReadOnly` does. This keeps the Kernel interface vocabulary-free (the model is a seam) and makes model choice part of per-agent physics. Flagging as a **contradiction-in-shape with §2.6's sketch** (`const model = yield* AiLanguageModel` at kernel-layer construction) — resolve per-term instead.

13. **Per-role step budgets validate `Budget` inside Agent terms** (`explorer-subagent` → §1.2.2). Their `stepCountIs(5)` explorer / `stepCountIs(15)` executor is a per-agent iteration ceiling. The design already permits `AI.budget` inside an Agent template; make sure the kernel enforces agent-scoped budgets independently of the enclosing loop's budget (nested envelopes, §8.4's "per-iteration budgets are semantic"). The explorer's fresh-context-per-call is our `fold = const(spec)` at the delegation boundary — subagent isolation is a memory strategy, which is §0.1's Claude Code point restated.

14. **The approval two-layer model: our tool Layers cover "who decides"; we lack a stated seam for "what policies apply"** (`approval-config`, `extension-points` → tool layers / harness seams). Their config union maps cleanly onto us: `interactive`/`background`/`delegated` are just different Layers implementing `Approve`/`AskHuman` per ring — the autonomy dial (§0.9), and `delegated.trust` is a Layer parameter. But their **event layer** — interceptors that can block or *rewrite* any tool call regardless of mode ("Regardless of what the human approves, never touch `.env`") — has no home in our design. Our `KernelEvent` stream (§2.3) is emit-only observability; the course's handlers are in the command path. Two options consistent with our inversion: (a) per-tool Layer decoration (their `wrapTool` ≡ a Layer that wraps a tool implementation) — works but is per-contract, not cross-cutting; (b) a harness-private `ToolInterceptor` seam (a `Context.Tag` the Cloudflare harness pulls with a pass-through default) that sees every `CallTool` command before execution and may block (synthesizing the `ToolResult` per insight #1) or modify. Recommend (b) as a named seam in §3.2 — it stays out of the Kernel vocabulary, satisfies their "defense in depth" argument, and gives `.env`-class project policies one place to live. **Gap flagged**: neither §2 nor §3 currently mentions interception; only emission.

15. **The Ask command should carry structured options, and the protocol lives in prose** (`structured-questions` → Ask command §2.4 + charters). Their `askUser` is `{ question, options: 2..4 }` — a schema, not free text. Our `Ask` command payload should likewise be schema'd (question + typed options + timeout), because every downstream surface (Discord buttons, Slack blocks, dev-console prompt, `step.waitForEvent` payload matching) benefits from structure, and the typed answer feeds back as `AskAnswer` feedback cleanly. Their pending-state trick — the tool result says "(Awaiting user response.)" so the model doesn't assume an answer — is our durable-wait made visible in-context; in our harness the wait is real (`step.waitForEvent`), but the *rendered transcript* should still show the pending question if the turn continues. The ambiguity protocol (search → ask → act) is charter prose, and our reference org's `Support` agent already encodes a version of it ("SearchIssues first… AskHuman for anything touching secrets"); adopt the explicit three-step ordering in agent templates where askable humans exist. Also inherit their friction warning: a ring whose `Bash` Layer is read-only or approval-gated may never gather enough context to ask a *good* question — a lint-adjacent design review point when composing Layers.

16. **The verification contract enriches our Check verdict** (`verification-contract` → `AI.check` / kernel default judge). Their gate sequence (typecheck → lint → test → build, discovered from the repo, fastest first) plus **scoped claims** (caused vs pre-existing failures) is a concrete spec for the Judge's verdict schema. Our design already has the strong structural version (the Judge runs `Bash` itself — "the Engineer's claim of done-ness is not a signal"), but the verdict shape is undesigned. Adopt: verdict = per-gate results `{ gate, command, outcome, causedByThisRun: boolean }` + overall goal-met, with the caused/pre-existing distinction computed by comparing against the iteration's *entry* state (which the Trace gives us for free — run the gates at iteration start or read the previous iteration's verdict). Their "hedged future tense is the tell" is a good heuristic for the kernel's default judge policy grading unverified claims. `discoverGates` (from `package.json`) is a sensible kernel-default judge behavior when a `Check` has no explicit grading template.

17. **The todo tool's single-active invariant is guardrails-in-code — and stale-state hygiene is fold hygiene** (`todo-tool` → tool layers / fold). "One rule the agent can't argue with" enforced in `execute` (reject `start` while another item runs) is Meta's guardrails-in-code (§8.3) at tool scale: put invariants in tool implementations, not prompts. If we ship a planning tool in the standard palette, enforce cardinality in the Layer. Their "don't carry stale `in_progress` items into a new session" is a fold rule: execution-state (as opposed to knowledge) should not survive the iteration boundary unless the fold explicitly re-justifies it — Ralph's fresh-context argument in miniature; worth a sentence in the fold seam docs.

18. **Skills = progressive disclosure = our cache-stability principle at the knowledge layer; map to world-side artifacts + a tool** (`skills-system` → tool layers / renderer). Names+descriptions resident (≈100 tokens), content on demand, capped, project-overrides-global. For us: skills are repo files (world-side memory, like `.alchemy/NOTES.md`) plus a `LoadSkill` tool Layer; the *list* renders into the agent's prompt (renderer support: a Layer-provided prompt fragment? today our prompt is purely the term — see the tension below). Their warning "treat this as a retrieval path, not a guarantee" and "if the model never loads a skill that would obviously help, your skill descriptions need sharper hooks" applies verbatim. **Tension with §1.6**: our render is a pure function of the *term*; a skills list is environment-derived prompt content (like their `buildSystemPrompt(ctx)` runtime fields: sandboxType, gitBranch, verificationCommands, AGENTS.md). The design doc should decide where environment-derived sections enter: keep `render(term)` pure/content-addressed, and let the *kernel* append a clearly-delimited, harness-supplied context block (whose churn is kept out of `promptHash` and out of the cached prefix's head). Right now §1.6 doesn't name this second block; flag as an under-designed area rather than a contradiction.

19. **`buildSystemPrompt` as a pure function is independent corroboration of the renderer** (`dynamic-prompt-construction` → §1.6). "Same context in, same prompt out… testable, composable, replaceable, deterministic" — the course reinvents render-purity for the same reasons we specified it (testability, versioning). Their smallest-possible prompt unit test (assert a section's presence/absence given ctx) is the model for our renderer golden tests. Their deliberate redundancy finding — tool routing stated in both descriptions *and* prompt "because models miss it in one" — supports our two-place rendering (tool name + one-liner in prose, full contract in schema section) and cautions against DRY-ing it away.

20. **`AGENTS.md` is world-side memory our charters already model — keep it in prose, not framework** (`project-context` → charters/fold). The course's per-project config file is exactly what `Fix`'s charter does explicitly ("give Engineer… CONTRIBUTING.md and .alchemy/NOTES.md"): the repo tells the agent how to behave, and the fold (Scribe) *writes back* the "Lessons learned" section their example shows humans writing by hand. No new term needed; the insight is that our fold-to-repo loop automates the part of AGENTS.md ("Lessons learned") that their harness leaves manual. The kernel's default agent context could include an AGENTS.md-discovery convention (harness seam), mirroring `discoverGates`.

21. **The 5-section description contract is authoring guidance for Tool terms, and partially lintable** (`descriptions-that-work` → Tool terms / `AI.lint`). Our Tool templates are the descriptions; `${Parameter}` interpolation covers their USAGE section mechanically (schema + description are one artifact — our claim §0.1, which their "USAGE earns its place when a parameter has constraints the model can't infer from the schema" independently motivates: our Parameter templates *can* carry those constraints in the schema description, closing the gap that forces their USAGE section to exist). WHEN/WHEN-NOT/DO-NOT-USE-FOR and EXAMPLES are prose conventions — document them as the house style for Tool terms; optionally `AI.lint` warns on very short tool templates (bash gravity is empirical and tier-dependent, so a nudge, not an error).

22. **Headless agent / surfaces-as-renderers is our events stream; resumable streams are Trace replay** (`web-surface`, `streaming-and-tool-rendering` → KernelEvents §2.3). Their chunk taxonomy (text-delta / tool-call / tool-result) is a strict subset of our `KernelEvent` vocabulary; their SSE bridge is "subscribe to `kernel.events`, filter by session, serialize." Their resumable-stream design (session persists; a stream is "one render of that session") is precisely Trace-as-single-representation: a reconnecting client replays the Trace to catch up, then tails live events. "The agent does not know there is a web" = the Kernel has no surface vocabulary — inversion (4) confirmed from the harness-builder's side. No design change; cite as validation.

23. **Event-bus ordering discipline transfers to Trace emission** (`extension-points` → step machine / Trace). "Logging before safety checks captures the call attempt even when it gets blocked" → our step machine should `Emit(ToolRequested)` *before* any interceptor/approval gate runs, and emit a distinct terminal event for blocked calls (`ToolFailed` with a `blocked` cause, or a dedicated variant) — otherwise the Trace "logs half the story" and the autoresearch ring can't see denials, which are among the most informative signals (Warp counts every intervention as telemetry, §8.3). Check `KernelEvent`'s core set (§2.3) accounts for blocked/denied as distinct from failed.

24. **The `session_before_compact` guardrail-injection hack is a problem our architecture dissolves — say so** (`extension-points` → fold/renderer). They must re-inject "preserve all safety constraints" at compaction because their system prompt and history are one mutable transcript. In our design the prompt is re-rendered from the immutable term every turn, and compaction (fold/ContextPolicy) operates only on the iteration history — guardrails *cannot* be compacted away because they were never in the compactable region. Worth an explicit sentence in §2's kernel obligations: the rendered term is re-supplied on every model call and is outside ContextPolicy's jurisdiction. (Their hack is evidence this failure mode is real in transcript-shaped harnesses.)

25. **Cost-aware lifecycle math justifies budget wiring at the sandbox seam, not just the loop** (`cloud-implementation`, `durable-workflows` → Budget / sandbox seam). Their $4.80-vs-$0.50 per session and the "where does the cost check go — stop, snapshot, or ask?" challenge map to our channels: sandbox idle-cost is *harness* budget (the Sandbox Layer's hibernation policy), while loop budgets (`AI.budget`) meter the work itself. The design doc's budget story (§1.2.2, §8.4) covers tokens/wallClock/usd/iterations/stall on rings; add a note that the Cloudflare harness's Sandbox seam owns machine-cost hygiene (inactivity hibernation, expiry-driven snapshot) independently of ring budgets, and that exceeding a *sandbox* cost threshold surfaces as an `Escalated` KernelEvent rather than `BudgetExceeded` (it's an ops signal, not a work-item failure).

26. **Explorer/executor as reference palette for our default kernel's delegation** (`task-tool` → Phase 2/4). When we ship standard sub-agent patterns (e.g., a `Researcher` in the reference org, or the kernel's default handling of `${Agent}`-as-tool), the course's tuned defaults are worth stealing: read-only + cheap model + tiny step budget for exploration; delegated-trust exec + stronger model + moderate budget for implementation; neither gets human-asking tools (escalation stays with the ring that holds the human-in-loop tool — for us, whichever term interpolates `${AskHuman}`). Their "don't add roles speculatively — each role is a new place for instructions to drift" is our lint-adjacent org-design guidance.

### Contradictions / tensions with `alchemy-ai-design.md`, summarized

- **Model-per-role vs kernel-held model** (insight #12): §2.6/§3.1 place `AiLanguageModel` in the kernel/harness `R`; course Module 6 argues models are role physics. Resolve the model at term-interpretation time (seam with kernel default), mirroring tool resolution.
- **No interception seam** (insights #14, #23): §2.3's events are emit-only; the course demonstrates a needed block/modify path for project-scoped policies. Add a harness-private `ToolInterceptor` seam (§3.2) — not Kernel vocabulary — and specify Trace emission ordering around it.
- **Verifier physics in the fixture** (insight #6): the `BashReadOnly` mutation-refusal mock contradicts the course's (better) COW-overlay approach to read-only execution; the design principle (§8.4 verifier-outside-write-scope) is fine, the demonstrated mechanism should change in Phase 3.
- **Environment-derived prompt content** (insight #18): §1.6's pure `render(term)` doesn't yet name where runtime context (skills list, discovered gates, AGENTS.md, sandbox identity) enters the prompt without destabilizing `promptHash`/cache. Under-designed rather than contradicted; the course's `PromptContext` is the checklist of what will need a home.
- **Checkpoint fossils** (insight #10): §3.2's `Resume` policy doesn't mention term-version (promptHash) validation of recovered checkpoints; the course's snapshot-fossil lesson says it must.
- **Tool-pairing invariant scope** (insight #1): §2.4 scopes it to trimming/recovery; the course's confabulation trap shows policy blocks are the more insidious producer of orphans. Broaden the invariant's statement.
