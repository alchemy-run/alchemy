# Pi (earendil-works/pi) — a study for Alchemy AI

Study of the pi coding agent (pi.dev, Mario Zechner / badlogic), focused on `packages/coding-agent`, conducted against a fresh shallow clone at `.vendor/pi` (July 2026, session format v3, coding-agent ≥0.74 era). All `file:line` citations are into `.vendor/pi`. Written to inform the Alchemy AI Kernel design (`alchemy-ai-design.md`).

---

## 1. Architecture overview

### Monorepo map

```
packages/ai             # "pi-ai" — unified LLM API: 15+ providers, streaming, auth/OAuth,
                        #   token+cost tracking, models catalog. No agent concepts.
packages/agent          # "pi-agent-core" — THE KERNEL. ~1,800 lines total:
                        #   agent-loop.ts (790 loc)  pure-ish loop: messages in, events out
                        #   agent.ts (575 loc)       stateful wrapper + steering/follow-up queues
                        #   types.ts (428 loc)       AgentLoopConfig = the seam record
                        #   harness/                 optional batteries (jsonl sessions, compaction,
                        #                            system-prompt, skills) — NOT used by the loop
packages/coding-agent   # the product/harness. core/ = AgentSession (3,187 loc), tools/ (7 tools),
                        #   extensions/ (loader/runner/types), skills, compaction, session-manager,
                        #   model-registry, settings, trust. modes/ = interactive TUI, print, rpc, json.
packages/tui            # terminal UI framework (differential rendering); irrelevant to kernel design
packages/orchestrator   # experimental, explicitly unstable; not studied further
```

### Where the kernel boundary actually sits

Pi's real kernel is `packages/agent/src/agent-loop.ts` plus the `AgentLoopConfig` interface (`packages/agent/src/types.ts:140-282`). The loop knows about exactly: messages, a model, tools, an abort signal, and **nine optional hook functions**. It does not know the words *session, skill, compaction, extension, permission, trust, UI, provider registry*. Every one of those lives one package up, in `coding-agent`, and reaches the loop only through the hook record:

```ts
// types.ts:140-282 — the complete seam set of a production harness
convertToLlm         // AgentMessage[] → provider Message[] (lossy projection)
transformContext     // context rewrite before convertToLlm (compaction/injection point)
getApiKey            // per-call key resolution (expiring OAuth tokens)
shouldStopAfterTurn  // graceful stop policy
prepareNextTurn      // swap context/model/thinking between turns (mid-session model switch)
getSteeringMessages  // mid-run user input, polled after each turn
getFollowUpMessages  // input delivered only when the agent would stop
beforeToolCall       // block/allow (permission seam)
afterToolCall        // rewrite tool results
```

`AgentSession` (`coding-agent/src/core/agent-session.ts`) is the single stateful facade that binds those hooks to the extension runner, the session tree, compaction, and the tool registry (`agent-session.ts:419-490`, `sdk.ts:359-363`). All four run modes (interactive TUI / print / `--mode json` / `--mode rpc`) and the SDK are thin projections over `AgentSession` (`modes/index.ts:1-15`, `core/sdk.ts`).

So pi's architecture is a **three-ring onion**: tiny hook-parameterized loop → opinionated harness with named components and override events → mode surfaces. The "minimal kernel" claim is true of ring 1; ring 2 is decidedly not vocabulary-free (see Judgments).

## 2. Per-topic findings

### 2.1 The loop

Core: `agent-loop.ts:155-275` (`runLoop`). Structure is **two nested while-loops**:

- **Inner loop** (`:174-260`): stream one assistant response (`streamAssistantResponse`, `:281-374`); collect `toolCall` blocks (`:203`); execute them (parallel by default, sequential if any tool demands it, `:420-428`); emit `turn_end`; run `prepareNextTurn` (may swap context/model/thinking, `:232-245`); check `shouldStopAfterTurn` (`:247-257`); poll the steering queue (`:259`). Continues while there are tool calls **or** pending steering messages.
- **Outer loop** (`:170, 262-272`): when the agent would stop, poll the follow-up queue (`:263`); if messages exist, re-enter the inner loop. Otherwise `agent_end`.

**Turn representation:** a *turn* = one assistant message + its tool results. There is no separate turn object; the transcript (`AgentMessage[]`) is the state, mutated in place (`:186-189, 219-221`).

**Exit conditions**, exhaustively: (a) assistant `stopReason ∈ {error, aborted}` (`:196-199`); (b) no tool calls and both queues empty (`:271`); (c) `shouldStopAfterTurn` returns true (`:247-257`); (d) all tool results in a batch set `terminate: true` — an early-termination hint any tool or `afterToolCall` hook can set (`:584-586`, `types.ts:77-86`); (e) abort signal. Notably, "model returned no tool calls" is exactly the default exit, and everything else is a policy hook — matching alchemy-ai-design §2.4's "termination is policy".

**A subtle correctness rule:** when `stopReason === "length"`, *all* tool calls in the truncated message are failed rather than executed, because streamed arguments are finalized with a salvage JSON parser and may validate while being silently incomplete (`:207-216, 383-408`). This is a real-world invariant worth stealing.

**Steering interrupts — precise semantics:** steering does **not** interrupt tool execution. A steering message is delivered *after the current assistant turn finishes executing all of its tool calls, before the next LLM call* (`:259`; `docs/rpc.md` "steer"). Only Escape/abort interrupts tools. Queue drain policy is configurable: `"one-at-a-time"` (default — one steering message per completed turn) or `"all"` (`agent.ts:123-157`, `types.ts:49`). The queues live on the `Agent` wrapper (`agent.ts:174-175, 274-281`); `Agent.prompt()` throws if a run is active — queueing is the only way in mid-run (`agent.ts:337-345`). *(Correction to the task brief: nothing in pi core "interrupts remaining tools" on steer; that phrasing matches the community pi-subagents extension's steering of child agents, not the core loop.)*

### 2.2 Memory & compaction

**System prompt layering** (`core/system-prompt.ts:28-173`): default prompt body ≈ 1.1 KB of text (~300 tokens) — tools list (one-line snippets), guidelines, pointers to pi's *own docs on disk* (`:140-147`, the hook for "ask pi to modify itself"). Then, appended in order: `APPEND_SYSTEM.md` text → `<project_context>` with all discovered `AGENTS.md`/`CLAUDE.md` files (global → parent dirs → cwd, concatenated) → the skills index → current date and cwd last (`:149-172`). `SYSTEM.md` replaces the default entirely; append still works on top. The "sub-1k-token prompt" claim from alchemy-ai-design §0.1 holds for the default body (before user context files, which are user-controlled).

**Skills = progressive disclosure without cache busting** (`core/skills.ts:335-361`): only each skill's `name`, `description`, and **file path** are rendered into an `<available_skills>` XML block in the system prompt, with the instruction "Use the read tool to load a skill's file when the task matches its description." The mechanics of cache preservation: the index is small and *stable* (changes only on skill add/remove → `/reload`), and the skill *body* enters context as an ordinary `read` tool result mid-conversation — i.e. appended at the context tail, never touching the cached prefix. `disable-model-invocation: true` frontmatter hides a skill from the model entirely (invocable only as `/skill:name`). Skills are plain `SKILL.md` files with YAML frontmatter, per the agentskills.io spec (name ≤64 chars lowercase, description ≤1024, `skills.ts:11-14, 92-127`).

**Compaction** (`core/compaction/compaction.ts`): episodic summarize-old/keep-recent. Defaults: `reserveTokens: 16384`, `keepRecentTokens: 20000` (`:122-126`). Trigger `shouldCompact`: `contextTokens > contextWindow - reserveTokens` (`:225-228`), checked at `agent_end` and before each prompt (`agent-session.ts:1938`), plus **overflow recovery**: a provider "context too long" error triggers compaction and an automatic retry of the aborted turn (`agent-session.ts:1900-1911`; reasons are `"manual" | "threshold" | "overflow"`).

The pipeline: `prepareCompaction(pathEntries, settings)` is a **pure function** producing a `CompactionPreparation` (`:634-731`): cut point, `messagesToSummarize`, `turnPrefixMessages` (if the cut splits a turn), `previousSummary` (for iterative update), extracted file operations, `tokensBefore`. Cut-point selection walks backward accumulating estimated tokens (chars/4 heuristic, `:253-296`) and **may never cut at a tool result** (`findValidCutPoints`, `:298-343`) — the tool-pairing invariant, load-bearing here exactly as alchemy-ai-design §2.4 predicts. If the cut splits a turn, the turn prefix gets its own summary merged in (`:737-813`). The summary itself is a fixed structured-markdown template (Goal / Constraints / Progress / Key Decisions / Next Steps / Critical Context, `:460-491`), with an *update* variant that merges new messages into the previous summary (`:493-530`) — an iterated fold in all but name. Result is persisted as a `CompactionEntry {summary, firstKeptEntryId, tokensBefore, details}` in the session tree; context rebuilding honors it (`docs/session-format.md`, Context Building).

**The extension seam** (`extensions/types.ts:578-599, 1089-1092`): `session_before_compact` fires with the full pure `preparation`, the branch entries, the trigger `reason`, `willRetry`, and a signal; a handler may **cancel** or return a complete replacement `CompactionResult`; on handler error the default runs (fallback-on-failure, `agent-session.ts:1985+`). `examples/extensions/custom-compaction.ts` demonstrates full replacement with a different (cheaper) model. `session_compact` fires after. Branch summarization (`/tree` navigation away from a branch) is the same shape: `session_before_tree` with a `TreePreparation`, replaceable summary (`types.ts:609-637`).

**Dynamic context injection:** two flavors. `before_agent_start` (fires after user prompt, before the loop) can return a `CustomMessage` to inject and/or a replacement system prompt *for that turn* (`types.ts:685-695, 1074-1078`; consumed at `agent-session.ts:1143-1171`; plan-mode uses it to inject `[PLAN MODE ACTIVE]…`, `examples/extensions/plan-mode/index.ts:201-247`). `context` (fires before *every* LLM call) can return a fully rewritten `messages` array (`types.ts:656-659, 1043-1045`), wired through `Agent.transformContext` (`sdk.ts:359-363`, chained across extensions in `extensions/runner.ts:927-948`). Plan-mode uses it to *filter out* stale injected context when the mode is off (`plan-mode/index.ts:177-198`).

### 2.3 Tool system

**The four core defaults**: `read`, `bash`, `edit`, `write` (`core/tools/index.ts:138-145`; `system-prompt.ts:90`). Pi actually ships **seven** built-ins — `grep`, `find`, `ls` are opt-in via `--tools` (`tools/index.ts:83-84`) — the "four tools" story is the default loadout, not the inventory. Each tool is a factory (`createBashTool(cwd, options)`) returning an `AgentTool`: TypeBox `parameters` schema, `label`, `execute(toolCallId, params, signal, onUpdate)` (`packages/agent/src/types.ts:370-394`). Output discipline is centralized: truncation defaults 2,000 lines / 50 KB with the full output spilled to a temp file and the path reported (`tools/truncate.ts:11-12`; bash details carry `fullOutputPath`).

**Execution semantics** (`agent-loop.ts:411-556`): per-batch mode is parallel by default; any tool with `executionMode: "sequential"` forces the whole batch sequential. In parallel mode, *preparation* (validation + `beforeToolCall`) is sequential in assistant order, execution is concurrent, `tool_execution_end` is emitted in completion order, but tool-result *messages* are appended in assistant source order — order-stability for the transcript. Errors: tools throw; the loop converts to an error tool result (`:699-708`); a missing tool name is an error result, not a crash (`:609-615`).

**Extension tools**: `pi.registerTool(ToolDefinition)` (`extensions/types.ts:437-484, 1211-1213`) — same shape plus `ctx: ExtensionContext` as a fifth execute arg, optional `promptSnippet` (one-liner in the system-prompt tools list), `promptGuidelines`, custom TUI renderers (`renderCall`/`renderResult`). Extensions can also **replace built-ins entirely** and toggle the active set at runtime (`setActiveTools`, `types.ts:1293-1299` — plan-mode flips between read-only and full sets, `plan-mode/index.ts:104-114`). Interception: the `tool_call` event's `input` is **mutable in place** and handlers may `{block, reason}` (`types.ts:879-893, 1049-1053`); `tool_result` may rewrite content/details/isError (`types.ts:1063-1067`). These bridge into the kernel's `beforeToolCall`/`afterToolCall` hooks at `agent-session.ts:419-466`.

### 2.4 Subagents — none built in, and what grew in the vacuum

Pi's stance (README Philosophy): *"No sub-agents. There's many ways to do this. Spawn pi instances via tmux, or build your own with extensions, or install a package that does it your way."* The stated workarounds are (a) tmux-spawned `pi` processes (full observability, direct interaction — also their answer to background bash), (b) extensions.

What the extension API makes possible, and what the community actually built:

- **`pi-sub-agent`** (pi.dev/packages/pi-sub-agent): a `subagent` tool that runs each delegated task as a `pi --mode json -p --no-session` subprocess; single/parallel/chain modes; bundles nine role agents (scout, planner, worker, reviewer, …); discovers user agents from `~/.pi/agent/agents/*.md` and project agents from `.pi/agents/*.md`.
- **`@tintinweb/pi-subagents`** (~580 stars, 20 contributors, 40 releases): Claude-Code-style `Agent` tool + `get_subagent_result` + `steer_subagent`; foreground/background with concurrency caps (default 4); **mid-run steering of children**; resume; `isolation: "worktree"` (git worktree per agent, auto-commit to branches); `inherit_context` (fork the parent conversation into the child); agent types as markdown files with YAML frontmatter (model, thinking, tool restrictions, `max_turns`); cron/interval **scheduling** of subagents; lifecycle events on `pi.events` (`subagents:created/started/completed/failed/steered/compacted`); live TUI fleet widget.
- **`@e9n/pi-subagent`**: adds orchestrator (agents spawn agents) and pool (long-lived children with persistent context) modes; subagents run `--no-extensions` by default with an extension whitelist, and an extension **blocklist** (`pi-subagent` itself is always blocked — recursion guard).

Structure lesson: every package converged on (1) subagent = *a tool*, (2) agent definitions = *prompt files with typed frontmatter*, (3) child = *a fresh pi process in JSON mode* (isolation by OS process), (4) results returned as a tool result (the summary-return pattern), (5) hand-rolled budgets (timeouts, `maxTotal`), events, steering, and scheduling — i.e. the community re-implemented, in untyped extension-space, most of what Alchemy's kernel natively types (`ForkLoop`, budgets, `KernelEvent`, triggers/cron).

### 2.5 Sessions, state, durability

**Format** (`docs/session-format.md`; `core/session-manager.ts`, 1,623 loc): one JSONL file per session at `~/.pi/agent/sessions/--<cwd-with-dashes>--/<timestamp>_<uuid>.jsonl`. Line 1 is a `SessionHeader` (version 3, uuid, cwd, optional `parentSession`). Every other line is an entry with `{type, id (8-char hex), parentId, timestamp}` — **the file is an append-only tree**; branching is in-place by appending a child to an earlier entry; the current position is just the leaf pointer. Entry types: `message` (wraps an `AgentMessage`), `model_change`, `thinking_level_change`, `compaction`, `branch_summary`, `custom` (extension state, **not** in LLM context), `custom_message` (extension message, **in** context), `label`, `session_info`.

**Branching/rewind:** `/tree` moves the leaf anywhere in the tree, optionally appending a `branch_summary` entry (LLM summary of the abandoned branch — extension-replaceable, cancellable); `/fork` copies the active path up to a chosen user message into a *new file*; `/clone` duplicates the active branch. Context rebuilding: `buildContextEntries()` walks leaf→root and honors compaction (`compaction entry first, then entries from firstKeptEntryId`, `session-format.md` §Context Building). Sessions v1 (linear) auto-migrate.

**Resume:** `pi -c` / `-r` / `--session <id>`; RPC `get_entries` supports a `since` cursor over the append-only file — entry ids double as durable cursors across client restarts (`docs/rpc.md` get_entries).

**What is NOT durable:** the steering/follow-up queues (in-memory arrays, `agent-session.ts:279-281`); in-flight tool executions; extension state that isn't explicitly persisted via `pi.appendEntry` (plan-mode persists its own state as `custom` entries and re-scans messages after resume to rebuild step-completion, `plan-mode/index.ts:339-389`); aborted partial assistant messages beyond what was flushed. There is no journal-before-execute: a crash mid-turn loses the turn. Durability = "the message tree so far", nothing finer-grained.

### 2.6 Async vs sync

Everything is one process, one active run. Asynchrony surfaces in three places: (1) the **event stream** — the kernel emits 10 event types (`agent/turn/message/tool_execution × start/end` + `message_update` streaming deltas + `tool_execution_update`, `packages/agent/src/types.ts:413-428`), and listeners are *awaited in order and included in run settlement* (`agent.ts:241-244, 527-573` — backpressure by construction; the run is not idle until `agent_end` listeners settle); (2) the **steering/follow-up queues** (§2.1); (3) **RPC mode** (`docs/rpc.md`): strict LF-delimited JSONL over stdio; commands (with optional `id` correlation) → one `response` each; events stream interleaved. `prompt` during streaming *requires* `streamingBehavior: "steer" | "followUp"`, otherwise errors. Extension UI calls in RPC mode become a **sub-protocol**: dialog methods (`select`/`confirm`/`input`/`editor`) emit `extension_ui_request` and block on a matching `extension_ui_response`; fire-and-forget methods (`notify`, `setStatus`, `setWidget`, …) emit without reply; timeouts auto-resolve server-side (`rpc.md` §Extension UI Protocol). A `queue_update` event mirrors queue state to clients.

### 2.7 Pluggability (the core topic)

**Extension module shape:** a TS/JS file default-exporting `(pi: ExtensionAPI) => void | Promise<void>` (`extensions/types.ts:1459-1468`). Async factories block startup — used for e.g. fetching remote model lists before `registerProvider`.

**The full API surface** (`extensions/types.ts:1159-1392`): `pi.on(event, handler)` for **~34 events** in five families — startup/trust (`project_trust`, `resources_discover`), session lifecycle (`session_start/_info_changed/_before_switch/_before_fork/_before_compact/_compact/_shutdown/_before_tree/_tree`), agent lifecycle (mirrors of all kernel events plus `before_agent_start`, `context`, `before_provider_request`, `before_provider_headers`, `after_provider_response`), model (`model_select`, `thinking_level_select`), input (`input`, `user_bash`, `tool_call`, `tool_result`). What handlers can **mutate/replace**, by event: `context` → whole message array; `before_agent_start` → injected message + per-turn system prompt (chained across extensions); `tool_call` → mutate `input` in place, or block; `tool_result` → content/details/isError; `message_end` → replace the finalized message (same role); `before_provider_request` → replace the raw payload; `before_provider_headers` → mutate headers; `session_before_compact`/`_before_tree`/`_before_fork`/`_before_switch` → cancel or substitute. Registration: `registerTool`, `registerCommand` (slash commands with autocomplete), `registerShortcut`, `registerFlag` (CLI flags!), `registerMessageRenderer`/`registerEntryRenderer` (TUI rendering of custom types), `registerProvider`/`unregisterProvider` (models + OAuth + custom `streamSimple`). Actions: `sendMessage` (custom message, `deliverAs: steer|followUp|nextTurn`), `sendUserMessage`, `appendEntry` (durable extension state), `setActiveTools`, `setModel`, `setThinkingLevel`, session naming/labels, `exec`, and a shared `EventBus` for extension↔extension communication (`types.ts:1391`).

**Command context** adds session control: `newSession`, `fork`, `navigateTree`, `switchSession`, `reload` (`types.ts:341-375`).

**Distribution:** pi packages = npm or git repos with a `pi` manifest key (`{extensions, skills, prompts, themes}` paths) or conventional dirs; `pi install npm:… | git:… [@ref]`, project-local `-l`, pinning, `pi update`, `pi config` enable/disable (README §Pi Packages). **Trust model:** project-local settings/extensions/skills load only after an explicit per-folder trust decision recorded in `~/.pi/agent/trust.json`; before trust, only user/global/CLI extensions load, and those may themselves handle the `project_trust` event (`types.ts:505-527`; README §Project Trust). Non-interactive modes never prompt — `defaultProjectTrust` decides.

**What remains hardcoded** (no event can change it): the loop shape itself (turn structure, queue drain points); session file format and tree semantics; the compaction *trigger policy* and cut-point machinery (only the summary is replaceable); the trust flow; queue drain modes (choose between two, can't redefine); tool-pairing rules; the four+three built-in tool implementations (replaceable only wholesale by name).

**"Ask pi to modify itself" + `/reload`:** the default system prompt embeds absolute paths to pi's own README, docs, and examples with instructions to read them when asked about pi (`system-prompt.ts:140-147`). So the workflow is: user asks pi to write an extension → pi reads its own extension docs → writes `~/.pi/agent/extensions/foo.ts` → user runs `/reload`, which tears down (`session_shutdown` event, `reason: "reload"`) and reloads extensions/skills/prompts/keybindings in-process (`ExtensionCommandContext.reload`, `types.ts:373-375`); themes hot-reload on file change without even that. Stale extension instances are invalidated via `assertActive`/`invalidate` (`types.ts:1543-1546`).

### 2.8 Human-in-the-loop

No permission popups in core. The replacement stack, in practice: (1) **containers/sandboxes** — README recommends running in a container; `examples/extensions/sandbox/` and `gondolin` show sandboxed execution, and `user_bash`/tool events allow swapping the bash `operations` for SSH/sandbox backends (`types.ts:1056-1061`); (2) **extension-built gates** — `examples/extensions/permission-gate.ts` is the 34-line canonical form: `tool_call` handler pattern-matches dangerous bash, `ctx.ui.select("Allow?")`, returns `{block: true}` on refusal, **blocks by default when `ctx.hasUI` is false** (`permission-gate.ts:19-30`); `confirm-destructive.ts`, `protected-paths.ts`, `dirty-repo-guard.ts` are variations; (3) **UI primitives that degrade by mode** — the same `ctx.ui.confirm/select/input/editor` works in TUI natively and over RPC via the sub-protocol; in print mode `hasUI` is false and gates must fail closed. Timeouts with auto-resolve keep unattended runs from hanging forever (`types.ts:91-96`). The autonomy dial is therefore *which extensions are installed* — pleasingly close to Alchemy's "autonomy is a Layer choice", but untyped and per-installation rather than per-ring.

### 2.9 Provider abstraction

`packages/ai` normalizes ~30 providers (Anthropic, OpenAI incl. Responses, Google, Bedrock, Vertex, Groq, Cerebras, OpenRouter, Copilot, ZAI, MiniMax, …) behind three API families and one `streamSimple(model, context, options) → AssistantMessageEventStream`; only tool-capable models are cataloged (`packages/ai/README.md`). Model metadata (`contextWindow`, `maxTokens`, per-token `cost`, `reasoning`, `thinkingLevelMap`, `compat`) is a generated catalog (`models.generated.ts`) plus user overlay `~/.pi/agent/models.json`, plus runtime `pi.registerProvider()` from extensions — which can also carry a full custom `streamSimple` and an OAuth flow (`login/refreshToken/getApiKey/modifyModels`, `extensions/types.ts:1399-1429`). Auth: subscription OAuth (Claude Pro/Max, ChatGPT, Copilot) or API keys with `$ENV` interpolation and `!command` resolution. **Mid-session model switching** is first-class: `set_model`/`/model`/Ctrl+P persist a `model_change` entry; the kernel picks it up because `prepareNextTurn` re-snapshots model+thinking from session state before *every* turn (`agent-session.ts:469-490`) — model is per-turn data, not construction-time config. Usage/cost accounting is normalized on every `AssistantMessage` (`session-format.md` Usage).

### 2.10 Integration

**SDK:** `createAgentSession({sessionManager: SessionManager.inMemory(), authStorage, modelRegistry, customTools, tools, noTools, resourceLoader, …})` → `{session}`; `await session.prompt("…")` (`core/sdk.ts:34-110, 385-407`; README §SDK). Everything the TUI uses is injectable: in-memory sessions, custom tools, disabled discovery, custom `streamFn`. OpenClaw embeds pi this way (per pi.dev; not verified in this repo). Multi-session runtimes via `createAgentSessionRuntime` (`core/agent-session-runtime.ts`).
**Print/JSON mode:** `pi -p "…"` reads piped stdin, prints, exits; `--mode json` streams every event as JSON lines — this is exactly what the subagent packages drive.
**RPC mode:** §2.6; explicitly recommended for non-Node integrations; a typed Node client ships at `modes/rpc/rpc-client.ts`.
One core serves all four because **`AgentSession` is the only brain**; each mode owns only I/O framing and an `ExtensionUIContext` implementation (interactive: real TUI; RPC: sub-protocol; print: `hasUI=false` no-ops).

## 3. Judgments

**What the minimal-kernel bet buys them.** (1) A 790-line loop that has barely changed while the product grew — the stability users explicitly cite when fleeing Claude Code ("every release changed the system prompt… I need a bicycle that works"). (2) A ~300-token default prompt + stable skills index → high cache hit rates and model-behavior predictability. (3) The extension API became the product: 64k stars, a package marketplace where sub-agents, plan mode, MCP bridges, and sandboxes are third-party — and *competing implementations* of each exist, which a built-in would have foreclosed. (4) Forkability as a feature: orgs are told to build their own harness policy on the SDK rather than accept a vendor's. (5) The four-mode story falls out almost for free because the kernel has no UI assumptions.

**Where it strains** (all verifiable in their tracker):

- **Budget/trigger granularity.** Compaction is only checked at turn boundaries; long tool loops grow context unbounded past the window before any check fires (issue #4325 — `shouldStopAfterTurn` was added to the kernel config *for* this but never wired into the harness). The minimal loop's "policy lives outside" stance left no place for *per-command* accounting until someone threads a new hook through.
- **Seam under-parameterization.** Extensions couldn't tell *why* compaction fired (`manual|threshold|overflow`) even though RPC exposed it (issue #5217); the workaround was monkey-patching private methods. Minimal seams rot when the event payload doesn't carry provenance.
- **Representation blindness in the fold.** Image tool-results bypass resizing and have no budget; compaction's text summarizer cannot shrink image bytes, so image-heavy sessions hit the provider's 32 MB limit and enter an *infinite re-compaction loop* (issue #5369). A compaction seam that only owns text is not actually the unit of memory.
- **Everything-is-an-extension tax.** The community rebuilt budgets, scheduling, events, steering, and isolation per subagent package, mutually incompatibly, with process-spawn semantics and no type-level guarantees (a child could re-load `pi-subagent` — recursion is prevented by a hand-maintained blocklist, not by construction).
- **Mutation-based hooks compose by luck.** `tool_call` handlers mutate `input` in place with "later handlers see earlier mutations. No re-validation is performed after mutation" (`types.ts:879-885`) — ordering-dependent, silently unsafe.

**Is "zero component vocabulary" validated?** Split verdict. Pi validates it *at the kernel boundary*: `packages/agent` genuinely has no words for session, skill, memory, sandbox — those are anonymous closures in `AgentLoopConfig`. But pi's *harness* (`coding-agent/core`) is full of named, hardcoded components with override events, because shipping working defaults requires owning the machinery: compaction's trigger policy and cut-point algebra, the session tree, the trust model, queue semantics are all fixed vocabulary. Pi's compromise shape is **"default machinery + before/after events + full-replacement escape hatch"** rather than "component as swappable service". Alchemy's claim is stronger — seams as `Context.Tag`s private to a harness Layer — and pi neither proves nor disproves it; what pi does prove is that the *interface above* the harness (our `Kernel` tag) can stay tiny under years of production pressure, and that one stateful facade can serve four surfaces. Caveat: pi's kernel has effectively **one** consumer harness; the multi-harness interchangeability Alchemy claims (memory/Cloudflare/wrapped-third-party behind one tag) is beyond what pi's history can validate.

## 4. Insights for Alchemy — numbered

1. **Pi's `AgentLoopConfig` is an empirically-discovered minimal seam checklist.** Observation: nine hooks (`convertToLlm`, `transformContext`, `getApiKey`, `shouldStopAfterTurn`, `prepareNextTurn`, steering/follow-up getters, before/after tool call) sufficed for a production harness (types.ts:140-282). → Implication: audit our Phase-2 `Kernel.memory` internal seams against this list. We have equivalents for most (ContextPolicy ↔ `transformContext`; tool Layers ↔ tool hooks; halt/budget ↔ `shouldStopAfterTurn`), but **`prepareNextTurn` (per-turn model/config swap) and the steering/follow-up queues have no Alchemy counterpart** — see #12 and #13.

2. **The step machine is the genuine differentiator; pi doesn't have one.** Observation: pi's loop mutates the transcript in place, calls `Date.now()` freely, and has no replay story; a crash mid-turn loses the turn (§2.5). → Implication: alchemy-ai-design §2.4's pure `step(state, feedback) → [state', commands]` is *not* validated by pi — it's a bet pi never made. What pi *does* validate is the event vocabulary around it: their 10 kernel events map almost 1:1 onto our `KernelEvent` core set (TurnStarted/Ended, Model*, Tool*, plus streaming deltas). Adopt their `message_update`/`tool_execution_update` streaming-delta pattern as `ModelDelta`/tool-progress events; adopt their rule that **the event stream settles before the run is idle** (agent.ts:241-244) as a Trace-write barrier.

3. **Tool-pairing invariant: independently confirmed.** Observation: pi's compaction cut-point logic may never cut at a tool result (compaction.ts:298-343), and truncated (`stopReason: "length"`) tool calls are failed wholesale rather than executed (agent-loop.ts:207-216). → Implication: §2.4's "kernel owns the tool-pairing invariant" is corroborated by both of pi's mechanisms; add the *truncated-arguments-fail-the-batch* rule to our kernel obligations — it's a corruption class we hadn't named (salvage-parsed JSON that validates but is incomplete).

4. **Two-stage context pipeline (`transformContext` → `convertToLlm`).** Observation: pi separates "rewrite the harness-level transcript" from "project to provider messages", and extension `context` handlers chain on the first stage only (sdk.ts:359-363, runner.ts:927-948). → Implication: keep the same split in our step machine: the fold and ContextPolicy operate on Trace-derived `StepState.messages`; the *renderer* owns the lossy projection to a provider request. Never let a memory policy touch the provider payload directly — pi's `before_provider_request` escape hatch exists but is a last resort, not the seam.

5. **Skills mechanics are directly liftable into the renderer.** Observation: progressive disclosure = stable tiny index in the cached prefix (name + description + *path*) + body loaded through an ordinary `read` tool call at the context tail (skills.ts:335-361). No cache bust, no special kernel support — the *filesystem and the read tool are the disclosure mechanism*. → Implication: our renderer rule "tool contracts render into the schema section, not prose" (§1.6) should be extended with a skills-like pattern: a term may reference large capability documents by *name+description+locator*, with retrieval being an ordinary Tool invocation recorded in the Trace. This needs no new term kind — it validates keeping the Kernel free of a "skills" concept.

6. **Compaction seam shape: pure preparation → replace-or-defer → persisted entry with provenance.** Observation: `prepareCompaction` is pure data; `session_before_compact` hands extensions the preparation and lets them cancel or fully substitute; failures fall back to the default; the result is a durable entry carrying `firstKeptEntryId` + `tokensBefore` (+ arbitrary `details`) (compaction.ts:634-731, types.ts:578-599). → Implication: shape our fold invocation identically: the kernel computes a pure `FoldPreparation` from the Trace, the Fold agent (or `const`) returns carried state, and the persisted fold snapshot must reference the trace span it compressed (their `firstKeptEntryId` ≙ our provenance link, §8.4's "recipe" requirement). Also adopt their *iterative update* prompt pattern (previous summary + new messages → merged summary) as the default fold policy for OM-style rings.

7. **The fold must own the full content model, or it isn't the fold.** Observation: pi's compaction can only summarize text; full-res images in the kept region made sessions *permanently uncompactable* (issue #5369). → Implication: our `Checkpoint`/fold command must have authority over every content block in `StepState` — including replacing oversized tool results with previews + drill-back references (the Claude Code pattern §0.1 already endorses). Flag in §6 risks: "fold blind spots (non-text content) create unrecoverable rings."

8. **Budget accounting must be per-command, not per-boundary.** Observation: compaction/budget checks only at turn boundaries let long tool loops blow past the window (issue #4325); the fix required threading a new hook through three layers. → Implication: in our step machine, budget decrement and ceiling checks belong in the command interpreter — *every* `CallModel`/`CallTool` feedback updates budget state, and `BudgetExceeded`/`Checkpoint` can be emitted between any two commands, not only at `IterationFolded`. This is cheap for us because §2.4 already centralizes commands; pi shows what happens when it's bolted on later.

9. **Seam events need provenance-rich, forward-compatible payloads.** Observation: `session_compact` lacking a `reason` field forced monkey-patching (issue #5217). → Implication: every `KernelEvent` should carry cause (`reason`/trigger ref/parent command id) from day one — our design already mandates `{ring, term, session, workItem}` provenance (§2.3); add *cause* to the list, and treat "extension had to reach into private internals" as the failure signal a seam is under-specified.

10. **Session-tree-as-durable-unit vs Trace-as-durable-unit — a real contradiction to resolve.** Observation: pi persists a *message/entry tree* (JSONL, id/parentId, in-place branching, entry ids as durable cursors); events are ephemeral; compaction, branch summaries, model changes, extension state are all *entries in the tree* (§2.5). Alchemy-ai-design §2.3 declares "the persisted event stream is the Trace — do not invent a second representation." → Implication: these can be reconciled only if our Trace events are sufficient to *reconstruct* the message tree (messages = a fold over events), and if branching/rewind is expressible as leaf-pointer moves over the event log. Decide in Phase 2: either (a) Trace events embed full message payloads (pi's `message` entries ≙ our `ModelCompleted`/`ToolCompleted` events — workable), or (b) we quietly grow a second store and violate §2.3. Also steal: **branch summarization is a fold at branch-switch** — one more caller of the same fold seam, not a new mechanism; and the `since`-cursor read API over an append-only log is exactly right for the Ring DO's `trace` accessor (kernel.ts fixture already returns the whole array — make it cursored).

11. **Subagent packages are a requirements catalog for `ForkLoop` + Layer composition.** Observation: with no kernel support, three community packages converged on: markdown-frontmatter agent definitions (model/thinking/tool restrictions/max_turns), worktree isolation, context inheritance (fork parent conversation), background execution with concurrency caps, mid-run steering of children, resume, cron scheduling, lifecycle events, recursion blocklists (§2.4). → Implication: check each against our vocabulary — agent definition ≙ `Agent` term + Layer; tool restriction ≙ capability-by-ref; max_turns/timeout ≙ `AI.budget`; scheduling ≙ `AI.every`; lifecycle events ≙ `KernelEvent`; isolation ≙ Sandbox seam; recursion guard ≙ *typed by construction* (a loop that doesn't interpolate itself can't fork itself). Two gaps our design should decide on explicitly: **context inheritance** (pi's `inherit_context` forks the parent transcript into the child — our fork semantics currently pass a work item, not a transcript; probably correct, but document why) and **steering a running child** (see #12).

12. **Steering/follow-up queues are a missing concept in our design.** Observation: pi's most-loved interactive feature is two typed mid-run input queues with precise delivery points (after current turn's tools / after the agent would stop) and drain policies, surfaced identically in TUI, RPC, and the SDK (§2.1, §2.6); even the subagent packages re-implemented steering for children. Alchemy-ai-design has no steering vocabulary — human input mid-run exists only as `Ask` (kernel-initiated) or external events. → Implication: for interactive rings, add steering as *kernel policy over the trigger vocabulary*: a steering message is a stimulus delivered at the turn boundary of a running run (a `Feedback` variant in the step machine, e.g. `Steered{messages}` consumed at the same point pi polls). This keeps zero new term kinds (it's an `EventSource` at the charter level) but the *step machine* needs the injection point specified now, or Cloudflare's Ring DO will have nowhere to put an incoming "actually, stop refactoring" webhook mid-run.

13. **Model is per-turn state, not a Layer — tension with our design.** Observation: pi re-resolves model + thinking level before every turn (`prepareNextTurn` refresh, agent-session.ts:469-490), persists switches as tree entries, and extensions register providers at runtime. Our §2.6/§3.1 satisfy the kernel with a single `AiLanguageModel` Layer, fixed at composition time. → Implication: keep the Layer as the *registry/default*, but the step machine's `CallModel` command should carry the model choice as data resolved per-turn (from carried state or ring policy), so harnesses can support mid-run model changes and per-role models (Judge on a cheap model — pi's custom-compaction example does exactly this for the summarizer) without recomposing Layers. Flag as a §6 open question.

14. **Extension mutation semantics are the anti-pattern; Layer substitution is the answer — but verify coverage.** Observation: pi's power hooks mutate events in place with order-dependent, non-revalidated semantics (types.ts:879-885), and multi-extension composition is "chained, last writer wins". → Implication: our equivalent powers must come from *substituting implementations* (tool Layers, Fold/Check refs, ContextPolicy) rather than mutating in-flight data — we already believe this (§1.4); the check to run: for each pi mutation point (tool args patching, result rewriting, per-turn prompt override, provider payload rewrite, header injection), name the Alchemy mechanism. Tool-arg patching and per-turn system-prompt override currently have **no** clean equivalent short of wrapping a tool Layer — acceptable, but document it as intentional (validation stays intact by construction, which is precisely the bug class pi accepts).

15. **The trust boundary and the oversight ring.** Observation: pi gates *project-local* code (extensions/settings/skills) behind an explicit per-folder trust decision, loading only user-level code before that (README §Project Trust). → Implication: Alchemy's oversight story ("the org's source is review-gated code, deployment is the trust gate", §0.10) is strictly stronger for production, but `alchemy dev` running a checked-out org repo has the same shape as pi's problem: terms and Layers *are* arbitrary code. A dev-mode trust prompt (or `--approve`) for org repos not previously seen is worth a line in Phase 2's `alchemy dev` plan.

16. **Self-modification depends on the harness exposing itself.** Observation: "ask pi to modify itself" works because the default system prompt hardcodes absolute paths to pi's own docs and examples, and `/reload` completes the loop in-process (§2.7). → Implication: Autoresearch (§4.1) proposes PRs against `src/org/` — its agent needs the same affordance: the reference org's Layers should include a capability exposing *the org's own rendered terms, docs, and Trace locations* (read-only, via `AI.observe` + a docs tool), or the system ring will be studying blind. Pi's "docs are load-bearing runtime artifacts, resolved by absolute path in the prompt" is a concrete, proven mechanic.

### Citation check against alchemy-ai-design.md §0.1

The design doc's pi bullet is accurate with two nuances: (a) "four tools" is the default loadout; seven built-ins exist (`grep`/`find`/`ls` opt-in) — immaterial to the thesis; (b) "typed extensions" — the API surface is typed TypeScript, but event dispatch and mutation semantics are dynamically composed and unvalidated after mutation; pi's type safety is at the signature level, not the composition level (which is exactly the gap Alchemy's Layer algebra targets). "Sub-1k-token prompt" ✓ (default body ≈300 tokens before user context files); "skills loaded on demand to preserve prompt cache" ✓ with mechanics now documented (§2.2); "extensions hook events like `before_agent_start`" ✓ (`extensions/types.ts:685, 1188`). One correction to fold back into any future brief: **steering does not interrupt remaining tool calls** in pi core; it is delivered after the current turn's full tool batch (§2.1).
