# Eve (vercel/eve) — study for Alchemy AI

Studied at commit cloned 2026-07-08 (`.vendor/eve`, shallow clone of `github.com/vercel/eve`, package `eve@0.22.1`, 47 released versions in the CHANGELOG). All paths below are relative to `.vendor/eve/` unless prefixed with `alchemy:`.

---

## 1. Architecture overview

Eve is a **filesystem-first framework for durable backend AI agents on Vercel**. One agent = one directory; every capability is a file in a conventional location, discovered and compiled into a manifest, then served as a Nitro HTTP app whose turns run as durable workflows on the **Workflow SDK** (`"use workflow"` / `"use step"` directives; Vercel Workflow in production, a disk-backed local "world" in dev).

### The filesystem convention

```text
my-agent/
├── agent/
│   ├── agent.ts            # defineAgent: model, compaction, limits, workflow world
│   ├── instructions.md     # always-on system prompt (or instructions.ts, build-time composed)
│   ├── tools/get_weather.ts        # defineTool; NAME = FILENAME SLUG (no `name` field)
│   ├── tools/bash.ts               # same-slug file OVERRIDES a built-in; disableTool() removes it
│   ├── skills/plan_a_trip.md       # on-demand procedures, loaded via load_skill tool
│   ├── channels/slack.ts           # defineChannel / slackChannel(...): inbound + delivery + resume token
│   ├── schedules/heartbeat.ts      # defineSchedule: cron + (markdown | run handler)
│   ├── connections/linear.ts       # MCP / OpenAPI tool sources with OAuth
│   ├── hooks/audit.ts              # defineHook: subscribe to stream events
│   ├── sandbox/                    # sandbox backend + /workspace seed
│   └── subagents/researcher/       # a full recursive agent root (own agent.ts REQUIRED description)
└── evals/*.eval.ts         # defineEval, driven over the public HTTP surface
```

Identity is **path-derived everywhere**: `agent/tools/get_weather.ts` registers the model-visible tool `get_weather` (`src/discover/grammar.ts:99-107`, `TOOL_SLUG_PATTERN` at `grammar.ts:107`); `agent/schedules/billing/sweep.ts` is schedule `billing/sweep`; `agent/subagents/researcher/` is the tool `researcher`. There is no authored `name` field anywhere, and collisions (a subagent named like a tool) **fail the build** rather than picking a winner (`docs/subagents.mdx:108`).

### Package map

- `packages/eve/src/discover/` (~7 kLoC) — reads the directory grammar into source refs; diagnostics for every convention violation.
- `src/compiler/` — normalizes each slot (`normalize-tool.ts`, `normalize-schedule.ts`, …) into a versioned **manifest** (schema v33 as of the dynamic-model work, `research/dynamic-model.md:139`).
- `src/runtime/` — boots the manifest into a `RuntimeTurnAgent` (resolved model, tools, subagent registry, hooks, channels, schedules).
- `src/execution/` — the durable layer: `workflow-entry.ts` (session driver workflow), `turn-workflow.ts` (per-turn workflow), `workflow-steps.ts` (`turnStep`, the `"use step"` unit), `durable-session-store.ts` (the persisted session snapshot), `durable-session-migrations/` (versioned migrators).
- `src/harness/` — the model loop: `tool-loop.ts` (2,433 lines, AI SDK `ToolLoopAgent`), `compaction.ts`, `input-requests.ts` (HITL), `session-limit-enforcement.ts` (token budgets), `emission.ts` (stream events).
- `src/channel/` — channel adapter core, cross-channel receive, schedule dispatcher; `src/public/channels/{slack,discord,github,linear,teams,telegram,twilio,chat-sdk}/` — first-party adapters.
- `src/internal/workflow/` — thin re-export of vendored `@workflow/core` (pinned `5.0.0-beta.28`, `packages/eve/package.json:317-323`).
- `src/evals/` — the eval runner; `src/cli/` — `eve init/dev/build/start/eval` + a full TUI.
- Repo meta: `research/` holds issue-backed design docs (high-signal); `konsistent.json` + `guard-invariants` mechanically enforce structural conventions; root `SKILL.md` tells coding agents to read `node_modules/eve/docs` (docs ship in the npm package).

### One-paragraph mental model

A **session** is a durable conversation (days/weeks). Each **turn** is a child workflow (`turnWorkflow`) started by a long-lived **driver workflow** (`workflowEntry`); each **step** is one `"use step"` call (`turnStep`) = one model call plus the tool calls it made. The full session state (message history, authored state, sandbox refs) is serialized into **every step's result** — the workflow step result is the persistence boundary. Waiting (human approval, question, OAuth, subagent completion, next user message) is a durable **park**: the workflow suspends on a named **hook** (`createHook`/`resumeHook`) holding no compute, and a delivery to the session's **continuation token** wakes it. There is no loop construct above the conversation: no triggers other than channels + cron schedules, no halt conditions, no verifier role. Eve is an execution-loop/conversation framework with excellent durability plumbing, not an organization-of-agents framework.

## 2. Per-topic findings

### 2.1 The loop

Three nested drivers, all in `src/execution/` + `src/harness/`:

1. **Session driver** — `workflowEntry` (`src/execution/workflow-entry.ts:67`, `"use workflow"` at `:68`). Creates the session (`createSessionStep`), then `runDriverLoop` (`workflow-entry.ts:145-287`): dispatch a turn, and on `park` re-key the delivery hook to the current continuation token and `await` the next delivery (`workflow-entry.ts:244-251`). The driver run is **pinned to the deployment that started it**; child turn workflows run on the **latest** deployment (`startWorkflowPreferLatest`, `workflow-steps.ts:580`; rationale in `durable-session-store.ts:10-16`).
2. **Turn workflow** — `turnWorkflow` (`src/execution/turn-workflow.ts:33`, `"use workflow"` at `:34`). A `while (true)` over `turnStep` (`turn-workflow.ts:75-149`); each iteration returns `continue | done | park | dispatch-workflow-runtime-actions` (`workflow-steps.ts:80-104`). The turn owns a per-turn **inbox hook** (`` `${completionToken}:inbox` ``, `turn-workflow.ts:46`) through which subagent results, HITL proxies, and raced user deliveries arrive mid-turn.
3. **Harness step** — `turnStep` (`src/execution/workflow-steps.ts:111`, `"use step"` at `:112`) deserializes context, hydrates the durable session, runs channel `deliver` hooks, then calls `createToolLoopHarness` (`src/harness/tool-loop.ts:435`), which wraps the AI SDK's `ToolLoopAgent` with **`stopWhen: isStepCount(1)`** (`tool-loop.ts:851`) — exactly one model call (plus its tool executions) per durable step.

**Turn representation:** `ModelMessage[]` history (AI SDK types) + a `SessionStateMap` (framework/tool state) + emission state (`{ turnId, sequence, stepIndex }`). **Exit conditions:** the model producing a terminal response ends the turn (`done`); a session in conversation mode then *parks* rather than exits; **task mode** (schedules, subagents with `outputSchema`) runs to completion and *may not park for input* — `"Task mode cannot wait for follow-up input"` is a hard error (`turn-workflow.ts:28,128-134`). Structured output is implemented as a synthetic `FINAL_OUTPUT_TOOL_NAME` tool (`tool-loop.ts:793-795`).

There is nothing resembling a pure `step(state, feedback) → [state', commands]` transition: the step body is imperative async code inside the journal boundary, and "commands" exist only implicitly as the `DurableStepResult` action union.

### 2.2 Memory & compaction

- **Cross-turn continuity = the raw history, persisted whole.** `projectToDurableSession` (`src/execution/session.ts:190-249`) keeps `history`, `state`, `sandboxState`, limits, depth; it **drops** model reference, tool schemas, and compaction thresholds, which are **rebuilt from the current deployment's `turnAgent` every turn** (`hydrateDurableSession`, `session.ts:256-317`; `refreshSessionFromTurnAgent`, `session.ts:129-158`). This per-field durable/rebuilt split is what makes "existing sessions adopt agent updates after a redeploy" work (`docs/concepts/execution-model-and-durability.md:20`).
- **Compaction** (`src/harness/compaction.ts`): trigger at `thresholdPercent` (default 0.9) of the context window (`session.ts:7`); `compactMessages` (`compaction.ts:107-169`) LLM-summarizes older history (system prompt at `compaction.ts:6-13`: "Goal, Instructions, Discoveries, Accomplished, Next steps"), keeps a token-budgeted recent window (default 10 messages), strips tool calls/results from the kept tail so no orphaned `tool_use` survives (`keepNonToolResultMessages`, `compaction.ts:179-199`), and shrinks the window iteratively if still over threshold. A compaction checkpoint is written to durable history (`compaction.completed` event). Compaction **re-injects framework tool state** — the active todo list, reset read-before-write tracking (`docs/concepts/default-harness.md:21`) — i.e. compaction is tool-state-aware, not just message-level.
- **Authored memory** — `defineState(name, initial)` (`docs/guides/state.md`): typed named slots in the durable session's `SessionStateMap`, `get()`/`update()` from tools/hooks, **never shared with subagents** (`state.md:66-68`). Anything cross-session is explicitly out of scope ("belongs in a connection or your own database", `state.md:72`); `docs/patterns/multi-tenant-memory.md` is a DIY pattern, not a framework feature.
- **No observational memory, no fold role, no cross-conversation memory.** "Keeps context across conversations" in their marketing means *long-lived sessions* (a Telegram chat = one session forever, with `/new` reset proposed in `research/channel-session-reset.md`), not memory across sessions.

### 2.3 Tool system

- `defineTool({ description, inputSchema (zod/Standard Schema), outputSchema?, execute(input, ctx), approval?, toModelOutput? })` (`src/public/definitions/tool.ts:111-127`). `ToolContext` (`tool.ts:82`) = `SessionContext` (`ctx.session.{id, auth.{initiator,current}, turn, parent}`) + `abortSignal`, `callId`, `getToken`/`requireAuth` (inline OAuth for the tool's own credentials), plus `ctx.getSandbox()`.
- **Registration by convention:** default export of `agent/tools/<slug>.ts`; slug charset enforced at discovery (`grammar.ts:107`). Built-ins (`bash`, `read_file`, `write_file`, `glob`, `grep`, `web_fetch`, `web_search`, `todo`, `ask_question`, `agent`, `load_skill`, `connection_search`) are overridden by authoring the same slug (spread `eve/tools/defaults` to keep schema + durable state key) or removed with a `disableTool()` sentinel; a sentinel filename matching no built-in **fails the build** (`docs/concepts/default-harness.md:72-80`).
- **Execution:** tools run inside the current `"use step"`; the AI SDK executes them within the model-call stream. Shell/file tools proxy into the per-session sandbox (backends: Vercel Sandbox, Docker, microsandbox, just-bash — `src/public/sandbox/backends/`). Errors: invalid tool-call input is passed back to the model as an error result so it can retry (CHANGELOG 0.22.0: "pass error messages when tool call input is invalid back to model instead of throwing"); tool exceptions become error tool results; classified transient model failures retry with backoff (`runModelCallWithRetries`, `tool-loop.ts:2385`), and a whole recovery pipeline handles empty responses and unsupported provider tools (`tool-loop.ts:1449-1704`).
- **Dynamic tools:** `defineDynamic({ events })` resolvers can add/remove tools per session/turn/step based on `ctx.session.auth` and channel metadata; dynamic tools override same-named authored tools (`tool-loop.ts:788-791`).

### 2.4 Subagents — definition and management

Two kinds (`docs/subagents.mdx`):

1. **Built-in `agent` tool** — a *copy of the current agent*: inherits tools, connections, instructions, auth, **shares the parent's sandbox filesystem**, but fresh history and fresh state. Parallel `agent` calls in one response fan out concurrently.
2. **Declared subagents** — `agent/subagents/<id>/` is a **full recursive agent root** (discovery reuses the same grammar, `src/discover/discover-subagent.ts`). `description` on its `agent.ts` is *required* — it is the delegation contract the parent's model reads (`subagents.mdx:38`). **Inheritance is zero**: absent slots fall back to framework defaults, never to the root's version — sharing a skill means copying the markdown (`subagents.mdx:56-70`).

**Lowering:** every subagent (copy, declared, or remote) becomes a model-visible tool with the frozen schema `{ message: string, outputSchema?: object }` (`src/runtime/subagents/registry.ts:27-43`). The child never sees the parent's history; `outputSchema` puts the child in task mode returning structured output as the tool result.

**Management/lifecycle:** each delegated child is its **own durable session and workflow** with its own stream; the parent parks on its turn inbox and the child resumes it with a `subagent-result` (`workflow-entry.ts:54-58`; `turn-workflow.ts:159-236`). Child continuation tokens are minted deterministically so retries address the same child hook (`mintSubagentContinuationToken`, `session.ts:179-181`). HITL and OAuth requests from descendants are **proxied up** to the root channel (`subagent-hitl-proxy`, `turn-workflow.ts:207-216`; CHANGELOG 0.22.1). Guardrails: `limits.maxSubagentDepth` (default 3; at the cap subagent tools stop being *advertised*, and a forced call is blocked at execution, `subagents.mdx:91-97`); children inherit a **share of the parent's remaining token quota** split across the dispatch batch, and completed child usage counts against the parent (`execution/dispatch-runtime-actions-step.ts:95`; CHANGELOG 0.21.0) — a delegation tree cannot outspend its root budget; on every inherited axis the tighter of configured and inherited wins (`execution/create-session-step.ts:76-77`).

**Dynamic workflows** (`docs/guides/dynamic-workflows.md`): the opt-in `Workflow` tool lets the *model author JavaScript* that orchestrates subagents (fan-out/map-reduce) as **one durable step**, executed in a QuickJS sandbox with an allowlist of exactly `tools.<subagentName>` bridges — no fs, net, env, or imports. Root-only, non-recursive, capped by `limits.maxSubagents` (default 100) with over-budget calls resolving to `WORKFLOW_SUBAGENT_LIMIT_REACHED` error results.

### 2.5 Sessions / state / durability (the core topic)

**The mechanism is Vercel's Workflow SDK, not event sourcing.** Functions marked `"use workflow"` are compiled (vendored `@workflow/core@5.0.0-beta.28`, re-exported via `src/internal/workflow/runtime.ts`) into resumable workflows; `"use step"` bodies are journaled: **completed steps never re-run — their recorded results are replayed; a step interrupted mid-execution re-runs** (`docs/concepts/execution-model-and-durability.md:41-45`). Non-idempotent side effects are the author's problem: "make charges idempotent, **or gate them with approval**" — an approval gate doubles as a replay barrier (`docs/tools/human-in-the-loop.md:57`).

- **Persistence shape:** every session-mutating step returns `serializedContext` (the runtime context, `serializeContext(ctx)`) plus `DurableSessionState` whose `snapshot` embeds the **entire `DurableSession`** — full message history included (`src/execution/durable-session-store.ts:52-104`; "Workflow step results are the atomic persistence boundary for session program memory", `durable-session-store.ts:4-6`). Encoding is `devalue` so `URL`/`Buffer`/`Date`/`Map`/`Set` round-trip (`durable-session-store.ts:128-130`). Attachment bytes are kept out of the snapshot by staging files to the sandbox and replacing `FilePart.data` with `eve-sandbox:` ref URLs, hydrated only for the wire call (`tool-loop.ts:598-604,667-671`).
- **Parking:** durable waits are Workflow **hooks**. The driver owns a session delivery hook keyed by the continuation token (re-keyed at every park, `workflow-entry.ts:211-213`); each turn owns an inbox hook (`turn-workflow.ts:46`); a per-session `:auth` hook serves OAuth callbacks (`workflow-entry.ts:156-158`). While parked the workflow holds no compute — waits of days are free.
- **Resume handles:** two deliberately separate capabilities — `continuationToken` (resume; channel-owned; exactly one active session may own a token, competing claims fail; `docs/concepts/execution-model-and-durability.md:55-61`) vs `sessionId`/`runId` (stream-and-inspect; runtime-owned) (`docs/concepts/sessions-runs-and-streaming.md:8-15`). Sessions can re-key (`session.setContinuationToken`) with claim-before-release linearization (`docs/channels/custom.mdx:216-247`).
- **Crash recovery:** resume from the last completed step; the stream is durable and replayable from any `startIndex` ("Every event is recorded before a step completes", `sessions-runs-and-streaming.md:93`).
- **Versioning discipline:** `DurableSessionState`/`Snapshot` carry a `version` with migrators (`durable-session-store.ts:10-16,32`; `execution/durable-session-migrations/`); turn workflow inputs are migrated on entry (`migrateTurnWorkflowInput`, `turn-workflow.ts:36`); the manifest schema is versioned (v33). Long-lived durable state forced version envelopes everywhere.
- **Pluggable store ("world"):** `@workflow/world-local` (disk, `.workflow-data`) in dev/self-host, `world-vercel` on Vercel, `experimental.workflow.world: "@workflow/world-postgres"` for self-hosted Postgres (`execution-model-and-durability.md:24-39`). The world backs "workflow state, queues, hooks, and streams"; protocol-version compatibility is checked at init. Self-hosting must also proxy `/.well-known/workflow/` or "sessions start but runs silently stall forever" (`docs/guides/deployment.md:135-137`).
- **Not FIFO:** eve explicitly disclaims a durable per-session message queue. Deliveries during an active turn drain best-effort at workflow boundaries and may be folded together; the documented contract is "wait for `session.waiting` before the next send", with channel-side queues recommended for bursts (`execution-model-and-durability.md:53-61`).
- **The war story:** turn/session **cancellation has failed to land five times** (#118/#127/#128/#135, #230, #347), every blocker in the trigger/cross-process layers — raced hooks in the driver, upstream Workflow bugs (hook dispose-before-reclaim determinism, duplicate step execution under one correlation id), delegate adoption races. The current plan ships a 5-layer stack bottom-up, layer 0 being pure `AbortSignal` propagation with no production trigger (`research/turn-cancellation-harness-abort.md:9-41`). `research/channel-session-reset.md` specifies the full capability-token cancel semantics (per-turn `cancelToken` bound to `(sessionId, turnId)`, session cancel with continuation-release as the reset linearization point).

### 2.6 Async vs sync

- **Channels** are the async entry points: normalize platform input → `send(message, { auth, continuationToken, state })` → session starts or resumes (`docs/channels/custom.mdx:16-56`). Route handlers (HTTP verbs + `WS()`), an `events` map reacting to the session's stream (delivery back to the platform), `receive(channel, …)` for cross-channel hand-off (incident webhook → Slack thread, `custom.mdx:120-156`).
- **Schedules** are cron entry points (§2.10). Markdown schedules run in **task mode** (no parking, output discarded); handler (`run`) schedules deliver into a channel and *can* park (`docs/schedules.mdx:32-87`; `src/channel/schedule.ts:65-117`).
- **Streaming:** one NDJSON event stream per session with a fixed vocabulary of ~25 event types (`sessions-runs-and-streaming.md:37-64`), incremental deltas carrying cumulative text, replayable via `startIndex`. Subagents stream on their own child session; the parent stream carries only `subagent.called`/`subagent.completed` + proxied interactive events.
- **Dispatch order is normative:** channel handler → metadata projection → hooks → dynamic resolvers, per event (`sessions-runs-and-streaming.md:115-124`).

### 2.7 Pluggability

Swappable: **workflow world** (local/Vercel/Postgres/custom), **sandbox backend** (Vercel/Docker/microsandbox/just-bash/custom `SandboxBackend`), **model** (any AI SDK gateway string or provider instance; `mockModel` for tests), **channels** (authored `defineChannel`), **tools/instructions/skills/model per-session** (`defineDynamic`), **host framework** (standalone Nitro, or mounted in Next/Nuxt/SvelteKit via `withEve`), **eval reporters** (Braintrust, JUnit). Convention-locked: the `agent/` directory grammar itself, path-derived identity, the harness loop (no way to replace the turn driver or the step decomposition), the event vocabulary, session/turn/step nesting, the compaction algorithm (tunable threshold only — "There is no per-tool hook", `default-harness.md:21`). Notably, eve built **konsistent** (structural-convention linter, `konsistent.json`) plus `guard:invariants` scripts to keep its own conventions mechanically enforced — convention systems need external enforcement machinery.

### 2.8 Human-in-the-loop

One pause-and-resume protocol for **approvals** and **questions** (`docs/tools/human-in-the-loop.md`):

- `approval:` on a tool: `never()` / `once()` / `always()` helpers or a **policy function** receiving `{ session, toolName, toolInput, approvedTools, callId }`, returning AI SDK approval statuses — `"user-approval"`, `"not-applicable"`, or auto `{ type: "approved" | "denied", reason }` (`human-in-the-loop.md:41-55`). Policies read `session.auth.current` (this turn's caller) vs `session.auth.initiator` (session creator) — schedule-dispatched turns carry the app principal, so the same tool can auto-run on cron and prompt for humans (`human-in-the-loop.md:59-84`).
- `ask_question` is a built-in tool **with no `execute`** — the model calls it with `{ prompt, options?, allowFreeform? }` and the harness parks (`human-in-the-loop.md:88-94`).
- Persistence: the pending batch is stored in session state (`setPendingInputBatch`, `harness/input-requests.ts`), an `input.requested` event carries the requests, the turn parks at `session.waiting` durably, and the answer arrives as structured `inputResponses` keyed by `requestId` *or* plain text matched against option ids/labels/indexes (`human-in-the-loop.md:96-107`). **Unrelated follow-up text does not deny a pending approval** — it is held and replayed after the approval resolves (`:107`).
- Channels render requests natively (Slack buttons/selects via Chat SDK cards); descendants' requests are proxied to the root channel. The same park machinery serves **OAuth** (`authorization.required`/`.completed`) and **budget exhaustion**: hitting the session token limit in an interactive session parks on a deterministic continuation prompt — "Continue" grants a fresh budget window, "Stop" ends gracefully; task mode instead fails with structured `SESSION_TOKEN_LIMIT_REACHED` (`src/harness/session-limit-enforcement.ts:37,104-128,202`; CHANGELOG 0.21.0).

### 2.9 Provider abstraction

Confirmed: the **AI SDK end-to-end** — `ToolLoopAgent`, `generateText`, `streamText` types (`tool-loop.ts:7-19`); models are gateway id strings (`"anthropic/claude-sonnet-5"`) resolved through Vercel AI Gateway by default, or direct provider instances with your own keys (`docs/guides/deployment.md:140-142`). Streaming deltas are re-emitted as eve protocol events. Prompt-cache handling is provider-aware (Anthropic cache breakpoints applied to system + last tool, `tool-loop.ts:630-631,709-711,847`). **Dynamic model selection** (in review, `research/dynamic-model.md`): `model: defineDynamic({ fallback, events })` with scope precedence step > turn > session > fallback; resolver failure degrades to fallback, never fails the turn; explicitly documented that **every model switch invalidates the provider prompt cache** (`dynamic-model.md:67-73`). Compaction may use a distinct cheaper model (`compaction.model`).

### 2.10 Integration

- **Verified event ingestion:** Slack verifies its signing secret (`src/public/channels/slack/verify.ts:10-49`); GitHub either verifies its App webhook secret or, via **Vercel Connect**, delegates App management, installation tokens, and webhook verification to the platform — inbound events are then verified by their *Vercel OIDC signature* (`docs/channels/github.mdx:9-43`). Telegram/Twilio/Teams/Discord/Linear adapters ship similarly. Crucially, **eve does not provision the external webhook**: you run `vercel connect attach --trigger-path /eve/v1/github` or configure the Slack/GitHub app manually.
- **Schedules → infrastructure:** the one place convention *does* provision infra — every `defineSchedule` compiles to a **Vercel Cron Job** entry in `.vercel/output/config.json` (UTC), or a Nitro scheduled task when self-hosted (`docs/schedules.mdx:101-109`). Dev never fires cron; a dev-only one-shot dispatch route (`POST /eve/v1/dev/schedules/:id`) triggers a schedule out of band and returns the started session ids (`schedules.mdx:90-99`).
- **Deployment:** `vercel deploy` (framework auto-detected, Agent Runs dashboard) or `eve build && eve start` anywhere Node runs, with an explicit checklist of the Vercel-only conveniences you lose (`deployment.md:120-152`). Multi-tenancy is patterns-level (per-tenant auth/approvals/memory docs under `docs/patterns/`), anchored on `session.auth` attributes.
- **Clients:** a typed TS client (`eve/client`) over the stable HTTP contract, `useEveAgent()` for React/Vue/Svelte, and a full dev TUI that can also target deployed URLs (`eve dev https://<app>`).
- **Evals:** `defineEval` files drive the agent **over the same public HTTP surface users hit**, with `t.send/t.respond`, deterministic assertion builders, and an LLM-judge surface that never uses the agent-under-test as judge; `mockModel` makes fixtures fully deterministic including scripted tool calls; gate-vs-soft severity rides on each assertion (`docs/evals/overview.mdx`).

## 3. Judgments

### What they got right

1. **Park/resume actually ships.** Durable human-scale waits (days) with zero held compute, one protocol shared by approvals, questions, OAuth, budget-continuation, and subagent completion. This is the single most battle-tested part of the codebase (the test suites around hooks and input-requests are enormous).
2. **Snapshot-in-step-result.** Making the workflow step result the atomic persistence boundary (no separate session DB write to race with the journal) is an elegant consistency move, and the `devalue` + `eve-sandbox:` ref discipline keeps snapshots serializable and lean.
3. **The durable/rebuilt field split.** Persist history + authored state; rebuild prompt/tools/model from the current deployment every turn. Sessions adopt redeploys without migration ceremonies. Pinned driver + latest-deployment child turns is a real answer to "redeploy mid-run".
4. **Auth provenance on every turn.** `session.auth.initiator` vs `.current`, with the schedule app principal, makes per-caller approval policies one `if` statement.
5. **Budget inheritance down the delegation tree** — children get a split of the parent's *remaining* quota and their spend counts against it; depth caps degrade by de-advertising tools before hard-blocking.
6. **Engineering culture as signal:** issue-backed `research/` plans with explicit layering and failure post-mortems; versioned envelopes + migrators for every durable shape; konsistent/guard-invariants; docs shipped inside the package with a root `SKILL.md` pointing coding agents at them; evals drive the public surface.
7. **Approval as replay barrier** — an honest, cheap answer to non-idempotent side effects under at-least-once step execution.

### What's weak or young

1. **Cancellation does not exist** after five attempts; the blockers are upstream Workflow SDK determinism bugs (hook reclaim, duplicate step execution). Everything that touches the hook layer across processes is fragile; the 47-release changelog is dense with races in exactly this zone (delivery/adoption races, fast-resume hook disposal, `turn-control` token per turn as a workaround — `workflow-entry.ts:161-165`).
2. **Message delivery is explicitly not a queue** — best-effort drain at workflow boundaries, coalescing, "keep your own per-session queue in the channel layer" (`execution-model-and-durability.md:53-61`). For an agent framework whose entry points are bursty chat surfaces, punting ordering to every channel author is a real gap.
3. **Durability is fat.** The entire message history serializes into every step result. Fine for chat sessions; hostile to long-running or high-iteration work. There is no fold — compaction is a context-window emergency measure (naive LLM summarization with a 280-char content truncation ruler, `compaction.ts:16,375-382`), not a memory design.
4. **No loop above the conversation.** No triggers besides channels/cron, no halt conditions, no verifier/judge role at runtime (evals are offline), no perpetual work, no concurrency policy. "Durable agent" means durable *session*.
5. **Coarse step granularity:** one step = one model call *plus all its tool executions*; a crash mid-tool re-runs the model call and every sibling tool. Their own docs push idempotency onto tool authors.
6. **The filesystem grammar has a big price tag:** ~7 kLoC of discovery + a normalization compiler + a versioned manifest + konsistent + build-time collision checks, all to recover invariants a type system would give statically. Subagent isolation-by-copying (duplicate the skill markdown per child) trades composition away for legibility.
7. **Task mode cannot wait** — schedules in markdown form can never ask a human, a structural limitation flagged in their own docs, and the conversation/task mode split leaks into a dozen code paths (`resolveEffectiveOutputSchema`, park gating, empty-delivery sentinels).

## 4. Insights for Alchemy

Eve is the closest philosophical competitor: durable agents + channels + schedules + HITL, but *filesystem-convention* where we chose *typed terms*, and *conversation-first* where we chose *loop-first*. Numbered observations, each mapped to our design (`alchemy:alchemy-ai-design.md`, cited by §).

1. **Step results as the persistence boundary → validate and sharpen our fold-as-checkpoint (§0.8, §3.2).** Eve independently converged on "the durable engine's step result *is* the session memory" (`durable-session-store.ts:4-6`) — the same claim as our "persisted step result is the folded state" Workflow row in §3.2's durability ladder. The difference: eve persists the *raw history* every step (fat), we persist the *fold* (lean). Their pain (attachment-ref indirection, snapshot bloat concerns) is evidence our fold is the better unit — but their design proves the mechanism works and shows the required hygiene: a `version` field on every durable envelope from day 1, and migrators as first-class code (`durable-session-migrations/`). **Action: add an explicit versioned-envelope + migration requirement to §2.3's Trace schema and §3.2's `Durability` seam.**

2. **The durable/rebuilt split answers "what exactly does the fold persist" (§2.4, §3).** Eve's `projectToDurableSession`/`hydrateDurableSession` pair persists history + authored state and *rebuilds prompt, tool schemas, model, and thresholds from the current deployment every turn* — which is exactly how a redeployed org should behave under our "oversight loop is the source file" doctrine (§0.10): edit a template, redeploy, and live rings adopt the new `promptHash` at the next iteration without state surgery. **Action: specify in §2.4 that `StepState` excludes anything derivable from the term (rendered prompt, tool contracts) and that the kernel re-renders from the current term at each iteration, stamping the new `promptHash` on Trace events.** Their pinned-driver/latest-child-workflow trick is the deployment-skew answer for our ring-DO (pinned reducer) vs Fix-Workflow (latest) split.

3. **Ask is bigger than AskHuman — unify all durable waits under one command (§2.4).** Eve routes approvals, model-initiated questions, OAuth authorization, budget-exhaustion continuation, *and* subagent completion through one park protocol with one event pair (`input.requested` → structured `inputResponses` by `requestId`). Our step machine has `Ask { tool: "human-class" }` and separately `ForkLoop`; §3.2 has `waitForEvent` for humans. **Action: generalize `Ask` to `Ask { requestId, payload }` = "park durably until a correlated answer arrives", with human approval, human question, OAuth, and budget-continuation as payload kinds.** Also copy two behavioral details: (a) unrelated input during a pending approval is *held and replayed*, never treated as denial; (b) a plain-text answer matching an option id/label resolves structurally. And adopt their budget move: `BudgetExceeded` in an interactive ring can *offer a continuation Ask* ("grant a fresh window?") instead of only failing — the autonomy dial applied to budget exhaustion.

4. **Two-token capability split for handles (§2.1 Kernel handles).** Eve separates the *resume* capability (`continuationToken`, single-owner, claim-linearized, channel-owned) from the *observe* capability (`sessionId` stream, replayable by index) and mints *cancel* capabilities per turn bound to `(session, turn)` (`research/channel-session-reset.md:94-123`). Our Phase-2 `AgentHandle`/`LoopHandle` should mirror this: `dispatch`/`send` rights, `events` subscription rights, and `interrupt` rights are different capabilities with different owners. The single-owner claim semantics (a competing claimer *fails*, never silently steals) is the correct default for ring identity reuse.

5. **Cancellation is where durable-agent frameworks go to die — our fiber model is a structural advantage, but only below the durability line (§2.5, §6).** Five failed attempts, all in trigger/cross-process layers; the in-process abort propagation "converged on the same shape three times" trivially. Effect gives us the propagation layer (interruption through fibers/Scope) for free — that is real leverage over eve. But their failures are precisely in what Effect does *not* cover: cancelling a **parked** durable wait, racing a cancel against a hook resume, descendant adoption races across processes. **Action: add to §6 risks: "durable cancel of parked work" as a named hard problem; design the ring-DO reducer so cancel is a *stimulus* processed through the same event path as any other (no second control plane), and pin eve's invariant in our conformance suite: a cancellation is never classified as a retryable/recoverable error.** Also steal `isTurnCancellation`-by-`name`-not-`instanceof` for anything crossing a serialization boundary.

6. **Eve disclaims ordered delivery; our `AI.each` must not (§1.2.2, §3.2).** Their continuation hook is "a resume handle, not a message-queue address", with best-effort coalescing and documented races. Our `each` term promises "a durable work queue with acknowledgement semantics" — that is a stronger contract than the closest competitor ships, so it needs real design: the §3.2 `WorkQueue` seam (Queues + DO dedupe/ack ledger) should specify ordering, coalescing, and burst behavior explicitly, because eve's experience says workflow-boundary drains make naive FIFO impossible. Their channel-layer-queue recommendation is what our Queue-fronted ring DO does natively.

7. **Filesystem vs typed terms — what each buys, explicitly.** What files buy eve: (a) *coding-agent legibility* — the project is its own prompt; `SKILL.md` + docs-in-package mean any agent can author an eve agent by reading disk; (b) zero-ceremony authoring (a markdown file is a schedule); (c) path-derived identity with no import graph. What it costs: ~7 kLoC discovery + compiler + manifest + konsistent to enforce what `tsc` enforces for us; name collisions surfaced only at build; capability audits impossible (nothing stops a subagent from getting `bash` — you must *disable* per-directory, our absence-of-ref denies by construction, §1.7); isolation-by-copying for shared skills. **Actions:** (a) our terms should ship an eve-grade *agent-authoring story*: docs in the package plus a `SKILL.md`-equivalent so coding agents can write Alchemy orgs — their `node_modules/eve/docs` convention is directly copyable; (b) consider a `defineX`-file *frontend* later, but the type-level audit (§1.4 consequence 4) is the moat — eve has no counterpart to "`Approve` appears nowhere in the composed layer closure"; (c) their build-fails-on-collision posture matches our `AI.lint` philosophy — keep lints loud.

8. **Subagent-as-tool with `{ message, outputSchema? }` — freeze the delegation ABI (§2.4).** Eve lowers *every* delegation (self-copy, declared, remote) to one frozen tool schema, and the required `description` on the child is the parent's routing contract. Our "agent wrapped as a tool is delegation" (§2.4) should likewise standardize the wire shape: the parent packs everything into `message` (no history bleed), `outputSchema` selects task mode. Their two-kind split maps cleanly to us: built-in copy ≈ `ForkLoop` of the same term with shared sandbox Layer; declared subagent ≈ a distinct Agent term with its own Layers (our version is strictly more compositional — they copy files, we `Layer.provide`). Also adopt: **at the depth cap, stop advertising delegation tools before hard-blocking** — degrade the model's option surface, don't just error.

9. **Budget propagation down the tree is settled design — copy it (§1.2.2 Budget, §2.5).** Children inherit a split of the parent's *remaining* quota; child spend debits the parent; tighter-of-configured-and-inherited wins on every axis. This is precisely our "authority flows down: budgets propagate down via fiber/Scope" (§0.6) made concrete, including the arithmetic. **Action: specify in §2.4 kernel obligations that `ForkLoop` carries a budget lease computed as a share of the parent's remainder, reconciled on child completion.**

10. **QuickJS dynamic workflows preview our deferred "dynamic charters" (§5 Deferred).** Model-authored JS orchestrating subagents as one durable step, allowlist-bridged (`tools.<name>` only), root-only, non-recursive, per-program call budget with typed over-budget error results, full observability parity with direct delegation. When we revisit agent-authored orchestration, this is the safety envelope to copy — and it stays consistent with our stance that fan-out is Effect concurrency inside a body, not a term: eve's Workflow tool is exactly "a pipeline inside one iteration", not a loop.

11. **Channels vs `EventSource`: our provisioning claim survives contact — but channels are bidirectional and ours aren't (§1.2.3).** Mechanism-by-mechanism: eve's channel = inbound normalization + signature verification + *resume-token ownership* + **delivery back to the surface**; the webhook itself is configured out-of-band (manually or via Vercel Connect). Our `EventSource` = typed payload + channel tag whose Layer *provisions the webhook at deploy* — a genuine differentiator eve does not have (their only convention-provisions-infra case is schedules → Vercel Cron, which validates the move at small scale). But our EventSource is inbound-only; replies in our model are ordinary Tools (`Reply`). That is cleaner separation, with one gap eve covers structurally: **rendering kernel-initiated interactions (Ask payloads) onto the surface that triggered the work**. Their channels render approvals as Slack buttons automatically because the channel sees the event stream. **Action: our human-tool Layers (`AskHumanDiscord`, §3.2) should be spec'd as *channel-paired*: the Layer that implements `Ask` for a ring should render onto, and accept answers from, the same surface whose EventSource triggered the run — otherwise every org hand-rolls the correlation.**

12. **Schedules validate `AI.every` and hand us the dev-mode answer (§1.2.2, §3.2).** Cron-as-file compiling to platform cron mirrors `AI.every` → DO alarm/Workflow cron. Two details worth copying verbatim: (a) **dev never fires cron; a dev-only one-shot dispatch route fires a trigger by name and returns the run handles** — `alchemy dev` needs exactly this for `AI.every` (and for `AI.on` event injection); (b) their conditional-delivery instruction (a polling schedule may finish without posting; the harness tells the model how to succeed silently, `schedules.mdx:80`) is a prompt-level pattern our renderer should provide for polling `every` rings. Their task-mode-cannot-park limitation is one we *don't* have: whether a scheduled ring can ask a human is, for us, just whether `AskHuman` is in its `Req` and which Layer implements it — typed, not modal. Worth stating in §1.7 as a comparison point.

13. **Compaction must be tool-state-aware — a concrete obligation for the ContextPolicy seam (§2.4, §3.2).** Eve's compaction re-injects the durable todo list and resets read-before-write tracking after summarizing, and strips tool calls from the kept tail specifically to preserve the pairing invariant. Our §2.4 tool-pairing invariant covers trimming; add the converse: **the fold/ContextPolicy seam needs a way for framework/tool state to survive or re-assert itself across compaction** (in our model: fold-time state is carried state, so this is naturally covered *if* tool-visible state lives in the fold, not the message list — make that explicit).

14. **Auth provenance belongs in the Trace (§2.3).** `session.auth.initiator` vs `.current`, with a distinguished app principal for schedule-fired turns, is what makes eve's per-caller approval policies trivial and their multi-tenant patterns possible. Our `KernelEvent` provenance is `{ ring, term, session, workItem }`; **add `auth: { initiator, current }`** so Check agents, budget policies, and `Approve` Layers can discriminate human-initiated vs ring-initiated work without a side channel — and so the autonomy dial can be *caller-sensitive*, not just ring-sensitive.

15. **Model strings + degrade-to-fallback, and the cache warning (§2.6).** Eve's dynamic-model design (scope precedence, serializable selections at session/turn scope, live instances only at step scope, resolver failure degrades to fallback and never fails the turn) is a good template if we ever make `AiLanguageModel` selection dynamic per ring/iteration. Their documented footgun — every model switch invalidates the provider prompt cache — reinforces our renderer's cache-stability rules (§1.6): our per-ring model choice is a Layer, i.e. session-stable by construction, which is the right default.

16. **Evals: drive the public surface, never judge with the doer (§2.6 conformance suite, §8.4 check).** Eve's eval runner boots the real server and drives the same HTTP contract users hit; `mockModel` lives *in the agent definition* so fixtures are deterministic locally and deployed; the LLM judge is explicitly a different model from the agent under test; gate-vs-soft severity is per-assertion. For our conformance suite and the Autoresearch ring's "every proposal ships an eval" rule (§4.1), adopt: conformance tests drive `LoopService.dispatch`/`Kernel.events` (the public contract), a `MockModel` Layer as the standard deterministic fixture, and judge-model-≠-doer-model as a lint on `AI.check`.

### Contradiction check against alchemy-ai-design.md

- **§2.4 "pure step machine, deterministic for replay":** eve does *not* replay steps deterministically — it persists step results and re-runs only interrupted steps (recorded-result replay, same family as CF Workflows). No contradiction with our Workflow-granularity row in §3.2, but note eve's step is *coarser* than our planned Command granularity (model call + all its tool calls in one step; crash mid-tool re-runs the model call). Our per-Command journal (`doFiber` row) is strictly stronger; eve's coarseness is evidence the fine-grained journal is worth the write amplification only at the turn tier — which is exactly how §3.2 tiers it. Consistent.
- **§0.8 "the fold is the unit of both memory and durability":** eve splits them (durability = raw history snapshot; memory = threshold compaction) and pays for it in snapshot size and in compaction being an emergency mechanism. Eve is the counterexample that *not* unifying them still ships — but their `eve-sandbox:` ref laundering and history-bloat management are costs our unified fold avoids. No design change; cite eve as the contrast case.
- **§1.2.3 "declaring the subscription provisions the wire":** eve does not do this (webhooks configured out-of-band; only schedules provision). Our claim of genuine novelty here stands, now verified against the closest competitor.
- **§2.5 loop runtime:** eve has no counterpart to triggers/halt/check/fold/budget-as-`Err` — its only "halt" is the model finishing a turn and its only budget exit is the token-limit continuation prompt. The loop taxonomy above the execution loop (§8) remains unoccupied territory in eve.
