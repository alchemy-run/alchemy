An alchemy app on Vercel is any number of **Functions** and
**Websites** — each one owning its own Vercel project — plus the
resources they talk to: Edge Configs, Blob stores, queue topics,
cron schedules — all declared in the same TypeScript program and
wired together by typed bindings. Deploy the whole thing with
`bun alchemy deploy`; alchemy figures out what changed.

New here? [Set up your token](/vercel/setup), then start the
[tutorial](/vercel/tutorial/part-1).

## No git, no build pipeline

alchemy does not connect a git repository and never triggers
Vercel's build pipeline. It bundles your code locally, uploads the
files, and creates a **prebuilt, immutable deployment** directly —
the same deploy path works from your laptop and from CI, with no
repo linking, no framework detection, and no `vercel.json`. Rollback
is a pure traffic operation: `Vercel.rollbackProduction` re-points
production at an earlier deployment without rebuilding anything —
see [Deployments & rollback](/vercel/compute/deployments-and-rollback).

## The whole surface in one file

One file declares the config, the storage, the queue, and the
Function that binds them all:

```typescript
// src/api.ts
import * as Vercel from "alchemy/Vercel";
import * as Effect from "effect/Effect";
import * as Schema from "effect/Schema";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export const Flags = Vercel.EdgeConfig("Flags", {
  items: { greeting: "hello" },
});

export const Uploads = Vercel.BlobStore("Uploads", { access: "public" });

export class Jobs extends Vercel.Topic<Jobs>()("jobs", {
  schema: Schema.Struct({ jobId: Schema.String }),
  region: "iad1",
}) {}

export default class Api extends Vercel.Function<Api>()(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const config = yield* Vercel.ReadEdgeConfig(Flags);
    const blob = yield* Vercel.ReadWriteBlob(Uploads);
    const jobs = yield* Vercel.SendMessage(Jobs);

    yield* Vercel.subscribe(Jobs, (job) =>
      Effect.log(`processing ${job.jobId}`),
    );

    yield* Vercel.cron("0 3 * * *", Effect.log("nightly cleanup"));

    return {
      fetch: Effect.gen(function* () {
        const greeting = yield* config.get("greeting").pipe(Effect.orDie);
        yield* blob
          .put("greetings/latest.txt", String(greeting), {
            contentType: "text/plain",
          })
          .pipe(Effect.orDie);
        yield* jobs.send({ jobId: "refresh-cache" }).pipe(Effect.orDie);
        return yield* HttpServerResponse.json({ greeting });
      }),
    };
  }).pipe(
    Effect.provide([
      Vercel.ReadEdgeConfigHttp,
      Vercel.ReadWriteBlobHttp,
      Vercel.SendMessageHttp,
      Vercel.QueueEventSourceLive,
      Vercel.CronEventSourceLive,
    ]),
  ),
) {}
```

Each `yield*` in the init is a **binding**: it provisions the
resource, connects it to the Function's project, and hands back a
typed runtime client — `config.get`, `blob.put`, `jobs.send` — with
tokens injected as env vars, no dashboard clicking.
`Vercel.subscribe` registers a push-delivered queue consumer and
`Vercel.cron` a schedule, both on the same deployment.

The stack file deploys it:

```typescript
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Vercel from "alchemy/Vercel";
import * as Effect from "effect/Effect";
import Api from "./src/api.ts";

export default Alchemy.Stack(
  "MyApp",
  { providers: Vercel.providers(), state: Vercel.state() },
  Effect.gen(function* () {
    const api = yield* Api;
    return { url: api.url }; // → https://<project>.vercel.app
  }),
);
```

```sh
bun alchemy deploy
```
