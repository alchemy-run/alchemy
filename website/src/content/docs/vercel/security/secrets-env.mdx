---
title: Secrets & env
description: Sync env vars onto a Vercel project from your Function's env prop — plain values become encrypted rows, Redacted secrets become write-only sensitive rows with fingerprint drift detection, and env changes redeploy exactly once.
---

On Vercel, environment variables live on the **project**, but a
deployment only sees the env that existed when it was created —
deployments are immutable. Alchemy hashes the fully-resolved desired
env and creates a new deployment exactly when that hash changes; an
identical deploy keeps the existing deployment untouched.

Vercel distinguishes three variable types: `plain` (readable),
`encrypted` (the default — decryptable via the API on most accounts),
and `sensitive` (**write-only** — the value can never be read back).
Alchemy routes values by shape: a plain value becomes an `encrypted`
row, a `Redacted` value becomes a `sensitive` row.

## Declare env on a Function

```typescript
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Vercel from "alchemy/Vercel";
import * as Effect from "effect/Effect";

const App = Alchemy.Stack(
  "MyApp",
  { providers: Vercel.providers(), state: Vercel.state() },
  Effect.gen(function* () {
    const api = yield* Vercel.Function("Api", {
      main: "./src/api.ts",
      env: { GREETING: "hello" },
    });
    return { url: api.url };
  }),
);
```

The `env` prop is synced onto the Function's project as env rows —
`GREETING` lands as an `encrypted` variable and arrives in
`process.env.GREETING` as a string at runtime. Values may be strings,
JSON-serializable values, `Redacted` secrets, `Config` reads, or
`Output`s of other resources' attributes:

```typescript
import * as Config from "effect/Config";

const hooks = yield* Vercel.Function("Hooks", {
  main: "./src/hooks.ts",
  env: {
    API_URL: api.url, // another resource's attribute Output
    SELF_URL: Vercel.Function.URL, // this Function's own read-back URL
    SIGNING_KEY: Config.redacted("SIGNING_KEY"), // deploy-machine secret
  },
});
```

`Config.redacted("SIGNING_KEY")` reads the **deploy machine's**
environment (your shell or CI) at deploy time; because it resolves to
a `Redacted`, it is stored as a `sensitive` row.

## Sensitive is write-only

A `Redacted` value forces `type: "sensitive"` regardless of any other
setting. Sensitive rows still appear in Vercel's env listing, but
their `value` comes back **empty** even with decryption requested —
Vercel never returns the plaintext. Your Function is unaffected: at
runtime the variable is a plain string in `process.env` like any
other.

```typescript
import * as Redacted from "effect/Redacted";

const fn = yield* Vercel.Function("SecretFn", {
  main: "./src/api.ts",
  env: {
    GREETING: "hi", // → encrypted
    SECRET_VALUE: Redacted.make("s3cret"), // → sensitive, write-only
  },
});
```

:::caution[Sensitive vars cannot target development]
Vercel rejects a sensitive row targeting the `development`
environment outright (live-verified: `BAD_REQUEST "You cannot set a
Sensitive Environment Variable's target to development"`). Alchemy
drops `development` from every sensitive row's targets automatically,
so sensitive rows default to `["production", "preview"]`.
:::

## Drift detection by fingerprint

A write-only value poses a diffing problem: how does the next deploy
know whether the secret changed if the cloud never returns it? Alchemy
persists an `alchemy:sha256:<hash>` **fingerprint** of every value it
writes and diffs the fingerprint instead of the value:

- Redeploying with the identical secret is a true no-op — no env
  write, no redeploy churn.
- Rotating the secret changes the fingerprint, rewrites the row, and
  forces exactly one new deployment (env only takes effect on new
  deployments).

The fingerprint also ships as the sensitive row's `comment`, so the
dashboard shows a human-visible hint of *which* value is deployed
without revealing it.

:::note[Encrypted rows can be unobservable too]
Teams on Vercel's v2 env encryption return ciphertext for `encrypted`
rows even when decryption is requested. The same persisted
fingerprint is the drift baseline there — diffing works identically
whether the cloud value is readable or not.
:::

## Async Functions: the InferEnv cast

Plain async handlers are the escape hatch from the Effect class DX —
no init phase, no bridge, just a web-standard `fetch` export reading
`process.env` directly. Type it with `Vercel.InferEnv` so the
handler knows exactly which keys exist:

```typescript
// alchemy.run.ts
export const Hooks = Vercel.Function("Hooks", {
  main: "./src/hooks.ts",
  env: {
    API_URL: api.url,
    SIGNING_KEY: Config.redacted("SIGNING_KEY"),
  },
});
export type HooksEnv = Vercel.InferEnv<typeof Hooks>;
```

```typescript
// src/hooks.ts
import type { HooksEnv } from "../alchemy.run.ts";

const env = process.env as HooksEnv;

export default {
  async fetch(request: Request): Promise<Response> {
    return fetch(`${env.API_URL}/verify`, {
      headers: { authorization: env.SIGNING_KEY },
    });
  },
};
```

`InferEnv` maps the `env` prop's keys to `string` — every value
arrives in `process.env` as a string on Vercel, secrets included.

## Config in Effect Functions

In an Effect-native Function, any `Config` yielded in the **init
phase** is read from the deploy environment, bound onto the project
env (`Redacted` ⇒ `sensitive`), and re-resolved from that binding at
runtime — the same spine as every alchemy platform:

```typescript
// src/api.ts
import * as Vercel from "alchemy/Vercel";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";
import * as Redacted from "effect/Redacted";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export default class Api extends Vercel.Function<Api>()(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    // init phase — read at deploy time, bound as a sensitive env var
    const apiKey = yield* Config.redacted("API_KEY");

    return {
      fetch: Effect.gen(function* () {
        return yield* HttpServerResponse.text(
          `key loaded: ${Redacted.value(apiKey).length} chars`,
        );
      }),
    };
  }),
) {}
```

Resolve `Config` in the outer `Effect.gen`, not inside `fetch` —
`fetch` never runs at deploy time, so a `Config` yielded only there
is never discovered or bound. A `Config` re-read inside a handler
decodes the raw source value, so combinators like
`Config.withDefault` re-run at runtime as expected.

## Manage a var on a project you don't deploy

`Vercel.ProjectEnv` manages a single env row on any project — a
feature flag on a `Vercel.Project` no compute resource owns, or a
variable on a pre-existing project:

```typescript
const legacy = yield* Vercel.Project("Legacy", {});

yield* Vercel.ProjectEnv("LegacyFlag", {
  project: legacy.projectId,
  key: "FLAG",
  value: "on",
  target: ["production"],
});
```

`target` scopes the row to deployment environments (`production`,
`preview`, `development` — all three by default), and `gitBranch`
narrows a preview-targeted row to one branch:

```typescript
yield* Vercel.ProjectEnv("StagingUrl", {
  project: legacy.projectId,
  key: "API_URL",
  value: "https://staging.api.example.com",
  target: ["preview"],
  gitBranch: "staging",
});
```

A `Redacted` value works here too — the row is stored `sensitive`
with the same fingerprint drift detection.

:::caution
Env vars on a project deployed by `Vercel.Function` are managed by
the Function's `env` prop. Don't also manage the same key with
`ProjectEnv` — the two owners will fight over the row.
:::
