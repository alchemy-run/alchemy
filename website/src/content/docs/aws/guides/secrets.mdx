Alchemy gives you two ways to handle secrets on AWS. The
cloud-agnostic path — `Config.redacted("MY_KEY")` in the function's
init phase — reads a value from your `.env` and delivers it to the
deployed function as an environment variable (see
[Secrets and env vars](/guides/secrets)). This page covers the
second path: **AWS Secrets Manager**, where the secret is a real
cloud resource with its own ARN, KMS encryption, and IAM-scoped
access that your Lambda reads at runtime.

## Create a secret

`AWS.SecretsManager.Secret` owns the secret's metadata and current
value. Pass the value as a `Redacted` string so it never appears in
logs or state:

```typescript
import * as AWS from "alchemy/AWS";
import * as Redacted from "effect/Redacted";

const dbSecret = yield* AWS.SecretsManager.Secret("DbSecret", {
  description: "Database credentials",
  secretString: Redacted.make(
    JSON.stringify({ username: "app", password: "super-secret" }),
  ),
  tags: { Environment: "dev" },
});
```

If you omit `name`, Alchemy generates a deterministic physical name
from the app, stage, and logical id. Changing `name` later
**replaces** the secret (new ARN); everything else — value,
description, KMS key, tags — updates in place, and each new value
gets a fresh `versionId`.

## Generate the value instead

For credentials nothing outside AWS ever needs to see, let Secrets
Manager generate the password at deploy time and merge it into a
JSON template:

```typescript
const dbSecret = yield* AWS.SecretsManager.Secret("DbSecret", {
  generateSecretString: {
    secretStringTemplate: JSON.stringify({ username: "app" }),
    generateStringKey: "password",
    PasswordLength: 32,
  },
});
```

The stored value becomes `{"username":"app","password":"<random>"}`
— the password comes from Secrets Manager's `GetRandomPassword` API
and never lives in your repo or `.env`. `generateStringKey` defaults
to `"password"` and the template defaults to `{}`.

## Read it from a Lambda

`GetSecretValue` is a binding: yielding it in the function's init
phase grants the IAM permissions at deploy time and returns a typed
client for runtime. Provide the `GetSecretValueHttp` layer on the
function's Effect:

```typescript
// src/api.ts
import * as AWS from "alchemy/AWS";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";
import * as Redacted from "effect/Redacted";

export default class Api extends AWS.Lambda.Function<Api>()(
  "Api",
  { main: import.meta.url, url: true },
  Effect.gen(function* () {
    const dbSecret = yield* AWS.SecretsManager.Secret("DbSecret", {
      generateSecretString: {
        secretStringTemplate: JSON.stringify({ username: "app" }),
        generateStringKey: "password",
        PasswordLength: 32,
      },
    });

    const getDbSecret = yield* AWS.SecretsManager.GetSecretValue(dbSecret);

    return {
      fetch: Effect.gen(function* () {
        const value = yield* getDbSecret();
        const creds = Redacted.isRedacted(value.SecretString)
          ? (JSON.parse(Redacted.value(value.SecretString)) as {
              username: string;
            })
          : undefined;
        return yield* HttpServerResponse.json({ user: creds?.username });
      }).pipe(Effect.orDie),
    };
  }).pipe(Effect.provide(AWS.SecretsManager.GetSecretValueHttp)),
) {}
```

At deploy time the binding adds `secretsmanager:GetSecretValue` and
`secretsmanager:DescribeSecret` to the function's execution role,
scoped to this secret's ARN only. At runtime `getDbSecret()` calls
the API directly — the value is fetched fresh on each call, not
baked into the environment. The response's `SecretString` is decoded
as a `Redacted` value, so it can't leak through logging; unwrap with
`Redacted.value` only at the point of use.

## Secrets Manager or env vars?

Reach for the env-based path
([Secrets and env vars](/guides/secrets)) when the value already
lives in your `.env` — a third-party API key your own code reads —
and it's the same story on every cloud.

Reach for Secrets Manager when the secret is an AWS-native concern:

- **Shared consumers** — other resources reference the secret by
  ARN (Aurora clusters and RDS proxies consume password-backed JSON
  secrets in exactly the shape `generateSecretString` produces).
- **Generated values** — the plaintext never enters your repo,
  `.env`, or deploy logs.
- **Least-privilege reads** — access is an IAM grant on one ARN,
  not an environment variable visible to the whole function config.
- **Rotation without redeploy** — put a new value (each gets a
  `versionId`) and running functions pick it up on their next
  `getSecretValue` call.

One destroy-time note: Alchemy deletes secrets with
`ForceDeleteWithoutRecovery`, so `stack.destroy()` removes the
secret immediately rather than scheduling AWS's usual recovery
window.
