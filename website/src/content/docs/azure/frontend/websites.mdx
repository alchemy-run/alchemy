Alchemy deploys frontends to Azure with a family of `Azure.Website`
resources. Each one builds your project through
`@alchemy.run/frontend-frameworks/<framework>`, uploads the static assets to
Blob Storage, and serves the site through Azure Front Door. A
server-rendered build also runs on an Azure Functions app (Flex
Consumption), which scales to zero. Your framework's own config file
(`vite.config.ts`, `astro.config.*`, `nuxt.config.ts`, ...) loads natively.
No Docker image, App Service plan, or container is involved.

| Build output | Origin behind Front Door | URL |
| --- | --- | --- |
| Static assets (Vite, Foldkit SPA or `output: "static"`, Astro `output: "static"`, `StaticSite`) | Storage account static website (`$web` container) | `https://{endpoint}.z01.azurefd.net` |
| Server (SSR frameworks, Foldkit `output: "server"`) | `/*` → Flex Consumption Function; the client directory's top-level paths → Blob Storage | `https://{endpoint}.z01.azurefd.net` |

```typescript
import * as Azure from "@alchemy.run/azure";

const site = yield* Azure.Website.Vite("Web", { location: "eastus" });
```

## Assets and caching

Alchemy uploads only new and changed files (by MD5) and deletes removed
files. It uploads with the deployer's Microsoft Entra token and grants the
deployer **Storage Blob Data Contributor** on the storage account; no
account keys or SAS tokens are used. Each file carries a `Cache-Control`
header:

- HTML: `max-age=0,no-cache,no-store,must-revalidate`, so a deploy is
  visible at once.
- Every other file: `max-age=31536000,public,immutable`.

Front Door caches what the headers allow. After an upload, Alchemy purges
the paths of replaced and deleted files from the endpoint (`/*` when more
than 100 paths changed). The purge runs on the edge after the deploy
returns.

## Front Door

Front Door Standard is on by default. It answers a single-page app's deep
link (for example `/counter/42`) with the app shell and a `200` status. A
new endpoint takes 10-20 minutes to serve everywhere, and each profile
bills a monthly base fee.

Share one profile across sites:

```typescript
const profile = yield* Azure.Cdn.Profile("Edge");
const web = yield* Azure.Website.Vite("Web", { frontDoor: { profile } });
```

Serve an assets-only build straight from the storage endpoint with
`frontDoor: false`. Deep links then answer `404` with the app shell. A
server build needs Front Door.

```typescript
const preview = yield* Azure.Website.Vite("Preview", { frontDoor: false });
```

## Shared infrastructure

Omit `storageAccount` and Alchemy creates a `Standard_LRS` account under
the site's namespace. The site goes into the stack's resource group unless
you pass `resourceGroup`. A server build's Function is set with
`location` (a region that offers Flex Consumption), `instanceMemoryMB`, and
`maximumInstanceCount`.

## Resources

- [`Vite`](/azure/frontend/vite) — client-only Vite apps.
- `StaticSite` — any build command's output directory (Hugo, Zola,
  Eleventy).
- `Foldkit`, `Astro`, `Nextjs`, `Vinext`, `Nuxt`, `ReactRouter`,
  `SolidStart`, `SvelteKit`, `TanStackStart`, `Waku`, `Octane`, `Vocs` —
  framework sites.
- `StaticWebsite` — the building block that publishes a directory to a
  storage account and purges Front Door.

During `alchemy dev` every site runs its framework's own dev server and no
Azure resources are created. `Alchemy.remote()` opts back into the live
deployment.
