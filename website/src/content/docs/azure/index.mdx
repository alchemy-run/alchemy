The Azure provider deploys resources through Azure Resource Manager (ARM)
with a Microsoft Entra service principal. Every resource is tagged with
the stack, stage, and logical ID that own it, so `alchemy unsafe nuke`
can find and clean up what Alchemy created.

New here? [Set up credentials](/azure/setup) first.

:::caution
The Azure provider is in preview. It covers about 1,190 resource types
across roughly 165 services — each service has a reference page under
**Resources** in the sidebar, e.g. [Azure.Storage](/providers/azure/storage).
:::

## How it works

- **Authentication** — a Microsoft Entra service principal stored in an
  Alchemy profile (`alchemy profile edit --add Azure`). Alchemy trades the
  client secret for a short-lived ARM token. In CI, set
  `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, and
  `AZURE_SUBSCRIPTION_ID` instead. See [Setup](/azure/setup).
- **Resource providers** — new subscriptions only register a few
  `Microsoft.*` namespaces. Alchemy registers the namespace a resource
  needs on first deploy, so you never see `MissingRegistration`.
- **Ownership** — every resource is branded with the stack, stage, and
  logical ID that own it (see [Ownership markers](#ownership-markers)).

## Providers

```typescript
import * as Azure from "@alchemy.run/azure";
import * as Layer from "effect/Layer";

providers: Azure.providers().pipe(
  // Optional: the default location for resources that don't set one.
  Layer.provideMerge(Azure.location("westeurope")),
),
```

Without an `Azure.location(...)` layer, resources default to the
profile's location, then `eastus`. A resource's recorded location always
wins, so changing the default never moves existing resources.

## Resource groups

Every Azure resource lives in a resource group. Alchemy creates one per
stack and stage, named `<stack>-<stage>` (for example `shop-prod`), and
puts every resource that doesn't set `resourceGroup` into it. Destroy
deletes the group after its resources, and only when it is empty and
carries the stack's ownership tags.

To deploy into a group someone else created, name it on the providers.
Alchemy references the group and never creates or deletes it:

```typescript
providers: Azure.providers().pipe(
  Layer.provideMerge(Azure.resourceGroup("rg-shop-prod")),
),
```

To set the group's name, location, or tags, declare it and provide it to
the resources that go into it:

```typescript
const group = yield* Azure.Resources.ResourceGroup("app", {
  name: "shop-prod",
  location: "westeurope",
});

yield* Effect.gen(function* () {
  yield* Azure.Storage.StorageAccount("files");
}).pipe(Effect.provide(Azure.resourceGroup(group)));
```

Set `resourceGroup` on one resource to put it in another group, such as
a shared networking group:

```typescript
const vnet = yield* Azure.Network.VirtualNetwork("vnet", {
  resourceGroup: "rg-network",
  addressPrefixes: ["10.0.0.0/16"],
});
```

:::caution
A resource's ID contains its resource group. Moving a resource to another
group, or switching the stack from the default group to a named one,
replaces the resource.
:::

Creating the default group needs permission to write resource groups in
the subscription. Without it, deploy fails with
`Azure.ResourceGroupCreateForbidden`; use `Azure.resourceGroup("<name>")`
instead.

## Resources

A storage account holds Blob, Queue, Table, and File storage. Accounts
are HTTPS-only, require TLS 1.2, and block anonymous blob access unless
you opt in:

```typescript
const account = yield* Azure.Storage.StorageAccount("files");

const uploads = yield* Azure.Storage.BlobContainer("uploads", {
  storageAccount: account.storageAccountName,
});
```

Grant access with a managed identity and a role assignment scoped to
the one resource it needs:

```typescript
const identity = yield* Azure.ManagedIdentity.UserAssignedIdentity("api");

yield* Azure.Authorization.RoleAssignment("api-reads-files", {
  scope: account.storageAccountId,
  roleDefinitionId: Azure.Authorization.BuiltInRole.StorageBlobDataReader,
  principalId: identity.principalId,
  principalType: "ServicePrincipal",
});
```

## Ownership markers

Resources that support tags carry `alchemy::stack`, `alchemy::stage`, and
`alchemy::id`. Two resource types have no tags:

- **Blob containers** store the same markers in container metadata as
  `alchemy_stack`, `alchemy_stage`, and `alchemy_id`.
- **Role assignments** end their description with
  `[alchemy <stack>/<stage>/<id>]`.

## Out of scope

The Azure SDK covers every Azure Resource Manager resource type. About
650 of them are deliberately not Alchemy resources:

| Reason | Examples |
| --- | --- |
| Retired or closed to new customers | Dev Box (no new customers since Nov 1, 2025), Cosmos DB for PostgreSQL (new clusters can't be created), Spring Apps, Customer Insights, Time Series Insights, Data Lake Analytics, Data Lake Storage Gen1, Front Door (classic), classic CDN, HPC Cache, Disk Pools, Lab Services, Logic Apps ISE, MySQL Single Server, Orbital, Scheduler, Dev Spaces, ML Studio (classic), Maps Creator, Playwright Testing |
| Data-plane or end-user data | Machine Learning job runs, Sentinel incidents, API Management portal content, migration and import/export jobs, runbook jobs, remediation tasks, what-if results |
| Actions, not desired state | Private endpoint connection approvals (managed from `Network.PrivateEndpoint`), maintenance triggers, troubleshooting runs, upgrade jobs |
| Billing and subscription objects | Billing accounts and profiles, reservations and savings plans, Marketplace terms, quota requests, support tickets, subscription creation, hardware orders (Data Box, Edge) |
| Closed or allow-listed previews | Delegated Network, Microsoft Purview cross-tenant objects, tenant-level service groups, M365 compliance private links |
| Read-only mirrors and system-managed objects | AWS Connector inventory (112 types), vCenter/Arc discovery projections, platform-created hardware inventory, subscription and tenant singletons without delete |
| Duplicates | Property setters folded into their parent (e.g. VPN connection shared keys, Web App settings), legacy aliases of current types |

## Requires external setup

These are implemented, but their live tests only run with
`AZURE_TEST_PAID=1` because they need something beyond a subscription:

- **Microsoft Discovery** — an allow-listed preview.
- **Confluent** — a signed-in user token, not a service principal.
- **Azure Stack HCI** — physical hardware.
- **VMware Solution** — host quota granted through a support ticket.
- **Power BI and Fabric capacities** — a tenant sign-up.

## Testing

Live tests run against a real subscription:

```sh
pnpm test test/Azure --profile <profile>
```

Lifecycles that cost more than about $1 or take longer than ~10 minutes
only run with `AZURE_TEST_EXPENSIVE=1`. Lifecycles that need a paid
plan, a partner SaaS, hardware, or a gated preview only run with
`AZURE_TEST_PAID=1`; without it, a probe test asserts the exact typed
error Azure returns.
