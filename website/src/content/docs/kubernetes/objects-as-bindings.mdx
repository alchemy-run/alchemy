Every Kubernetes object Alchemy deploys — a raw
[`AWS.EKS.Manifest`](/providers/aws/eks/manifest), or the
Deployment/Service/ServiceAccount and Job/CronJob objects the
[`AWS.EKS.Deployment`](/providers/aws/eks/deployment) and
[`AWS.EKS.Job`](/providers/aws/eks/job) platforms synthesize —
goes through one internal EKS Kubernetes client. This page explains
that machinery: how requests are authenticated, how server-side
apply converges an object, how unknown kinds (CRDs) are resolved,
and the order objects are applied and pruned in.

It assumes you already have a cluster and working AWS credentials —
see [setup](/kubernetes/setup) and the
[Kubernetes overview](/kubernetes) if not.

## Manifests are resources

`Manifest` is an ordinary Alchemy resource with its own provider and
state entry — it deploys, diffs, refreshes, and deletes like the
rest of your Stack:

```typescript
const config = yield* AWS.EKS.Manifest("AppConfig", {
  cluster,
  manifest: Kubernetes.configMap({
    metadata: { name: "app-config", namespace: "default" },
    data: { EXAMPLE: "true" },
  }),
});
```

Object identity — cluster, `apiVersion`/`kind`, name, namespace — is
immutable: changing any of it is a **replacement** (the new object
is applied, then the old one is deleted). Everything else converges
in place. `read` refreshes the resource from the live API server (a
404 means the object is gone and it will be re-created), and delete
is idempotent — an already-deleted object, or a cluster that was
destroyed first, is not an error.

## Server-side apply

Each object is converged with a single Kubernetes
[server-side apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/)
request — a `PATCH` with `Content-Type: application/apply-patch+yaml`
against the object's path with `?fieldManager=alchemy&force=true`.
Server-side apply is a true upsert: create-if-missing and
converge-if-present in one call. The API server diffs the submitted
definition against the live object and takes ownership of the fields
you declare (`force=true` reclaims fields another manager grabbed),
so re-running a deploy with no changes is a no-op and drift in
managed fields is corrected. Note that apply returns as soon as the
API server accepts the patch — it does not wait for a Deployment to
roll out or a Job to complete.

Authentication rides your AWS credentials: each request carries a
`k8s-aws-v1.<presigned STS GetCallerIdentity>` bearer token, and the
cluster is trusted via its `certificateAuthorityData` attribute. No
kubeconfig is involved — see [setup](/kubernetes/setup).

## Any kind, via discovery

Well-known kinds (Namespace, ServiceAccount, ConfigMap, Secret,
Service, Deployment, StatefulSet, DaemonSet, Job, CronJob, Pod)
resolve their API paths from a built-in table. Anything else —
including arbitrary CRDs — is resolved through the Kubernetes
[API discovery](https://kubernetes.io/docs/reference/using-api/api-concepts/#discovery-api)
endpoint (`/apis/{group}/{version}` or `/api/v1`), so custom
resources need no registration:

```typescript
const widget = yield* AWS.EKS.Manifest("Widget", {
  cluster,
  manifest: {
    apiVersion: "acme.io/v1",
    kind: "Widget",
    metadata: { name: "w", namespace: "default" },
    spec: { size: 3 },
  },
});
```

The only requirement is `metadata.name` — server-side apply needs a
concrete name to address the object.

## Ordering and pruning

The `Deployment` and `Job` platforms own a *set* of objects, applied
in dependency-safe rank order — Namespaces before the
ServiceAccounts and ConfigMaps inside them, Services before the
Deployments and Jobs that back them — with each rank chunk applied
in parallel (unknown kinds land last). Pruning is the mirror image:
each reconcile compares the previously applied refs (stored on the
resource's `kubernetesObjects` attribute) against the desired set,
and objects that dropped out are deleted first, in reverse rank
order — a 404 response is tolerated, so an already-gone object is
not an error.

On `stack destroy`, each resource deletes its own objects before its
AWS-side pieces (the Pod Identity association, ECR repository, and
IAM role for the platforms). If the cluster itself was destroyed
first, its objects went with it — deletion detects the missing
cluster and skips cleanly.

## What the platforms synthesize

`Deployment` applies a `ServiceAccount`, an `apps/v1 Deployment`,
and a `v1 Service`; `Job` applies a `ServiceAccount` and a
`batch/v1 Job` (or `CronJob` when `schedule` is set). The refs are
visible on the `kubernetesObjects` attribute, and the K8s-native
names come back as attributes (`deploymentName`, `serviceName`,
`serviceAccountName`, `jobName`). To adjust the synthesized Pod
template, pass `podTemplate` — a typed deep-partial merge — before
reaching for a raw `Manifest`:

```typescript
const tuned = yield* AWS.EKS.Deployment("Api", {
  cluster,
  main: import.meta.url,
  port: 3000,
  podTemplate: Kubernetes.podTemplate({
    spec: { nodeSelector: { pool: "arm" } },
  }),
});
```

For any shape the platforms don't model — StatefulSets, DaemonSets,
bare Pods, CRDs — declare an `AWS.EKS.Manifest` alongside them.
