`alchemy/Kubernetes` is **types and builders only**: 1:1 TypeScript
mirrors of the Kubernetes API object model plus zero-runtime typed
constructors. There are no resource providers, no apply engine, and
no cluster abstraction in it — deploying to Kubernetes is per-cloud.
On AWS that means three `AWS.EKS` resources:
[`Deployment`](/providers/aws/eks/deployment) for replicated
servers, [`Job`](/providers/aws/eks/job) for run-to-completion work,
and [`Manifest`](/providers/aws/eks/manifest) for any raw object.

New here? [Set up](/kubernetes/setup) — your AWS credentials are the
credentials.

## Typed builders

Each builder fills in `apiVersion`/`kind` and hands back the
fully-typed object — nothing more:

```typescript
import * as Kubernetes from "alchemy/Kubernetes";

const manifest = Kubernetes.statefulSet({
  metadata: { name: "cache", namespace: "apps" },
  spec: {
    serviceName: "cache",
    replicas: 3,
    selector: { matchLabels: { app: "cache" } },
    template: {
      metadata: { labels: { app: "cache" } },
      spec: { containers: [{ name: "redis", image: "redis:7" }] },
    },
  },
});
```

Builders exist for `pod`, `deployment`, `statefulSet`, `daemonSet`,
`job`, `cronJob`, `service`, `configMap`, `secret`, `namespace`,
`serviceAccount`, and `podTemplate`. Use them wherever a
Kubernetes-typed value is accepted — `AWS.EKS.Manifest.manifest`,
`AWS.EKS.Deployment.podTemplate` — or skip them and write the
object literal; the types are the same either way.

## Apply any manifest

`AWS.EKS.Manifest` applies the object onto a cluster via
server-side apply. Any kind works — the typed kinds above, or an
untyped custom resource (CRDs are resolved through the Kubernetes
API discovery endpoint, so they need no registration):

```typescript
const sts = yield* AWS.EKS.Manifest("Cache", {
  cluster,
  manifest, // the typed StatefulSet from above — or any raw object
});

const widget = yield* AWS.EKS.Manifest("Widget", {
  cluster,
  manifest: {
    apiVersion: "acme.io/v1",
    kind: "Widget",
    metadata: { name: "w", namespace: "default" },
    spec: { size: 3 },
  },
});
```

How apply, ordering, and pruning work is covered in
[How objects deploy](/kubernetes/objects-as-bindings).

## Platforms for the common shapes

You rarely need raw manifests for your own code.
`AWS.EKS.Deployment` and `AWS.EKS.Job` synthesize the Kubernetes
objects (Deployment + Service + ServiceAccount; Job or CronJob) plus
the container image, ECR repository, and pod-identity IAM wiring in
one resource — with the same authoring triad as Lambda and
Cloudflare Workers (external image, inline Effect, tagged Effect):

```typescript
const api = yield* AWS.EKS.Deployment("Api", {
  cluster,
  image: "registry.k8s.io/echoserver:1.10",
  replicas: 2,
  port: 8080,
  serviceType: "LoadBalancer",
});
```

The [EKS guide](/aws/compute/eks) covers both platforms, bindings,
and pod identity. When a platform's synthesized pod template needs
tuning, the escape hatch is typed too:

```typescript
const tuned = yield* AWS.EKS.Deployment("Api", {
  cluster,
  main: import.meta.url,
  port: 3000,
  podTemplate: Kubernetes.podTemplate({
    spec: {
      tolerations: [{ key: "gpu", operator: "Exists" }],
      nodeSelector: { pool: "arm" },
    },
  }),
});
```

`podTemplate` is a deep-partial merge into the synthesized template:
objects merge recursively, arrays and primitives replace.
