`alchemy/Kubernetes` manages workloads on **any Kubernetes cluster**:
a local [kind](https://kind.sigs.k8s.io) cluster, k3s on a VM, an
on-prem fleet, GKE, AKS, or an [EKS](/aws/compute/eks) cluster
declared in the same Stack. You describe servers, jobs, and raw
Kubernetes objects as Resources in TypeScript; Alchemy applies them
to the cluster with server-side apply, tracks them in state, and
deletes them on destroy.

```typescript
import * as Alchemy from "alchemy";
import * as Kubernetes from "alchemy/Kubernetes";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "MyApp",
  {
    providers: Kubernetes.providers(),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const cluster = Kubernetes.KubeConfig({ context: "kind-alchemy" });

    const web = yield* Kubernetes.Deployment("Web", {
      cluster,
      name: "web",
      image: "ghcr.io/stefanprodan/podinfo:6.15.0",
      port: 9898,
      replicas: 2,
      serviceType: "ClusterIP",
    });

    return { service: web.serviceName };
  }),
);
```

## Clusters

Every resource takes a `cluster` prop that says where it runs and
how to authenticate. The cluster itself is not a resource here —
it's plain connection data.

- **[Connecting to clusters](/kubernetes/clusters/connecting)** —
  `Kubernetes.KubeConfig(...)` for anything `kubectl` can reach
  (including `exec` credential plugins such as `aws eks get-token`,
  `kubelogin`, and `gke-gcloud-auth-plugin`), or a raw
  `Kubernetes.Connection` with a bearer token, client certificate,
  or exec plugin.
- **[Managed clusters](/kubernetes/clusters/managed)** — pass an
  `AWS.EKS.Cluster` resource directly. Its platform adapter adds
  a container registry (ECR), workload identity (EKS Pod Identity),
  and internet-facing load balancers.

## Workloads

- **[Deployments](/kubernetes/workloads/deployments)** — a
  replicated server: a Kubernetes `Deployment` + `Service` +
  `ServiceAccount`, with a `url` when the Service is a
  `LoadBalancer`.
- **[Jobs & CronJobs](/kubernetes/workloads/jobs)** —
  run-to-completion work. Set `schedule` and the Job becomes a
  `CronJob`.
- **[Container images](/kubernetes/workloads/images)** — every
  workload runs exactly one of `image` (a registry reference),
  `context` (your Dockerfile), or `main` (a bundled Effect program).
- **[Configuration & bindings](/kubernetes/workloads/bindings)** —
  environment variables, values from other resources, and cloud
  credentials through workload identity.

## Objects

- **[Manifests](/kubernetes/objects/manifests)** — apply any single
  Kubernetes object: Namespaces, ConfigMaps, StatefulSets,
  Ingresses, and custom resources.
- **[Helm charts](/kubernetes/objects/helm-charts)** — render a chart
  with the local `helm` CLI and apply its objects as one resource.

## Concepts

- **[How objects are managed](/kubernetes/concepts/object-lifecycle)**
  — server-side apply, apply and delete ordering, pruning, drift,
  and what triggers a replacement.
- **[Cluster adapters](/kubernetes/concepts/cluster-adapters)** — the
  extension point that gives each cluster platform its
  authentication, registry, and identity behavior.

## What each cluster supports

The workload resources are the same everywhere. What changes is
what the cluster's platform adapter provides:

| Capability                                         | Any cluster (kubeconfig, token, client cert, exec) | `AWS.EKS.Cluster`                 |
| -------------------------------------------------- | -------------------------------------------------- | --------------------------------- |
| `Deployment` / `Job` with `image`                  | Pulled by the cluster as written                   | Mirrored into a per-workload ECR repository |
| `Deployment` / `Job` with `main` or `context`      | —                                                  | Built and pushed to ECR           |
| Environment variables and `env` bindings           | Yes                                                | Yes                               |
| Cloud credential bindings (IAM)                    | —                                                  | EKS Pod Identity role             |
| `LoadBalancer` Service `url`                       | Whatever the cluster's load balancer controller assigns | Internet-facing NLB on Auto Mode |
| `Manifest` and `HelmChart`                         | Yes                                                | Yes                               |

## What are you building?

| You're building                         | Reach for                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------------- |
| An HTTP service from a public image     | [`Deployment`](/kubernetes/workloads/deployments) with `image`                              |
| An Effect HTTP server with AWS bindings | [`Deployment`](/kubernetes/workloads/deployments) with `main` on [EKS](/kubernetes/clusters/managed) |
| A database migration or seed step       | [`Job`](/kubernetes/workloads/jobs)                                                         |
| A nightly batch task                    | [`Job`](/kubernetes/workloads/jobs#run-on-a-schedule) with `schedule`                       |
| A Namespace, ConfigMap, or Secret       | [`Manifest`](/kubernetes/objects/manifests)                                                 |
| A StatefulSet, Ingress, or custom resource | [`Manifest`](/kubernetes/objects/manifests)                                              |
| A cluster add-on (metrics, ingress, operators) | [`HelmChart`](/kubernetes/objects/helm-charts)                                       |
| Your own Dockerfile on a non-EKS cluster | [`Docker.Image`](/kubernetes/workloads/images#build-your-own-image-for-any-cluster) + `Deployment` |
