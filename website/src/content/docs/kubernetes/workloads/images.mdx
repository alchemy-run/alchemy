Every [Deployment](/kubernetes/workloads/deployments) and
[Job](/kubernetes/workloads/jobs) runs exactly one image source, set
flat on its props:

| Source              | Props                                   | What runs                                                  |
| ------------------- | --------------------------------------- | ---------------------------------------------------------- |
| Registry reference  | `image`                                 | A pre-built image such as `nginx:1.27`                     |
| Your Dockerfile     | `context`, optional `dockerfile`        | An image built from your Dockerfile                        |
| Effect program      | `main`, optional `handler` and `build`  | Your Effect program, bundled into a generated image        |

If several are present, `main` wins, then `image`, then
`context`/`dockerfile`. (With `main`, `image` means something else —
see [Bundle an Effect program](#bundle-an-effect-program).)

## What each cluster supports

Building an image means pushing it somewhere the cluster can pull
from, and that registry comes from the cluster's
[adapter](/kubernetes/concepts/cluster-adapters):

| Source    | EKS (`AWS.EKS.Cluster`)                          | Any other cluster                    |
| --------- | ------------------------------------------------ | ------------------------------------ |
| `image`   | Mirrored into a per-workload ECR repository      | Used as written; the nodes pull it   |
| `context` | Built locally and pushed to ECR                  | Not supported                        |
| `main`    | Bundled, built, and pushed to ECR                | Not supported                        |

On a cluster without a registry, a `main` or `context` workload
fails with *this cluster has no managed image registry*. Build and
push the image yourself and pass the result as `image` — see
[Build your own image for any cluster](#build-your-own-image-for-any-cluster).

## Run a registry image

```typescript
const cache = yield* Kubernetes.Deployment("Cache", {
  cluster,
  image: "valkey/valkey:8.1",
  port: 6379,
  serviceType: "ClusterIP",
});
```

Alchemy decides whether to update from the reference string and the
target platform. Re-pushing the same tag doesn't redeploy anything,
so pin a version (or a digest, `repo@sha256:…`) and change it to
roll out a new image. On EKS the pinned image is copied into ECR once
per change.

## Build your Dockerfile

On EKS, point `context` at a directory with a Dockerfile:

```typescript
const legacy = yield* Kubernetes.Deployment("Legacy", {
  cluster,
  context: "./legacy",
  port: 8080,
});
```

`dockerfile` defaults to `${context}/Dockerfile`; pass a path
(relative to the directory you deploy from) to use another one.
Alchemy hashes the build context and the Dockerfile, so editing any
file in the context triggers a rebuild and a rollout on the next
deploy. Building uses the local Docker CLI.

## Bundle an Effect program

With `main`, the workload's implementation is an Effect in the same
module:

```typescript
export default Kubernetes.Deployment(
  "Api",
  { cluster, main: import.meta.url, port: 3000 },
  Effect.gen(function* () {
    return {
      fetch: Effect.succeed(HttpServerResponse.text("ok")),
    };
  }),
);
```

Alchemy bundles the module with rolldown, wraps it in a generated
entrypoint (an HTTP server for a Deployment, a run-to-completion
program for a Job), and builds an image from a generated Dockerfile.
The related props:

- **`handler`** — the named export to run. Defaults to `"default"`.
- **`image`** — the base image of the generated Dockerfile. Defaults
  to `oven/bun:1`; any image that can run Bun works.
- **`dockerfile`** — a base environment Dockerfile (a path, or inline
  content) when you need system packages.
- **`build`** — bundler options. Unused code is tree-shaken, and
  `effect`, alchemy, and `@distilled.cloud` are marked side-effect
  free so they prune aggressively. Add your own side-effect-free
  packages with `build: { pure: { packages: ["my-lib"] } }`, or turn
  the behavior off with `build: { pure: false }`.

A change to the bundled output triggers a rebuild and a rollout.

## CPU architecture

`architecture` (`"amd64"` by default, or `"arm64"`) sets the platform
images are built and mirrored for. Match it to your nodes — Graviton
node pools on EKS need `"arm64"`. Registry images used as written on
other clusters are pulled by the nodes for their own architecture,
so prefer multi-architecture images there.

## Build your own image for any cluster

On clusters without a registry adapter, build and push with
[`Docker.Image`](/docker/build-and-push) in the same Stack and pass
its reference:

```typescript
import * as Docker from "alchemy/Docker";
import * as Config from "effect/Config";

const image = yield* Docker.Image("ApiImage", {
  name: "acme/api",
  tag: "v1.4.0",
  build: { context: "./api", platform: "linux/amd64" },
  registry: {
    server: "ghcr.io",
    username: "acme-bot",
    password: Config.Redacted("GHCR_TOKEN"),
  },
});

const api = yield* Kubernetes.Deployment("Api", {
  cluster,
  image: image.imageRef,
  port: 8080,
});
```

Add `Docker.providers()` to the Stack's providers. Change `tag` for
each release so the reference changes and the Deployment rolls out.

For a kind cluster, skip the registry: build the image locally and
copy it onto the nodes with `kind load docker-image acme/api:dev
--name <cluster>`, then use `image: "acme/api:dev"`. Use a tag other
than `latest` so Kubernetes doesn't try to pull it from a registry.

## Pull from a private registry

Nodes need credentials to pull private images. Create an
image-pull Secret with a [Manifest](/kubernetes/objects/manifests)
and reference it from the pod template:

```typescript
const pullSecret = yield* Kubernetes.Manifest("GhcrPullSecret", {
  cluster,
  manifest: {
    apiVersion: "v1",
    kind: "Secret",
    type: "kubernetes.io/dockerconfigjson",
    metadata: { name: "ghcr", namespace: "apps" },
    data: { ".dockerconfigjson": dockerConfigJsonBase64 },
  },
});

const api = yield* Kubernetes.Deployment("Api", {
  cluster,
  namespace: "apps",
  image: "ghcr.io/acme/api:v1.4.0",
  port: 8080,
  podTemplate: {
    spec: { imagePullSecrets: [{ name: pullSecret.name }] },
  },
});
```

On EKS this isn't needed: images are mirrored into ECR, and the
nodes can pull from it.
