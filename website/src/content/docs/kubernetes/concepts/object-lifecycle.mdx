---
title: How objects are managed
description: How Alchemy applies, orders, prunes, and deletes Kubernetes objects — server-side apply and field ownership, drift, replacement, unreachable clusters, and adoption.
---

Every Kubernetes resource in Alchemy — [`Deployment`](/kubernetes/workloads/deployments),
[`Job`](/kubernetes/workloads/jobs),
[`Manifest`](/kubernetes/objects/manifests), and
[`HelmChart`](/kubernetes/objects/helm-charts) — turns into one or
more Kubernetes objects. This page describes what happens to those
objects across deploys.

| Resource     | Objects it owns                                               |
| ------------ | ------------------------------------------------------------- |
| `Deployment` | ServiceAccount, Deployment, Service                           |
| `Job`        | ServiceAccount, Job or CronJob                                |
| `Manifest`   | The one object in `manifest`                                  |
| `HelmChart`  | Every object in the render, plus the Namespace with `createNamespace` |

## Server-side apply

Alchemy writes objects with Kubernetes
[server-side apply](https://kubernetes.io/docs/reference/using-api/server-side-apply/)
under the field manager `alchemy`, with `force` enabled. Each apply
sends the complete desired object, and the API server merges it:

- **Alchemy owns the fields it sends.** Forcing means a conflicting
  value set by another manager (`kubectl edit`, another tool) is
  overwritten, and Alchemy becomes that field's owner.
- **Fields Alchemy stops sending are removed** — unless another
  manager also set them.
- **Fields Alchemy never sends are left alone.** Controllers can
  keep writing `status`, autoscalers can manage fields Alchemy
  doesn't set, and annotations added by other tools survive.

One consequence: if a HorizontalPodAutoscaler manages a Deployment's
replicas, Alchemy's `replicas` value (default `1`) still overwrites
them on each apply. Write the workload as a
[Manifest](/kubernetes/objects/manifests) without `spec.replicas`
when an autoscaler should own the count.

## Apply and delete order

Within one resource, Alchemy applies objects in dependency order —
Namespaces, then CustomResourceDefinitions, then ServiceAccounts,
ConfigMaps and Secrets, Services, workloads, and finally any other
kind — and deletes them in the reverse order. Objects at the same
level are applied in parallel.

Across resources, the order comes from Output references. A
Deployment whose `namespace` is `ns.name` deploys after the `ns`
Manifest and is destroyed before it. Resources that don't reference
each other deploy in parallel.

## Pruning

Alchemy records every object each resource applied. When an update
produces a different set — a chart's new version drops a template, a
Job's spec changes its name, a Deployment moves namespace — Alchemy
deletes the objects that are no longer in the set before applying
the new ones.

Deletes use background propagation, so a deleted Job takes its pods
with it and a deleted Deployment takes its ReplicaSets.

## When objects are applied

Alchemy applies a resource's objects when the resource is created or
updated. A resource updates when its props change, or when the
content of its image source (a `context` directory, a bundled `main`
program, a local chart directory) changes.

A deploy with no changes applies nothing. Edits made out of band —
`kubectl scale`, `kubectl edit` — stay in place until the resource
is next applied. To converge everything back to your program, force
an apply of every resource:

```sh
alchemy deploy --force
```

[`alchemy drift`](/cli/drift) detects objects deleted out of band —
a Manifest's object, or the ServiceAccount of a Deployment or Job —
and reports the resource as missing; `alchemy drift --repair`
recreates it. It doesn't compare object fields, and a HelmChart is
only checked for a reachable cluster.

## Replacement

A resource is replaced when its identity changes:

| Resource     | Identity                                            |
| ------------ | --------------------------------------------------- |
| `Deployment` | Cluster and namespace                               |
| `Job`        | Cluster and namespace                               |
| `Manifest`   | Cluster, `apiVersion`, `kind`, `name`, `namespace`  |
| `HelmChart`  | Cluster, release name, namespace                    |

Replacement creates the new generation first, then deletes the old
one. When both generations contain an object with the same name in
the same place — the same cluster reached through a different
connection, or a chart object whose name ignores the release name —
deleting the old generation removes the object the new one just
applied. Run `alchemy deploy --force` after such a change. See
[Move a resource to another cluster](/kubernetes/clusters/connecting#move-a-resource-to-another-cluster)
and [Helm charts](/kubernetes/objects/helm-charts#release-name-and-namespace).

## Deploys don't wait for readiness

Applying succeeds as soon as the API server accepts the objects. A
Deployment's pods may still be pulling images, and a Job may still
be running or failing. The one exception is a `LoadBalancer` Service,
whose deploy waits up to about three minutes for an address. Use
`kubectl rollout status`, a smoke-test
[Job](/kubernetes/workloads/jobs), or your own health checks to
gate on readiness.

## Transient errors

Applies retry on API server errors (5xx), throttling (429), and
authentication or authorization failures (401 and 403, which are
common for a few seconds after a managed cluster or access entry is
created), for about a minute. Validation errors (such as 422) fail
immediately with the API server's message.

## Destroy and unreachable clusters

`alchemy destroy` connects to each resource's cluster using the
connection stored in state and deletes its objects. What happens
when the cluster can't be reached depends on why:

- **The cluster is gone** — a managed cluster reports that it was
  deleted. Its objects went with it, so Alchemy treats them as
  deleted and still removes the workload's ECR repository and Pod
  Identity role.
- **The cluster is unreachable** — a kubeconfig cluster that's
  stopped, or a network problem. `Deployment` and `Job` skip their
  in-cluster objects and still remove adapter-owned cloud resources;
  `Manifest` and `HelmChart` fail so you can retry once the cluster
  is back.

Deleting an object that's already gone is not an error, so destroy
can be re-run safely.

## Adoption and listing

Kubernetes objects carry no Alchemy ownership marker, so Alchemy
doesn't enumerate or adopt existing objects. Applying a Manifest or
chart whose objects already exist takes over their fields through
server-side apply; from then on Alchemy manages and deletes them like
objects it created.
