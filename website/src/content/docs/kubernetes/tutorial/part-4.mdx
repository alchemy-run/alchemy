In [Part 3](/kubernetes/tutorial/part-3) you ran Jobs and a CronJob.
Now you'll install third-party software the way most clusters get
it — from a Helm chart — and then delete everything with one
command.

The chart is [metrics-server](https://github.com/kubernetes-sigs/metrics-server),
which collects CPU and memory usage from each node and powers
`kubectl top`. kind doesn't ship with it.

## Install helm

`Kubernetes.HelmChart` renders charts with the `helm` CLI on your
machine. Install it if you haven't
([instructions](https://helm.sh/docs/intro/install/)), for example:

```sh
brew install helm
```

## Add the chart

```diff lang="typescript"
+  const metricsServer = yield* Kubernetes.HelmChart("MetricsServer", {
+    cluster,
+    chart: "metrics-server",
+    repo: "https://kubernetes-sigs.github.io/metrics-server/",
+    version: "3.14.0",
+    namespace: "kube-system",
+  });
```

`chart` + `repo` name a chart in a classic Helm repository; `chart`
also accepts an `oci://` reference or a local chart directory.
`version` pins the chart so every deploy renders the same objects.
Cluster add-ons conventionally live in `kube-system`, which already
exists, so no Namespace resource is needed.

## Name the release

```diff lang="typescript"
version: "3.14.0",
+releaseName: "metrics-server",
namespace: "kube-system",
```

Charts name their objects after the Helm release name. Without
`releaseName`, Alchemy generates one from the stack, stage, and
logical ID, and the chart's Deployment ends up with a long generated
name. Choose the release name before the first deploy: changing it
later replaces the whole chart.

## Pass chart values

kind's kubelets serve self-signed certificates, so metrics-server
must skip verifying them. Charts take their configuration as
**values** — the same shape as a `values.yaml` file:

```diff lang="typescript"
  namespace: "kube-system",
+  values: {
+    args: ["--kubelet-insecure-tls"],
+  },
});
```

Alchemy ran `helm template` locally and applied the nine rendered
objects — a Deployment, a Service, RBAC roles and bindings, and the
`APIService` that registers the metrics API — through the same
server-side apply path as a Manifest. There is no `helm install` and
no release record in the cluster: `helm list -A` shows nothing.
Alchemy owns the objects directly.

## Verify it worked

Wait for metrics-server to roll out, give it a minute to collect its
first samples, then ask for pod usage:

```sh
kubectl -n kube-system rollout status deployment/metrics-server
kubectl top pods -n my-app
```

```text
NAME                  CPU(cores)   MEMORY(bytes)
web-c65f4dd44-h8d8d   1m           16Mi
web-c65f4dd44-rw7jm   1m           16Mi
```

## Change a value

Values are part of the chart's identity. Change one — say, run two
replicas — and the next deploy re-renders the chart and applies the
difference:

```diff lang="typescript"
values: {
  args: ["--kubelet-insecure-tls"],
+  replicas: 2,
},
```

If a new render leaves out an object that the previous render
contained, Alchemy deletes it from the cluster.

Alchemy deletes everything in reverse dependency order: the Jobs
before the Deployment they call, and the Deployment before its
Namespace. The chart depends on nothing else in the stack, so its
objects are deleted in parallel. The cluster itself belongs to kind;
remove it when you're done:

```sh
kind delete cluster --name alchemy
```

## Recap

Over four parts you built and removed a complete local deployment:

- A podinfo Deployment in its own Namespace, configured from
  TypeScript
- A smoke-test Job that re-runs when its spec changes, plus a
  CronJob
- metrics-server installed from a pinned Helm chart, with Alchemy
  owning every rendered object

of program at Amazon EKS and run an Effect HTTP server with AWS
