A managed cluster resource can be passed directly as the `cluster`
of any Kubernetes resource. Today that's
[`AWS.EKS.Cluster`](/providers/aws/eks/cluster): its attributes
include a `connection`, and its platform adapter (registered by
`AWS.providers()`) does more than authenticate.

```typescript
import * as AWS from "alchemy/AWS";
import * as Kubernetes from "alchemy/Kubernetes";

const cluster = yield* AWS.EKS.Cluster("Cluster", {
  compute: "auto",
  resourcesVpcConfig: { subnetIds: network.privateSubnetIds },
});

const api = yield* Kubernetes.Deployment("Api", {
  cluster,
  main: import.meta.url,
  port: 3000,
});
```

Compose both provider layers in the Stack:

```typescript
providers: Layer.mergeAll(AWS.providers(), Kubernetes.providers()),
```

See [EKS](/aws/compute/eks) for creating the cluster itself: Auto
Mode, access entries, add-ons, and HyperPod.

## What the EKS adapter adds

| Concern          | On EKS                                                                                                      | On other clusters                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Authentication   | Short-lived SigV4 tokens minted from your AWS credentials; no kubeconfig                                    | Kubeconfig, token, client cert, or exec    |
| Container images | A private ECR repository per workload; `main` bundled, `context` built, `image` mirrored into it            | `image` pulled as written                  |
| Cloud access     | An IAM role per workload, attached to its ServiceAccount through EKS Pod Identity                            | Environment variables only                 |
| Load balancers   | `LoadBalancer` Services get an internet-facing Network Load Balancer on Auto Mode                           | Whatever the cluster's controller provides |
| Container entry  | Generated Effect entrypoints resolve AWS credentials from Pod Identity                                      | Platform-neutral entrypoint                |

### Authentication

Alchemy signs a short-lived bearer token with your AWS credentials
(the same token `aws eks get-token` produces) for every request. The
principal that created the cluster is its admin by default; grant
anyone else access with [`AWS.EKS.AccessEntry`](/providers/aws/eks/accessentry).

### Images in ECR

Each `Deployment` and `Job` gets its own ECR repository. `main`
programs are bundled and built into an image, `context` Dockerfiles
are built, and `image` references are pulled and pushed into the
repository, so pods only pull from your account. Set `architecture:
"arm64"` for Graviton nodes; the default builds `amd64`. The
repository is deleted when the workload is destroyed. See
[Container images](/kubernetes/workloads/images).

### Pod Identity

Each workload gets an IAM role and a
[`PodIdentityAssociation`](/providers/aws/eks/podidentityassociation)
for its ServiceAccount. AWS bindings used by the workload — say,
`AWS.DynamoDB.PutItem(table)` — add their IAM statements to that
role, and the pod receives temporary credentials for it through the
EKS Pod Identity agent. There are no access keys and no IRSA
annotations to manage. Attach additional AWS-managed or
customer-managed policies with `identity.managedPolicyArns`:

```typescript
const worker = yield* Kubernetes.Job("Export", {
  cluster,
  main: import.meta.url,
  identity: {
    managedPolicyArns: ["arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess"],
  },
});
```

See [Configuration & bindings](/kubernetes/workloads/bindings).

### Load balancers

EKS Auto Mode's built-in load balancer controller only handles
Services with `loadBalancerClass: eks.amazonaws.com/nlb`, and it
creates internal load balancers by default. On `LoadBalancer`
Services Alchemy sets that class (when the cluster has Auto Mode's
load balancing enabled) and the
`service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing`
annotation, so `url` is reachable from the internet. Your own
`serviceAnnotations` take precedence — set the scheme to `internal`
to keep a service private:

```typescript
const internal = yield* Kubernetes.Deployment("Internal", {
  cluster,
  image: "ghcr.io/acme/internal:v1",
  port: 8080,
  serviceAnnotations: {
    "service.beta.kubernetes.io/aws-load-balancer-scheme": "internal",
  },
});
```

### Cleanup

The ECR repository and Pod Identity role outlive the cluster's own
objects. On destroy Alchemy deletes the in-cluster objects if the
cluster is still reachable, then deletes the repository and role
whether or not the cluster still exists, so destroying a cluster and
its workloads together leaves nothing behind in AWS.

## Target an EKS cluster you don't manage

To deploy onto a cluster created elsewhere, build the connection
yourself. The adapter looks up the endpoint and certificate
authority from the cluster name:

```typescript
import "alchemy/AWS";

const cluster: Kubernetes.Connection = {
  auth: { kind: "aws-eks", clusterName: "shared-prod", region: "us-west-2" },
};
```

`region` defaults to the Stack's AWS region. The `aws-eks` auth kind
is added to the `Kubernetes.Connection` type by importing
`alchemy/AWS`, and it still requires `AWS.providers()` in the Stack.
Your AWS principal needs an access entry on that cluster. Workloads
get the same ECR, Pod Identity, and load balancer behavior as on a
Stack-managed cluster.

## GKE, AKS, and other managed clouds

Other managed Kubernetes services work through their kubeconfig
contexts and exec plugins — see
[Cloud CLI contexts](/kubernetes/clusters/connecting#cloud-cli-contexts).
They are authentication-only: run pre-built `image` references, pass
configuration through `env`, and grant cloud access through that
cloud's own workload identity (configured with
[Manifests](/kubernetes/objects/manifests) and the
`podTemplate` escape hatch). A platform can gain registry and
identity support by contributing a
[cluster adapter](/kubernetes/concepts/cluster-adapters).
