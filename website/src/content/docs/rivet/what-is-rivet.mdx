[Rivet](https://rivet.dev) is an open-source platform for stateful programs called **Actors**. An Actor is a small, long-lived program with a name and its own data: one chat room, one game, one user's session. Rivet keeps every Actor's data, runs each one on demand, and routes calls to it by name.

`@alchemy.run/rivet` presents Rivet's Actors as **Durable Objects**, with the same shape as Cloudflare's, and deploys everything Rivet needs into your Stack, on the cloud you choose. This page introduces each concept once, with the chat rooms the [tutorial](/rivet/tutorial/part-1) builds as the example.

Here is the whole picture, which the rest of this page explains piece by piece. A caller names a room; the control plane finds it, or starts it on a node in its pool; and the room answers from its own state.

## Durable Objects: a class and its instances

A Durable Object starts as a class. `Room` says what every room can do:

```typescript title="src/room.ts"
export default class Room extends Rivet.DurableObject<Room>()(
  "Room",
  { main: import.meta.url },
  Effect.gen(function* () {
    return Effect.gen(function* () {
      const state = yield* Rivet.DurableObjectState;
      return {
        join: () =>
          Effect.gen(function* () {
            const visitors = ((yield* state.storage.get<number>("visitors")) ?? 0) + 1;
            yield* state.storage.put("visitors", visitors);
            return visitors;
          }),
      };
    });
  }).pipe(Effect.provide(Default)),
) {}
```

An **instance** is one room: the lobby, the kitchen. Every instance runs the same code against its own state. In Rivet's terms, the class is an Actor name and each instance is an Actor with its own key.

See [Durable Object](/rivet/durable-objects).

## One instance per name

You never create an instance. Every name exists from the start, and the first call to a name brings its instance to life:

```typescript title="src/api.ts"
const rooms = yield* Room;
const visitors = yield* rooms.getByName("lobby").join();
```

However many callers ask for the lobby, from however many servers, they reach the same instance. There's never a second lobby with a different idea of who's in it. That's what lets a room count its visitors or keep its messages in order without coordinating with anything else: it's the only thing that knows about the lobby.

## State that lives with the instance

Each instance has its own storage, kept by Rivet: key-value entries, a SQLite database, and one alarm.

```typescript title="src/room.ts"
yield* state.storage.put("visitors", visitors);
yield* (yield* state.storage.sql.exec("INSERT INTO messages (author, text) VALUES (?, ?)", author, text)).toArray();
yield* state.storage.setAlarm(now + 60 * 60 * 1000);
```

The lobby's messages live in the lobby's database and nobody else's, so a room never filters out other rooms' rows or fetches its state from somewhere else. The **alarm** is a time at which Rivet calls the room's `alarm` handler, whether or not anyone else calls it.

See [Storage](/rivet/storage).

## Sleeping and waking

An instance doesn't run forever. When a room goes quiet, Rivet puts it to sleep and frees its node. The next call wakes it, on whichever node is free, and its data is exactly as it was.

So you can have far more rooms than your nodes could hold at once: only the ones in use take up room on a node. A room's code starts again on every wake: anything it holds in memory is gone, and anything in its storage remains.

## Calls by name

An instance answers calls through its methods. A caller names the instance and the method, and gets back a typed result:

```typescript title="src/api.ts"
const lobby = rooms.getByName("lobby");
const visitors = yield* lobby.join();
```

Besides a value, a method can return a `Stream` that delivers values as they're produced, or fail with a tagged error the caller catches by name. A room with a `fetch` handler answers HTTP requests too, and a caller forwards one with `lobby.fetch(request)`. A caller can be anything: a Cloudflare Worker, a Lambda, a container, or another Durable Object.

See [Calling a Durable Object](/rivet/calling).

## Many calls at once

An instance runs in one place, but it can take more than one call at once. While one call waits on another Durable Object or an HTTP request, the next one starts.

Storage is the exception. Once a call starts reading and writing, no other call touches storage until the first one waits on something else. So a method that reads a value and writes it back never loses another call's write. For a change that has to wait in the middle, or undo itself on failure, use a transaction.

See [Storage](/rivet/storage#change-state-safely-while-calls-overlap).

## The control plane

The **control plane** is Rivet's engine: the part that remembers. It keeps every instance's data, knows which node each running instance is on, and decides where to start a sleeping one.

It runs as one or more engines. One engine keeps its data on its own disk, which is fine on your machine. Production control planes run three or more, sharing the durable copy of every instance's data through object storage, so losing one loses nothing.

See [Control Plane](/rivet/control-planes).

## Namespaces

A control plane is divided into **namespaces**. Each namespace has its own pools and its own instances, so the same `Room` in two namespaces is two separate sets of rooms.

Alchemy creates one namespace per stage. Your `dev` stage's lobby and your `prod` stage's lobby never meet, even on one control plane.

## Pools and nodes

A **pool** is a group of machines, called **nodes**, that run your code. Each class runs on one pool. When a room wakes, the control plane starts it on one of its pool's nodes.

Nodes connect out to the control plane and wait for work. Nothing connects in to them, so they need no public address and no load balancer, and a pool can run on a different cloud from its control plane.

See [Pool](/rivet/pools).

## The gateway

Callers don't talk to nodes. They send each call to the control plane's **gateway**, an HTTP endpoint that takes the class, the instance's name and the request, and passes it to the node running that instance, starting it first if it's asleep.

```text
POST /gateway/Room/request/<path>?rvt-namespace=<stage>&rvt-key=lobby&rvt-method=getOrCreate
```

So a caller needs only the control plane's address and a token, and no route to the nodes at all.

## Your control plane, or Rivet Cloud

You can run the control plane yourself, on Docker, AWS, GCP, Kubernetes, Fly or Hetzner, or let [Rivet Cloud](https://rivet.dev) run it for you. Either way, your nodes run in a pool you deploy, on any cloud.

See [Rivet Cloud](/rivet/rivet-cloud).

## How @alchemy.run/rivet models these concepts

Each concept on this page is something you declare in your Stack.

A Durable Object class is a [`Rivet.DurableObject`](/rivet/durable-objects): its methods, `fetch` and `alarm` become a Rivet Actor, its storage becomes `Rivet.DurableObjectState`, and `yield* Room` gives any runtime a typed client that calls it through the gateway.

Actors you've already written with RivetKit, in its async or Effect form, deploy the same way: a `Rivet.DurableObject` given just their entry file runs them unchanged. See [Three ways to build Actors](/rivet/actors).

A control plane is a Layer, one per place it can run. It creates the engines, disks, storage, load balancer and admin token on that cloud, and a namespace for your stage. A pool is a Layer too, given the control plane it joins:

```typescript title="src/cluster.ts"
export const Cluster = RivetHetzner.ServerControlPlane("Rivet");

export const Default = RivetHetzner.ServerPool("Default").pipe(Layer.provide(Cluster));
```

A class names its pool with `Effect.provide(Default)`, and each deploy bundles every class on a pool into one program for its nodes. Because the control plane and the pool are just Layers, moving to another cloud changes this file and nothing else.
