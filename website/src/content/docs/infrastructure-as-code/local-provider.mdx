During `alchemy dev`, some resources should not touch the cloud. A Worker
runs in a local `workerd`, and a dev server is a child process on your
machine. A **local provider** serves a resource type in dev, next to the
**live provider** that `alchemy deploy` uses.

This guide shows how to build one. A local provider is a second
implementation of the lifecycle from
[Custom Provider](/infrastructure-as-code/custom-provider), so start there
if you haven't built a provider. For the user-facing dev model and
`remote()`, see [Local development](/environments/local-development).

## What the engine does for you

The engine records which implementation reconciled each resource. Moving
a resource between local and live is planned as a **replacement**. The
provider that created an instance also deletes it, so a deploy right
after a dev session tears down the local instances with your local
provider.

## Register both with `ProviderLayer.dual`

```typescript
import * as ProviderLayer from "alchemy/Local/ProviderLayer";
import * as Layer from "effect/Layer";

export const WorkerProvider = () =>
  ProviderLayer.dual(Worker, {
    live: () => LiveWorkerProvider(),
    // Mode-specific deps (workerd, Docker) go inside the thunk, never globally.
    local: () =>
      LocalWorkerProvider().pipe(Layer.provide(localRuntimeServices())),
  });
```

Neither variant builds at registration. Each builds and is memoized the
first time a plan, delete, or nuke needs it. A plain `alchemy deploy`
builds the local provider only when it has a local instance to tear down.

:::note[Share dependency layers by reference]
Variant builds are memoized by layer identity. If several local providers
share a dependency layer, such as Cloudflare's `localRuntimeServices()`,
the factory must return a module-memoized reference so they all get one
instance per stack build.
:::

Sometimes the local instance is an entry in a shared registry, not a
process. Cloudflare's local Queue is an entry in `LocalRuntimeState`,
reconciled with three idempotent map operations. For that case, write a
plain provider for `local` and skip `LocalProvider.make`.

## Long-running processes with `LocalProvider.make`

A process-shaped local provider has a problem ordinary providers don't.
Its physical resource is a running process that state can't see, so a
resource can be `created` while its process died with the last dev
session. `LocalProvider.make` handles that machinery, and you write how
to boot one instance.

### Declare the provider with `start`

```typescript
import * as LocalProvider from "alchemy/Local/LocalProvider";
import * as Effect from "effect/Effect";

export const DevProviderLocal = () =>
  LocalProvider.make(
    Dev,
    import.meta.resolve("./Local.ts", import.meta.url),
    Effect.gen(function* () {
      const { spawn } = yield* CommandExecutor;

      return {
        start: Effect.fn(function* ({ news }) {
          const child = yield* spawn(news);
          const url = yield* waitForUrl(child);
          return { url };
        }),
      } satisfies LocalProvider.LocalProviderSpec<Dev>;
    }),
  );
```

`start` boots one instance in the ambient `Scope` and returns attributes
at readiness. The process keeps running after `start` returns, until the
runner closes the scope on restart or delete.

The second argument is the URL of a module whose default export is this
provider's layer. `Command.Dev` points it at a small `Local.ts`:

```typescript
// Local.ts
export default DevProviderLocal().pipe(Layer.provide(CommandExecutorLive()));
```

During `alchemy dev`, the sidecar imports this module and serves the
provider over RPC. The registry of running processes lives in the
sidecar, so it survives hot reloads of your code. Outside dev, the
provider runs in-process and no sidecar starts.

### Handle processes that die on their own

```diff lang="typescript"
 start: Effect.fn(function* ({ news, invalidate }) {
   const child = yield* spawn(news);
   const url = yield* waitForUrl(child);
+  yield* child.exitCode.pipe(
+    Effect.exit,
+    Effect.flatMap(() => invalidate),
+    Effect.forkScoped,
+  );
   return { url };
 }),
```

`invalidate` drops the instance from the running registry, so the next plan
reports `update` and reconcile boots a fresh one.

### Narrow the restart surface with `resolveConfig`

```diff lang="typescript"
 return {
+  // Only these fields decide whether a running instance must restart.
+  resolveConfig: ({ news }) =>
+    Effect.succeed({ command: news.command, env: news.env }),
   start: Effect.fn(function* ({ config, invalidate }) {
-    const child = yield* spawn(news);
+    const child = yield* spawn(config);
     // ...
   }),
 };
```

The runner hashes the result of `resolveConfig` to choose between noop
and restart. It passes the same value to `start`, so the config that
decides a restart and the config that starts the process can't drift.
Without `resolveConfig`, the config is the resolved props and bindings.

:::tip[Config must be plain data]
`resolveConfig` runs inside `diff` on every plan. Keep it cheap and
side-effect-free, with no closures or live objects. Derive plain
descriptors here, and build runtime objects from them inside `start`.
:::

### Clean up cross-restart state with `stop`

```diff lang="typescript"
 return {
   resolveConfig: ({ news }) => ...,
   start: Effect.fn(function* ({ config, invalidate }) { ... }),
+  // Delete-only. The runner does not call it on restarts.
+  stop: Effect.fn(function* ({ fqn }) {
+    yield* stopProxy(fqn);
+  }),
 };
```

Anything `start` acquires dies with the instance scope. `stop` is only for
state that survives restarts on purpose, like a URL proxy that keeps the
address stable across rebuilds. Key that state by `fqn`, because logical
IDs can repeat across namespaces.

### What the runner generates

From `start`, `resolveConfig`, and `stop`, the runner generates `diff`,
`reconcile`, `delete`, and `list`. A running instance with an equal config
hash is a noop, and anything else restarts. A replacement's old-generation
delete can't kill its successor. See the JSDoc on
[`LocalProvider.make`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Local/LocalProvider.ts)
for each generated operation.

## Route deploy-time data-plane calls with `dataPlane`

Binding clients can run at deploy time, inside an `Action` body or a
plan-time `execute`. Their calls must reach the data plane where the bound
resource lives. Pass the local mode's environment override as `dataPlane`:

```typescript
ProviderLayer.dual(Bucket, {
  live: () => BucketProvider(),
  local: () => provideProviderContext(BucketProvider(), flociServices()),
  // Endpoint, credentials, and region for the emulator. Pass a module-memoized layer.
  dataPlane: flociServices,
  // liveDataPlane: the inverse, for Alchemy.remote() resources during alchemy dev.
});
```

With `dataPlane` set, a client bound to a local-mode resource calls the
emulator even when the ambient profile holds live credentials. A client
bound to an `Alchemy.remote()` resource keeps calling the real cloud.
Alchemy routes each bound resource separately, even within one Action.

During `alchemy dev` the ambient environment is the emulator. Pass the live
mode's environment as `liveDataPlane` so that clients bound to
`Alchemy.remote()` resources call the real cloud.

## Testing

`Test.make({ dev: true })` gives a test file `alchemy dev` semantics.
`remote()` works in tests the same way it works in programs:

```typescript
const { test } = Test.make({ providers, dev: true });

test.provider("promotes a dev worker to a live worker", (stack) =>
  Effect.gen(function* () {
    yield* program.pipe(stack.deploy); // local, the dev default
    // Same props pinned live. The plan is a replacement: the live provider
    // creates the deployed worker and the local provider stops workerd.
    yield* program.pipe(Alchemy.remote(), stack.deploy);
    yield* stack.destroy();
  }),
);
```

With `dev: true`, RPC-backed local providers run in a sidecar process by
default, the same topology as `alchemy dev`. This catches a local provider
that needs services only the main process has. See
[Test harness › sidecar](/testing/test-harness#sidecar) for the
`sidecar: false` opt-out, and [Test harness › dev](/testing/test-harness#dev)
for the `ALCHEMY_TEST_DEV` override.

  the smallest `LocalProvider.make` provider. It spawns a command,

  the registry-style case, a plain local provider under `dual`.
