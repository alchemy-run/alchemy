During `alchemy dev`, some resources should not touch the cloud. A Worker
runs in a local `workerd`, and a dev server is a child process on your
machine. A **local provider** is the implementation that serves a resource
type in dev. It sits alongside the **live provider** used by
`alchemy deploy`.

This guide covers how to build one. For the user-facing dev model, and
for opting a resource out of local emulation with `remote()`, see
[Local development](/environments/local-development). If you haven't built
a provider before, start with
[Custom Provider](/infrastructure-as-code/custom-provider). A local
provider is a second implementation of the same lifecycle contract.

## What the engine does for you

The engine remembers which implementation reconciled each resource. Moving
a resource between local and live is planned as a **replacement**. Every
instance is deleted by the provider that created it, so a deploy right
after a dev session tears down the local instances with your local
provider. You implement the lifecycle, and the engine handles the
switching.

## Register both: `ProviderLayer.dual`

```typescript
import * as ProviderLayer from "alchemy/Local/ProviderLayer";
import * as Layer from "effect/Layer";

export const WorkerProvider = () =>
  ProviderLayer.dual(Worker, {
    live: () => LiveWorkerProvider(),
    local: () =>
      LocalWorkerProvider().pipe(Layer.provide(localRuntimeServices())),
  });
```

Neither variant is built at registration. Each is built and memoized the
first time a plan, delete, or nuke needs it. For example, a deploy
constructs the local provider only if it has an instance to tear down.

### Route deploy-time data-plane calls: `dataPlane`

Binding clients can run at deploy time, inside an `Action` body or a
plan-time `execute`. Their API calls must target the data plane where the
bound resource lives. Pass the local mode's environment override as
`dataPlane`. The override sets the endpoint, credentials, and region. It
is the same layer the local lifecycle runs under.

```typescript
ProviderLayer.dual(Bucket, {
  live: () => BucketProvider(),
  local: () => provideProviderContext(BucketProvider(), flociServices()),
  dataPlane: flociServices,
});
```

With `dataPlane` registered, a client bound to a local-mode resource is
routed to the emulator even when the ambient profile carries live
credentials. A client bound to an `Alchemy.remote()` resource keeps
hitting the real cloud. Routing is decided per bound resource, within the
same Action.

`liveDataPlane` is the inverse. During `alchemy dev` the ambient
environment is the emulator, so pass the live mode's environment as
`liveDataPlane` to make clients bound to `Alchemy.remote()` resources use
the real cloud. Pass a module-memoized layer reference for both options.

### Compose local deps inside the thunk

Put mode-specific dependency layers (`workerd`, Docker) inside the
`local` thunk, never globally. This keeps a plain `alchemy deploy` from
constructing local machinery it doesn't need.

:::note[Share dependency layers by reference]
Variant builds are memoized by layer identity. If several local providers
share a dependency layer, such as Cloudflare's `localRuntimeServices()`,
the factory must return a module-memoized reference so they all get one
instance per stack build.
:::

## Long-running processes: `LocalProvider.make`

A process-shaped local provider has a problem ordinary providers don't
have. Its "physical resource" is a running process that state can't see.
A resource can be marked `created` while its process died with the last
dev session. `LocalProvider.make` handles that machinery. You write how to
boot one instance.

### Declare the provider with `start`

```typescript
import * as LocalProvider from "alchemy/Local/LocalProvider";
import * as Effect from "effect/Effect";

export const DevProviderLocal = () =>
  LocalProvider.make(
    Dev,
    import.meta.resolve("./Local.ts", import.meta.url),
    Effect.gen(function* () {
      const { spawn } = yield* CommandExecutor;

      return {
        start: Effect.fn(function* ({ news }) {
          const child = yield* spawn(news);
          const url = yield* waitForUrl(child);
          return { url };
        }),
      } satisfies LocalProvider.LocalProviderSpec<Dev>;
    }),
  );
```

The second argument is the URL of a module whose default export is this
provider's layer. The dev sidecar imports it to serve the provider over
RPC. `Command.Dev` points it at a small `Local.ts`:

```typescript
// Local.ts
export default DevProviderLocal().pipe(Layer.provide(CommandExecutorLive()));
```

`start` boots one instance in the ambient `Scope` and returns Attributes at
readiness. The process keeps running after `start` returns, until the
runner closes the scope on restart or delete.

### Handle processes that die on their own

```diff lang="typescript"
 start: Effect.fn(function* ({ news, invalidate }) {
   const child = yield* spawn(news);
   const url = yield* waitForUrl(child);
+  yield* child.exitCode.pipe(
+    Effect.exit,
+    Effect.flatMap(() => invalidate),
+    Effect.forkScoped,
+  );
   return { url };
 }),
```

`invalidate` drops the instance from the running registry, so the next plan
reports `update` and reconcile boots a fresh one.

### Narrow the restart surface with `resolveConfig`

```diff lang="typescript"
 return {
+  // Only these fields decide whether a running instance must restart.
+  resolveConfig: ({ news }) =>
+    Effect.succeed({ command: news.command, env: news.env }),
   start: Effect.fn(function* ({ config, invalidate }) {
-    const child = yield* spawn(news);
+    const child = yield* spawn(config);
     // ...
   }),
 };
```

The runner canonically hashes the result of `resolveConfig` to decide
between noop and restart. It passes the same value to `start`, so the
config that decides a restart and the config that starts the process can
never drift.

:::tip[Config must be plain data]
`resolveConfig` runs inside `diff` on every plan. Keep it cheap and
side-effect-free, with no closures or live objects. Derive plain
descriptors here, and build runtime-rich structures from them inside
`start`.
:::

### Clean up cross-restart state with `stop`

```diff lang="typescript"
 return {
   resolveConfig: ({ news }) => ...,
   start: Effect.fn(function* ({ config, invalidate }) { ... }),
+  // Delete-only: NOT called on restarts.
+  stop: Effect.fn(function* ({ fqn }) {
+    yield* stopProxy(fqn);
+  }),
 };
```

Anything `start` acquires dies with the instance scope. `stop` is only for
state that intentionally survives restarts, like a URL proxy kept so the
address stays stable across rebuilds. Key cross-restart state by `fqn`.
Logical ids can repeat across namespaces.

### What the runner generates

- **`diff`** returns `noop` for a running instance with an equal config
  hash. Anything else returns `update`. A fresh dev session has an empty
  registry, so processes restart even though they were previously
  `created`.
- **`reconcile`** reuses the running instance on a hash match. Otherwise it
  tears the instance down and forks `start` in a scope that outlives the
  deploy.
- **`delete`** tears down only the matching `instanceId`, so a
  replacement's old-generation delete can't kill its successor. Then it
  runs `stop`.
- **`list`** returns every running instance's Attributes.

:::note[The dev sidecar]
The second argument (`providersUrl`) serves the provider over RPC. During
`alchemy dev`, the registry of running processes lives in a sidecar that
survives user-code hot reloads. Outside dev, the provider is constructed
in-process and no sidecar is spawned.
:::

## Not everything is a process

Sometimes the local "instance" is an entry in a shared registry. For
example, Cloudflare's local Queue is an entry in `LocalRuntimeState`,
reconciled with three idempotent map operations. In that case, skip
`LocalProvider.make` and write a plain provider registered via `dual`.

## Testing

```typescript
const { test } = Test.make({ providers, dev: true }); // dev-mode default

test.provider("promotes a dev worker to a live worker", (stack) =>
  Effect.gen(function* () {
    yield* program.pipe(stack.deploy); // local (dev default)
    // Same props, pinned live: planned as a REPLACEMENT — the live
    // provider creates the deployed worker, the local provider kills
    // workerd.
    yield* program.pipe(Alchemy.remote(), stack.deploy);
    yield* stack.destroy();
  }),
);
```

`Test.make({ dev: true })` gives the file `alchemy dev` semantics.
`remote()` works in tests the same way it works in programs.

With `dev: true`, RPC-backed local providers run in a sidecar process by
default, the same topology as `alchemy dev`. This catches a local provider
that needs services only the main process has. See
[Test harness › sidecar](/testing/test-harness#sidecar) for the
`sidecar: false` opt-out, and
[Test harness › dev](/testing/test-harness#dev) for the
`ALCHEMY_TEST_DEV` override.
