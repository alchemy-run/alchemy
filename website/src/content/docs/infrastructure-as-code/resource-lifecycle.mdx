Every [resource](/infrastructure-as-code/resource) goes through the
same lifecycle of **plan → reconcile → (replace) → delete**. This page
explains each step and how Alchemy recovers when a deploy fails
partway. One engine drives `alchemy deploy`, `alchemy destroy`, and
`alchemy dev`, and the [CLI reference](/cli) lists their flags.

## Plan

When you run `alchemy deploy`, Alchemy first **plans** the change. It
compares the desired state in your code against the last persisted
state and classifies each resource:

- **Create** (`+`): declared in code, not in state.
- **Update** (`~`): declared and persisted, but properties differ.
- **Replace** (`±`): the change requires destroy-and-recreate.
- **Delete** (`-`): persisted but no longer declared.
- **No-op** (`•`): unchanged.

Each provider's [`diff`](/infrastructure-as-code/provider#diff) decides
between an in-place update and a replacement. Plan compares your code
against saved state, so a change made in the cloud console doesn't
show up. Run these commands to see or override the plan:

```sh
alchemy plan                    # print the plan without applying it
alchemy deploy --dry-run        # same as alchemy plan
alchemy deploy --detect-drift   # find and repair changes made outside Alchemy
alchemy drift                   # report drift without deploying
alchemy deploy --force          # reconcile resources that would be a no-op
```

See [drift](/cli/drift) for drift detection.

## Apply

Alchemy then **applies** the plan. It walks resources in dependency
order, calls each provider's lifecycle operation, and resolves the
results as [Outputs](/infrastructure-as-code/outputs) that downstream
resources read:

```typescript
const bucket = yield* Cloudflare.R2.Bucket("Bucket"); // reconciled first
const worker = yield* Cloudflare.Worker("Api", {
  main: import.meta.url,
  env: { BUCKET: bucket.bucketName }, // waits for the Bucket's output
});
```

## Reconcile

Alchemy calls one **convergent** function, `provider.reconcile`, for a
first create, an in-place update, and an adoption of existing
infrastructure. It observes live cloud state and brings it to the
desired props from any starting point, so a crashed reconcile resumes
correctly on the next run. See
[Provider › reconcile](/infrastructure-as-code/provider#reconcile) for
the parameter contract and the observe, ensure, and sync shape.

A second pass, called **convergence**, re-runs `reconcile` for any
resource whose inputs changed because an upstream output changed
mid-deploy.

### Cycles

Two runtimes that bind each other form a cycle, so neither can wait
for the other's outputs. See
[Circular Bindings](/infrastructure-as-effects/circular-bindings) for
how to declare one. Alchemy applies a cycle in four steps:

  edges={[
    { from: "Decl", to: "Pre" },

    { from: "Reconcile", to: "Converge" },

/>

1. **Declare**: both Tags register up front, so the graph knows that
   A and B exist.
2. **Precreate**: each provider's
   [`precreate`](/infrastructure-as-code/provider#precreate) reserves
   the resource and its URL without the other side's outputs. Members
   of the cycle wait only for this signal, which breaks the deadlock.
3. **Reconcile**: both sides reconcile concurrently. A binding to the
   other side may see the precreate stub's outputs.
4. **Converge**: a loop re-resolves each resource's props and bindings
   against the latest outputs. It re-runs `reconcile` for any resource
   whose inputs changed, and repeats until nothing changes.

## Replace

Some property changes can't be applied in place, such as changing a
DynamoDB table's partition key. The provider's `diff` returns a
replacement:

```typescript
// default: create-first
return { action: "replace" };

// for resources that can't coexist with their replacement,
// such as a fixed physical name or a singleton
return { action: "replace", deleteFirst: true };
```

A create-first replacement runs in three steps:

1. Alchemy creates a new resource with a new instance ID.
2. It updates downstream resources to reference the new resource.
3. It deletes the old resource.

The new and old resources coexist briefly, so dependents get a clean
cutover, and the old resource stays alive if the create fails. With
`deleteFirst: true`, Alchemy deletes the old generation before it
creates the new one.

Changing a **logical ID** also plans a replacement. If you only renamed
the resource, declare it with `renamedFrom` instead. See
[Rename a resource](/infrastructure-as-code/renaming).

## Delete

Alchemy calls `provider.delete` when a resource disappears from your
code, when a replacement supersedes it, or when you run
`alchemy destroy`. Delete is **idempotent**, so deleting a resource
that is already gone succeeds.

`alchemy destroy` is a plan that marks every persisted resource for
deletion. It removes resources in **reverse dependency order**, so
dependents go first:

## Removal policy

Each resource carries a **removal policy**. It decides what happens to
the cloud object when the resource is deleted, whether it was
orphaned, destroyed, or superseded by a replacement:

- `destroy`: calls `provider.delete`, then drops the state row. Most
  resource types default to this.
- `retain`: skips `provider.delete`, then drops the state row. Alchemy
  forgets the resource and only the cloud object survives. A few
  resource types whose contents are irreplaceable default to this,
  such as [`GitHub.Repository`](/github/repository) and
  `Cloudflare.Zone`.

Set the policy by piping a declaration through `retain()` or
`destroy()`. It applies to every resource declared inside the piped
effect, so it can decorate one resource or a whole scope:

```typescript
import * as Cloudflare from "alchemy/Cloudflare";
import * as RemovalPolicy from "alchemy/RemovalPolicy";
import { Stack } from "alchemy/Stack";

Effect.gen(function* () {
  const stack = yield* Stack;

  // never deleted by Alchemy
  const uploads = yield* Cloudflare.R2.Bucket("Uploads").pipe(
    RemovalPolicy.retain(),
  );

  // retained in prod, torn down in every other stage
  const cache = yield* Cloudflare.R2.Bucket("Cache").pipe(
    RemovalPolicy.retain(stack.stage === "prod"),
  );
});
```

The policy is a decoration, so changing it plans a **no-op** with no
reported changes. The deploy still writes the new policy to the state
row, and a later orphan delete reads it from there. A policy change
takes effect from the very next deploy.

:::caution
`retain` protects the resource from Alchemy, not from the provider's
own delete semantics. Deleting a resource still cascades however that
cloud API cascades, so deleting a bucket that a provider empties first
destroys its objects.

Retain a resource **before** the deploy that would remove it, and
prefer moving irreplaceable data behind a retained resource.
:::

## Recovering from failures

State persistence can fail after a cloud operation succeeds, for
example when the network drops between "bucket created" and "state
saved". Alchemy saves each resource's in-progress status to the
[state store](/state-store) before it calls the provider:

```text
creating  → created              # reconcile of a new resource
updating  → updated              # reconcile of a changed resource
replacing → replaced → created   # old generation kept under `old`, then deleted
deleting  → (row removed)
```

A crash leaves a resource in an intermediate status. The next deploy
reads it and resumes where the last one stopped:

- **Reconcile**: the saved `creating` row keeps the **instance ID**
  that Alchemy generated before the first provider call. A retry
  computes the same
  [physical name](/infrastructure-as-code/resource#physical-name), so
  the observe step finds the resource instead of creating a duplicate
  and re-syncs any aspect that drifted.
- **Delete**: a missing resource counts as already deleted.
- **Read**: providers that implement `read` let Alchemy rebuild state
  from the live cloud when persistence failed. See
  [Adoption](#adoption).

Errors follow the same split between provider and engine:

- **Retryable errors**, such as eventual consistency and dependency
  races, are retried inside each provider's lifecycle operations. The
  engine does not retry a failed operation.
- **Non-retryable errors**, such as validation and authorization,
  fail the operation. Errors from `diff` and `read` surface during
  plan. Errors from `reconcile` and `delete` surface during apply.

## Adoption

When the engine plans a resource with no prior state, it calls
`provider.read` if the provider implements it. This covers two cases:

- **State recovery**: a previous deploy created the resource, but
  state was lost before the store persisted it. `read` finds the live
  resource, and the engine rebuilds `created` state from its
  attributes.
- **Adoption**: you deploy against infrastructure that Alchemy doesn't
  manage yet, or you wiped state on purpose. `read` recognizes the
  resource, and the engine imports it into the new state.

The engine silently adopts a resource that `read` recognizes as owned
by this stack. A resource that exists but belongs to someone else fails
with `OwnedBySomeoneElse`. To allow the takeover, re-run with
`--adopt` or scope the effect with `adopt(true)`:

```sh
alchemy deploy --adopt
```

See [Provider › read](/infrastructure-as-code/provider#read) for how
providers signal ownership and
[Adopting Resources](/cli/adopting-resources) for the CLI flag.
