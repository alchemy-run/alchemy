Every [Resource](/infrastructure-as-code/resource) goes through the same lifecycle:
**plan → reconcile → (replace) → delete**. The plan classifies each
resource as create, update, replace, delete, or no-op. The provider
implements one `reconcile` function that converges the cloud's actual
state to the declared state. The same function handles the first
provisioning, a routine update, or an adoption takeover. For the CLI
flags that drive these operations, see the
[CLI reference](/cli).

Both create and update intents resolve to the provider's single
`reconcile` function. Replace runs `reconcile` against a fresh
instance id and then deletes the old generation. The same engine
drives `alchemy deploy`, `alchemy destroy`, and `alchemy dev`.

## Plan

When you run `alchemy deploy`, alchemy first **plans** the change.
It compares the desired state (what your code declares) against the
last persisted state and classifies each resource:

- **Create** (`+`): declared in code, not in state
- **Update** (`~`): declared and persisted, but properties differ
- **Replace** (`±`): the change requires destroy-and-recreate
- **Delete** (`-`): persisted but no longer declared
- **No-op** (`•`): unchanged

## Reconcile

Alchemy calls one function, `provider.reconcile`, whether a resource
is being created for the first time, updated in place, or adopted
from existing infrastructure.

Reconcile must be **convergent**. Given the desired props, it
observes live cloud state and brings it to that state from any
starting point. It must also be safe to retry. A partial reconcile
that crashed midway resumes correctly on the next run. Physical
names are deterministic from `stack/stage/logical-id`, so the
reconciler finds the existing resource and does not duplicate it.
The parameter contract (`news`/`output`/`olds`/`bindings`) and the
observe → ensure → sync shape are the provider's concern. See
[Provider › reconcile](/infrastructure-as-code/provider#reconcile).

A second pass, called **convergence**, re-runs `reconcile` for any
resource whose inputs changed because an upstream output changed
mid-deploy.

## Replace

Some property changes can't be applied in place, such as changing a
DynamoDB table's partition key. For these, the provider's `diff`
returns `{ action: "replace" }`, and alchemy:

1. Creates a new resource with a new instance ID
2. Updates downstream resources to reference the new resource
3. Deletes the old resource

The new and old resources coexist briefly, so dependents get a clean
cutover without downtime.

Changing a **logical ID** also plans a replacement. If you only
renamed the resource, declare it with `renamedFrom` instead. See
[Renaming Resources](/infrastructure-as-code/renaming).

## Delete

`provider.delete` is called when a resource disappears from your
code, when a replacement supersedes it, or when you run
`alchemy destroy`. Like create, delete must be **idempotent**.
Deleting a resource that is already gone is a success, not an error.

`alchemy destroy` is a plan where every persisted resource is marked
for deletion. Resources are removed in **reverse dependency order**,
so dependents go first.

## Removal policy

Each resource carries a **removal policy**. The policy decides what
happens to the physical cloud object when the resource is deleted.
This applies whether the resource is orphaned, destroyed, or
superseded as a replacement's old generation:

| Policy      | What the engine does                                     |
| ----------- | -------------------------------------------------------- |
| `destroy`   | Calls `provider.delete`, then drops the state row         |
| `retain`    | Skips `provider.delete`, then drops the state row         |

Alchemy forgets the resource under either policy. Under `retain`, only
the cloud object survives. Most resource types default to `destroy`. A
few whose contents are irreplaceable default to `retain` (e.g.
[`GitHub.Repository`](/github/repository), `Cloudflare.Zone`).

Set the policy by piping a declaration through `retain()` or
`destroy()`. It applies to every resource declared inside the piped
effect, so it can decorate one resource or a whole scope:

```typescript
import * as RemovalPolicy from "alchemy/RemovalPolicy";

Effect.gen(function* () {
  const stack = yield* Stack;

  // never deleted by alchemy
  const uploads = yield* R2.Bucket("Uploads").pipe(RemovalPolicy.retain());

  // retained in prod, torn down in every other stage
  const cache = yield* R2.Bucket("Cache").pipe(
    RemovalPolicy.retain(stack.stage === "prod"),
  );
});
```

The policy is a decoration, not a prop, so changing it produces no
diff. The resource plans as a **no-op** and the plan reports no
changes. The deploy still persists the new policy onto the state row.
The orphan delete reads the policy from there, long after the
declaration is gone. A policy change therefore takes effect from the
very next deploy.

:::caution
`retain` protects the resource from *alchemy*, not from the provider's
own delete semantics. Deleting a resource still cascades however that
cloud API cascades. For example, deleting a bucket that a provider
empties first destroys its objects. Retain a resource **before** the
deploy that would remove it. Prefer moving irreplaceable data behind
a retained resource.
:::

## Idempotency and recovery

State persistence can fail after the cloud operation succeeds. For
example, the network drops between "bucket created" and "state
saved". Alchemy handles this by requiring `reconcile` and `delete` to
be safe to retry:

- **Reconcile**: deterministic physical names and the observe step
  let a retry find the existing resource without creating a
  duplicate. The retry also re-syncs any aspect that drifted.
- **Delete**: a missing resource is treated as already deleted.
- **Read**: providers can implement `read` so alchemy can recover
  state from the live cloud when persistence fails partway. `read`
  also detects adoptable resources on a fresh state store.

## Adoption

When the engine plans a resource that has no prior state, it calls
`provider.read` if the provider implements it. This serves two
overlapping purposes:

- **State recovery**: the resource was created on a previous deploy,
  but state was lost between the cloud op succeeding and the store
  persisting. `read` finds the live resource and the engine rebuilds
  `created` state from its attributes.
- **Adoption**: you are deploying against existing infrastructure
  that you did not manage with Alchemy yet, or you wiped state on
  purpose. `read` recognizes the resource and the engine imports it
  into the new state.

The engine silently adopts a resource that `read` recognizes as ours.
A resource that exists but *isn't* ours fails with
`OwnedBySomeoneElse`. Re-run with `--adopt`, or scope the effect with
`adopt(true)`, to allow the takeover. The provider contract defines
how providers signal ownership through `read`'s return value. See
[Provider › read](/infrastructure-as-code/provider#read). For the CLI flag, see
[Adopting Resources](/cli/adopting-resources).

## Errors

- **Retryable errors** (eventual consistency, dependency races) are
  retried automatically with backoff.
- **Non-retryable errors** (validation, authorization) fail
  immediately and surface in the plan output.
- **Partial failures** are safe to re-run because operations are
  idempotent.

## Driving the lifecycle from the CLI

The same engine powers all of these commands:

| Command            | What it does                                  |
| ------------------ | --------------------------------------------- |
| `alchemy plan`     | Run plan, print diff, exit                    |
| `alchemy deploy`   | Plan, prompt for approval, apply              |
| `alchemy destroy`  | Plan with everything marked deleted, apply    |
| `alchemy dev`      | Plan + apply continuously on file changes     |

See the [CLI reference](/cli) for the full set of flags
(`--yes`, `--force`, `--dry-run`, `--stage`, `--profile`, ...).

Every lifecycle operation on this page is implemented per resource
type by a [Provider](/infrastructure-as-code/provider).
