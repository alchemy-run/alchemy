A reference reads something already deployed from the persisted
[state store](/state-store) at plan time. Use one to borrow a resource
from another stage, another stack, or both. Every plan re-reads the
upstream's state, so the downstream always sees what was last
deployed.

## Requirements

- **Same state backend**: references read the state store of the
  stack doing the referencing. Both stacks must use the same backend,
  for example both `Cloudflare.state()` in the same account.
- **The fully qualified name**: the ID you pass is the resource's
  [fully qualified name](/infrastructure-as-code/resource#fully-qualified-names).
  For a resource declared inside `Namespace.push("Site")`, pass
  `"Site/Assets"`, not `"Assets"`.
- **An upstream deploy**: the upstream must already be deployed to the
  exact `{ stack, stage }` you name. See [Deploy order](#deploy-order).

## Reference another stage

Pass `stage` to `Resource.ref` to read a resource from a different
stage of this stack:

```typescript
const { stage } = yield* Alchemy.Stack;

// `staging` owns the database, and `pr-*` stages borrow it
const project = stage.startsWith("pr-")
  ? yield* Neon.Project.ref("app-db", { stage: "staging" })
  : yield* Neon.Project("app-db", { region: "aws-us-east-1" });
```

The reference has the same type as `yield* Neon.Project("app-db", { … })`,
so you can pass it anywhere the real resource is accepted. Destroying a
borrower never touches the resources it references.

## Reference another stack

Pass `stack` too for a resource in a different stack:

```typescript
const sharedBucket = yield* Cloudflare.R2.Bucket.ref("Assets", {
  stack: "shared-infra", // defaults to the current stack
  stage: "prod",         // defaults to the current stage
});
```

`{ stack, stage, id }` is the full address. Pin `stage` when the
stacks' stages don't line up. For example, `pr-147` has no counterpart
in `shared-infra`.

## Depend on a stack's outputs

To consume a whole stack, declare a typed handle for it and deploy the
stack with `.make`:

```typescript
// backend/src/Stack.ts
export class Backend extends Alchemy.Stack<
  Backend,
  { url: string }
>()("Backend") {}

// backend/alchemy.run.ts
export default Backend.make(
  { providers: Cloudflare.providers(), state: Cloudflare.state() },
  Effect.gen(function* () {
    // ...
    return { url: worker.url.as<string>() };
  }),
);
```

Import the handle in another stack and `yield*` it:

```typescript
// inside the frontend stack's Effect.gen
const a = yield* Backend;                // current stage
const b = yield* Backend.stage.prod;     // pinned to "prod"
const c = yield* Backend.stage["pr-42"]; // any stage name

a.url; // Output<string>
```

Every successful apply persists what the stack's effect returned as a
per-stage output record, and `yield* Backend` reads it back as typed
Outputs. See [Multiple Stacks](/project-structure/monorepo-multi-stack)
for a full two-package walkthrough.

## Deploy order

Deploy the upstream first. If it isn't deployed to the exact
`{ stack, stage }` the reference names, the plan fails with a typed
`InvalidReferenceError`:

```sh
alchemy deploy --stage staging   # creates app-db
alchemy deploy --stage pr-147    # borrows staging's app-db
```

Destroy in reverse order.

## Escape hatches

- When the resource constructor isn't in scope, build the reference
  with `Alchemy.ref<Type>(id, { stack, stage })` and wrap it in
  [`Output.of`](/infrastructure-as-code/outputs#of).
- When a typed stack handle isn't in scope, read the output record with
  [`Output.stackRef`](/infrastructure-as-code/outputs#stackref).

Prefer `Resource.ref` and `yield* MyStack`, which do the same lookups
with real type bindings.
