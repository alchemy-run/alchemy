---
title: Rename a resource
description: Change a resource's logical ID and keep its cloud resource by migrating its state instead of replacing it.
type: how-to
---

Changing a [logical ID](/infrastructure-as-code/resource#logical-id)
normally plans a
[replacement](/infrastructure-as-code/resource-lifecycle#replace).
Alchemy creates a new resource and deletes the old one, including its
data and attachments. This page shows how to rename a resource and keep
the cloud resource it manages.

## Declare the rename

Change the logical ID and pipe the declaration through
`Alchemy.renamedFrom` with the old ID:

```diff lang="typescript"
-const bucket = yield* Cloudflare.R2.Bucket("Bucket");
+const bucket = yield* Cloudflare.R2.Bucket("Assets").pipe(
+  Alchemy.renamedFrom("Bucket"),
+);
```

The next deploy moves the state row from `Bucket` to `Assets` and plans
one **update** that re-brands the resource's ownership tags under the
new ID. The [instance ID](/infrastructure-as-code/resource#physical-name)
and physical name stay the same, and nothing is created or deleted:

```text
Plan: 1 to update
[Assets] update (renamed from Bucket)
```

Keep the decoration in place. Once no state row exists under the old
ID, it does nothing.

## Renamed more than once

List every former ID, most recent first. Alchemy checks them in order
and migrates from the first matching row:

```typescript
// rename history: Bucket → StaticAssets → Assets
yield* Cloudflare.R2.Bucket("Assets").pipe(
  Alchemy.renamedFrom("StaticAssets", "Bucket"),
);
```

## Namespaces

A former ID resolves against the surrounding `Namespace.push`, exactly
like the resource's own ID. Write it as you would have written the ID
in the same position:

```typescript
// FQN `Site/Assets`, former FQN `Site/Bucket`
yield* Cloudflare.R2.Bucket("Assets").pipe(
  Alchemy.renamedFrom("Bucket"),
  Namespace.push("Site"),
);
```

If the resource moved between namespaces, pass the absolute form. It
is the full [FQN](/infrastructure-as-code/resource#fully-qualified-names)
exactly as it appears in state:

```typescript
// former FQN `LegacySite/Assets`, not `NewSite/LegacySite/Assets`
yield* Cloudflare.R2.Bucket("Assets").pipe(
  Alchemy.renamedFrom({ fqn: "LegacySite/Assets" }),
  Namespace.push("NewSite"),
);
```

## Give the old name to a new resource

A new resource can take the old ID in the same deploy. The rename claim
wins the state row, and Alchemy creates the new resource fresh:

```typescript
// `Assets` keeps the cloud resource previously known as `Bucket`.
// This `Bucket` is a brand-new one.
const assets = yield* Cloudflare.R2.Bucket("Assets").pipe(
  Alchemy.renamedFrom("Bucket"),
);
const bucket = yield* Cloudflare.R2.Bucket("Bucket");
```

The re-branding update is why the migration never plans a no-op. It
keeps the reused ID from adopting the wrong cloud resource.

## What the plan rejects

The plan fails before it touches anything in these cases:

- **Two claims on one former ID**: two resources that pass the same
  former ID fail instead of racing for the row.

  ```typescript
  yield* Cloudflare.R2.Bucket("Assets").pipe(Alchemy.renamedFrom("Bucket"));
  yield* Cloudflare.R2.Bucket("Files").pipe(Alchemy.renamedFrom("Bucket"));
  // ✗ Resources 'Assets' and 'Files' both claim former FQN 'Bucket'
  ```

- **Swaps**: exchanging two live IDs is a rename cycle, because the
  migrations would overwrite each other's rows. Rename through a
  temporary ID across two deploys instead.

  ```typescript
  yield* Cloudflare.R2.Bucket("A").pipe(Alchemy.renamedFrom("B"));
  yield* Cloudflare.R2.Bucket("B").pipe(Alchemy.renamedFrom("A"));
  // ✗ Rename cycle detected among ['A', 'B']
  ```

- **A different-typed row at the new ID**: migrating over it would
  abandon its cloud resource. Delete or rename that resource first.

  ```typescript
  // state already holds a KV.Namespace at 'Assets'
  yield* Cloudflare.R2.Bucket("Assets").pipe(Alchemy.renamedFrom("Bucket"));
  // ✗ a state row of a different type already occupies 'Assets'
  ```

The plan accepts these cases and never touches the cloud to resolve
them:

- **Leftover copy**: a crashed deploy can leave rows at both IDs with
  the same instance ID. Only a migration copies an instance ID, so
  Alchemy drops the leftover from state only.
- **Old ID reused later**: a former row with a different instance ID
  belongs to another resource. Alchemy ignores the alias, and the row
  follows normal lifecycle rules.
- **Different-typed former row**: a former row of another resource type
  is never migrated. Alchemy creates this resource fresh, and the old
  row is a normal orphan delete.
- **Shifts**: renames can pass through each other in one deploy, such
  as `A → B` and `B → C`. Each row follows its resource, along with any
  pending replacement cleanup.
