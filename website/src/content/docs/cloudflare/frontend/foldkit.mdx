[Foldkit](https://foldkit.dev) is an Elm-architecture frontend
framework built on Effect. A Foldkit app builds through Vite, so
`Cloudflare.Website.Foldkit` deploys one as a Cloudflare Worker with
a single declaration: no adapter, no build command, no output
directory, no Wrangler configuration.

`Foldkit` is [`Cloudflare.Website.Vite`](/cloudflare/frontend/vite)
with Foldkit's defaults: one `vite build` over the project. The
client output deploys as the Worker's static assets. When the app's
own `vite.config.ts` asks for a server build, that same `vite build`
also emits `dist/server/fetch.js` — a Web `fetch` handler with the
built shell embedded — and that handler is the Worker, exactly the
way a TanStack Start server bundle is. Every prop this page doesn't
cover behaves as it does on `Vite`.

How a Foldkit app is delivered is a property of the app's Vite
config, not of the declaration. The same declaration deploys a
client-only, prerendered, server-rendered, or hybrid app; the build
writes down which, and the asset routing follows from that — no
`assets` config for any of them. See
[Asset routing](#asset-routing).

## Configure Vite

Your Vite config stays exactly what `create-foldkit-app` gives you —
the `foldkit()` plugin, and the `optimizeDeps.entries` hint pointing
Vite's dependency scan at your app's entry module:

```typescript
// vite.config.ts
import { foldkit } from "@foldkit/vite-plugin";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [foldkit()],
  optimizeDeps: {
    entries: ["src/entry.ts"],
  },
});
```

Alchemy runs Vite programmatically on the project root and layers
its Cloudflare integration on top of this config — the Foldkit
plugin and the rest of your setup are preserved as-is. This is a
client-only app: a plain `vite build`, deployed as assets.

:::note[Pinned Effect versions]
Foldkit pins its `effect` peer dependency to an exact version.
Alchemy runs your app's own Vite build with your app's own
`node_modules`, so that pin is between Foldkit and your package
manager — Alchemy imposes no Effect version on your frontend.
:::

### Server-rendered and prerendered

A deployment that renders outside the browser declares its server
entry in this file, exactly as `create-foldkit-app`'s SSR and SSG
scaffolds generate it:

```diff lang="typescript"
// vite.config.ts
+import { randomUUID } from "node:crypto";

+process.env.FOLDKIT_BUILD_ID ||= randomUUID();
+const buildId = process.env.FOLDKIT_BUILD_ID;

export default defineConfig({
-  plugins: [foldkit()],
+  plugins: [
+    foldkit({
+      buildId,
+      ssr: {
+        serverEntry: "/src/entry.server.ts",
+        build: true,
+      },
+    }),
+  ],
  optimizeDeps: {
    entries: ["src/entry.ts"],
  },
});
```

`ssr.build` is what makes the one `vite build` emit the `fetch`
handler next to the browser bundle. Alchemy deploys it as the
Worker; nothing in `alchemy.run.ts` names an entry.

To prerender instead, ask the build to generate the paths the entry
exports as `prerenderPaths`:

```diff lang="typescript"
ssr: {
  serverEntry: "/src/entry.server.ts",
-  build: true,
+  build: { prerender: true },
},
```

The handler is still built and still deployed: prerendered routes
are served as files, and any route the entry did not list renders on
request. Prerender every route for a fully static site, some of them
for a hybrid one.

`buildId` is compiled into both bundles as
`import.meta.env.FOLDKIT_BUILD_ID`. Give CI a real per-deployment
value — a commit SHA or a release tag — and store the fallback on
`process.env` rather than computing it inline, so the client bundle
and the server bundle see the same id. See Foldkit's
[server rendering](https://foldkit.dev/core/server-rendering) docs
for the hydration contract.

## Declare the Website

Declare the site as a module-level const (rather than inline in the
Stack) and derive the typed shape of its bindings from it:

```typescript
// alchemy.run.ts
import * as Cloudflare from "alchemy/Cloudflare";

export const Website = Cloudflare.Website.Foldkit("Foldkit");

export type WebsiteEnv = Cloudflare.InferEnv<typeof Website>;
```

That declaration is the whole of it, whichever way the app is
delivered. `WebsiteEnv` is the typed shape of the Worker's bindings;
a client-only app with a `main` entry imports it in
[Custom Worker entry](#custom-worker-entry).

For an app in a subdirectory of a monorepo, point `rootDir` at it:

```typescript
export const Website = Cloudflare.Website.Foldkit("Foldkit", {
  rootDir: "applications/web",
});
```

## Add it to the Stack

Yield the class from your Stack and return its URL — see
[examples/cloudflare-foldkit](https://github.com/alchemy-run/alchemy/tree/main/examples/cloudflare-foldkit)
for the client-only shape and
[examples/cloudflare-foldkit-ssr](https://github.com/alchemy-run/alchemy/tree/main/examples/cloudflare-foldkit-ssr)
for the server-rendered one:

```typescript
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "CloudflareFoldkitExample",
  {
    providers: Cloudflare.providers(),
    state: Cloudflare.state(),
  },
  Effect.gen(function* () {
    const worker = yield* Website;

    return {
      url: worker.url,
    };
  }),
);
```

## Asset routing

The asset layer answers a request before the Worker sees it, so what
it does with a request that matches no file decides whether a page
ever renders. Getting it wrong fails quietly: the site serves 200s
that carry an empty document. `Foldkit` derives it from the build, so
nothing needs declaring.

A server-rendered or prerendered build writes
`dist/server/foldkit.build.json` beside the handler, recording which
paths it prerendered, and `Foldkit` reads it:

- A prerendered route is a file, and the default `htmlHandling`
  serves `/about` from `about/index.html`.
- Every other request reaches the `fetch` handler, which answers a
  miss for a hashed asset with a 404 and renders a page.
- The build keeps the unfilled template out of the client output, so
  `/` is a file only when the build prerendered it; otherwise the
  front page reaches the handler like any other route.

A client-only build writes no manifest, and that is its signature:
nothing renders outside the browser, so a deep link like
`/counter/42` is a request for a file that doesn't exist. It gets
`notFoundHandling: "single-page-application"` — the template is
served and the app's router resolves the path once it boots — the
same default `AWS`, `Fly`, `Hetzner`, and `Railway`'s `Foldkit`
resources apply.

Anything you set in `assets` wins over what is derived. An app that
ships a real 404 page opts out of the fallback:

```typescript
export const Website = Cloudflare.Website.Foldkit("Foldkit", {
  assets: {
    notFoundHandling: "404-page",
  },
});
```

## Add environment variables

Browser code has no server to ask, so anything a client-only app
needs from the rest of your Stack is baked into the bundle at build
time — pass a `VITE_`-prefixed key in `env`:

```diff lang="typescript"
// alchemy.run.ts
export const Website = Cloudflare.Website.Foldkit("Foldkit", {
+  env: {
+    VITE_API_URL: backend.url.as<string>(),
+  },
});
```

Type it for your Foldkit code with Vite's standard `ImportMetaEnv`
augmentation:

```typescript
// src/vite-env.d.ts
/// <reference types="vite/client" />

interface ImportMetaEnv {
  readonly VITE_API_URL: string;
}
```

Client code reads it as `import.meta.env.VITE_API_URL`. See
[Environment](/cloudflare/frontend/vite#environment) for the full
inlining semantics.

The same `env` prop also carries runtime bindings — KV namespaces,
secrets, other Workers — to a `main` entry, where they are read from
the Worker's env rather than inlined into the bundle.

## Custom Worker entry

A client-only app that must also do something at the edge — serve an
API route, wrap the app in error reporting, export Durable Object
classes — points `main` at its own module. The module builds through
Vite's `ssr` environment and becomes the deployed Worker entry. The
client build is still reachable through the Worker's `ASSETS`
binding, so the Worker answers its own routes and hands everything
else back to the asset layer:

```typescript
// src/worker.ts
import type { WebsiteEnv } from "../alchemy.run.ts";

export default {
  async fetch(request: Request, env: WebsiteEnv): Promise<Response> {
    const url = new URL(request.url);

    if (url.pathname === "/api/ticker") {
      const body = await env.TICKER.get("ticker:clubs");
      return new Response(body, {
        headers: { "content-type": "application/json" },
      });
    }

    return env.ASSETS.fetch(request);
  },
};
```

Your `vite.config.ts` needs no changes — the injected Cloudflare
plugin points the `ssr` environment at `main` itself. Just declare
the entry and bind what the Worker needs:

```typescript
// alchemy.run.ts
const ticker = yield* Cloudflare.KV.Namespace("Ticker");

export const Website = Cloudflare.Website.Foldkit("Foldkit", {
  main: "src/worker.ts",
  env: { TICKER: ticker },
  assets: {
    runWorkerFirst: ["/api/*"],
  },
});
```

`runWorkerFirst` sends `/api/*` to the Worker ahead of the asset
layer. The client-only fallback is still derived — a deep link the
Worker hands back through `env.ASSETS.fetch` is answered with the
template as before.

Bindings passed in `env` are reachable from this Worker entry (and
from cron handlers), not from browser code. `env.TICKER` is typed as
a KV namespace and `ASSETS` comes with the resource, so nothing here
is hand-written — renaming a binding in `alchemy.run.ts` is a type
error in your Worker.

A server-rendered or prerendered app cannot take a `main`: with
`ssr.build` set, Foldkit's plugin owns the server entry, and the
build fails if another module claims it. Put edge logic for such an
app in its `renderPage` entry, or in a separate Worker.

## Local dev

```sh
bun alchemy dev
```

`alchemy dev` runs the app's own Vite dev server, so Foldkit's
state-preserving live reload and its devtools wiring work unchanged. A
server-rendered app renders in dev through the same `ssr.serverEntry`
Foldkit's own `vite dev` uses — Alchemy leaves Vite's `ssr`
environment in place when nothing of yours runs in workerd — and a
client-only app with a `main` entry sees real KV namespaces and
secrets through that entry.

Pin the dev server's address when several apps run in one Stack:

```typescript
export const Website = Cloudflare.Website.Foldkit("Foldkit", {
  dev: { host: "127.0.0.1", port: 5180, strictPort: true },
});
```
