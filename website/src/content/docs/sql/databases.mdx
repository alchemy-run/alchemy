Choose the database separately from the runtime that executes your queries.
A Worker can use Neon, a Lambda can use Aurora, and a container service can
connect to an existing Postgres database. Network reachability and the driver
matter as much as the database's SQL dialect.

## Match the client to the database

[Effect SQL](/sql/effect-sql/postgres) and [Drizzle](/sql/drizzle/postgres)
have Postgres and MySQL clients, plus separate D1 integrations.
[Prisma ORM v8](/sql/prisma/contracts) currently targets PostgreSQL 17+.
Check the deployed engine version rather than assuming a provider's default
satisfies that requirement.

Aurora DSQL speaks the Postgres wire protocol but has different SQL and DDL
constraints. Its Drizzle integration is not evidence of Prisma ORM support.
The **RDS Data API** executes statements over HTTPS and is a different runtime
interface from a Postgres/MySQL connection string.

Hyperdrive is a connection pool/proxy, not a database. Use it from Cloudflare
Workers when the selected integration calls for it; Lambda and container
integrations do not require it.

## Decide where migrations run

A provider may expose a deploy-time `migrations` property, a separate migration
resource, or require a runner with access to the database's private network.
Read the database guide before choosing an apply strategy. Generate schemas
with [Drizzle](/sql/drizzle/migrations) or
[Prisma](/sql/prisma/migrations), or use
[hand-written SQL files](/sql/effect-sql/migrations).
