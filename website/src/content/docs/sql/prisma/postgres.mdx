Prisma ORM v8 (the `8.0.0-rc` line) on Postgres, end to end: a
contract, a `Prisma.Contract` resource that emits it and plans
migrations on deploy, a `Prisma.Migrate` resource that applies them,
and a Worker that queries through the Prisma client over Hyperdrive.

:::caution
Prisma v8 is a release candidate. It is a ground-up rewrite of Prisma
ORM (contract-first, no `prisma generate`, a new migration system) and
this Alchemy integration targets **PostgreSQL 17+ only** — no MySQL, no D1.
Alchemy pins the exact RC version; expect breaking changes between release candidates.

In rc.11, Prisma's published declarations lose authoring metadata. Import
`defineContract` from `alchemy/Prisma/ORM/ContractBuilder` to use Alchemy's
compatibility types for scalar fields, relations, prepared parameters, and
Postgres aggregates. This exports Prisma's original runtime function and
builders; it does not introduce a separate schema language or require
application code generation. The underlying declaration gaps are tracked in
[Prisma #30341](https://github.com/prisma/orm/issues/30341).
:::

Prisma ORM and its CLI are optional Alchemy peers. This Worker example also
installs Arktype to configure Prisma's internal validator for workerd:

## Configure validation for Workers

Cloudflare Workers prohibit runtime JavaScript compilation during requests.
Configure Prisma's Arktype dependency before importing the native contract builder:

```typescript
// src/prisma/validation.ts
import { configure } from "arktype/config";

configure({ jitless: true });
```

Keep this in a separate module, imported first by the contract below. If your
application declares `"sideEffects": false` in `package.json`, preserve this
bootstrap with `"sideEffects": ["./src/prisma/validation.ts"]` instead. Otherwise
a bundler can remove the configuration call. Ordinary Node and Bun applications
do not need this Worker-specific setup.

## Define the contract

Prisma v8 is contract-first, and TypeScript is the headline authoring
form — models are code, built with the `defineContract` DSL.
Everything — types, runtime IR, the migration graph — derives from
it:

```typescript
// src/prisma/contract.ts
import "./validation.ts";
import { defineContract } from "alchemy/Prisma/ORM/ContractBuilder";

export const contract = defineContract({}, ({ field, model, rel }) => ({
  models: {
    User: model("User", {
      fields: {
        id: field.id.uuidv7Native(),
        email: field.text().unique(),
        name: field.text(),
        createdAt: field.temporal.createdAtString(),
      },
      relations: {
        posts: rel.hasMany("Post", { by: "authorId" }),
      },
    }),

    Post: model("Post", {
      fields: {
        id: field.id.uuidv7Native(),
        title: field.text(),
        authorId: field.uuidNative(),
      },
      relations: {
        author: rel.belongsTo("User", { from: "authorId", to: "id" }),
      },
    }),
  },
}));
```

The deployment resources can also read Prisma's `.prisma` schema language.
The runtime API shown here takes the native TypeScript contract directly;
emitted files remain deployment and migration artifacts.

The compatibility adapter supports explicit storage names with
`.sql({ table: "users" })` and `.column("created_at")`. Global `snake_case`
naming is rejected rather than inferred incorrectly. Defaults on
`field.namedType(...)` retain Prisma's declarations and can still require an
explicit value in create inputs.

## Point the config at it

`prisma.config.ts` is the single source of truth for the
toolchain — the CLI and alchemy's resources both read it:

```typescript
// prisma.config.ts
import { defineConfig as ormConfig } from "@prisma/orm-postgres/config";
import { definePrismaConfig } from "prisma/config";

export default definePrismaConfig({
  orm: ormConfig({
    contract: "./src/prisma/contract.ts",
    // contract.json + contract.d.ts land here
    output: "./src/prisma/generated",
  }),
});
```

## Declare the contract resource and database

`Prisma.Contract` runs `prisma contract emit` on every deploy
and — when the contract drifted from the migration graph — plans a new
migration package. `Prisma.Migrate` applies pending packages to a
database. Passing the contract's output creates the dependency edge:
emit and plan first, apply second, in one `alchemy deploy`. On Neon:

```typescript
// src/db.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as Neon from "alchemy/Neon";
import * as Prisma from "alchemy/Prisma";
import * as Effect from "effect/Effect";

export const Db = Effect.gen(function* () {
  const contract = yield* Prisma.Contract("contract");

  const project = yield* Neon.Project("app-db");
  const branch = yield* Neon.Branch("app-branch", { project });

  yield* Prisma.Migrate("migrate", {
    url: branch.connectionUri,
    contract,
  });

  return branch;
});

export const Hyperdrive = Effect.gen(function* () {
  const branch = yield* Db;
  return yield* Cloudflare.Hyperdrive.Connection("app-hyperdrive", {
    origin: branch.origin,
  });
});
```

Any Postgres 17+ works the same way — a [Prisma Postgres](/prisma)
database's `directConnectionString`, an RDS instance, or a
self-hosted URL. Register `Prisma.providers()` alongside your cloud
providers in the Stack. [Migrations](/sql/prisma/migrations) covers
what the deploy does — and what it refuses to decide for you.

## Connect in a Worker

Hyperdrive pools connections at the edge. Pass its connection string and the
native TypeScript contract to the runtime factory; application code imports
neither generated JSON nor generated declarations:

```typescript
// src/api.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as PrismaPostgres from "alchemy/Prisma/ORM/Postgres";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";
import { contract } from "./prisma/contract.ts";
import { Hyperdrive } from "./db.ts";

export default class Api extends Cloudflare.Worker<Api>()(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const conn = yield* Cloudflare.Hyperdrive.Connect(Hyperdrive);
    const db = yield* PrismaPostgres.Postgres(conn.connectionString, { contract });

    return {
      fetch: Effect.gen(function* () {
        const users = yield* db.orm.public.User.all();
        return yield* HttpServerResponse.json({ users });
      }),
    };
  }).pipe(Effect.provide(Cloudflare.Hyperdrive.ConnectBinding)),
) {}
```

Nothing connects at init — the client is built per event, its pool
opens on the first query, and `close()` runs when the event settles
(see [Connection lifecycle](/sql/effect-sql/lifecycle)). Plan and
deploy never open a connection.

## Queries are Effects

The `orm` lane chains exactly like Prisma's own client
(namespaced per Postgres schema — `db.orm.public.*`), but every
terminal yields an Effect with typed errors. Queries are lazy and
re-runnable: `Effect.retry` re-issues the query.

```typescript
const user = yield* db.orm.public.User.where({ email })
  .include("posts")
  .first();

if (user) {
  yield* db.orm.public.Post.create({ title, authorId: user.id });
}

// row types narrow with the chain: select projects, include augments
const slim = yield* db.orm.public.User.select("id", "email").all();
```

`update` and `delete` require a prior `.where(...)` — at compile
time, same as Prisma. Failures surface as granular tagged
errors: each SQL integrity violation has its own tag
(`UniqueViolationError`, `ForeignKeyViolationError`,
`NotNullViolationError`, `CheckViolationError`), other
statement failures are `QueryError` (with the normalized
`sqlState`), connection failures are `ConnectionError` (with
the driver's `transient` retry hint), and Prisma's structured
codes split by category into `OrmError` / `RuntimeError`
with an autocompleting `code` field:

```typescript
const outcome = yield* db.orm.public.User.create({ email, name }).pipe(
  Effect.catchTag("Prisma.UniqueViolationError", () =>
    Effect.succeed("already registered"),
  ),
);
```

## The sql lane and raw SQL

`db.sql` is Prisma's pure query builder — plans are data, no
connection behind them — and `db.execute` / `db.stream` run them:

```typescript
const plan = db.sql.public.User.select("id", "email").build();
const rows = yield* db.execute(plan);          // Effect<{id, email}[]>
const feed = db.stream(plan);                  // Stream<{id, email}>
```

The Stream surfaces consume Prisma's async iterators. Its long-lived Postgres
driver buffers raw results, so using a Stream does not guarantee bounded memory.

## Prepared queries

A prepared query retains its typed parameters and resolves the current
execution's client each time it runs:

```typescript
const findUser = yield* db.prepare({ email: "pg/text@1" }, (sql, params) =>
  sql.public.User
    .select("id", "email")
    .where((fields, fns) => fns.eq(fields.email, params.email))
    .build(),
);
const users = yield* findUser.query({ email: "alice@example.com" });
const stream = findUser.query({ email: "alice@example.com" }).stream;
```

An affected-count plan instead returns a handle with `execute(params)`, which
produces statement statistics. Inside a transaction, `tx.prepare` binds both
query and mutation handles to that transaction's connection.

## Transactions

`db.transaction` runs an Effect on a dedicated connection — commit on
success, rollback on failure or interruption. `tx.rollback()` aborts
with a typed `Prisma.RollbackError`:

```typescript
yield* db.transaction((tx) =>
  Effect.gen(function* () {
    const user = yield* tx.orm.public.User.create({ email, name });
    if (!invited) return yield* tx.rollback();
    return user;
  }),
);
```

Surfaces the Effect facade does not cover yet (`groupBy`, `combine`,
`variant`, `prepare`) remain reachable through the promise-land
escape hatch: `db.use((c) => ...)`.
