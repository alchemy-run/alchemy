`Drizzle.Schema` puts `drizzle-kit generate` inside the deploy
graph: on each deploy it diffs your schema module against the latest
checked-in snapshot, writes any pending migration SQL to `out`, and
the database resource downstream applies it via `migrations` — in
that order, because `schema.out` is an `Output` the database depends
on.

```typescript
const schema = yield* Drizzle.Schema("app-schema", {
  schema: "./src/schema.ts",
  out: "./migrations",
  dialect: "sqlite",
});

const db = yield* Cloudflare.D1.Database("app-db", {
  migrations: schema,
});
```

## What a deploy actually does

- **No drift** — the schema matches the latest snapshot: nothing is
  generated, the resource is a noop, and nothing cascades into the
  database resource.
- **Unambiguous drift** — a new table, a new column: the migration
  SQL is generated automatically and applied in the same deploy.
- **Ambiguous drift** — a change drizzle-kit cannot decide alone
  (did you rename `email` to `contact`, or drop one column and add
  another? a change that would lose data): it needs your answer.
  - In a terminal, `alchemy deploy` surfaces drizzle-kit's
    interactive prompts and you answer inline.
  - Non-interactively (CI, `--yes` pipelines), the deploy **fails**
    with drizzle-kit's report and instructions: run
    `drizzle-kit generate` yourself, answer the prompts, commit the
    generated files, and redeploy. The generated SQL is applied to a
    real database in the same deploy — alchemy never guesses on a
    destructive choice.

Generated files land under `out` as ordered migration directories
containing `migration.sql` and `snapshot.json`. Commit them — they
are source code, shared with every other environment that deploys
the same app.

## Or: run drizzle-kit yourself

`Drizzle.Schema` is optional. If you prefer to run
`drizzle-kit generate` manually and commit the output, point
`migrations` at the checked-in directory — the database resource
only sees `.sql` files:

```typescript
const db = yield* Cloudflare.D1.Database("app-db", {
  migrations: "./drizzle", // drizzle-kit's default out
});
```

## Durable Object migrations

Each Durable Object instance has its own SQLite database. Read a
checked-in migration directory with `Cloudflare.SqlMigrations` in
the **outer** Effect, then pass the result to `Drizzle.DurableObject`
in the **inner** Effect. Files are read during construction/planning;
pending SQL runs when each instance activates, before its methods
become available. Deploying does **not** migrate every object in a
namespace.

### Generate and commit the SQL

Use a SQLite drizzle-kit config:

```typescript
// drizzle.config.ts
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  dialect: "sqlite",
  schema: "./src/schema.ts",
  out: "./drizzle",
});
```

Define tables and
[`defineRelations`](https://orm.drizzle.team/docs/relations-v2) for
typed queries:

```typescript
// src/schema.ts
import { defineRelations } from "drizzle-orm";
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const users = sqliteTable("users", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  name: text("name").notNull(),
});

export const relations = defineRelations({ users });
```

Run `pnpm exec drizzle-kit generate` and commit its output, including
snapshots. The modern layout uses directories such as
`drizzle/20260919000000_create_users/migration.sql`.
`SqlMigrations` reads existing files; it does not run drizzle-kit or
wait for `Drizzle.Schema` to generate them during reconciliation.
The files must already exist when planning starts, including in CI.

### Load the directory in the outer Effect

```typescript
// src/Users.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as Drizzle from "alchemy/Drizzle/Cloudflare";
import * as Effect from "effect/Effect";
import { relations, users } from "./schema.ts";

export class Users extends Cloudflare.DurableObject<Users>()(
  "Users",
  Effect.gen(function* () {
    const migrations = yield* Cloudflare.SqlMigrations("./drizzle");

    return Effect.gen(function* () {
      const db = yield* Drizzle.DurableObject({ migrations, relations });

      return {
        addUser: (name: string) => db.insert(users).values({ name }).returning(),
        listUsers: () => db.query.users.findMany(),
      };
    });
  }),
) {}
```

`./drizzle` is relative to the **current working directory of the
Alchemy command**, not `Users.ts`. The records and SQL are embedded
in the Worker JavaScript — there are no migration environment
variables, `.sql` imports, or `migrations.js` imports to configure.
Run commands from the project directory. After changing migration files,
restart `alchemy dev` or run another deploy to capture the new records;
the SQL directory is not part of the JavaScript import watcher.

To choose another tracking table, use
`Cloudflare.SqlMigrations({ dir: "./drizzle", table: "app_migrations" })`.
The default is `__alchemy_migrations`, the shared Alchemy migration
history used by other SQL integrations.

### Apply migrations before activation

`Drizzle.DurableObject` opens Drizzle over the current instance's
SQLite storage through `drizzle-orm/effect-sqlite-do`. The returned
queries are Effects, like [`Drizzle.D1`](/sql/drizzle/d1) and
[`Drizzle.Postgres`](/sql/drizzle/postgres).

Directory-based migrations use Alchemy's shared migration engine.
Each pending file and its history entry run together in a native,
synchronous SQLite transaction. If a file fails, that file rolls
back and activation fails; successfully applied earlier files stay
committed. The next activation retries the pending file. Do not edit
or rename already-applied files.

`Drizzle.DurableObject` treats migration failures as defects so a failed
initialization prevents the instance from serving requests. The underlying
migration errors are `MigrationError` and `MigrationHistoryConflictError`.
Queries retain their own typed `EffectDrizzleQueryError` channel, and query
transactions can also fail with effect-sql's `SqlError`.

No ORM is required: call
[`Cloudflare.applySqlMigrations(migrations)`](/sql/effect-sql/migrations#durable-object-migrations)
in the inner Effect to use the same migration engine with raw SQL.

### Existing Drizzle migrations

Passing the generated `migrations.js` object to
`Drizzle.DurableObject({ migrations, relations })` remains supported.
That input still uses **Drizzle's migrator**, not Alchemy's shared
engine. Merely changing its `migrationsTable` to
`"__alchemy_migrations"` does not convert the history or switch engines.

To move to Alchemy-managed migrations, replace the bundle import with
`yield* Cloudflare.SqlMigrations("./drizzle")` in the outer Effect.
On activation, the shared engine adopts matching existing modern
Drizzle history, applies only pending files, and leaves
`__drizzle_migrations` frozen. This is a **one-way** transition:
stop using Drizzle's migrator after adoption. Keep all historical
migration files in the checkout; unmatched history fails with
`MigrationHistoryConflictError` rather than guessing what ran.

The old `meta/_journal.json` layout is rejected. Run
`pnpm exec drizzle-kit up`, review and commit the upgraded files,
then plan again.

For a complete Worker with named-object POST and GET routes, see
[the Durable Object SQL example](https://github.com/alchemy-run/alchemy/tree/main/examples/cloudflare-durable-object-sql).

## Migrating from drizzle-kit

Already ran `drizzle-kit migrate` against the database before
Alchemy? For database resources, no baselining is needed: on the first
deploy Alchemy copies
the applied history out of `__drizzle_migrations` (the `drizzle`
schema on Postgres) into its own `__alchemy_migrations` table —
hashes carry over verbatim, since both record sha256 of
`migration.sql` — and only genuinely pending migrations run. The
drizzle table is left frozen, never written or dropped.

It's a one-way move: from then on Alchemy owns the bookkeeping, so
retire `drizzle-kit migrate` from your workflow (`drizzle-kit
generate` is subsumed by `Drizzle.Schema`). See
[adopting an existing database](/sql/effect-sql/migrations#adopting-an-existing-database)
for the shared mechanics and guard rails.

## Destroy never deletes migrations

The provider's `delete` operation is a deliberate no-op. Removing
the resource (or destroying the stack) never wipes the migrations
directory — migration files are source code you commit, not cloud
state to tear down.

## Dialects

`dialect` selects drizzle-kit's target: `"postgres"` (the default)
for [Neon / PlanetScale / Fly / Hyperdrive-fronted
Postgres](/sql/drizzle/postgres), `"mysql"` for
[PlanetScale MySQL](/sql/drizzle/mysql), `"sqlite"` for
[D1](/sql/drizzle/d1).
