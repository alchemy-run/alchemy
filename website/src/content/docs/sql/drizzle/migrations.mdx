---
title: Drizzle migrations
description: Drizzle.Schema regenerates migration SQL as part of every deploy, and wiring its out output into a database's migrationsDir input orders generation before application.
---

`Drizzle.Schema` makes schema generation part of the deploy graph:
drizzle-kit runs as a resource, and the migration SQL it emits is a
resource output. Passing that output — the `out` directory — to a
database resource's `migrationsDir` input creates a dependency edge,
so every deploy regenerates pending migrations first and applies them
second, in one `alchemy deploy`.

This page covers the generation side. The application side — how a
directory of `.sql` files is ordered, hashed, and applied by D1,
Neon, or PlanetScale — is the
[migrationsDir contract](/sql/migrations), and it works the same
whether the files are generated or hand-written.

`drizzle-kit` and `drizzle-orm` are optional peer dependencies of
alchemy, so install both in your project. Register the provider with
`Drizzle.providers()` in your Stack.

## Declare the schema

```typescript
const schema = yield* Drizzle.Schema("app-schema", {
  schema: "./src/schema.ts",
});
```

`schema` points at your schema module, which is loaded via dynamic
`import()` so drizzle-kit can introspect the table definitions and
diff them against the latest snapshot. Generated migrations land
under `out` (default `./migrations`), each written as
`{out}/{timestamp}_migration/` containing `migration.sql` and
`snapshot.json`; `dialect` selects which `drizzle-kit/api-*` module
loads and defaults to `"postgres"`.

## Wire it into the graph

```typescript
export const NeonDb = Effect.gen(function* () {
  const schema = yield* Drizzle.Schema("app-schema", {
    schema: "./src/schema.ts",
    out: "./migrations",
  });

  const project = yield* Neon.Project("app-db", {
    region: "aws-us-east-1",
  });

  const branch = yield* Neon.Branch("app-branch", {
    project,
    migrationsDir: schema.out,
  });

  return { project, branch, schema };
});
```

`schema.out` is an `Output`, not a plain string — passing it to
`migrationsDir` is what creates the dependency edge that forces the
engine to run `Drizzle.Schema` before `Neon.Branch`, even though both
values happen to spell `./migrations`. On D1 the same wiring is
`migrationsDir: schema.out` on `Cloudflare.D1.Database`, with
`dialect: "sqlite"` on the schema —
[Drizzle on D1](/cloudflare/data/d1-drizzle) walks through it
end-to-end.

## What a deploy does

```typescript
{
  out: string;          // migrations directory, cwd-relative
  snapshotHash: string; // sha256 of the latest snapshot.json
  migrations: string[]; // migration directory names, in order
}
```

On each deploy the resource diffs the schema module against the
latest snapshot and regenerates only when drizzle-kit would emit new
SQL — an unchanged schema is a noop, not an update (a regression test
in `Schema.test.ts` guards this: an unconditional update cascaded
into spurious `Neon.Branch` updates downstream). The attributes above
are what downstream consumers read: `out` is kept cwd-relative so
state stays portable across machines, and `snapshotHash` /
`migrations` let a `migrationsDir` consumer detect drift and reapply.

## Checked-in drizzle-kit output

`Drizzle.Schema` is optional. If you prefer to run
`drizzle-kit generate` yourself and commit the output, point
`migrationsDir` at the checked-in directory — the
[contract](/sql/migrations) only sees `.sql` files:

```typescript
const db = yield* Cloudflare.D1.Database("app-db", {
  migrationsDir: "./drizzle", // drizzle-kit's default out
});
```

This is the working path for MySQL today, where schema generation is
not wired through `Drizzle.Schema` — generate with
`drizzle-kit generate --dialect mysql` and check the files in.

## The migrations table

Drizzle's own migrator tracks applied files in a
`drizzle_migrations` table. D1's `migrationsTable` prop exists for
this compatibility:

```typescript
const db = yield* Cloudflare.D1.Database("app-db", {
  migrationsDir: schema.out,
  migrationsTable: "drizzle_migrations",
});
```

The tracking schema is wrangler-compatible
(`id, name, applied_at`), so moving between wrangler, drizzle-kit,
and alchemy does not re-apply history.

## Destroy never deletes migrations

The provider's `delete` operation is a deliberate no-op. Removing the
resource (or destroying the stack) never wipes the migrations
directory, because migration files are source code you commit, not
cloud state to tear down.

## Dialects

`postgres` is the default. `sqlite` is the D1 path — pass
`dialect: "sqlite"` and wire `schema.out` into
`Cloudflare.D1.Database`'s `migrationsDir`. `mysql` uses the
checked-in flow above. Application mechanics per provider are indexed
in the [migrationsDir contract](/sql/migrations#per-provider-notes).
