This page takes a project from one `alchemy.run.ts` to a layout that
scales, then shows the two ways to lay out a monorepo. The target shape
follows
[`examples/cloudflare-neon-drizzle`](https://github.com/alchemy-run/alchemy/tree/main/examples/cloudflare-neon-drizzle):

```sh
.
├── alchemy.run.ts          # composition root: stack, providers, state store, outputs
├── .alchemy/               # local state, gitignore it
├── src/
│   ├── Api.ts              # Worker declaration + runtime code
│   ├── Db.ts               # database unit: Schema + Project + Branch + Hyperdrive
│   ├── Photos.ts           # one-line resource
│   ├── Sandbox.ts          # Container class
│   ├── Sandbox.runtime.ts  # SandboxLive (.make())
│   └── schema.ts           # plain application code (Drizzle schema)
└── test/                   # tests mirror the src/ tree
    └── integ.test.ts       # deploys the stack, hits the live URL
```

Three rules produce this shape:

- Put each resource or layer in its own file.
- Group resources that change together.
- Keep `alchemy.run.ts` as the composition root.

## Start with one file

Everything in `alchemy.run.ts` is a good starting point:

```typescript
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Effect from "effect/Effect";

export const DB = Cloudflare.D1.Database("DB");

export const Bucket = Cloudflare.R2.Bucket("Bucket");

export const Worker = Cloudflare.Worker("Worker", {
  main: "./src/worker.ts",
  env: { DB, Bucket },
});

export default Alchemy.Stack(
  "CloudflareWorker",
  {
    providers: Cloudflare.providers(),
    state: Cloudflare.state(),
  },
  Effect.gen(function* () {
    const worker = yield* Worker;
    return { url: worker.url.as<string>() };
  }),
);
```

Split the file once it collects runtime code, stage logic, and a dozen
resources.

## Put each resource in its own file

A resource declaration is a value, so give it its own module. It stays
inert until a stack yields it, so importing the file deploys nothing.

```typescript
// src/Photos.ts
import * as Cloudflare from "alchemy/Cloudflare";

export const Photos = Cloudflare.R2.Bucket("Photos");
```

A Worker gets the same treatment. `main: import.meta.url` makes the file
its own entrypoint, so the declaration and the runtime code live together
with no separate `wrangler.toml`.

```typescript
// src/Api.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as Effect from "effect/Effect";

export default class Api extends Cloudflare.Worker<Api>()(
  "Api",
  { main: import.meta.url }, // this file is the Worker entry
  Effect.gen(function* () {
    return {
      fetch: Effect.gen(function* () {
        // handle requests
      }),
    };
  }),
) {}
```

Each layer also gets one file (see
[Layers](/infrastructure-as-effects/layers)). Containers take two files.
The class goes in `src/Sandbox.ts` and its `.make()` layer (`SandboxLive`)
goes in `src/Sandbox.runtime.ts`, so a Durable Object that imports the
class does not bundle the container runtime (see
[Run a Container](/cloudflare/compute/run-a-container)).

## Group resources by concern

Resources that share a lifecycle share a file. A migration touches the
schema, the project, and the branch, because `Drizzle.Schema` regenerates
the SQL and `Neon.Branch` applies it.

```typescript
// src/Db.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as Drizzle from "alchemy/Drizzle";
import * as Neon from "alchemy/Neon";
import * as Effect from "effect/Effect";

// A unit: an exported Effect that anything can build on.
export const NeonDb = Effect.gen(function* () {
  const schema = yield* Drizzle.Schema("app-schema", {
    schema: "./src/schema.ts",
    out: "./migrations",
  });
  const project = yield* Neon.Project("app-db", { region: "aws-us-east-1" });
  const branch = yield* Neon.Branch("app-branch", {
    project,
    migrations: schema, // Schema runs first, then Branch applies the SQL
  });
  return { project, branch, schema };
});

// A second unit that builds on the first.
export const Hyperdrive = Effect.gen(function* () {
  const { branch } = yield* NeonDb;
  return yield* Cloudflare.Hyperdrive.Connection("app-hyperdrive", {
    origin: branch.origin,
  });
});
```

Each unit is an Effect that other units and the stack can yield. Both
`Hyperdrive` and `alchemy.run.ts` yield `NeonDb`. Alchemy memoizes each
resource by its [logical ID](/infrastructure-as-code/resource#logical-id),
so it provisions the database once.

Stage-specific props also live next to the resource, read with
`yield* Alchemy.Stack` or
[`Stack.useSync`](/infrastructure-as-code/stack#stackusesync-for-module-scope-resources).

## Make `alchemy.run.ts` the composition root

With the units in `src/`, the root file names the stack, merges
providers, picks a state store, and wires units into outputs:

```typescript
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Drizzle from "alchemy/Drizzle";
import * as Neon from "alchemy/Neon";
import * as Effect from "effect/Effect";
import * as Layer from "effect/Layer";

import Api from "./src/Api.ts";
import { Hyperdrive, NeonDb } from "./src/Db.ts";

export default Alchemy.Stack(
  "CloudflareNeonDrizzleExample",
  {
    providers: Layer.mergeAll(
      Cloudflare.providers(),
      Drizzle.providers(),
      Neon.providers(),
    ),
    state: Alchemy.localState(), // writes .alchemy/
  },
  Effect.gen(function* () {
    const { branch } = yield* NeonDb;
    const hd = yield* Hyperdrive;
    const api = yield* Api;

    return {
      url: api.url.as<string>(),
      branchId: branch.branchId,
      hyperdriveId: hd.hyperdriveId,
    };
  }),
);
```

If `alchemy.run.ts` keeps growing, something is missing a home in `src/`.

The CLI loads `alchemy.run.ts` from the directory you run it in. Relative
paths in props resolve from that same directory, not from the file that
declares them.

```sh
alchemy deploy                          # ./alchemy.run.ts
alchemy deploy infra/app.ts             # another entrypoint, positionally
alchemy deploy --config infra/app.ts    # or with --config
```

Moving the entrypoint does not move relative paths. Anchor them with
`import.meta` when that matters (see
[Anchor every path](/project-structure/monorepo-single-stack#anchor-every-path)).

## Monorepos

A monorepo has a backend package and a frontend that calls it. You also
choose where the stacks live.

### One stack at the workspace root

```sh
.
├── package.json     # workspaces: ["frontend", "backend"]
├── alchemy.run.ts   # the one stack, deploys both packages
├── backend/         # Worker + API schema + typed client
└── frontend/        # React app, built by the stack
```

Both packages deploy in one plan. The frontend reads the Worker's URL
from the in-memory Output, so you need no references and no deploy
order. See [Deploy a monorepo with one stack](/project-structure/monorepo-single-stack).

### One stack per package

```sh
.
├── package.json           # workspaces: ["frontend", "backend"]
├── backend/
│   ├── alchemy.run.ts     # Backend stack
│   └── src/Stack.ts       # typed handle the frontend imports
└── frontend/
    └── alchemy.run.ts     # Frontend stack, yield* Backend
```

The frontend reads the backend's deployed outputs through a typed
cross-stack reference. Each package deploys and destroys on its own. See
[Deploy a monorepo with many stacks](/project-structure/monorepo-multi-stack).

### Choose a layout

- **One stack**: start here. It has one plan, one state file, and no
  ordering constraints.
- **One stack per package**: use it when packages deploy on different
  cadences, such as different teams or different CI. Also use it when the
  backend has consumers beyond this frontend, or when you need to
  `destroy` one package without touching the other.
