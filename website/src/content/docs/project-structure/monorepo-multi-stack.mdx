This guide gives each package its own `alchemy.run.ts` and connects them
with a typed stack handle. It follows
[`examples/monorepo-multi-stack`](https://github.com/alchemy-run/alchemy/tree/main/examples/monorepo-multi-stack):

```sh
.
├── package.json           # workspaces: ["frontend", "backend"]
├── backend/
│   ├── alchemy.run.ts     # Backend stack, deploys the Worker
│   ├── package.json       # name: "backend", exports "." → src/index.ts
│   └── src/
│       ├── index.ts       # re-exports Stack.ts (plus the typed client)
│       ├── Service.ts     # the Worker
│       └── Stack.ts       # typed handle, outputs { url: string }
└── frontend/
    ├── alchemy.run.ts     # Frontend stack, references Backend
    ├── package.json       # depends on "backend": "workspace:*"
    └── src/
        └── main.tsx       # reads import.meta.env.VITE_API_URL
```

The stacks share no plan. The backend persists its outputs to the
[state store](/state-store), and the frontend's plan reads them back. Each
stack deploys, destroys, and runs in CI on its own, but they must deploy
in order.

To deploy everything in one plan instead, see
[Deploy a monorepo with one stack](/project-structure/monorepo-single-stack).

## Define the typed stack handle

The handle is the contract between the two stacks. It names the stack and
declares its output shape:

```typescript
// backend/src/Stack.ts
import * as Alchemy from "alchemy";

export class Backend extends Alchemy.Stack<
  Backend,
  {
    url: string;
  }
>()("Backend") {}
```

Both sides import this class. The backend deploys under its name, and the
frontend gets typed outputs from it. Keep the handle in its own file that
imports only `alchemy`, because importing `backend/alchemy.run.ts` would
pull the backend's Worker and resources into the frontend's program.

## Deploy the backend stack

`Backend.make` is `Alchemy.Stack` bound to the handle's name:

```typescript
// backend/alchemy.run.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as Effect from "effect/Effect";
import Service from "./src/Service.ts";
import { Backend } from "./src/Stack.ts";

export default Backend.make(
  {
    providers: Cloudflare.providers(),
    state: Cloudflare.state(),
  },
  Effect.gen(function* () {
    const api = yield* Service;
    return {
      // Not checked against the handle's { url: string }. Keep them in sync.
      url: api.url.as<string>(),
    };
  }),
);
```

On deploy, Alchemy persists the resolved `url` to the state store as the
stack's output.

## Export the handle

The frontend imports the handle from the backend package like any other
workspace export. Two package fields make `import { Backend } from "backend"`
resolve:

- `frontend/package.json` depends on `"backend": "workspace:*"`.
- `backend/package.json` maps `exports["."]` to `./src/index.ts`, which
  re-exports `Stack.ts`.

## Reference the backend from the frontend

`yield* Backend` reads the backend's persisted outputs from the state
store at plan time:

```typescript
// frontend/alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import { Backend } from "backend";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "Frontend",
  {
    providers: Cloudflare.providers(),
    state: Cloudflare.state(), // must be the backend's store
  },
  Effect.gen(function* () {
    const backend = yield* Backend; // same stage as this deploy

    const website = yield* Cloudflare.Website.Vite("Website", {
      env: {
        VITE_API_URL: backend.url, // Output<string>
      },
    });

    return {
      url: website.url.as<string>(),
    };
  }),
);
```

The fields of `backend` are Outputs, so pass them to props like any other
[Output](/infrastructure-as-code/outputs). The reference resolves the
stage the frontend deploys to, so the `sam` frontend reads the `sam`
backend and `pr-42` reads `pr-42`.

:::caution
Both stacks must use the same state store, because the frontend reads the
backend's outputs through its own `state` layer. `Alchemy.localState()`
writes to `.alchemy/state` in the directory you run `alchemy` from, so
running from each package gives each package its own store. The
frontend's plan then fails with `InvalidReferenceError` (see
[State Store](/state-store)).
:::

## Deploy in order

Deploy the backend to the stage first, then the frontend:

<Tabs syncKey="pkgManager">
  <TabItem label="bun" icon="bun">
    <Code code={"cd backend && bun alchemy deploy --stage sam\ncd ../frontend && bun alchemy deploy --stage sam"} lang="sh" />
  </TabItem>
  <TabItem label="npm" icon="npm">
    <Code code={"cd backend && npx alchemy deploy --stage sam\ncd ../frontend && npx alchemy deploy --stage sam"} lang="sh" />
  </TabItem>
  <TabItem label="pnpm" icon="pnpm">
    <Code code={"cd backend && pnpm alchemy deploy --stage sam\ncd ../frontend && pnpm alchemy deploy --stage sam"} lang="sh" />
  </TabItem>
  <TabItem label="yarn" icon="seti:yarn">
    <Code code={"cd backend && yarn alchemy deploy --stage sam\ncd ../frontend && yarn alchemy deploy --stage sam"} lang="sh" />
  </TabItem>
</Tabs>

Without a backend deploy on that stage, the frontend's plan fails with
`InvalidReferenceError` because there are no persisted outputs to read.
Destroy in reverse order, frontend first.

Relative paths such as `main` and `rootDir` resolve against the directory
you run `alchemy` from. From the workspace root
(`alchemy deploy backend/alchemy.run.ts`) they resolve from the root, so
anchor them as in
[Anchor every path](/project-structure/monorepo-single-stack#anchor-every-path).

## Pin to a specific stage

The bare `yield* Backend` reads the same stage on both sides and is the
right default. To point every frontend preview at the production backend,
pin the stage:

```diff lang="typescript"
   Effect.gen(function* () {
-    const backend = yield* Backend;
+    const backend = yield* Backend.stage.prod;
     // ...
   })
```

`Backend.stage` is a proxy keyed by stage name, so any string works, such
as `Backend.stage.staging` or `Backend.stage["pr-42"]`.
