---
title: Secrets & Config
description: Use effect/Config to read env vars at Construction time and have Alchemy automatically bind them onto the deploy target.

Alchemy integrates with [effect/Config](https://effect.website/docs/configuration)
to automatically bind env vars to your Worker or Lambda environment ([Runtime](/infrastructure-as-effects/runtime)).
Bound values come from the env of whoever runs the deploy, so they naturally
vary per [stage](/environments/stages) and [profile](/environments/profiles).

## Build a secret-manager integration

Alchemy secret managers are ordinary Effect layers that provide the public
`SecretManager` service. The resolver receives only the Alchemy stack name and
optional concrete stage, and returns an Effect `ConfigProvider`:

```typescript
import {
  SecretManager,
  SecretManagerError,
  type SecretManagerLayer,
  type SecretManagerService,
} from "alchemy";
import * as ConfigProvider from "effect/ConfigProvider";
import * as Effect from "effect/Effect";
import * as Layer from "effect/Layer";

const service: SecretManagerService = {
  name: "Acme Secrets",
  resolve: ({ stack, stage }) =>
    Effect.tryPromise({
      try: async () => {
        const values = await loadAcmeSecretSet({ stack, stage });
        return ConfigProvider.fromUnknown(values);
      },
      catch: (cause) =>
        new SecretManagerError({
          manager: "Acme Secrets",
          message: `Could not load secrets for stack '${stack}'.`,
          cause,
        }),
    }),
};

export const secrets = (): SecretManagerLayer =>
  Layer.succeed(SecretManager, service);
```

`Layer.succeed` is appropriate when constructing the service itself is
synchronous and its remote work happens in `resolve`. Integrations that need an
Effectful or scoped service lifecycle can use `Layer.effect` or `Layer.scoped`
instead. This is the standard Effect service/layer model; integrations do not
need access to Alchemy's stack-session or CLI internals.

Applications consume an external integration through its domain-level layer
factory. For example, if the implementation above were published as
`@acme/alchemy-secrets`:

```typescript
import * as Alchemy from "alchemy";
import * as Acme from "@acme/alchemy-secrets";

export default Alchemy.Stack("app", {
  secrets: Acme.secrets(),
});
```

Alchemy's default configuration is available through Effect `Config` while
`resolve` runs, so an integration can read the bootstrap credentials it needs.
Alchemy then composes the returned provider over that default provider. Keep
provider-specific selection, authentication, validation, and private runtime
metadata inside the integration package.

## Validate and load secrets with Varlock

[Varlock](https://varlock.dev) can resolve and validate a stack's configuration
before Alchemy builds its providers, state store, or resources. Install it in
your project and add its secret-manager layer to the Stack:

```sh
pnpm add varlock
```

```typescript
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Varlock from "alchemy/Varlock";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "App",
  {
    providers: Cloudflare.providers(),
    state: Cloudflare.state(),
    secrets: Varlock.secrets(),
  },
  Effect.gen(function* () {
    const apiKey = yield* Config.redacted("API_KEY");
    // Declare resources that use apiKey...
  }),
);
```

Application code still reads values through Effect `Config`. Use
`Config.redacted` for secrets so the value remains protected in local values
and diagnostics; Alchemy will bind any Config value captured during
Construction as a platform secret as described below.

### Select Varlock environments from Alchemy stacks and stages

Alchemy exposes the stack name as `ALCHEMY_STACK` and the concrete deployment
stage as `ALCHEMY_STAGE` while Varlock resolves the environment. Point
Varlock's `@currentEnv` at the stage and use either value in the schema:

```dotenv
# @currentEnv=$ALCHEMY_STAGE
# ---
ALCHEMY_STACK=
ALCHEMY_STAGE=

# @sensitive
API_KEY=
```

An `alchemy deploy --stage production` then selects `.env.production` and
`.env.production.local` using Varlock's normal rules. See Varlock's
[environment guide](https://varlock.dev/guides/environments/) for its process
variable precedence and environment-file selection. Commands that inspect a
project without selecting a stack stage leave Varlock's native environment
selection unchanged.

Varlock-resolved values take precedence. The existing process, `.env`, or
`--env-file` configuration is used only when the post-Varlock environment does
not contain the requested key. Explicit profile selection remains the final
override for Alchemy's profile configuration. Without a `secrets` layer,
Alchemy's existing configuration precedence is unchanged.

Alchemy passes both the stack name and the optional concrete stage to the
configured secret manager. Secret-manager implementations may apply their own
selection rules using either value; applications still receive the result as
an Effect `ConfigProvider`.

:::warning[Deploy-time integration]
This integration loads and validates secrets for the Alchemy process. It does
not install Varlock's global console patch, response leak scanner, or private
`__VARLOCK_ENV` binding in deployed Workers. Continue to use `Config.redacted`
and Alchemy's normal runtime bindings. Varlock does not yet expose the public
binding producer that non-Wrangler deployment tools need for its in-Worker
runtime protections.

See Varlock's
[non-Wrangler Cloudflare guidance](https://varlock.dev/integrations/cloudflare/#non-wrangler-deploy-tools-alchemy-sst-pulumi)
and the upstream
[public binding API request](https://github.com/dmno-dev/varlock/issues/735).
:::

Secret managers run after the stack module has been imported. Read Config
inside Effects and Layers, not by eagerly executing a Config effect at module
scope.

## Load secrets from Doppler

Alchemy can download a Doppler config directly through Doppler's HTTPS API; no
Doppler CLI or additional package is required. Provide `DOPPLER_TOKEN` through
Alchemy's default configuration (`process.env`, `.env`, or `--env-file`). The
default provider is available through Effect `Config` while a secret manager
resolves, and Alchemy composes it underneath the returned provider afterward.
Prefer a read-only, config-scoped
[service token](https://docs.doppler.com/docs/service-tokens) for deployment:

```typescript
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Doppler from "alchemy/Doppler";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "App",
  {
    providers: Cloudflare.providers(),
    state: Cloudflare.state(),
    secrets: Doppler.secrets(),
  },
  Effect.gen(function* () {
    const apiKey = yield* Config.redacted("API_KEY");
    // Declare resources that use apiKey...
  }),
);
```

A config-scoped service token already identifies its project and config. For
tokens that can access multiple configs, map the Alchemy stack and stage
explicitly:

```typescript
secrets: Doppler.secrets(({ stack, stage }) => ({
  project: stack,
  config: stage ?? "dev",
}));
```

Doppler values take precedence over the original Alchemy provider, which
remains available as fallback. Download, authentication, selector, and payload
failures surface as `SecretManagerError`. See Doppler's
[secrets download API](https://docs.doppler.com/reference/secrets-download)
for the underlying endpoint.

## Load secrets from Infisical

Map each Alchemy stack and stage to an Infisical project, environment, and
folder. The adapter uses Infisical's HTTPS API directly, so it does not require
the Infisical CLI or an additional package:

```typescript
import * as Alchemy from "alchemy";
import * as Infisical from "alchemy/Infisical";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "App",
  {
    secrets: Infisical.secrets(({ stack, stage }) => ({
      projectId: "00000000-0000-0000-0000-000000000000",
      environment: stage ?? "dev",
      secretPath: `/${stack}`,
    })),
  },
  Effect.gen(function* () {
    const apiKey = yield* Config.redacted("API_KEY");
    // Declare resources that use apiKey...
  }),
);
```

Provide either `INFISICAL_TOKEN`, or a Universal Auth machine identity through
`INFISICAL_UNIVERSAL_AUTH_CLIENT_ID` and
`INFISICAL_UNIVERSAL_AUTH_CLIENT_SECRET`. An existing access token takes
precedence. `INFISICAL_AUTH_ORGANIZATION_SLUG` optionally scopes Universal Auth
to a sub-organization. For EU Cloud or a self-hosted instance, set
`INFISICAL_API_URL`; the default is Infisical US Cloud.

Imported secrets are included by default, with secrets in the selected folder
taking precedence over imported values. The selector can also control folder
recursion, secret-reference expansion, personal overrides, and imported-secret
inclusion. Infisical values take precedence over Alchemy's original provider,
which remains available as fallback. Authentication, selector, download, and
payload failures surface as `SecretManagerError`. See Infisical's
[Universal Auth login](https://infisical.com/docs/api-reference/endpoints/universal-auth/login)
and [list-secrets API](https://infisical.com/docs/api-reference/endpoints/secrets/list).

## Load secrets from AWS Secrets Manager

Treat one AWS secret as the configuration set for a stack instance. Its
`SecretString` must be a JSON object with string values:

```json
{
  "API_KEY": "secret-value",
  "DATABASE_URL": "postgres://..."
}
```

Map the Alchemy stack and stage to the secret's name or ARN:

```typescript
import * as Alchemy from "alchemy";
import * as AWS from "alchemy/AWS";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "App",
  {
    secrets: AWS.SecretsManager.secrets(({ stack, stage }) => ({
      secretId: `${stack}/${stage ?? "dev"}`,
      region: "us-east-1",
    })),
  },
  Effect.gen(function* () {
    const apiKey = yield* Config.redacted("API_KEY");
    // Declare resources that use apiKey...
  }),
);
```

The selector can return a secret name or ARN directly, or an object containing
`secretId` with optional `region`, `versionId`, and `versionStage` fields. The
selected region takes precedence over `AWS_REGION` and `AWS_DEFAULT_REGION`.

Complete static credentials from Alchemy's default configuration are supported
through `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and the optional
`AWS_SESSION_TOKEN`. Otherwise, the adapter uses the standard Node.js AWS
credential chain, including shared AWS profiles, IAM Identity Center, container
credentials, and instance-role credentials. The identity needs
`secretsmanager:GetSecretValue`; secrets encrypted with a customer-managed KMS
key also require `kms:Decrypt`.

Binary secrets are rejected, as are JSON values that are not flat objects of
strings. AWS values take precedence over Alchemy's original provider, which
remains available as fallback. Selection, authentication, AWS API, and payload
failures surface as `SecretManagerError`. See AWS's
[GetSecretValue API](https://docs.aws.amazon.com/secretsmanager/latest/apireference/API_GetSecretValue.html)
and [credential provider chain](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/setting-credentials-node.html).

## Bind a secret to your Worker

Any `Config` value that is evaluated with `yield*` in the [Construction phase](/infrastructure-as-effects/phases)
of (for example) a Worker, is automatically bound to its environment
at deploy time. It is always bound as a secret (`secret_text` on
Cloudflare) regardless of which `Config` constructor you use.

```typescript
import * as Cloudflare from "alchemy/Cloudflare";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";
import * as Redacted from "effect/Redacted";

export default Cloudflare.Worker(
  "Worker",
  { main: import.meta.url },
  Effect.gen(function* () {
    const apiKey = yield* Config.redacted("API_KEY"); 
    // apiKey is Redacted<string> — usable here in Construction AND captured as a binding

    return {
      fetch: Effect.gen(function* () {
        return new Response(`Bearer ${Redacted.value(apiKey)}`);
      }),
    };
  }),
);
```

:::tip
See [Phases](/infrastructure-as-effects/phases) for why Construction and Runtime run separately.
:::

## Use the value during Construction

Unlike an [Output](/infrastructure-as-code/outputs), the value can be used immediately
within the Construction phase. For example, to initialize a client:

```typescript
export default Cloudflare.Worker(
  "Worker",
  { main: import.meta.url },
  Effect.gen(function* () {
    const apiKey = yield* Config.redacted("OPENAI_API_KEY");
    const client = createOpenAI(Redacted.value(apiKey));

    return {
      fetch: Effect.gen(function* () {
        const reply = yield* Effect.tryPromise(() => client.chat(/* ... */));
        return new Response(reply);
      }),
    };
  }),
);
```


## Transformations

Any combinator works — `withDefault`, `orElse`, `mapAttempt`, and so
on. What gets bound is the *source* value (the raw env var), not the
transformed result; the combinators run again at runtime against that
source.

```typescript
const port = yield* Config.number("PORT").pipe(
  Config.withDefault(3000),
);
```

- If `PORT` is set, its raw value is bound. At runtime `Config.number("PORT")`
  reads it from the binding and the combinators re-apply.
- If `PORT` is not set, nothing is bound. At runtime the source is
  still empty and `Config.withDefault(3000)` produces `3000` again.

Because a default is never bound, its code runs in both phases — keep
it deterministic, so both phases evaluate to the same value.

## Footgun: don't `yield*` Config at runtime

If you only `yield*` the `Config` in `fetch`, it will not be bound to the environment
because `fetch` does not run during deployment, so the engine never discovers it.

```typescript
export default Cloudflare.Worker(
  "Worker",
  { main: import.meta.url },
  Effect.gen(function* () {
    return {
      fetch: Effect.gen(function* () {
        // 🚫 nothing is bound to the Worker — API_KEY won't exist at runtime
        const apiKey = yield* Config.redacted("API_KEY");
        // ...
      }),
    };
  }),
);
```

Always resolve the `Config` in the outer `Effect.gen` (Construction) — even
if you only need the value inside `fetch`. Capture it in a `const`,
and reference that `const` from the runtime body:

```typescript
// ✅ bound in Construction, used in Runtime
Effect.gen(function* () {
  const apiKey = yield* Config.redacted("API_KEY");
  return {
    fetch: Effect.gen(function* () {
      return new Response(Redacted.value(apiKey));
    }),
  };
});
```

Once a `Config` has been resolved during Construction, re-yielding the same
`Config` anywhere at runtime — inside `fetch`, deep in a nested
effect, or in a service layer — resolves it from the binding and
produces the same value.

## Async Workers — bind via `env`

Async (non-Effect) Workers don't have a constructor `Effect.gen` to
`yield*` into, so you put the `Config` on the resource's `env`
prop instead. Alchemy resolves each `Config` at deploy time and
records the appropriate binding — same end result as the `yield*`
form, just declared statically:

```typescript
// alchemy.run.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as Config from "effect/Config";

export const Worker = Cloudflare.Worker("Worker", {
  main: "./src/worker.ts",
  env: {
    API_KEY: Config.redacted("API_KEY"),
    HOST:    Config.string("HOST"),
    Bucket, // resource references work the same
  },
});

export type WorkerEnv = Cloudflare.InferEnv<typeof Worker>;
```

```typescript
// src/worker.ts
import type { WorkerEnv } from "../alchemy.run.ts";

export default {
  async fetch(request: Request, env: WorkerEnv) {
    return new Response(`Bearer ${env.API_KEY}`);
  },
};
```

`env.API_KEY` is the resolved string at runtime — Cloudflare hands
the `secret_text` value to the async handler directly, no
`Redacted.value` unwrap. The always-binds-as-secret rule and
transformation semantics from the previous sections still apply.

For the step-by-step "wire up `OPENAI_API_KEY` from `.env`" walk,
see [Secrets & env on Cloudflare](/cloudflare/security/secrets-env) or
[on AWS](/aws/security/secrets-env).
