title: Secret providers
description: Tell a Stack where its configuration comes from — dotenv files, Doppler, Infisical — in what order, and what shape it must have.
---

Every `Config.String("DATABASE_URL")` a stack reads has to come from
somewhere. By default that somewhere is a `.env` file next to your
stack, plus whatever is in the shell. The `secrets` option lets you
say more: read several sources in order, pull them from a secrets
manager, pick different sources per [stage](/environments/stages),
and declare the shape the result must have before a single resource
is touched.

```typescript
export default Alchemy.Stack(
  "MyApp",
  {
    providers: Cloudflare.providers(),
    state: Cloudflare.state(),
    secrets: {
      providers: [Alchemy.Secrets.DotEnv()],
    },
  },
  Effect.gen(function* () {
    const dbUrl = yield* Config.Redacted("DATABASE_URL");
    // ...
  }),
);
```

`secrets.providers` is an ordered list of sources. Leave `secrets`
out entirely and you get `[Secrets.DotEnv()]`, which is why a plain
`.env` works with no configuration at all.

## Precedence

Values are layered so that the most deliberate source wins:

1. Command-line flags: `--env-file` and `--profile`.
2. The process environment. A variable exported in your shell or set
   by CI beats every provider, always.
3. The last provider in the list.
4. ... down to the first provider.

Think of the list as base-to-override, the way you would order
`.env` then `.env.production`. This ordering is also why a provider
can depend on an earlier one: each provider is built with the
configuration assembled so far, so a Doppler layer can read
`DOPPLER_TOKEN` from a dotenv layer placed before it.

The process environment sitting above everything is deliberate. It
means a one-off `DATABASE_URL=... alchemy deploy` works exactly as you
would expect, and a CI runner never has to fight a file that was
committed by mistake.

When that is the wrong trade, for instance a production deploy that
must use exactly what the secrets manager holds, set
`processEnv: false` and the shell is not consulted at all. Auth
providers read CI credentials such as `CLOUDFLARE_API_TOKEN` through
the same configuration, so CI still needs the environment somewhere;
list `Secrets.ProcessEnv()` as the first provider to keep it as a
fallback that any later provider overrides:

```typescript
secrets: {
  processEnv: false,
  providers: [
    Alchemy.Secrets.ProcessEnv(),
    Alchemy.Secrets.Doppler({ project: "my-app", config: "prd" }),
  ],
},
```

Command-line flags keep their place at the top either way.

## Sources per stage

A provider accepts either plain options or an Effect that produces
them. The Effect runs with the [Stage](/environments/stages) in
scope, which is how one stack definition serves `dev`, `pr-42`, and
`prod` from different places:

```typescript
secrets: {
  providers: [
    Alchemy.Secrets.DotEnv(
      Effect.gen(function* () {
        const stage = yield* Stage;
        return { path: [".env", `.env.${stage}`] };
      }),
    ),
  ],
},
```

The same shape works for [Doppler](/environments/doppler) and
[Infisical](/environments/infisical), where the stage usually selects
a config or an environment rather than a file.

## Declare a schema

Missing configuration is best discovered before a deploy starts, not
half-way through when a Worker binding fails to resolve. Give
`secrets.schema` an [Effect Schema](https://effect.website/docs/schema/introduction/)
and Alchemy validates the assembled configuration against it once
every provider has loaded:

```typescript
secrets: {
  providers: [Alchemy.Secrets.DotEnv()],
  schema: Schema.Struct({
    DATABASE_URL: Schema.Redacted(Schema.String),
    PORT: Schema.Int,
    SENTRY_DSN: Schema.optional(Schema.String),
  }),
},
```

A key that is absent or fails to decode stops the stack with a
`ConfigError` naming the offending key. The schema is optional: with
none declared, each `Config` value is checked where it is read, as
before. Anything
[`Config.schema`](https://effect.website/docs/configuration/) accepts
works here, including nested structs, so a schema can grow with the
project instead of being rewritten.

## Dotenv details

`Secrets.DotEnv` reads one file or an ordered list, later files
overriding earlier ones. The implicit default `.env` may be absent;
a file you name explicitly must exist, and a missing one fails the
stack with its path in the message. Empty values are real values and
override earlier files, which is how `.env.test` can blank out a key
from `.env`. Pass `expandVariables: true` to expand `${OTHER}`
references inside a file.

Nothing is written to `process.env`. The values live in Effect's
[ConfigProvider](https://effect.website/docs/configuration/), so
two stacks in one process, or two stages deployed concurrently, never
see each other's files.

`--env-file` on the command line is honoured whether or not the
stack declares providers. When it declares none, that file replaces
`.env` as the implicit default; when it does, the file is layered on
top as a command-line override.

## Seeing what loaded

Run any command with `--log-level debug` and each provider reports
the variable names it contributed, never their values:

```text
Loaded 3 secrets from dotenv (.env, .env.prod): DATABASE_URL, PORT, SENTRY_DSN
Loaded 12 secrets from Doppler (project 'app' config 'prd'): API_KEY, DATABASE_URL, ...
Stack secrets satisfy the declared schema
```

This is the first place to look when a value is not what you
expected. Because sources are listed in order, the last line that
mentions a key is the provider whose value won, unless the shell had
it set.

## Bring your own source

A provider is any Effect `Layer` that provides a `ConfigProvider`, so
anything from `ConfigProvider.fromUnknown` to a custom client fits in
the list without an adapter:

```typescript
secrets: {
  providers: [
    ConfigProvider.layer(ConfigProvider.fromUnknown(defaults)),
    Alchemy.Secrets.DotEnv(),
  ],
},
```

The built-in providers follow one convention worth copying: they log
their keys at debug level, fail with a message that names the source,
and do nothing during
[auth-provider discovery](/environments/auth-providers), which
builds the stack just to find out which clouds it uses and must work
offline.
