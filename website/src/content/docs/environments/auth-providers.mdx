Resources never take API keys as props. Each cloud registers an
**auth provider**, the service that turns a stored login into live
credentials whenever lifecycle code calls the cloud. Read this page to
understand how credentials resolve and refresh, or before you
[build your own](/environments/custom-auth-provider).

## Where credentials come from

Each cloud's `providers()` layer bridges its auth provider to a
credentials service with a `fromProfile` or `fromAuthProvider` layer:

```typescript
// alchemy/Cloudflare/CloudflareEnvironment
export const fromProfile = () =>
  Layer.effect(
    CloudflareEnvironment,
    Effect.gen(function* () {
      const { resolve } = yield* resolveProviderConfig<
        CloudflareAuthConfig,
        CloudflareResolvedCredentials
      >(CLOUDFLARE_AUTH_PROVIDER_NAME);
      return yield* resolve.pipe(Effect.orDie, Effect.cached);
    }),
  );
```

`resolveProviderConfig` picks one of two sources per provider:

- **The environment**: when `CI=true`, or when every required variable
  in the provider's contract is set, Alchemy calls the provider's
  `readEnvironment`. It never creates or touches a profile. See
  [Profiles › Environment variables outside CI](/environments/profiles#environment-variables-outside-ci)
  and [CLI › provider](/cli/provider) for each provider's variables.
- **The selected profile**: otherwise Alchemy loads the provider's
  stored document from the [profile](/environments/profiles#where-profiles-live)
  and calls the provider's `read`. An unconfigured provider fails with
  the exact `alchemy profile edit` command to run. Resolution never
  starts a login flow.

## Credentials are lazy Effects

Nothing in Alchemy holds credentials as a plain value. Each cloud's
environment service is a `Context.Service` whose value is itself an
Effect:

```typescript
// alchemy/Cloudflare/CloudflareEnvironment
export class CloudflareEnvironment extends Context.Service<
  CloudflareEnvironment,
  Effect.Effect<CloudflareResolvedCredentials>
>()("Cloudflare::CloudflareEnvironment") {}

// alchemy/AWS/Environment goes one level deeper, so expiring SSO and
// assumed-role sessions re-resolve on each access
export interface AWSEnvironmentShape {
  accountId: AccountID;
  region: RegionID;
  credentials: Effect.Effect<ResolvedCredentials, CredentialsError>;
  // ...
}
```

Provider layers build on every CLI invocation, possibly before a
profile exists, so a layer can't bake in a resolved key. An Effect
resolves at the point of use and can carry its own refresh logic, so an
OAuth token or IAM role session renews itself.

## What lifecycle code yields

Inside `reconcile`, `read`, or `delete`, a handler yields the
environment twice. The first `yield*` gets the Effect out of the
service, and the second runs it.

```typescript
// Cloudflare
const { accountId } = yield* yield* CloudflareEnvironment;

// AWS: AWSEnvironment.current does the double yield for you
const { accountId, region } = yield* AWSEnvironment.current;
```

Most handlers never touch credentials directly. They call distilled SDK
operations, which require the SDK's `Credentials` service. That service
is also a lazy Effect, and the distilled HTTP client re-runs it on every
request, so refresh logic runs per request.

## Refresh, write-back, and locking

Cloudflare's OAuth method shows why `read` is an Effect. Every resolve
checks expiry, refreshes early, and writes the new token back:

```typescript
// alchemy/Cloudflare/Auth/AuthProvider, inside read (method: "oauth")
const now = yield* Clock.currentTimeMillis;
const fresh =
  creds.expires > now + 10_000
    ? creds
    : yield* OAuthClient.refresh(creds).pipe(
        // a failed refresh becomes NeedsReauth ("needs re-login" in the UI)
        Effect.mapError((e) => new NeedsReauth({ /* ... */ cause: e })),
      );
if (fresh !== creds) {
  // persist the refreshed token to the profile
  yield* (updateConfig?.({ method: "oauth", /* ... */ }) ?? Effect.void);
}
```

- **Write-back**: Alchemy passes `updateConfig` to `read`, so refreshed
  tokens land in the profile.
- **Never prompt**: `read` fails with `NeedsReauth` instead of starting
  a login. `alchemy profile refresh` runs the login or refresh without
  changing the method, and `profile edit --reconfigure` changes it.
- **Locking**: `read`, `details`, and `logout` run under a
  cross-process file lock, so two concurrent deploys can't double-spend
  a single-use refresh token. `configure` and `login` stay outside the
  lock because a browser grant can take minutes. A login that silently
  refreshes a rotate-on-use token takes the lock itself around that step.
- **Serialized prompts**: interactive flows run one at a time, so
  prompts from different providers don't interleave.
- **Once per process**: `fromProfile` wraps resolution in
  `Effect.cached`, so the profile-level `read` runs once. Ongoing
  refresh happens inside the credential Effects the SDKs re-run.

## The provider interface

An auth provider implements `AuthProviderImpl` and registers by name in
the `AuthProviders` registry through `AuthProviderLayer`. `alchemy profile edit`
reads that registry to run each provider's `configure` and `login`. See
[`Auth/AuthProvider.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Auth/AuthProvider.ts)
for every method and its contract.
