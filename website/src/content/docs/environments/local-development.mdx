`alchemy dev` runs your stack on your machine. Your compute runs
locally, the services around it are emulated, and code changes hot
reload in milliseconds. `Alchemy.remote()` runs any resource against
the real cloud when you need it.

This page covers the concepts shared by every cloud. For what each
cloud emulates, see its guide:

- **[Cloudflare local development](/cloudflare/local-development)**:
  Workers run in workerd. Simulators cover KV, R2, D1, Queues,
  Hyperdrive, Workflows, Containers, and the Worker binding surface,
  such as browser rendering, images, email, cron, and Stream.
- **[AWS local development](/aws/local-development)**: Lambda and ECS
  run in Docker containers with close to 40 emulated services, such as
  S3, DynamoDB, SQS, SNS, EventBridge, and API Gateway. No AWS account
  is required.

## How it works

```sh
alchemy dev
```

Three things happen:

1. **Emulatable services run locally.** Resources whose provider
   ships a local implementation are created as local simulators. No
   cloud calls are made.
2. **Your code runs locally.** Workers execute in workerd, Lambda
   functions and ECS tasks run in Docker containers, and websites run
   on their framework's own dev server. Bindings are wired to the
   local simulators, and logs and stack traces come straight from the
   local process.
3. **File changes hot reload.** When you edit your code, the running
   compute swaps in the new code without a redeploy.

Resources whose provider has no local implementation deploy to the
real cloud, in the [`dev_$USER` stage](/environments/stages) by
default. That stage is separate from the `live_$USER` stage of
`alchemy deploy`, so a bare `alchemy dev` cannot replace a stage you
deployed.

```sh
alchemy destroy --stage dev_$USER   # tear down the local-dev stage
```

Code changes take effect in milliseconds. Resources stay running
across reloads, and only your application code is rebuilt.

Any process with a dev server, such as Vite or Next, can join the loop
through [Command.Dev](/command/dev-servers). `alchemy dev` starts it and
restarts it when its inputs change. On deploy it is a no-op.

## Local by default, live on demand

In dev, emulatable resources run as simulators, and every other
resource runs live. A local resource's id starts with `dev:`, which
proves that no cloud call ran.

Node-side capability clients use the same simulators as your compute.
A seed script in an [Action](/infrastructure-as-code/action) that
writes to a `dev:` KV Namespace or S3 bucket writes to the same
simulator your Worker or Lambda reads.

### Running a resource live in dev

`Alchemy.remote()` opts a resource, or a whole scope, out of local
emulation:

```typescript
import * as Alchemy from "alchemy";

// One resource
const worker = yield* Worker("Api", { ... }).pipe(Alchemy.remote());

// A whole scope. Captured at registration, like adopt().
yield* Effect.gen(function* () {
  const api = yield* Worker("Api", { ... });
  const site = yield* Worker("Site", { ... });
}).pipe(Alchemy.remote());
```

`remote()` is a no-op during `alchemy deploy`, and on resources with
no local emulation. If a remote resource needs credentials you don't
have, `alchemy dev` tells you before it touches anything.

Local and live resources combine into hybrid topologies. For example,
a local Worker can produce into a live queue whose local consumer
drains it, or a local Lambda can read a live Secrets Manager secret.
See the per-cloud guides for examples.

### Switching is a replacement

A resource moves between local and live when you deploy after a dev
session, or when you add or remove `remote()`. The engine plans that
move as a replacement. It creates the new instance live, then tears
down the local one (the workerd instance, the Docker container, or
the dev process), so dev state never becomes cloud state.

## Dev vs deploy

- **Emulatable services**: local simulators in `alchemy dev`
  (`remote()` for live), deployed to the cloud by `alchemy deploy`.
- **Everything else**: deployed to the cloud in both, to your
  personal `dev_$USER` stage in dev.
- **Application code**: runs locally in workerd or Docker in dev,
  deployed to the cloud by deploy.
- **File watching**: hot reload on change in dev, manual redeploy
  otherwise.
- **Debugging**: local logs and stack traces in dev, tailed logs
  after a deploy.
- **Speed**: milliseconds in dev, seconds to minutes for a deploy.

To automate the deploy side, see [CI](/environments/ci).
