`alchemy dev` runs your stack on your machine. Your compute runs
locally (Workers in workerd, Lambda and ECS in Docker
containers). The services around it are emulated, and code
changes hot reload in milliseconds. `Alchemy.remote()` runs any
resource against the real cloud when you need it.

This page covers the concepts shared by every cloud. For what
each cloud emulates and how, see the dedicated guides:

- **[Cloudflare local development](/cloudflare/local-development)**:
  Workers run in workerd. Simulators cover KV, R2, D1, Queues,
  Hyperdrive, Workflows, Containers, and the Worker binding
  surface (browser rendering, images, email, cron, Stream, …).
- **[AWS local development](/aws/local-development)**: Lambda
  and ECS run in Docker containers with close to 40 emulated
  services (S3, DynamoDB, SQS, SNS, EventBridge, API Gateway, …).
  No AWS account is required.

## How it works

```sh
alchemy dev
```

Three things happen:

1. **Emulatable services run locally.** Resources whose provider
   ships a local implementation are created as local simulators
   with `dev:`-prefixed ids. No cloud calls are made.
2. **Your code runs locally.** Workers execute in workerd,
   Lambda functions and ECS tasks run in Docker containers, and
   websites run on their framework's own dev server. Bindings are
   wired to the local simulators.
3. **File changes hot reload.** When you edit your code, the
   running compute swaps in the new code without a redeploy.

Resources whose provider has no local implementation deploy to
the real cloud. By default they go into the
[`dev_$USER` stage](/environments/stages). This stage is separate
from `alchemy deploy`'s `live_$USER` stage, so a bare
`alchemy dev` cannot replace a stage you deployed. A stack can mix
emulated and live-only resources. Tear the local-dev stage down
with `alchemy destroy --stage dev_$USER`.

- Code changes take effect in milliseconds
- Resources stay running across reloads. Only your application
  code is rebuilt

Any process with a dev server, such as Vite or Next, can join the
loop through [Command.Dev](/command/dev-servers). `alchemy dev`
starts it and restarts it when its inputs change. On deploy it is
a no-op.

## Local by default, live on demand

In dev, emulatable resources run as simulators. A local
resource's id is `dev:`-prefixed. The prefix also proves that no
cloud call ran.

The local simulators serve more than your compute's bindings.
Node-side capability clients follow the same rule. A seed script
in an [Action](/infrastructure-as-code/action) that writes to a
`dev:` KV Namespace or S3 bucket writes to the same local
simulator your Worker or Lambda reads.

Every other resource runs live in dev automatically.
`Alchemy.remote()` (below) runs an emulatable resource against
the real cloud when local fidelity isn't enough.

## Debugging

Because your code runs locally, you can attach a debugger:

- Set breakpoints in your IDE
- Inspect variables and call stacks
- Profile performance

## Running a resource live in dev

`Alchemy.remote()` opts a resource out of local emulation. The
resource runs live even in dev:

```typescript
import * as Alchemy from "alchemy";

const worker = yield* Worker("Api", { ... }).pipe(Alchemy.remote());
```

During `alchemy deploy` the pin is a no-op because everything is
already live. If a remote resource needs credentials you don't
have, `alchemy dev` tells you before it touches anything.

### Opt out a whole scope

```typescript
yield* Effect.gen(function* () {
  const api = yield* Worker("Api", { ... });
  const site = yield* Worker("Site", { ... });
}).pipe(Alchemy.remote());
```

The policy is ambient and captured at registration, like
`adopt()`. Everything inside the scope runs live. Resources with
no local emulation already run live in dev, so `remote()` on them
is a no-op.

Local and live resources combine into hybrid topologies. For
example, a local Worker can produce into a live queue whose local
consumer drains it, or a local Lambda can read a live Secrets
Manager secret. See the per-cloud guides for examples.

### Switching is a replacement

A resource moves between local and live when you deploy after a
dev session or when you add or remove `remote()`. The move is
planned as a **replacement**. The new instance is created live,
and the local one (the workerd instance, the Docker container, the
dev process) is torn down. Dev state never silently becomes cloud
state.

## Dev vs Deploy

|                     | `alchemy dev`                            | `alchemy deploy`   |
| ------------------- | ---------------------------------------- | ------------------ |
| Emulatable services | Local simulators (`remote()` for live)   | Deployed to cloud  |
| Everything else     | Deployed to cloud (personal stage)       | Deployed to cloud  |
| Application code    | Runs locally (workerd, Docker)           | Deployed to cloud  |
| File watching       | Hot reload on change                     | Manual redeploy    |
| Debugging           | Attach local debugger                    | Tail logs          |
| Speed               | Milliseconds                             | Seconds to minutes |

To automate the deploy side, see the [CI guide](/environments/ci).

## Testing in dev mode

The [test harness](/testing/test-harness) has the same switch.
`Test.make({ dev: true })` runs a suite's `deploy(Stack)` against
the local emulators (Cloudflare in workerd, AWS in Docker) instead
of the real cloud. It is off by default and works on both the Bun
and Vitest adapters. Integration tests then run on your machine
with no cloud calls and no separate `alchemy dev` terminal. See
[Test harness → dev](/testing/test-harness#dev).
