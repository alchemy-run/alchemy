[Doppler](https://www.doppler.com) organizes secrets into projects,
each with configs such as `dev`, `stg`, and `prd`. `Doppler.Secrets`
downloads one config into the stack's
[secret providers](/environments/secret-providers), without writing
anything to `process.env` or to disk.

```typescript
import * as Doppler from "alchemy/Doppler";

secrets: [
  Doppler.Secrets(({ stage }) => ({
    project: "my-app",
    config: stage === "prod" ? "prd" : "dev",
  })),
],
```

Browser login and personal tokens can read many configs, so `project`
and `config` are required with those. A
[service token](https://docs.doppler.com/docs/service-tokens) is
scoped to one config, so both may be omitted. To let `pr-42` inherit
from `dev`, map preview stages onto Doppler's
[branch configs](https://docs.doppler.com/docs/branch-configs).

## Connect your account

Run `alchemy profile edit --add Doppler` and pick a method. Alchemy
stores the token in your [profile](/environments/profiles).

- **Login**: opens the Doppler dashboard. Approve the request, and the
  token shows up in Doppler as `Alchemy (<your hostname>)`.
  `alchemy profile edit --remove Doppler` revokes it.
- **API token**: takes a service or
  [personal token](https://docs.doppler.com/docs/personal-tokens) you
  already have.

```sh
# Non-interactive API token setup
alchemy profile edit --add Doppler --method api-token --set token=env:DOPPLER_TOKEN
```

## In CI

Alchemy never reads profiles in CI, so the environment decides. The
simplest option is a service token in `DOPPLER_TOKEN`:

```yaml
- run: bun alchemy deploy --stage prod --yes
  env:
    DOPPLER_TOKEN: ${{ secrets.DOPPLER_TOKEN }}
```

On Doppler's Team and Enterprise plans, OIDC avoids storing a
long-lived token. Create a
[service account identity](https://docs.doppler.com/docs/service-account-identities)
that trusts your platform's OIDC issuer, and set `DOPPLER_IDENTITY_ID`.
Alchemy exchanges the platform's identity token for a short-lived
Doppler token on every run.

```yaml
jobs:
  deploy:
    permissions:
      id-token: write   # lets the job request an OIDC token
      contents: read
    steps:
      - run: bun alchemy deploy --stage prod --yes
        env:
          DOPPLER_IDENTITY_ID: ${{ vars.DOPPLER_IDENTITY_ID }}
```

The token's issuer, subject, and audience must match the identity's
trust policy. Use your job's actual subject claim, which can vary with
the repository, branch, environment, and organization settings.

Alchemy also detects Vercel, GitLab, and Google Cloud runtimes. See
[CLI › provider › OIDC tokens](/cli/provider#oidc-tokens) for the per-platform OIDC variables
(`DOPPLER_OIDC_TOKEN`, `DOPPLER_OIDC_AUDIENCE`) and
`alchemy provider check-env`.

`DOPPLER_TOKEN` wins over `DOPPLER_IDENTITY_ID`, and either wins over a
profile. A teammate can deploy with a token they were handed.
