[Doppler](https://www.doppler.com) organises secrets into projects,
each with configs such as `dev`, `stg`, and `prd`. `Secrets.Doppler`
downloads one config and makes every secret in it available to
`Config` for the rest of the deploy, without writing anything to
`process.env` or to disk.

```typescript
secrets: {
  providers: [
    Alchemy.Secrets.Doppler({ project: "my-app", config: "dev" }),
  ],
},
```

Add it to a stack's [secret providers](/environments/secret-providers)
and every `Config.String`, `Config.Redacted`, and
[Worker binding](/environments/secrets) resolves from Doppler.

## Connect your account

Run `alchemy profile edit --add Doppler`. You are offered two ways in:

- **Login** opens the Doppler dashboard in your browser. Approve the
  request and Alchemy stores the resulting token in your
  [profile](/environments/profiles). Nothing else to copy. The token
  shows up in Doppler as `Alchemy (<your hostname>)`, so you can
  revoke it from the dashboard at any time, or with
  `alchemy profile edit --remove Doppler`, which revokes it for you.
- **API token** takes a token you already have, either a
  [service token](https://docs.doppler.com/docs/service-tokens)
  scoped to one config or a
  [personal token](https://docs.doppler.com/docs/personal-tokens).

Scripts and agents can skip the prompt:

```sh
alchemy profile edit --add Doppler --method api-token --set token=env:DOPPLER_TOKEN
```

## Pick a config per stage

A browser login or personal token can see every project, so it must
be told which one to read: `project` and `config` are required for
those. Most stacks derive the config from the
[stage](/environments/stages):

```typescript
Alchemy.Secrets.Doppler(
  Effect.gen(function* () {
    const stage = yield* Stage;
    return {
      project: "my-app",
      config: stage === "prod" ? "prd" : "dev",
    };
  }),
),
```

Doppler's own [branch configs](https://docs.doppler.com/docs/branch-configs)
map neatly onto preview stages if you want `pr-42` to inherit from
`dev` with a few overrides.

A service token is already scoped to a single config, so with one of
those both options may be omitted and Doppler serves the config the
token belongs to.

## In CI

The stack does not change between your machine and CI. The
`Secrets.Doppler({ project, config })` line above is all it ever
says; which credential backs it is decided by where the command runs.
Locally that is the profile. In CI, where profiles are never
consulted, it is the environment, and there are two ways to fill it.

The simplest is a [service token](https://docs.doppler.com/docs/service-tokens)
in `DOPPLER_TOKEN`:

```yaml
- run: bun alchemy deploy --stage prod --yes
  env:
    DOPPLER_TOKEN: ${{ secrets.DOPPLER_TOKEN }}
```

The better one, on Doppler's Team and Enterprise plans, is to hold no
Doppler credential in CI at all. Create a service account with a
[service account identity](https://docs.doppler.com/docs/service-account-identities)
that trusts your platform's OIDC issuer, and set `DOPPLER_IDENTITY_ID`
to it. Alchemy finds the platform's own identity token and exchanges
it for a short-lived Doppler token on every run. Nothing else is
configured on the Alchemy side:

```yaml
jobs:
  deploy:
    permissions:
      id-token: write   # lets the job request an OIDC token
      contents: read
    steps:
      - run: bun alchemy deploy --stage prod --yes
        env:
          DOPPLER_IDENTITY_ID: ${{ vars.DOPPLER_IDENTITY_ID }}
```

Detection covers Vercel, GitHub Actions, GitLab CI, Fly.io, and
Google Cloud. On GitHub the job needs `id-token: write`, as above; on
GitLab the job needs an
[`id_tokens`](https://docs.gitlab.com/ee/ci/secrets/id_token_authentication.html)
block; Vercel, Fly, and Cloud Run need nothing extra. On the Doppler
side, bind the identity's subject claim to your repository so no
other workflow can use it. If the identity expects a specific
audience, put it in `DOPPLER_OIDC_AUDIENCE`. A platform that is not
detected can hand its token over in `DOPPLER_OIDC_TOKEN`.

When both variables are present, `DOPPLER_TOKEN` wins and no OIDC
exchange happens. Either one also wins over a profile on your own
machine, so a teammate without a browser login can still deploy with
a token they were handed. `alchemy provider check-env` lists all of
these alongside the other providers' variables.

## When something goes wrong

Every failure names Doppler and what was asked for. A wrong slug
reads `Doppler could not find project 'my-app' config 'prd': ...`, a
revoked token tells you which profile to refresh, and a login token
used without `project` and `config` explains that both are required.
With `--log-level debug` the provider also lists the secret names it
loaded, which is the quickest way to confirm the right config was
read.
