---
title: Credentials & bindings
description: Which API key deploys your stack, which key each host gets at runtime, and what each key may do.
---

Two kinds of keys reach ClickHouse Cloud in an Alchemy app: the one that deploys the stack, and one per binding that a host uses while it runs.

## The deploy key

Alchemy deploys with the key in your profile, or in `CLICKHOUSE_CLOUD_API_KEY_ID` and `CLICKHOUSE_CLOUD_API_KEY_SECRET` when they are set (see [Setup](/clickhouse-cloud/setup)). It needs the **Admin** role to create services, keys and roles.

Several profiles can hold different keys, for example one per organization:

```sh
alchemy profile edit --add ClickHouseCloud --profile staging
alchemy deploy --profile staging
```

Alchemy reads the profile on the first ClickHouse call, not when the stack loads, so a stack that only touches other providers needs no ClickHouse key. When the profile has no organization ID, Alchemy asks the API which organization the key belongs to. It keeps the answer for the rest of the run, and asks again if the question failed.

## A key per binding

ClickHouse Cloud trusts no OIDC issuer, so a Worker or a Lambda can't trade its own identity for access. Each binding instead gives its host a custom role and an API key that holds only that role:

```typescript
const getService = yield* ClickHouseCloud.Service.GetService(Analytics);
```

This creates a role that allows `control-plane:service:view` on `instance/<serviceId>` and nothing else, and a key holding it. The key's ID, secret and API URL reach the host through its runtime context, so the secret never sits in your code or its bundle.

| Binding | Permissions | On |
| --- | --- | --- |
| `Service.GetService` | `service:view` | the service |
| `Service.UpdateServiceState` | `service:view`, `service:manage` | the service |
| `Backup.ListBackups`, `Backup.GetBackup` | `service:view`, `service:view-backups` | the service |
| `ClickPipes.GetClickPipe` | `service:view`, `service:manage-clickpipes` (reading a pipe needs it) | the pipe's service |
| `ClickPipes.UpdateClickPipeState`, `DiscoverClickPipeSchema` | `service:view`, `service:manage-clickpipes`, `sql-console:database:access` | the service |
| `QueryApiEndpoints.RunQueryApiEndpoint` | `service:view-query-api-endpoints`, and the key is added to the endpoint's allowed keys | the endpoint's service |
| `Postgres.GetPostgresService` and the other Postgres reads | `postgres-service:view` | `postgres/*`: a role on one Postgres service's ID grants nothing |
| `Postgres.UpdatePostgresServiceState` | `postgres-service:view`, `postgres-service:manage` | `postgres/*` |
| `Billing.GetUsageCost`, `GetCreditBalances` | `organization:view`, `organization:view-billing` | the organization |
| `Organization.ListActivities`, `GetActivity` | `organization:view`, `organization:view-activities` | the organization |

All permissions except `sql-console:database:access` start with `control-plane:`; ClickPipes refuse a key without database access. ClickHouse adds the permissions a granted one implies, so a role you inspect in the console can list a few more `view` permissions than the table.

Each key counts toward the organization's API key quota (`api-keys-per-organization`). A Worker with ten bindings holds ten keys.

:::note[Beta endpoints]
Some bindings call API endpoints ClickHouse marks Beta (stable contract, no breaking changes expected): `Billing.GetCreditBalances`, the Notifications bindings, the organization quota bindings, `ClickPipes.DiscoverClickPipeSchema`, the ClickStack alert and Snapshot bindings, and the Postgres bindings except `Connect`. The [overview](/clickhouse-cloud) lists the resources.
:::

## Keys you declare

An `ApiKeys.ApiKey` is a key the stack owns, for a service outside Alchemy. Its secret is shown only when the key is created, so Alchemy keeps it in state:

```typescript
const key = yield* ClickHouseCloud.ApiKeys.ApiKey("Exporter", {
  assignedRoleIds: [viewer.roleId],
});
// key.keyId and key.keySecret
```

If a key with the same name already exists and isn't in state, the deploy fails rather than taking it over. With `adopt(true)`, Alchemy takes it over by replacing it with a new key, because it can never read the old key's secret. Anything still using the old key stops working, so give the new secret to it.

## Postgres connections

`Postgres.Connect` is different: it opens no API call. It hands the host the service's connection string, host name, user, password and CA certificates through its runtime context, and the host connects with its own driver over TLS. The server's certificate is signed by the service's own CA, so pass `caCertificates` to the driver (`ssl: { ca }`) to verify it. The Postgres API has only the superuser, so the host connects as the superuser; create a narrower role in your migrations and pass its credentials yourself when that matters.
