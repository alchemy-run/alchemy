A `Domain.Model` is one bounded context running as a whole: its aggregates, the views built from their events, and the policies that act on them. This page follows a single deposit through a running model, then shows how to declare one, run it, and call it from your own code.

If the words aggregate, view and policy are new, read [What is Domain-Driven Design?](/domain/what-is-ddd) first.

## The command reaches one instance

Every command names its target, the id of one aggregate instance. `DepositMoney` targets an `AccountId`, so the model routes it to account `a-1` and nowhere else.

Each instance handles one command at a time. If two commands for `a-1` arrive together, the second waits until the first has committed, then sees the state it left behind. Commands for different accounts run in parallel, since they can't affect each other.

## The aggregate decides

The instance loads its current state and calls the aggregate's `decide` handler for the command.

```typescript title="src/Account.ts"
DepositMoney: (s, cmd) =>
  s._tag !== "Open"
    ? new NotOpen()
    : [new MoneyDeposited({ amount: cmd.amount, balanceAfter: s.balance + cmd.amount })],
```

If it returns a rejection, the command ends there. Nothing is recorded, and the caller gets the rejection as a typed error, here `NotOpen`.

If it returns events, each one is folded into the state with `evolve`, in order.

## The events and the state commit together

The new events are appended to the instance's stream, each with the next sequence number. In the same atomic write, the instance stores its new state and version, the reply to the caller, and a delivery for every view and policy that consumes these events. Either all of it is stored, or none of it is.

The caller then gets a receipt: the stream and the version it committed at, the events, and the reply.

Every command also carries an id. If a client resends the same command after a dropped connection, the instance finds the receipt it stored for that id and returns it again. The money is deposited once.

## Views and policies catch up

After the commit, each delivery is sent on. `AccountSummary` folds `MoneyDeposited` into its balance; `Statement` adds a line. Each one receives every event it consumes at least once, in the order its source recorded them, even if something restarts in between.

That's why the dashed edges above come after the receipt. For a moment, the account knows the new balance and the summary doesn't yet. A reader who needs their own write passes the receipt along, and the view waits until it has applied that version before answering.

## Declare the model

A model lists what runs together. It can start as a single aggregate.

```typescript
// src/Bank.ts
import * as Domain from "alchemy/Domain";
import { Account } from "./Account.ts";

export class Bank extends Domain.Model("Bank", {
  aggregates: [Account],
}) {}
```

Adding a view to `views` is enough for the model to deliver the events it reads. You never wire an event to a view by hand.

```typescript
// src/Bank.ts
import * as Domain from "alchemy/Domain";
import { Account } from "./Account.ts";
import { AccountSummary } from "./AccountSummary.ts";

export class Bank extends Domain.Model("Bank", {
  aggregates: [Account],
  views: [AccountSummary],
}) {}
```

A policy is declared in one place and implemented in another, because its implementation usually needs things from outside the model, like a client for another aggregate or a payment provider. The declaration goes in `policies`; the implementation is a Layer you keep beside it.

```typescript
// src/Bank.ts
import * as Domain from "alchemy/Domain";
import { Account } from "./Account.ts";
import { AccountSummary } from "./AccountSummary.ts";
import { Customer } from "./Customer.ts";
import {
  MainAccountProvisioning,
  MainAccountProvisioningLive,
} from "./MainAccountProvisioning.ts";

export class Bank extends Domain.Model("Bank", {
  aggregates: [Account, Customer],
  views: [AccountSummary],
  policies: [MainAccountProvisioning],
}) {}

export const BankPolicies = MainAccountProvisioningLive;
```

## Run it

A declaration doesn't run anything. `Bank.layer(BankPolicies)` turns it into a Layer that hosts the model, and a platform underneath decides where its state lives.

```typescript
// src/BankInMemory.ts
import * as Domain from "alchemy/Domain";
import * as Layer from "effect/Layer";
import { Bank, BankPolicies } from "./Bank.ts";

export const BankInMemory = Bank.layer(BankPolicies).pipe(Layer.provide(Domain.InMemory));
```

`Domain.InMemory` keeps everything in memory, which is what tests want. Swap it for another platform and the model runs there unchanged; every platform keeps the guarantees above. See [Hosting](/domain/cloudflare).

## Call it from your code

Inside the hosted model, each aggregate and view is a service. `yield* Account` gives you a client for every account, and `send` takes the target id and the command.

```typescript
// src/depositAndRead.ts
import * as Effect from "effect/Effect";
import { Account, AccountId, DepositMoney } from "./Account.ts";
import { AccountSummary } from "./AccountSummary.ts";

export const depositAndRead = Effect.gen(function* () {
  const accounts = yield* Account;
  const summaries = yield* AccountSummary;
  const accountId = AccountId.make("a-1");
  const receipt = yield* accounts.send(accountId, new DepositMoney({ amount: 100 }));
  return yield* summaries.query(Account.ref(accountId), { atLeast: receipt });
});
```

Passing the receipt as `atLeast` is the read-your-own-write from earlier: `query` waits until the summary has applied the deposit.

Clients outside the model, a browser or another service, reach it through an [Api](/domain/api) instead, which decides what each kind of client may send and read.

## Keep one language per model

A model is one bounded context, so every name in it means one thing. When two parts of the business use a word differently, give each its own model. One model never sends commands to another model's aggregates directly; it calls that model's Api.
