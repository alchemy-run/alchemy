title: What can be verified
description: The TypeScript, the Effect helpers and the schemas that Verify reads as logic, and what happens to code outside that set.
---

`Verify` proves a rule by reading your `decide`, `evolve`, `keyOf` and rules as logic. It reads a subset of TypeScript. Code outside it is never guessed at: the report names the file, the line and what it met, and the rule is not proved.

```text
Not read
  Label.aggregate.ts:23  reads .localeCompare of a string
```

What a handler returns has to depend only on what it is given: the state, the command and the context. It can return a value or an Effect, written with `Effect.gen` or `Effect.fn`. It can call other functions in your own files, which are read the same way. A function from Effect is read if it is listed under [Library functions](#library-functions), and one from [a package of your own](#your-own-packages) is read like your files. An exported function that cannot be read is [opaque](#opaque-functions).

## Statements

Read: `const`, `let` and `var`, assignment to a local variable or to several at once (`[x, y] = [y, x]`), `+=` and the other compound assignments, `++` and `--`, `if` and `else`, `switch`, `return`, block statements, and function declarations, which a block can call before the line that declares them.

Loops are read: `for`, `for…of`, `for…in`, `while` and `do…while`, with `break` and `continue`. A loop has to end after a number of turns the prover can count, so a loop over a list from the state or a command is tried for short lists only (see [Lists](#lists)).

Not read: `try`, `catch` and `throw`, `async` and `await`, `for await`, labels, and generators other than `Effect.gen`, `Effect.fn`, `Option.gen` and `Result.gen`. A `class` is read only where it extends one of `effect/Data`'s and adds nothing: `class Overweight extends Data.TaggedError("Overweight")<{ over: number }> {}`.

## Expressions

Read:

- Arithmetic on whole numbers: `+`, `-`, `*`, `/`, `%`, and the comparisons `<`, `<=`, `>`, `>=`.
- `===` and `!==`. `==` and `!=` are read only against `null`.
- `&&`, `||`, `??`, `!`, the conditional `a ? b : c`, and optional chaining: `a?.b`, `a?.b.c()` and `f?.()`.
- `typeof`, `void` and `in`.
- Object and array literals, spread in both, and property access by a name or by a key the prover can see.
- Destructuring of objects and arrays, with defaults and rest patterns.
- Arrow functions and function expressions, and calls to them.
- Template literals, and `+` on strings. A number, a boolean, `null` and `undefined` are written into one as JavaScript writes them.
- `new` on an event, a rejection or a command, and the class's `make`: `Started.make({})` is `new Started({})`.
- `new` on a class of `effect/Data` (`Data.Class`, `Data.TaggedClass`, `Data.Error`, `Data.TaggedError`) or of `effect/Schema` (`Schema.Class`, `Schema.TaggedClass`, `Schema.TaggedError`). The instance is its fields and its `_tag`.
- TypeScript's `as`, `satisfies` and `!`, which change nothing at run time.

Not read: bitwise operators, `**`, `instanceof`, the comma operator, regular expressions, tagged templates, `delete`, `this`, a getter or a setter in an object literal, and a property read by a key that depends on an input.

## Numbers

A whole number is exact, and a `bigint` is exact with no limit. A number is assumed to stay within ±2^53, which the report lists under what it assumes.

A division is read where its result is exact: through `Math.floor`, `Math.ceil` or `Math.trunc`, or compared with a whole number. `Math.abs` is read too, and `Math.max` and `Math.min` of any number of numbers.

Arithmetic on numbers that may not be whole is not proved. A solver counts exactly and JavaScript rounds, so `0.1 + 0.2 === 0.3` is true to one and false to the other. Keep money in whole cents, or in a [decimal](#decimals).

`effect/Number` and `effect/BigInt` are the same operators as functions, and are read the same way: `Number.sum`, `Number.clamp`, `BigInt.max`.

## Decimals

A `BigDecimal` is exact, and so is the solver's arithmetic, so a rule about money written in decimals is proved as written:

```typescript
invariants: {
  NeverRefundedMoreThanCharged: (ledger) =>
    BigDecimal.isLessThanOrEqualTo(ledger.refunded, ledger.charged),
  TheFeesAreATenthOfTheCharges: (ledger) =>
    BigDecimal.equals(ledger.fees, BigDecimal.multiply(ledger.charged, FEE)),
},
```

A sum, a difference, a product, a comparison, `min`, `max`, `clamp`, `abs`, `negate`, `floor`, `ceil` and `truncate` are read on any decimal. A division is read only between decimals the code writes: the library rounds one that does not end, and the solver does not.

## Strings

A string is compared with `===`, joined with `+` or a template literal, and has a `length`.

On a string from the state or a command, these methods are read: `startsWith`, `endsWith`, `includes`, `indexOf`, `lastIndexOf`, `charAt`, `concat`, `slice`, `substring`, `split`, and `replace` and `replaceAll` of one string by another. `effect/String` has the same as functions.

An id that holds structure is taken apart the usual ways, and a rule about a part is proved:

```typescript
invariants: { NameHasNoAt: (tag) => !tag.name.includes("@") },
decide: {
  BySlice: (_tag, c) => [new Named({ name: c.ref.slice(0, c.ref.indexOf("@")) })],
  BySplit: (_tag, c) => [new Named({ name: c.ref.split("@")[0]! })],
  ByLast: (_tag, c) => [new Versioned({ version: c.ref.slice(c.ref.lastIndexOf("@") + 1) })],
},
```

`slice` and `substring` are read at any place: one the code writes, one counted from the end, or one an input decides, such as where a separator is. The separator given to `indexOf`, `lastIndexOf` and `split` is a string the code writes.

The first part of a `split` and the last are read however many parts there are: `parts[0]`, `parts.at(-1)` and `const [name] = ref.split("@")`. Code that counts the parts, or reads one in the middle, is read for a string of up to two separators, and its rule is then checked for short lists only.

A method that changes letters is read only on a string the code writes: `toUpperCase`, `toLowerCase`, `trim`, `padStart`, `repeat`. `localeCompare`, `normalize` and regular expressions are not read at all. Two strings from an input are not put in order: `Order.String` is read on strings the code writes.

## Lists

An array the code builds has a known length, and everything is read on it: an index, `length`, `at`, `slice`, `concat`, `includes`, `indexOf`, `join`, `flat`, `toReversed`, and the methods that take a function, `map`, `filter`, `flatMap`, `find`, `findIndex`, `findLast`, `findLastIndex`, `some`, `every`, `forEach` and `reduce`. `push` is read on an array the code made, not on one it was given.

A list that comes from the state or a command has no known length, so it is tried with every length up to two items more than its schema asks for. A rule that passes that way is `Checked`, not `Proved`, and the report says how long the lists were.

`Object.keys`, `Object.values` and `Object.entries` are read on an object whose keys are known.

## Hash sets and hash maps

A `HashSet` and a `HashMap` from the state or a command are tried like a list: with up to two items, no two of them equal. Whether a value is in one is read as it is, for every value:

```typescript
invariants: {
  OnlyAMemberHasPoints: (roster) =>
    HashMap.every(roster.points, (_points, person) => HashSet.has(roster.members, person)),
  TheTotalIsTheSumOfThePoints: (roster) =>
    roster.total === HashMap.reduce(roster.points, 0, (sum, points) => sum + points),
},
```

The library gives the items of a set and the pairs of a map in the order of their hashes, which is not an order the code chose. So code that reads them in order (`reduce`, `forEach`, `findFirst`, `HashMap.keys`, a `for…of` loop, a spread) is read once for every order, and a rule is proved only if it holds in each. Up to four items are read that way. `Equal.equals` compares two sets, two maps, two decimals and two objects by what they hold.

## Schemas

The state, each command's input and each request context start as any value their schema allows. These are read:

- `Schema.String`, `Schema.Number`, `Schema.Int`, `Schema.BigInt` and `Schema.Boolean`.
- `Schema.Literal` and `Schema.Literals`, `Schema.Null` and `Schema.Undefined`.
- `Schema.Struct` and `Schema.TaggedStruct`, with optional fields.
- `Schema.Union`, `Schema.NullOr` and the others built on it. A proof starts from each member in turn.
- `Schema.TaggedUnion`, and a union made one with `Schema.toTaggedUnion`. Its `guards`, `isAnyOf`, `match` and `matchOrElse` are read as tests of the tag: `Status.guards.Open(ticket.status)`.
- `Schema.Array`, tried as described under [Lists](#lists).
- `Schema.Option`, started as `none` and as `some`.
- `Schema.Result`, started as a success and as a failure.
- `Schema.DateTimeUtc`, and `Schema.Duration` as a whole number of milliseconds.
- `Schema.BigDecimal`. A `Schema.Rational` is not started from: make a fraction from whole numbers with `Rational.make`.
- `Schema.HashSet` and `Schema.HashMap`, tried as described under [Hash sets and hash maps](#hash-sets-and-hash-maps).
- A branded schema, read as what it brands.

A field that may be left out, a union and an `Option` are each a choice, and a proof takes every choice in turn. The choice is made when the code first reads the field, so a field no handler or rule reads adds nothing: a decision that reads only `items.length` is read once for each length, however many optional fields an item has.

Checks on a number are read: `isInt`, `isFinite`, `isGreaterThan`, `isGreaterThanOrEqualTo`, `isLessThan`, `isLessThanOrEqualTo`, `isBetween`, and `isMultipleOf` a whole number. On a string or a list, `isMinLength` and `isMaxLength` are read. On a decimal, `isGreaterThanBigDecimal`, `isGreaterThanOrEqualToBigDecimal`, `isLessThanBigDecimal`, `isLessThanOrEqualToBigDecimal` and `isBetweenBigDecimal` are read.

A check the prover does not read is not assumed and not dropped in silence. The report lists it under "Schema checks not proved kept", with the command that writes the field.

A `Schema.Record`, and any other schema not listed, is a value the prover cannot see into. Code that only passes it along is still read. Code that looks inside it is not.

## The rest of Effect

Every module of Effect is either read as above, run as it is, or left unread on purpose.

**Run as it is, on values the code writes.** A pure function the prover has no reading of its own for is computed by the library itself when every argument is known: a constant, or something made from constants. That covers `SemVer`, `SemVerRange`, `ByteSize`, `Trie`, `TextDiff`, `JsonPatch`, `JsonPointer`, `Glob`, `RegExp.escape`, `Formatter`, `LogLevel`, `Cron.parse` and `Cron.match`, and the functions of the modules above that are not listed, such as `Array.rotate`, `String.camelToSnake` and `Duration.format`.

```typescript
const MINIMUM = SemVer.parseUnsafe("1.9.3");
const LIMIT = ByteSize.mebibytes(5);
```

Called on a value from the state or a command, or given a function of yours, such a function is not read, and the report names it. `Combiner` and `Reducer` are made from functions, and `Bytes` works on byte arrays, so they are not read: write the fold.

Every name on these lists has a line in a table the tests run: each call is read on values the prover knows and on values the solver holds, and both have to be what the real code gives. The language is a list of the same kind, one entry for each way a piece of it is written, marked as read or not. A test fails when a function, a method or a form of the language has no line in a table, and when a table is written with a form the list does not have.

**Left unread.** A call to one of these is reported with its name, and the rule is not proved.

- **The outside world.** `Random`, `Config`, `ConfigProvider`, `FileSystem`, `Path`, `Terminal`, `Stdio`, `Effect.promise`, and the packages under `effect/http`, `effect/sql`, `effect/rpc`, `effect/ai`, `effect/cluster`, `effect/workflow` and the others. A handler is a function of the state, the command and the time. What it needs from outside comes in as a field of the command.
- **Time passing and things running together.** `Effect.sleep`, `timeout`, `retry`, `repeat`, `race` and `fork`, `Schedule`, `Scheduler`, `Fiber`, `FiberHandle`, `FiberMap`, `FiberSet`, `Deferred`, `Latch`, `Semaphore`, `PartitionedSemaphore`, `Queue`, `PubSub`, `Pool`, `Cache`, `ScopedCache`, `Request`, `RequestResolver`, `Channel`, `Pull`, `Take`, `SubscriptionRef`, `SynchronizedRef`, `ExecutionPlan` and the `Tx` modules. Which of two things happens first is not something a handler decides, and a handler does not wait. `Cron.next`, `prev` and `sequence` read the clock when they are given no time.
- **Wiring.** `Layer`, `LayerMap`, `LayerRef`, `Context`, `References`, `Scope`, `ScopedRef`, `RcMap`, `RcRef`, `Resource`, `Runtime`, `ManagedRuntime`, `Logger`, `Tracer`, `Metric`, `ErrorReporter`. They say how a program is put together and watched, not what it decides. A request context a handler yields is read, as above.
- **Schemas as code.** `Schema.decode`, `encode`, `is`, and `SchemaAST`, `SchemaGetter`, `SchemaIssue`, `SchemaParser`, `SchemaRepresentation`, `SchemaTransformation`, `ChannelSchema`, `JsonSchema`, `StandardSchema`, `Arbitrary`. A schema is read where it describes the state, a command or an event. Decoding with one inside a handler is not.
- **Values changed in place, or known by where they are.** `Graph`, `HashRing`, `MutableList`, and `Hash`. A graph and a ring are built by changing one, and a hash of an object is where it sits in memory. Put a call to one in an exported function, which is then [opaque](#opaque-functions).
- **Nothing to run.** `Types`, `HKT`, `Unify`, `Utils`, `Pipeable`, `Effectable`, `Differ`, `PlatformError`, `Redactable`, `Version`, and `Newtype` and `Brand` beyond the two functions above.

In `Effect.gen`, `yield*` on an `Option` or a `Result` is not read: it fails where it runs. Use `Option.gen` and `Result.gen`, or `Effect.fromOption` and `Effect.fromResult`.

## Effects and failures

Inside `Effect.gen` and `Effect.fn`, `yield*` is read on an effect, on a rejection (which rejects the command), on an error of `Data.TaggedError` or `Schema.TaggedError` (which fails with it) and on a request context (which gives any value its schema allows).

A helper's failure is handled the way the code handles it, and becomes a rejection only where the code makes it one:

```typescript
class Overweight extends Data.TaggedError("Overweight")<{ readonly over: number }> {}

decide: {
  Pack: Effect.fn(function* (parcel, command) {
    const weights = yield* Effect.forEach(command.items, weigh);
    const total = yield* Effect.fromResult(fits(parcel.grams, Number.sumAll(weights))).pipe(
      Effect.mapError((error) => new TooHeavy({ over: error.over })),
    );
    return [new Packed({ grams: total - parcel.grams })];
  }),
},
```

A defect is not a failure. After `Effect.die`, `Effect.orDie` or a `getOrThrow` on nothing, the command fails and records nothing, and no `catch` after it handles it.

`Effect.all`, `forEach` and the others run one effect after another. Their `concurrency` option changes nothing a handler can see, since nothing in a handler waits.

## Streams

A stream is read where it is a list worked through in order: made from values the code has, changed one item at a time, and run to a value.

```typescript
const kept = yield* Stream.fromIterable(command.readings).pipe(
  Stream.filter((reading) => reading >= 0),
  Stream.mapEffect(checked),
  Stream.take(2),
  Stream.runCollect,
);
```

It is read as the library runs it. A step that runs an effect for each item takes the items one at a time, so a stream that stops early runs the effects the real one runs and no others: above, a reading after the second is never checked, and a failure it would have given never happens.

- **Made with:** `make`, `succeed`, `empty`, `fromIterable`, `fromArray`, `fromEffect`, `fromArrayEffect`, `fromIterableEffect`, `sync`, `suspend`, `unwrap`, `fail`, `die`, `range`, `iterate`, `unfold`, `paginate`.
- **Changed with:** `map`, `as`, `filter`, `filterMap`, `filterEffect`, `mapEffect`, `tap`, `flatMap`, `take`, `takeWhile`, `takeUntil`, `takeRight`, `drop`, `dropWhile`, `scan`, `mapAccum`, `concat`, `prepend`, `zip`, `zipWith`, `zipWithIndex`, `changes`, `changesWith`, `rechunk`, `grouped`, `drain`.
- **Failures:** `catch`, `catchTag`, `catchTags`, `catchIf`, `orElseSucceed`, `mapError`, `orDie`.
- **Run with:** `runCollect`, `runFold`, `runFoldEffect`, `runForEach`, `runForEachWhile`, `runHead`, `runLast`, `runCount`, `runSum`, `runDrain`, `mkString`, and `run` into a sink.
- **Sinks:** `Sink.collect`, `count`, `sum`, `drain`, `head`, `last`, `take`, `reduce`, `fold`, `every`, `some`, `find`, `forEach`, `succeed`, `fail`, `map`. A sink that has what it wants pulls nothing more.

`Stream.iterate`, `unfold` and `paginate` may never end. One that is cut with `take` is read; one run to its end is not, and the report says so. A `take` of a count that comes from an input is not read, since how many items that is, is not a thing the prover sees.

Not read: a stream of time (`tick`, `debounce`, `throttle`, a schedule), of a queue or a pub-sub, a `merge` of two streams, and `mapEffect` or `flatMap` with a `concurrency` above one. Which item comes first there is not something the code decides.

## Your own files

A name a handler uses is found where its file declares or imports it, and the file it comes from is read the same way.

```typescript
import { canClose, limit as LIMIT } from "./rules.ts";
import * as Rules from "./rules.ts";
import byDefault from "./rules.ts";

const { step, bounds: [low, high] } = SETTINGS;
```

Read: named, renamed, namespace and default imports, and a file re-exporting another's names with `export { a as b } from`, `export * from` and `export * as rules from`. At the top of a file, `const`, `let` and `var` are read, a pattern on the left of one too, with function declarations and anything a file exports by default. A function can use a constant declared below it, and two files can import each other.

A namespace has what its file exports: `Rules.hidden` is `undefined` for a name the file keeps to itself.

An exported `enum` or `namespace` is the value the loaded file holds. One a file keeps to itself is not read, and neither is a `class` with a body: a class is read where it extends one of `effect/Data`'s or `effect/Schema`'s and adds nothing.

## Your own packages

Rules that several aggregates share often live in a package of their own. Its code is read like the files of the model:

```typescript title="packages/domain/src/Ticket.aggregate.ts"
import { canClose } from "@acme/rules";

decide: {
  Close: (ticket) => (canClose(ticket) ? [new Closed({})] : []),
},
```

An import is found the way Node finds it: in the nearest `node_modules`, through the `exports` of the package's `package.json`. The code it leads to is held to everything above. Effect and Alchemy are never read this way: the prover knows their functions from the list above.

## Opaque functions

A hash, a parser or a string helper is not code the prover reads, and a rule about something else should not wait on it. Put it in a function your file exports:

```typescript title="packages/domain/src/hash.ts"
import { createHash } from "node:crypto";

export const idOf = (seq: number) => createHash("sha256").update(String(seq)).digest("hex");
```

```typescript title="packages/domain/src/Ticket.aggregate.ts"
evolve: {
  Started: (ticket, _event, envelope) => ({ ...ticket, lastRun: idOf(envelope.seq) }),
  Closed: (ticket) => ({ ...ticket, open: false }),
},
transitions: {
  AClosedTicketStaysClosed: ({ before, after }) => before.open || !after.open,
},
```

The prover cannot read the body of `idOf`, so it does not look inside it. A call gives a value that can be kept in the state, put in an event and passed along. Two calls on the same arguments are the same value, so `idOf(a) === idOf(a)` is true. A condition on the result, as in `if (isValid(command.email))`, is tried both ways.

The result is also taken for what the code uses it as. Where the solver picks a value for it, the real function is run on the same arguments, and an answer the real function does not give is ruled out.

```typescript title="packages/domain/src/Transfer.decision.ts"
export class Pay extends Domain.Decision(PayRef, {
  reads: { from: Account, to: Account },
  keyOf: (cmd) => ({ from: nameOf(cmd.from), to: nameOf(cmd.to) }),
  decide: ({ from, to }, cmd) =>
    nameOf(cmd.payee) === from.id
      ? new SelfPay()
      : Option.isNone(versionOf(cmd.ref))
        ? new BadRef()
        : cmd.amount > from.state.balance
          ? new Short()
          : [
              from.record(new Debited({ amount: cmd.amount })),
              to.record(new Credited({ amount: cmd.amount })),
            ],
}) {}
```

In `keyOf`, what `nameOf` returns is an id: the accounts read are the ones it names. Compared with `from.id` it is text, and next to a number or a boolean it is one of those. `Option.isNone(versionOf(cmd.ref))` takes the result for an `Option`: a `None` on one path, and a `Some` of a value the prover does not look inside on another.

A result that is spread, looped over, or read with an array's `map`, `filter` and the like is a list of up to two items, so `keyOf: (cmd) => ({ to: [...partsOf(cmd.to)] })` reads one account for each. Its rule is then checked for short lists only. A number is any number: nothing says the function gives a whole one. It is compared with `<` and `===`, and a sum or a product of it is not read.

A rule that reads into the result any other way is not proved, and the report says which function stands in the way, and why it was not read:

```text
Not read
  Ticket.aggregate.ts:32  reads .length of what idOf returned, which the prover does not look inside: idOf reads .update of what createHash returned, which the prover does not look inside: createHash is a function of node:crypto, which is not code the prover reads
```

Where the prover runs your real code, to confirm a counterexample or to check its own reading, it calls the real function. A counterexample is always one the real `idOf` produces.

This takes the function to be pure: the same result for the same arguments, and nothing changed. The report lists each such function under what it assumes. A function is never taken to be pure when what stops the prover could make it otherwise: a global such as `Date` or `Math.random`, a package function the prover has no model for, or a change to a value it was given. That code is reported as not read.

Where you know such a function is pure, name it. A function the prover could read can be named too, to keep its body out of the proof:

```typescript title="packages/domain/test/Ticket.test.ts"
import * as DateTime from "effect/DateTime";

Verify.aggregate(Ticket, { opaque: [DateTime.formatIso] });
```

## What a handler is given

`decide` is read with its three arguments: the state, the command, and the context with `id`, `now`, `commandId`, `stream` and `version`. `now` is any time, so a rule that depends on the clock is proved for every time. `evolve` is read with the state, the event and its envelope.

The clock inside `decide` is that same `now`. `yield* DateTime.now` and `yield* Clock.currentTimeMillis` give the time the command is handled at, in the proof and when the command runs:

```ts
Renew: Effect.fn(function* (lease) {
  const now = yield* DateTime.now;
  if (DateTime.isLessThanOrEqualTo(lease.until, now)) return yield* new Lapsed();
  return [Renewed.make({ until: DateTime.addDuration(lease.until, "30 days") })];
}),
```

A time is compared and moved in whole milliseconds. A month and a year are not one length, so `DateTime.add(time, { months: 1 })` is not read. The clock anywhere but `decide` is not the time of a command, and is not read.

A request context a handler yields is any value its schema allows. Middleware is not run, so a rule is proved for every caller, including ones your middleware would turn away.

## When code is not read

A rule whose command meets unread code is not proved, and the verification fails. The line in the report says what to change:

```text
Not read
  Label.aggregate.ts:23  reads .localeCompare of a string
```

Rewrite the line with what is read, or put it in an exported function, which is then [opaque](#opaque-functions). You can also move it out of the handler: compute it where the command is built and pass the result in as a field. What `decide` then checks is the field, which the prover reads.

A policy's or a saga's handler is read the same way when the model is searched. One the search cannot follow fails the check until it is allowed by name:

```typescript
Verify.model(Bank, {
  apis: [CustomerApi],
  allow: { skipped: ["FraudReview"] },
});
```
