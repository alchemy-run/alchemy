A command asks one aggregate instance for a change. It's a request, so it can be refused, and it's named as an instruction: `OpenAccount`, `DepositMoney`, `WithdrawMoney`.

A command is also a contract. Before you send one, its declaration tells you which instance it goes to, what data it carries, which events it may record, which refusals it may return, and what you get back.

## Find the commands in your business

Commands come from the verbs people use when they describe their work. At a bank, for example, a customer *opens* an account, *deposits* money, *withdraws* cash, *requests* a transfer; a support agent *freezes* an account, *approves* a large transfer. Each of those sentences is a command, named the way the business says it.

The opposite is a command named after the data it touches: `UpdateAccount`, `SetBalance`, `PatchCustomer`. Those say what changes in storage, but not why. An `UpdateAccount` that sets `frozen: true` and one that sets `owner: "kim"` are different requests with different rules: who may make them, when they're refused, and what the history should say afterwards. Give each intent its own command, `FreezeAccount` and `ChangeOwner`, so each gets its own rules, its own refusals and its own event.

A useful test: read the command's name aloud to someone who works in the business. If they'd say "yes, customers do that", it's a good command. If they'd ask "update it how?", split it.

## Carry the intent, not the outcome

A command carries what the caller knows and wants. It doesn't carry what the aggregate will work out. A withdrawal says how much to withdraw; it doesn't say what the balance will be afterwards, because only the account knows its balance at the moment it decides.

```typescript
new WithdrawMoney({ amount: 30 }); // the intent
new MoneyWithdrawn({ amount: 30, balanceAfter: 70 }); // the outcome, decided by the account
```

That split keeps every rule in the aggregate. A client can't send a balance it made up, and two clients that both read a balance of 100 can't both withdraw 80: the account decides each withdrawal against its own state, one at a time.

## Declare a command

Here is a withdrawal from the bank in the [tutorial](/domain/tutorial/part-1).

```typescript title="src/WithdrawMoney.command.ts"
export class WithdrawMoney extends Domain.Command("WithdrawMoney", {
  input: { accountId: AccountId, amount: Schema.Int },
  events: [MoneyWithdrawn],
  rejects: [NotOpen, InsufficientFunds],
  reply: { balance: Schema.Int },
}) {}
```

The first argument is the command's name. It's how the command is identified on the wire and in the aggregate's handlers, so it must be unique within a model.

## Describe it

A command's last argument is its [annotations](/domain/annotations). Its `description` is what a person or an agent reads before sending it: the [MCP](/domain/mcp) tool's description, the [CLI](/domain/cli) subcommand's help, and the operation's description in the [OpenAPI document](/domain/http-api).

```typescript title="src/WithdrawMoney.command.ts"
export class WithdrawMoney extends Domain.Command(
  "WithdrawMoney",
  {
    input: { accountId: AccountId, amount: Schema.Int },
    events: [MoneyWithdrawn],
    rejects: [NotOpen, InsufficientFunds],
    reply: { balance: Schema.Int },
  },
  { description: "Take money out of an account. The amount is in cents." },
) {}
```

## Keep it with its events and rejections

A command, the events it records and the rejections it returns are one unit: you read them together, and change them together. Put them in one file named after the command, with a `.command.ts` suffix, like `WithdrawMoney.command.ts`. See [Project layout](/domain/project-layout).

```typescript title="src/WithdrawMoney.command.ts"
export class MoneyWithdrawn extends Domain.Event("MoneyWithdrawn", {
  amount: Schema.Int,
  balanceAfter: Schema.Int,
}) {}

export class InsufficientFunds extends Domain.Rejection("InsufficientFunds", {
  balance: Schema.Int,
  requested: Schema.Int,
}) {}
```

When more than one command uses something, it moves to a file of its own. Deposits and withdrawals both refuse an account that isn't open, so `NotOpen` has its own file, `NotOpen.rejection.ts`, and both import it.

```typescript title="src/NotOpen.rejection.ts"
export class NotOpen extends Domain.Rejection("NotOpen") {}
```

The aggregate's file then holds only its state and how it decides and evolves, and imports each command from its file. The same goes for ids, like `AccountId`, which the commands and the aggregate share.

## Name the instance it is for

A command's input includes the id of the instance it is for. A withdrawal is for one account, so its input has an `accountId`.

```typescript title="src/Account.id.ts"
export const AccountId = Schema.String.pipe(Schema.brand("AccountId"));
```

The brand makes the id its own type. A `CustomerId` is a string too, but passing one where an `AccountId` is expected is a type error, so a command can't be sent to the wrong kind of instance.

The aggregate that handles the command says which field that is, with `keyOf`. The model routes the command to that one instance.

```typescript title="src/Account.aggregate.ts"
keyOf: (cmd) => cmd.accountId,
```

`keyOf` receives any of the aggregate's commands, so they share the field's name. It must return the aggregate's own id: returning a `CustomerId`, or a plain string, from `Account`'s `keyOf` is a type error.

A command that involves several instances names each of them in its input, and a [decision](/domain/decision) implements it.

## Carry the request's data

`input` lists the fields the caller provides, each as a schema. You create the command with them, and the aggregate reads them in `decide`.

```typescript title="src/Account.aggregate.ts"
decide: {
  WithdrawMoney: (account, cmd) =>
    account._tag !== "Open"
      ? new NotOpen()
      : cmd.amount > account.balance
        ? new InsufficientFunds({ balance: account.balance, requested: cmd.amount })
        : [new MoneyWithdrawn({ amount: cmd.amount, balanceAfter: account.balance - cmd.amount })],
},
```

The schemas also decode the command when it arrives from a client, so `decide` only ever sees well-formed input. A command with no input, like a request to close an account, leaves `input` out.

## Declare every outcome

A command can end in one of two ways: the aggregate records events, or it refuses. `events` lists the events the command may record, and `rejects` lists the refusals it may return.

A refusal is a `Domain.Rejection`, a typed error that can carry data about why.

```typescript title="src/WithdrawMoney.command.ts"
export class InsufficientFunds extends Domain.Rejection("InsufficientFunds", {
  balance: Schema.Int,
  requested: Schema.Int,
}) {}
```

Both lists are enforced by the types. The aggregate's `decide` handler for `WithdrawMoney` can only return `MoneyWithdrawn` events or one of its two rejections. And whoever sends it gets exactly `NotOpen | InsufficientFunds` in the error channel, so they can handle each case by name.

A rejection means nothing happened. No event is recorded and the state is unchanged, so the caller can safely try again with different input.

Name a rejection after the business reason, the way you'd explain it to the customer: `InsufficientFunds`, `NotOpen`, `DailyLimitExceeded`. Give it the data the caller needs to do something about it. `InsufficientFunds` carries the balance and the amount requested, so an app can say "you have 50, you asked for 80" without a second read.

## Annotate a rejection

`Domain.Rejection` is `Schema.TaggedError` with its own type filled in, so its third argument takes the same annotations. An HTTP API reads `httpApiStatus` from it, as it does for any Effect error:

```typescript title="src/NotOwner.rejection.ts"
export class NotOwner extends Domain.Rejection(
  "NotOwner",
  {},
  { httpApiStatus: 403, description: "Only the account's owner may do this." },
) {}
```

These are the rejection's [annotations](/domain/annotations) too, so `NotOwner.annotations.description` reads the description back.

`rejects` takes any tagged error class, so a `Schema.TaggedError` of your own, or one of Effect's `HttpApiError` classes, works as a rejection too:

```typescript
class WithdrawMoney extends Domain.Command("WithdrawMoney", {
  input: { accountId: AccountId, amount: Cents },
  events: [MoneyWithdrawn],
  rejects: [InsufficientFunds, HttpApiError.Forbidden],
}) {}
```

## Report a fact that can't be refused

Some commands don't ask permission. They tell the model about something that already happened outside it: a card payment settled at the payment processor, a deadline passed. The model can't refuse a fact, so these commands declare no `rejects`. Their aggregate records what the fact means for it instead, even when the news is bad.

```typescript title="packages/domain/src/Account/RecordSettlement.command.ts"
export class RecordSettlement extends Domain.Command("RecordSettlement", {
  input: { accountId: AccountId, settlementId: Schema.String, amount: Cents },
  events: [SettlementReceived, SettlementOnClosedAccount],
}) {}
```

Money that settles on a closed account is still recorded, as `SettlementOnClosedAccount`, and a policy refunds it. See [External System](/domain/external-system#turn-outside-events-into-commands).

## Reply to the caller

`reply` is what the caller gets back after the events commit. Here, the balance after the withdrawal.

The aggregate computes it from its state after the events, in a `reply` handler named after the command.

```typescript title="src/Account.aggregate.ts"
reply: {
  DepositMoney: (s) => ({ balance: s._tag === "Open" ? s.balance : 0 }),
  WithdrawMoney: (s) => ({ balance: s._tag === "Open" ? s.balance : 0 }),
},
```

A command without a `reply` still tells the caller where it committed. See [the receipt](#send-it) below.

## Guard it with middleware

Before a command reaches its aggregate, it can pass through middleware. In the full example bank, a withdrawal first authenticates the caller with `Session`, then asks for a second factor with `MfaChallenge`.

```typescript title="packages/domain/src/Account/WithdrawMoney.command.ts"
export class WithdrawMoney extends Domain.Command("WithdrawMoney", {
  middleware: [Session, MfaChallenge],
  input: { accountId: AccountId, amount: Cents },
  events: [MoneyWithdrawn],
  rejects: [NotOpen, NotOwner, Frozen, InsufficientFunds, DailyLimitExceeded],
  reply: { balance: Cents },
}) {}
```

Nothing from its input reaches a trace unless its `decide` annotates it; see [Observability](/domain/observability).

Middleware runs in list order, so `Session` authenticates before `MfaChallenge` challenges, and any of it can stop the command with its own error, like `Unauthorized`. What it provides, such as who the caller is, travels with the command to the aggregate, where `decide` reads it to authorize the change. See [Sessions and middleware](/domain/sessions).

A client can run the same `decide` with `Account.predict` when it provides what the middleware would, from a client-side Layer. See [Optimistic updates](/domain/optimistic-updates#bound-this-pattern).

## Send it

Inside a hosted model, you send a command through the client of the aggregate that handles it.

```typescript title="src/MainAccountProvisioning.policy.ts"
yield* accounts
  .send(new OpenAccount({ accountId: AccountId.make(`${source.id}-main`), owner: source.id }))
  .pipe(Effect.catchTag("AlreadyOpen", () => Effect.void));
```

From a client of an [Api](/domain/api), each command is a method that takes the input and optional call options: `bank.WithdrawMoney({ accountId, amount: 2_000 })`.

Either way, `send` succeeds once the events have committed, with a receipt. It holds the stream and the version the instance committed at, the events it recorded, and the reply.

## Choose when it answers

A command answers as soon as its events are committed. The [views](/domain/view) apply them a moment later, so a read straight after the answer can miss the command. A read that must include it passes the receipt as [`atLeast`](/domain/view#views-catch-up-after-the-commit).

```typescript title="packages/server/test/depositThenRead.ts"
const receipt = yield* bank.DepositMoney({ accountId, amount: 500 });
const summary = yield* bank.AccountSummary.get(accountId, { atLeast: receipt });
```

That is `consistency: "eventual"`, the default. A command sent through an Api with `consistency: "strong"` answers once every view its events reach has applied them. Whoever reads a view after the answer, this client or any other, sees the command.

```typescript title="packages/server/test/depositStrong.ts"
yield* bank.DepositMoney({ accountId, amount: 500 }, { consistency: "strong" });
const summary = yield* bank.AccountSummary.get(accountId); // includes the deposit
```

If a view hasn't applied the events within 10 seconds, a strong command fails with `ConsistencyTimeout`. The command did not fail: its events are committed, and the error carries the `stream` and `version` they were committed at. Send it again under the same [command id](#send-it-exactly-once) to get its receipt.

Strong consistency covers the model's views. A [projection](/domain/projection) writes to a store of your own, often in batches, so a command doesn't wait for it: a [query](/domain/query#read-your-own-write) over that store takes the receipt. A view that a deploy is still filling with history is not waited for either.

A command sent from inside the model, by a policy or a saga through an aggregate's client, always answers at the commit.

### Set it for a whole client

A client reads `Domain.DefaultConsistency` once, when it is built, and uses it for every command sent without a `consistency`. Provide `"strong"` to a client whose callers read views after they write and carry no receipt between the two, such as an agent's tools.

```typescript title="packages/server/src/strongBank.ts"
export const strongBank = CustomerApi.clientHttp("https://bank.example.com/api").pipe(
  Effect.provideService(Domain.DefaultConsistency, "strong"),
);
```

A call on that client can still pass `consistency: "eventual"`.

### What the wait costs

An eventual command is one call to the aggregate. A strong command also waits for each view to receive the events, so it takes longer with every view they reach.

On Cloudflare, with the model near its callers, an eventual command answers in 30 to 100 milliseconds. A strong one usually answers in 100 to 400 milliseconds, and within a second 99 times in 100.

The first command to an instance is slower, because the platform creates its object and one for each view: about half a second eventual, and 1 to 2.5 seconds strong. An instance nobody has used for a while pays part of that again.

Ask for `"strong"` when the next thing the caller does is read a view and it has no receipt to pass. Keep the default when the caller shows the result from the receipt, [predicts it](/domain/optimistic-updates), or passes the receipt to its read.

## Send it exactly once

Networks fail after a command commits but before its receipt arrives. A client that retries could withdraw twice.

Every command has an id to prevent that. The instance stores each receipt under its command's id, and when the same id arrives again, it returns the stored receipt without deciding again. Pass your own `commandId` when you might retry:

```typescript title="packages/server/test/withdrawOnce.ts"
const first = yield* bank.WithdrawMoney({ accountId, amount: 2_000 }, { commandId: requestId, ...mfa });
const retry = yield* bank.WithdrawMoney({ accountId, amount: 2_000 }, { commandId: requestId, ...mfa });
first.version === retry.version; // true
```

Both calls return the same receipt, and the money leaves the account once. Without a `commandId`, each send gets a fresh one.

An id names one command. Through an Api, a send that reuses an id with another input fails with `CommandIdReused` and applies nothing:

```typescript title="packages/server/test/withdrawOnce.ts"
const other = yield* bank
  .WithdrawMoney({ accountId, amount: 500 }, { commandId: requestId, ...mfa })
  .pipe(Effect.flip);
other._tag; // "CommandIdReused"
```

A front end that builds ids from its state can repeat ids it already sent when it restores old state, such as server-rendered state or a history entry. Send each new command under a new id.

The instance keeps a fingerprint of each encoded command with its receipt: the SHA-256 of its JSON with object keys sorted, so the order of fields doesn't matter. A receipt stored before fingerprints has none, and answers a resend with any input. Commands sent in process, by a [policy](/domain/policy) or a saga step that runs again, keep their first receipt whatever input they send now. A command that a [Decision](/domain/decision) implements does too.

Commands sent by a [policy](/domain/policy) get ids derived from the event that caused them, so a policy that runs twice for the same event sends the same commands, and each takes effect once.

## Send it later

A command can also be scheduled to arrive at a later time, which is how deadlines work: "expire this transfer if nobody approves it within a day". Only commands that can't be refused can be scheduled, because there's no caller waiting to handle a rejection. See [Deadlines](/domain/deadlines).

```typescript title="packages/domain/src/Transfer/TransferApprovalDeadline.policy.ts"
yield* transfers.schedule(new ExpireTransfer({ transferId: source.id }), { after: APPROVAL_WINDOW });
```

Scheduling again under the same command id replaces the earlier command, even one that already ran.
