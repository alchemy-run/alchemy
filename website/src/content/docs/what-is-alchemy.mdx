Alchemy is **Infrastructure as Code** built in pure
[Effect](https://effect.website), with **Infrastructure as Effects**
on top. Infrastructure as Code declares, diffs, and deploys cloud
resources the way Terraform or Pulumi does. Infrastructure as Effects
lets the code that runs on those resources live in the same program,
as typed Effects and layers.

This file holds the whole application, an R2 Bucket and a Worker that
serves files from it. A small stack file deploys it (below).

```typescript
// src/api.ts
import * as Cloudflare from "alchemy/Cloudflare";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export const Uploads = Cloudflare.R2.Bucket("Uploads");

export default Cloudflare.Worker(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const bucket = yield* Cloudflare.R2.ReadWriteBucket(Uploads);

    return {
      fetch: Effect.gen(function* () {
        const obj = yield* bucket.get("hello.txt");
        return obj
          ? HttpServerResponse.text(yield* obj.text())
          : HttpServerResponse.text("Not found", { status: 404 });
      }),
    };
  }).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)),
);
```

The Bucket is declared next to the Worker that uses it. `bucket` is a
typed client the handler closes over. Binding `Uploads` inside the
Worker adds the Bucket to the stack, so you don't yield it separately.

## Infrastructure as Code

The core of Alchemy is Infrastructure as Code, in the same family as
Terraform, Pulumi, CloudFormation, and the CDK.

### Stack

A **stack** is the unit you deploy. It is an Effect that yields
resources and returns the outputs you want printed:

```typescript
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Effect from "effect/Effect";
import Api from "./src/api.ts";

export default Alchemy.Stack(
  "MyApp",
  { providers: Cloudflare.providers(), state: Cloudflare.state() },
  Effect.gen(function* () {
    const api = yield* Api;
    return { url: api.url };
  }),
);
```

`alchemy deploy` creates the Bucket, bundles the Worker, wires the
binding between them, and prints the URL. Every deploy targets a
[stage](/environments/stages), an isolated copy of every resource, so
`dev` and `prod` never touch each other.

Alchemy reads the current state, diffs it against your program, shows
the plan, and applies it in dependency order. The terminal below shows
that loop for a stack with a Bucket, a KV Namespace, and a Worker
bound to both:

**State** is where the result persists between runs, so the next
deploy only touches what changed. The `state` option picks where it's
stored, as [State Store](/state-store) explains. See
[Stacks](/infrastructure-as-code/stack) for every stack option.

### Resource

A **resource** is a cloud entity in a stack managed by Alchemy, such
as a bucket, a database, a queue, a Worker, or a DNS record. Yield it
in the stack to add it to the plan:

```typescript
const bucket = yield* Cloudflare.R2.Bucket("Uploads"); // logical ID "Uploads"
// bucket.bucketName is an Output
```

Alchemy tracks each resource across deploys by its logical ID. Its
outputs are typed values you can pass into other resources. Here the
physical bucket name Alchemy generated becomes an environment variable
on a Worker:

```typescript
const bucket = yield* Cloudflare.R2.Bucket("Uploads");

yield* Cloudflare.Worker("Api", {
  main: "./src/api.ts",
  env: { BUCKET_NAME: bucket.bucketName },
});
```

See [Resources](/infrastructure-as-code/resource) and
[Outputs](/infrastructure-as-code/outputs).

### Provider

A **provider** tells Alchemy how to read, diff, create, update, and
delete one resource type. Each cloud ships its providers as an Effect
`Layer`, and a stack takes as many as it needs:

```typescript
providers: Layer.mergeAll(Cloudflare.providers(), AWS.providers()),
```

The type system checks the wiring. Yield an AWS resource in a stack
that only provides `Cloudflare.providers()` and the program does not
compile. See [Multiple providers](/infrastructure-as-code/stack#multiple-providers)
for the wiring, [Custom Provider](/infrastructure-as-code/custom-provider)
to write your own, and [Provider contract](/infrastructure-as-code/provider)
for the operations a provider implements.

## The same app with Infrastructure as Code alone

With only Infrastructure as Code, Alchemy looks and works like any
other IaC tool. One file declares the Bucket and the Worker and passes
the Bucket on the Worker's `env`:

```typescript
// alchemy.run.ts
import * as Cloudflare from "alchemy/Cloudflare";

export const Uploads = Cloudflare.R2.Bucket("Uploads");

export const Api = Cloudflare.Worker("Api", {
  main: "./src/api.ts",
  env: { Uploads },
});

export type ApiEnv = Cloudflare.InferEnv<typeof Api>;
// ...plus the default-exported Alchemy.Stack that yields Api, as above
```

A second file is the handler. It reads the Bucket from that env:

```typescript
// src/api.ts
import type { ApiEnv } from "../alchemy.run.ts";

export default {
  async fetch(request: Request, env: ApiEnv) {
    const obj = await env.Uploads.get("hello.txt");
    return obj
      ? new Response(await obj.text())
      : new Response("Not found", { status: 404 });
  },
};
```

This style works and is supported. `InferEnv` types the env from the
declaration, which most IaC tools do not do.

The two files are still held together by the name `Uploads`, and the
handler knows nothing about how the Bucket got there. Infrastructure
as Effects turns those two files into the one at the top of this page.

## Infrastructure as Effects

Infrastructure as Effects adds runtimes and bindings to
Infrastructure as Code.

### Runtime

A **runtime** is a resource that carries the code it runs, such as a
Worker, Lambda Function, Container, or Server. That code is always
written the same way, as an **Effectful Constructor**:

```typescript
Effect.gen(function* () {
  // bind what you need
  const bucket = yield* Cloudflare.R2.ReadWriteBucket(Uploads);

  // return what you expose
  return { fetch: /* ... */ };
});
```

The outer Effect runs at deploy time and at cold start, and what it
returns runs per request. A Worker returns `fetch`, a Durable Object
returns its RPC methods, and a Workflow returns its run function.
Every runtime in Alchemy is a variation on that shape, as
[Runtime](/infrastructure-as-effects/runtime) shows.

### Binding

A **binding** connects a resource to the runtime that uses it:

```typescript
const bucket = yield* Cloudflare.R2.ReadWriteBucket(Uploads);
// bucket.get / bucket.put / bucket.list, typed end to end
```

It returns a typed client and generates what that client needs to
work. On Cloudflare that is a native Worker binding. On AWS it is an
IAM statement scoped to one resource, plus the resource's name in the
Function's environment:

```typescript
const getItem = yield* AWS.DynamoDB.GetItem(Jobs);
// → { Action: ["dynamodb:GetItem"], Resource: [Jobs.tableArn] }
// → Jobs_tableName=Jobs-a1b2c3
```

You don't reach for `env.Uploads` or write a policy by hand. The
binding is the SDK. See [Binding](/infrastructure-as-effects/binding).

### Layers

Every binding is a contract paired with a layer that fulfills it. You
write the handler against the contract, and the layer decides how.
Swap the layer and the handler doesn't change:

```diff lang="typescript"
 Effect.gen(function* () {
   const bucket = yield* Cloudflare.R2.ReadWriteBucket(Uploads);
   // ...
-}).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)); // native Worker binding
+}).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketHttp));    // HTTP with a scoped token
```

The same split works for services of your own. A layer can own
resources and bindings outright:

```typescript
export const JobServiceKV = Layer.effect(
  JobService,
  Effect.gen(function* () {
    const Jobs = yield* Cloudflare.KV.Namespace("Jobs");      // a resource, owned by the layer
    const kv = yield* Cloudflare.KV.ReadWriteNamespace(Jobs); // and its binding
    return { getJob: (id: string) => kv.get<Job>(id, "json") };
  }),
);
```

You write business logic against the `JobService` contract. The layer
decides the infrastructure behind it, so the same handler can read
jobs from KV in a Worker or from DynamoDB in a Lambda Function. See
[Layers](/infrastructure-as-effects/layers) for the full `JobService`
example and which hosts each layer supports.
