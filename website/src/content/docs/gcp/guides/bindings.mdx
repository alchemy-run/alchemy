---
title: How bindings grant IAM
description: What a yield* of a GCP binding actually does — the per-host service account, the role it grants, and how removing a binding revokes it.
---

On GCP, giving a container permission to call an API normally means
three separate things: create a service account, attach it to the Cloud
Run service, and add role bindings to the project IAM policy. Alchemy
collapses all three into the line that gets you the callable.

```typescript
const publish = yield* GCP.PubSub.Publish(topic);
```

That expression:

1. Creates (or adopts) a runtime service account for this host.
2. Adds `roles/pubsub.publisher` to it on that one topic's IAM policy.
3. Injects whatever the call needs into the revision.
4. Returns a typed function you call from a request handler.

It is the GCP counterpart of AWS `policyStatements` on a Lambda and of
the scoped `AccountApiToken` a Cloudflare binding mints.

## The per-host service account

Every effectful GCP host — `GCP.Run.Service` (and its alias
`GCP.Function`), `GCP.Run.Job`, `GCP.Run.WorkerPool`, and
`GCP.CloudFunctions.Function` — gets its own account. The id is the
host's name plus a hash of its type and full resource name, so no two
hosts share an account — not across stages, and not the old and new
generation of a replacement:

```
alch-api-3f9c0a1b2d@my-project.iam.gserviceaccount.com
```

Accounts Alchemy mints carry the display name `alchemy-host`, which is
how `pnpm nuke:gcp` finds them. Alchemy also grants
`roles/iam.serviceAccountUser` to the Cloud Run and Cloud Functions
service agents so they can `actAs` the account, and retries the deploy
while that grant propagates.

Pass your own `serviceAccount` on the host and Alchemy uses it instead.
The difference is what happens on removal, below.

## Which role a binding grants

Each binding grants the narrowest predefined role that covers its
operation, on the resource it is bound to wherever the service has
resource-level IAM — the GCP counterpart of an AWS statement's
`Resource: [arn]`:

| Binding | Role | Granted on |
| --- | --- | --- |
| `GCP.PubSub.Publish` | `roles/pubsub.publisher` | the topic |
| `GCP.PubSub.Pull`, `Acknowledge` | `roles/pubsub.subscriber` | the subscription |
| `GCP.Storage.GetObject` | `roles/storage.objectViewer` | the bucket |
| `GCP.Storage.PutObject`, `DeleteObject` | `roles/storage.objectUser` | the bucket |
| `GCP.SecretManager.AccessSecretVersion` | `roles/secretmanager.secretAccessor` | the secret |
| `GCP.KMS.Encrypt` / `Decrypt` | `roles/cloudkms.cryptoKeyEncrypter` / `Decrypter` | the key |
| `GCP.CloudTasks.CreateTask` | `roles/cloudtasks.enqueuer` | the queue |
| `GCP.Run.RunJob` | `roles/run.jobsExecutorWithOverrides` | the job |
| `GCP.BigQuery.InsertAll` | `roles/bigquery.dataEditor` | the table |
| `GCP.Firestore.*` | `roles/datastore.user` / `datastore.viewer` | the project |

Services with no resource-level IAM (Firestore, Memorystore, Cloud SQL,
Vertex AI, …) fall back to the narrowest role on the project. The
Memorystore RESP bindings (`ReadRedis`, `WriteRedis`, `ReadWriteRedis`)
grant nothing at all: RESP authenticates with the instance's AUTH
string, which travels to the runtime with the connection URL.

## Adding and removing

The set of bindings you yield *is* the desired IAM state. The host
records every grant it made; on the next deploy, a grant no binding
asks for any more is revoked from that resource — delete a `yield*` and
the permission goes away. For an Alchemy-minted account, the project
policy is also synced against what GCP reports, so project roles added
out of band are removed too. Accounts you supply yourself only ever
lose grants Alchemy recorded, because Alchemy cannot tell which of the
account's other roles matter.

Policies are updated read-modify-write under their etag, so parallel
hosts deploying against one project or topic converge instead of
overwriting each other. Conditional role bindings are never touched.

Destroying the host revokes every role Alchemy granted and deletes the
minted account.

## Provide the implementation

Yielding a binding gives you the interface. The layer that implements
it is provided once, at the end of the host's Effect:

```typescript
export default class Api extends GCP.Function<Api>()(
  "Api",
  { main: import.meta.url, location: "us-central1" },
  Effect.gen(function* () {
    const publish = yield* GCP.PubSub.Publish(topic);
    // ...
  }).pipe(
    Effect.provide([GCP.PubSub.PublishHttp]),
  ),
) {}
```

The convention is the binding name plus `Http`: `Publish` →
`PublishHttp`, `GetDocument` → `GetDocumentHttp`. Forget one and the
type error names the missing layer.

## Errors are typed

Bindings return the operation's real error union, so the failure modes
are in the type rather than in a status-code comparison:

```typescript
const link = yield* getDocument({ documentPath: `links/${code}` }).pipe(
  Effect.catchTag("NotFound", () => Effect.succeed(undefined)),
);
```

`NotFound`, `Forbidden`, `BadRequest`, and `Conflict` are the tags you
will handle most. Anything you do not catch stays in the channel until
you `Effect.orDie` it.

## Which host to use

- **`GCP.Function`** — alias of `GCP.Run.Service`. An HTTP server with
  a `fetch` entry. Scales to zero. Public only when you pass
  `invokerIamDisabled: true`.
- **`GCP.Run.Job`** — a `run` entry that executes and exits. Nothing is
  billed between executions. Start it with a `GCP.Run.RunJob` binding
  or Cloud Scheduler.
- **`GCP.Run.WorkerPool`** — a long-running pool with no request path,
  for pulling from a queue continuously.
- **`GCP.CloudFunctions.Function`** — the zip-source gen2 API. It does
  not take `main`; use it when you have an archive rather than a
  bundle. Bindings yielded in its Effect still grant IAM and inject env
  for the archive's code, but the Effect itself does not run there.

The first three build a container image locally, which means Docker
has to be running to deploy them.
