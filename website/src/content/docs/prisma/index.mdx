The Prisma provider manages your Prisma schema as a resource:
`Prisma.Schema` wraps `prisma migrate diff` so `alchemy deploy`
regenerates pending migration SQL whenever `schema.prisma` changes,
and the database resource downstream —
[Neon.Branch](/neon/guides/prisma),
[Planetscale.PostgresBranch](/planetscale/guides/prisma), or
[Cloudflare.D1.Database](/cloudflare/data/d1) — applies it via
`migrationsDir`. There is no setup page because there is nothing to
set up: the provider has no credentials — it just needs `prisma` and
`@prisma/client` installed (optional peers of alchemy). At runtime
you add exactly one driver adapter for your database
(`@prisma/adapter-pg`, `@prisma/adapter-d1`,
`@prisma/adapter-planetscale`, or `@prisma/adapter-neon`).

## Resources

`Schema` is the only resource. Its `out` output feeds the database's
`migrationsDir` input, so the engine orders schema generation before
migration apply in the same deploy:

```typescript
export default Alchemy.Stack(
  "MyStack",
  {
    providers: Layer.mergeAll(
      Cloudflare.providers(),
      Prisma.providers(),
      Neon.providers(),
    ),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const schema = yield* Prisma.Schema("app-schema", {
      schema: "./prisma/schema.prisma",
    });
    const project = yield* Neon.Project("app-db");
    const branch = yield* Neon.Branch("app-branch", {
      project,
      migrationsDir: schema.out,
    });
    return { branchId: branch.branchId };
  }),
);
```

[Migrations as resources](/prisma/migrations) walks through the full
pattern. The diff runs entirely offline — schema against the last
`snapshot.prisma`, no shadow database and no interactive
`prisma migrate dev` step — and the lifecycle is deliberately
conservative: `diff` returns an update only when prisma would
actually emit new SQL, so no-drift deploys are a noop that never
cascades into the database resource, and `delete` is a deliberate
no-op, because migration files are typically checked in and removing
the resource should never wipe them.

## The runtime clients

Each driver adapter has an entry point that takes your generated
`PrismaClient` class and returns a client whose queries are Effects —
yield them directly inside a Worker:

```typescript
import { postgres } from "alchemy/Prisma/Postgres";
import { PrismaClient } from "./generated/client.ts";

export default class Api extends Cloudflare.Worker<Api>()(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const hd = yield* Cloudflare.Hyperdrive.Connect(Hyperdrive);
    const prisma = yield* postgres(PrismaClient, hd.connectionString);

    return {
      fetch: Effect.gen(function* () {
        const users = yield* prisma.user.findMany();
        return yield* HttpServerResponse.json(users);
      }),
    };
  }).pipe(Effect.provide(Cloudflare.Hyperdrive.ConnectBinding)),
) {}
```

`yield* prisma.user.findMany()` produces
`Effect<User[], PrismaError>` — the full generated client surface is
lifted, so every model delegate and `$queryRaw` work the same way.
The client (and the connection pool its adapter owns) is built
lazily on the first query and memoized per execution — a
`fetch`/`queue`/`scheduled` event, a Durable Object call, a Workflow
run, or a Lambda invocation — then `$disconnect`ed when that
execution's scope closes; plan- and deploy-time evaluation never
opens a connection. Four adapters ship as subpath imports:
`alchemy/Prisma/Postgres` (any Postgres URI — Hyperdrive, Neon,
PlanetScale Postgres), `alchemy/Prisma/D1`,
`alchemy/Prisma/PlanetScale` (fetch-based MySQL), and
`alchemy/Prisma/Neon` (Neon's serverless WebSocket driver); the
generic `Prisma.client(make)` from `alchemy/Prisma` wraps any other
adapter. For the Worker wiring itself — Hyperdrive, `ConnectBinding`,
`nodejs_compat`, and the exact install commands — follow
[Prisma on Workers](/cloudflare/data/prisma).

## Compose with your cloud

[Prisma on Workers](/cloudflare/data/prisma) is the canonical Worker
wiring guide, covering both the D1 and the Hyperdrive/Postgres
paths. On the database side, [Neon](/neon/guides/prisma) and
[PlanetScale](/planetscale/guides/prisma) each wire `schema.out`
into their branch resources, while
[Neon migrations](/neon/data/migrations) and
[PlanetScale migrations](/planetscale/data/migrations) explain how
each provider orders, hashes, and applies the generated files. For
per-stage database tiering built on the same schema resource, see
[Branch from a shared database](/cloudflare/data/branch-from-shared-database).
