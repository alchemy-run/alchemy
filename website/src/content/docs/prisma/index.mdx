The Prisma provider manages your Prisma schema as a resource:
`Prisma.Schema` wraps `prisma migrate diff` so `alchemy deploy`
regenerates pending migration SQL whenever `schema.prisma` changes,
and the database resource downstream —
[Neon.Branch](/neon/guides/prisma),
[Planetscale.PostgresBranch](/planetscale/guides/prisma), or
[Cloudflare.D1.Database](/cloudflare/data/d1) — applies it via
`migrationsDir`. There is no setup page because there is nothing to
set up: the provider has no credentials — it just needs `prisma` and
`@prisma/client` installed (optional peers of alchemy). At runtime
you add exactly one driver adapter for your database
(`@prisma/adapter-pg`, `@prisma/adapter-d1`,
`@prisma/adapter-planetscale`, or `@prisma/adapter-neon`).

## Resources

`Schema` is the only resource. Its `out` output feeds the database's
`migrationsDir` input, so the engine orders schema generation before
migration apply in the same deploy:

```typescript
export default Alchemy.Stack(
  "MyStack",
  {
    providers: Layer.mergeAll(
      Cloudflare.providers(),
      Prisma.providers(),
      Neon.providers(),
    ),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const schema = yield* Prisma.Schema("app-schema", {
      schema: "./prisma/schema.prisma",
    });
    const project = yield* Neon.Project("app-db");
    const branch = yield* Neon.Branch("app-branch", {
      project,
      migrationsDir: schema.out,
    });
    return { branchId: branch.branchId };
  }),
);
```

The diff runs entirely offline — schema against the last
`snapshot.prisma`, no shadow database — so no-drift deploys are a
noop that never cascades into the database resource, and `delete` is
a deliberate no-op, because migration files are checked in and
removing the resource should never wipe them.

## The Prisma path

1. [Migrations as resources](/prisma/migrations) — declare
   `Prisma.Schema` and wire its `out` into a database's
   `migrationsDir`, so every deploy regenerates and applies pending
   SQL in order
2. [Client generation](/prisma/generate) — the deploy runs
   `prisma generate` with zero-config injection; target `workerd`
   for Workers, keep the node default for Lambda and containers
3. [Query with Effect](/prisma/effect) — hand the generated client
   to an adapter entry point and `yield*` queries with a typed
   `PrismaError` channel, or construct it directly in
   [async Workers](/prisma/async)
4. [Effect schemas](/prisma/effect-schemas) — decode rows with the
   generated `effect/Schema` structs and reuse the shapes in RPC and
   HTTP contracts
5. Wire your database — [Workers](/cloudflare/data/prisma),
   [Neon](/neon/guides/prisma), or
   [PlanetScale](/planetscale/guides/prisma)

Already running Prisma?
[Adopt an existing project](/prisma/adopt) — the first deploy
records a baseline snapshot and your `prisma migrate dev` history
carries over untouched.

## Compose with your cloud

[Prisma on Workers](/cloudflare/data/prisma) is the canonical Worker
wiring guide, covering both the D1 and the Hyperdrive/Postgres
paths. On the database side, [Neon](/neon/guides/prisma) and
[PlanetScale](/planetscale/guides/prisma) each wire `schema.out`
into their branch resources, while
[Neon migrations](/neon/data/migrations) and
[PlanetScale migrations](/planetscale/data/migrations) explain how
each provider orders, hashes, and applies the generated files. For
per-stage database tiering built on the same schema resource, see
[Branch from a shared database](/cloudflare/data/branch-from-shared-database).
