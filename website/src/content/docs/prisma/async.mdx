Prisma on alchemy works from plain async Workers too: the same
`Prisma.Schema` resource generates migrations, the same
`migrationsDir` wiring applies them on deploy, and the same
generated client serves the handler — constructed directly with the
official driver adapter, exactly as Cloudflare's own Prisma docs
show. Only client construction differs from the
[Effect client](/prisma/effect); the two styles coexist in one
stack.

## Bind the database on `env`

```typescript
// alchemy.run.ts
Effect.gen(function* () {
  const database = yield* Db;

  const worker = yield* Cloudflare.Worker("Api", {
    main: "./src/worker.ts",
    env: {
      DB: database,
    },
  });

  return { url: worker.url.as<string>() };
});
```

Bind the yielded handle — `database`, the value produced by
`yield* Db` in the stack — so the Worker receives the exact database
the stack migrated. Passing the module-level `Db` declaration itself
would instantiate a second database namespaced under the Worker,
separate from the one your migrations ran against.

## The handler

```typescript
// src/worker.ts
import type { D1Database } from "@cloudflare/workers-types";
import { PrismaD1 } from "@prisma/adapter-d1";
import { PrismaClient } from "../prisma/generated/client.ts";

interface Env {
  DB: D1Database;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const prisma = new PrismaClient({ adapter: new PrismaD1(env.DB) });
    const widgets = await prisma.widget.findMany({
      orderBy: { id: "asc" },
    });
    return Response.json({ widgets });
  },
};
```

`env.DB` is the native `D1Database` binding, and the handler builds
the client per request with `@prisma/adapter-d1` — the standard
Prisma-on-D1 setup, with alchemy involved only at deploy time. The
`PrismaClient` import points at the same
[generated output](/prisma/generate) an Effect Worker uses.

## The Hyperdrive variant

```typescript
// src/worker.ts
import type { Hyperdrive } from "@cloudflare/workers-types";
import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient } from "../prisma/generated/client.ts";

interface Env {
  HYPERDRIVE: Hyperdrive;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const prisma = new PrismaClient({
      adapter: new PrismaPg(env.HYPERDRIVE.connectionString),
    });
    const widgets = await prisma.widget.findMany();
    return Response.json({ widgets });
  },
};
```

For Postgres, bind the Hyperdrive connection on `env` the same way
(`env: { HYPERDRIVE: hyperdrive }`, plus the `nodejs_compat`
compatibility flag the pg adapter needs) and hand its
`connectionString` to `@prisma/adapter-pg`. The
[Workers guide](/cloudflare/data/prisma) covers provisioning the
Hyperdrive and the database behind it.

## Both styles in one stack

```typescript
Effect.gen(function* () {
  const database = yield* Db;

  const api = yield* Api; // Effect Worker (yields Db itself)

  const legacy = yield* Cloudflare.Worker("LegacyApi", {
    main: "./src/worker.ts",
    env: { DB: database },
  });

  return {
    url: api.url.as<string>(),
    legacyUrl: legacy.url.as<string>(),
  };
});
```

An Effect Worker and an async Worker deploy side by side against
the one migrated database — one `Prisma.Schema`, one migration
pipeline, one generated client, two handler styles. This is exactly
how alchemy's own live test fixture runs, so incremental adoption in
either direction is a supported path, not a fork in the road.
