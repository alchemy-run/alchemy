---
title: Client generation
description: Every deploy runs prisma generate with zero-config defaults — a prisma-client generator block is injected when the schema declares none, shaped by the generateClient prop.
---

Every deploy that touches a `Prisma.Schema` also runs
`prisma generate`, so the typed client stays in sync with the schema
that just produced your migrations. Generation is zero-config: the
schema file needs no `generator` block for it, and one prop covers
everything you'd otherwise configure by hand.

## Zero-config injection

```typescript
const schema = yield* Prisma.Schema("app-schema", {
  schema: "./prisma/schema.prisma",
});
```

When `schema.prisma` declares no `prisma-client` generator block,
the resource injects one at generate time, with output `./generated`
next to the schema file (matching Prisma's own convention of
resolving generator output relative to the schema). A block declared
in the schema always wins over the injected default — injection only
fills the gap when there is none.

## Target runtimes

```typescript
const schema = yield* Prisma.Schema("app-schema", {
  schema: "./prisma/schema.prisma",
  generateClient: { runtime: "workerd" },
});
```

`runtime` selects the platform the generated client targets:
`"nodejs"` (the default), `"workerd"`, `"bun"`, `"deno"`,
`"edge-light"`, or `"react-native"`. On Cloudflare Workers,
`"workerd"` is required — the default node-runtime client cannot
start on workerd (it resolves file paths at module init) — and it
loads its query compiler as a real WebAssembly module, which
alchemy's bundler uploads natively with zero extra config. The node
default is the right target for Lambda and containers.

## Shape the injected block

```typescript
const schema = yield* Prisma.Schema("app-schema", {
  schema: "./prisma/schema.prisma",
  generateClient: {
    output: "./src/generated",
    runtime: "workerd",
  },
});
```

`output` moves where the injected generator writes the client,
resolved relative to the schema file. These options shape only the
injected block — a generator block declared in `schema.prisma`
carries its own `output` and `runtime` and is used as-is.

## Checked-in clients

```typescript
const schema = yield* Prisma.Schema("app-schema", {
  schema: "./prisma/schema.prisma",
  generateClient: false,
});
```

`generateClient: false` is for clients that are checked in or
generated by another pipeline: the schema's `prisma-client` blocks
are skipped during the deploy's generate step, while every other
generator — including the [effect/Schema generator](/prisma/effect-schemas)
— still runs. Migrations regenerate exactly as before; only client
emission is affected.

## The dev loop

```prisma
// prisma/schema.prisma
generator client {
  provider = "prisma-client"
  output   = "./generated"
  runtime  = "workerd"
}
```

Declaring the block in `schema.prisma` keeps plain `prisma generate`
working outside deploys — useful while iterating on queries before
anything is deployed. The deploy respects the declared block
verbatim, so both paths emit the identical client.

## Import the client

```typescript
import { PrismaClient } from "./prisma/generated/client.ts";
```

The generated client's entry point is `client.ts` inside the output
directory. Pass the class to a
[runtime adapter entry point](/prisma/effect) in an Effect Worker,
or construct it directly with a driver adapter in an
[async Worker](/prisma/async) — both consume the same generated
output.
