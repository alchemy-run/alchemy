`Prisma.Website` builds your frontend with its own framework and deploys
it to [Prisma Compute](/prisma/compute/apps). The shared
`@alchemy.run/frontend-frameworks` Node targets produce the server and
assets; **Prisma runs that output on Bun**, uploaded as a `tar.gz`
artifact. There is no Docker build, registry, or container image to manage.

Even fully static sites run a static-file server on Compute. These
resources do not publish an assets-only deployment to a global CDN.

Omit `project` and the live deployment creates a `Prisma.Project` with
`createDatabase: false`. Pass an existing project to put the site next to
other apps or a database. `alchemy dev` runs the framework's native dev
server instead; the Website creates no Prisma project, database, app, or
domain in that mode.

## How to choose

Use the resource named after your framework. It understands the
framework's config, output layout, build, and dev server. Config files
load natively; deploy-specific overrides belong in option bags such as
`astro`, `nuxt`, `kit`, or `vite`.

Use `Vite` for client-only SPAs and multi-page HTML apps. SSR frameworks
that use Vite still need their own resources. Use `StaticSite` for a
shell command that emits a directory of files.

Shared props are `rootDir`, `memo`, `env`, `assets`, `dev`, `domain`,
and `project`. Framework-specific configuration belongs in the named
option bags, not in a Dockerfile or Compute build command.

The framework guides explain the adapter requirements: Astro and
SvelteKit get injected adapters; Nuxt and SolidStart use the managed
Nitro Node preset; Octane requires the shared `node()` marker adapter.
Next.js runs a normal Next server on Bun, not OpenNext.

Runtime dependencies are traced from the installed application into the archive;
Prisma does not run a package installation after upload. Native addons must be
built for Prisma's Linux runtime. A deployment from macOS does not cross-compile
native dependencies, so use a compatible Linux build environment for applications
that require them.

## Install

[Set up Prisma credentials](/prisma/setup) for live deployments. Install
the build integration in your frontend project:

<PackageManagers dev="@alchemy.run/frontend-frameworks @vercel/nft" />

Keep the framework's own dependencies and config. The integration is
loaded from your project at build time; `@vercel/nft` traces the runtime
dependencies for Prisma's artifact. Both are build-time dependencies.
In a monorepo, make the integration available to the frontend project
and the tracing peer available to the deployment workspace.
Each framework guide includes equivalent npm, pnpm, and yarn commands.

## Declare a Website

```typescript
// alchemy.run.ts
import * as Prisma from "@alchemy.run/prisma";

export const Website = Prisma.Website.Vite("Website", {
  rootDir: "./app",
});
```

`rootDir` defaults to `"."`. Builds are memoized from input content;
`memo` controls which changes trigger a rebuild.

## Add it to the Stack

```typescript
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "MyWebsite",
  { providers: Prisma.providers(), state: Alchemy.localState() },
  Effect.gen(function* () {
    const site = yield* Website;
    return { url: site.url };
  }),
);
```

The result is `{ url, compute, project, domain }`. `site.url` is the
Compute endpoint on deploy and the local dev-server address during
`alchemy dev`; the three backing resources are undefined during native
dev. `domain` is the hostname's `Prisma.RoutingUrl`, undefined when no custom hostname is requested.
`Alchemy.localState()` keeps state on this machine; keep that state
available for subsequent deploys and teardown.

## Share a project

Declare a project Effect when several sites should share one:

```typescript
export const Site = Prisma.Project("Site", { createDatabase: false });
```

Pass that Effect to the Website; it is resolved only on the live path:

```typescript
export const Website = Prisma.Website.Vite("Website", { project: Site });
```

You can also pass an existing project ID. The Website does not create
or own a project supplied by ID.

## Environment variables

Top-level `env` is applied before build and dev, and passed to Compute
for the live runtime. It is process environment, not Worker bindings.
Server code reads `process.env`; browser inlining follows the framework's
rules (`VITE_*`, `NEXT_PUBLIC_*`, or `PUBLIC_*`). Never put secrets in
client-visible keys.

```typescript
const site = yield* Prisma.Website.Vite("Web", {
  env: { VITE_API_URL: api.url },
});
```

A Website's automatically created project has no database. For a project
with its default database, Prisma supplies `DATABASE_URL` and
`DATABASE_URL_POOLED` to Compute; leave those system-managed keys out of
`env`. For an independently managed database, use a
[Connection](/prisma/data/connections) and pass its outputs explicitly.

## Local development

<PackageManagers run="alchemy dev" />

Framework resources run their native dev servers with HMR. `dev` options
configure the local server; the Website does not create cloud resources.
`StaticSite` can run a supplied `dev.command`, or build and serve files
locally. Sibling resources in the Stack retain their own lifecycle.

Opt a Website into live deployment during dev explicitly:

```typescript
export const Website = Prisma.Website.Vite("Website").pipe(
  Alchemy.remote(),
);
```

## Custom domains

```typescript
const site = yield* Prisma.Website.Astro("Web", {
  domain: "app.example.com",
});
```

`domain` saves the hostname as a [`Prisma.RoutingUrl`](/prisma/compute/apps#routing-urls) and changes `site.url` to `https://app.example.com` from the first deploy. A hostname serves only once a verified [domain ownership](/prisma/compute/apps#domain-ownership) covers it, so the site also declares a `Prisma.DomainOwnership` for its hostname, returned as `site.domainOwnership`. Destroying the site deletes both. A domain ownership belongs to the whole workspace, so deleting it stops every hostname that relies on it alone.

The deploy does not wait for the hostname to serve. `site.domain` is the RoutingUrl: its `status` is `pending` until Prisma finds the hostname's DNS records, and its `records` lists the `TXT` record that proves your workspace owns the hostname and the `CNAME` to the regional switchboard. Publish them with your DNS host; Prisma makes the RoutingUrl `active` once it finds them.

:::note
`site.domain` is the hostname's `Prisma.RoutingUrl`, not a `Prisma.CustomDomain`. Read `records` where you read `dnsRecords`, `status` (`active` once the hostname has gone live; it does not say whether it serves now), `state` (what the hostname is doing now, such as `waiting_for_dns`, `certificate_failed`, or `active` when it serves) and `firstUnmetCondition` where you read `foundryStatus` and `failureReason`, and `routingUrlId` where you read `customDomainId`.
:::

To publish both records in the same deploy, pass the DNS host as `dns`:

```typescript
const site = yield* Prisma.Website.Astro("Web", {
  domain: { name: "app.example.com", dns: Cloudflare.DNS.Adapter() },
});
```

With `dns`, the domain ownership publishes the `TXT` and waits up to 3 minutes for it before Prisma saves the domain ownership, then the RoutingUrl publishes the `CNAME` and waits up to 3 minutes for it before Prisma first looks at the hostname. The waits run one after the other, about 7 minutes at most. Prisma orders a certificate for each new hostname, for each hostname change, and again when an order fails or is stuck, and a workspace may order 10 an hour; see [Certificates](/prisma/compute/apps#certificates).

`AWS.Route53.Adapter()` and `Hetzner.DNS.Adapter()` work the same way. See [DNS Adapters](/infrastructure-as-code/dns-adapters) and [Routing URLs](/prisma/compute/apps#routing-urls) for what `dns` publishes and when.

### Several sites under one domain

When several sites share a domain, declare one domain ownership for it, and pass it to each site as `ownership`. No site owns it: destroying a site leaves it.

```typescript
const dns = Cloudflare.DNS.Adapter();
const example = yield* Prisma.DomainOwnership("Example", { project, domain: "*.example.com", dns });
yield* Prisma.Website.Vite("Web", { project, domain: { name: "www.example.com", dns, ownership: example } });
yield* Prisma.Website.Vite("Docs", { project, domain: { name: "docs.example.com", dns, ownership: example } });
```

A site given `ownership` declares no domain ownership and publishes no `TXT`. `ownership` must be for the site's hostname, or for the wildcard one label above it; otherwise the deploy stops before the site's hostname is saved. When `ownership` is not `verified`, the deploy logs a warning: an `unverified` one serves nothing until Prisma verifies it, and an `expiring` one keeps a serving hostname serving only until its `expiresAt`, unless its `TXT` is published. For a domain ownership declared in the stack, the warning is about the status the stack last saved, which an unchanged redeploy does not refresh.

For a domain ownership made in the Console or by another stack, pass a lookup. It is read while the deploy is planned and never changed, and the deploy fails if it does not exist:

```typescript
const shared = Prisma.DomainOwnership.lookup({ project, domain: "*.example.com" });
yield* Prisma.Website.Vite("Web", { project, domain: { name: "www.example.com", dns, ownership: shared } });
```

Cases to know:

- A wildcard does not cover its apex, and Prisma names the `TXT` of `*.example.com` and of `example.com` the same. A site on `example.com` that declares its own domain ownership would publish, and on destroy delete, the `TXT` the wildcard relies on. Declare a domain ownership for the apex without `dns`, and pass it as `ownership`: the wildcard's `TXT` proves it.
- A site whose hostname a wildcard already covers still declares a domain ownership for its exact hostname unless given `ownership`. That works, but the extra domain ownership and `TXT` are not needed; pass the wildcard instead.
- Switching a serving site to `ownership` deletes the site's own domain ownership after the RoutingUrl is updated. If the one passed is not verified yet, the hostname stops serving until it is. Pass `ownership` once it is verified.
- A site's own domain ownership cannot be looked up: the stack manages it, and the lookup is refused. To move it out of the site, deploy the site once with `.pipe(RemovalPolicy.retain())`, then declare a `Prisma.DomainOwnership` for the same domain with `.pipe(adopt(true))` and pass it as `ownership`. Without the retained deploy, the stack deletes the row after adopting it.
- Every domain ownership route needs `workspaceManage` access to the workspace. A deployer with a token limited to one project, or without that access, cannot deploy a site with a domain.

### Upgrading a site deployed with an earlier release

A site deployed with an earlier release keeps serving through the upgrade: the RoutingUrl takes over the hostname Prisma recorded for the site's custom domain, and its `CNAME` stays published. Its workspace usually already has a domain ownership for the hostname. Prisma made one for each custom domain created before RoutingUrls, as `expiring`: it keeps the hostname serving until its `expiresAt`, about 30 days after Prisma made it, and then stops it unless Prisma finds its `TXT`. The earlier release published no `TXT`.

Such a site refuses to deploy while the deploy is planned, before anything changes: the refusal names `Prisma.DomainOwnership`, or with `dns` `Prisma.DomainVerification`, and says to re-run with `--adopt`. Choose the fix by who should own the domain ownership:

- **The site should own it**, the usual case for one site on its hostname: after reading `alchemy plan`, pipe `adopt(true)` onto the site's call for one deploy. With `dns`, the site then publishes the `TXT`, and Prisma verifies the domain ownership. The site owns it from then on and deletes it when destroyed. `adopt(true)` adopts every resource of the site, not only the domain ownership; for example, a RoutingUrl another stage on the same Branch uses with the same `logicalId` moves to this site's app. `--adopt` is wider still: it adopts everything in the deploy.
- **It is managed elsewhere**, shared by several sites or by an Admin: pass `ownership: Prisma.DomainOwnership.lookup({ project, domain: "app.example.com" })`. The site then publishes no `TXT`, and destroying it leaves the domain ownership. If it is `expiring`, the deploy logs a warning, and the hostname stops serving at its `expiresAt` unless whoever manages it publishes its `TXT`.

Deploy the upgrade with the same `domain` first, and change the hostname in a later deploy. A deploy that upgrades and changes the hostname at once stops serving the old hostname without checking that the new one can serve.

### Changing or removing the hostname

Changing the hostname of a site that serves it replaces the site's domain ownership: the new one and its `TXT` are saved before the RoutingUrl, and the old ones are deleted after it. The change is refused until the new hostname can serve; with `dns` it usually passes in one deploy. See [Routing URLs](/prisma/compute/apps#routing-urls).

Removing `dns` from a site removes its `TXT` and `CNAME`. To publish them with another tool instead, publish them there first: `_prisma-verification.<hostname>` with your workspace's value and the `CNAME` to the switchboard. Copy them from your DNS host, because `site.domain.records` is empty once the hostname is `active`.
