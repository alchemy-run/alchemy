`Prisma.Compute` deploys an application onto Prisma's managed
runtime. One resource covers the whole path: optional build, artifact
upload, deployment, health check, and promotion — see
[Deployments](/prisma/compute/deployments) for the lifecycle.

## Framework apps

For frontend frameworks, prefer the [`Prisma.Website` family](/prisma/frontend/websites).
It provides framework-specific builds and native dev servers with the
same `rootDir`, `env`, `assets`, `dev`, and `domain` vocabulary as other
providers. Its output still runs on Bun in Compute, including static
sites. Use `Prisma.Compute` directly for custom builds, server apps,
and the Effect-native handlers below.

Point `path` at the app. With `build: "auto"`, alchemy detects the
framework, builds it, archives the output, and deploys the correct
server entrypoint:

```typescript
const app = yield* Prisma.Compute("api", {
  project,
  path: "./app",
  build: "auto",
  healthCheck: { path: "/api/health" },
  destroyOldDeployment: true,
});
```

The server must listen on `PORT` (injected at runtime). Auto-build
supports Bun, Next.js, Nuxt, Astro, TanStack Start, Vite, and NestJS. Generic
Vite projects are deployed as static SPAs. Use an
explicit build object when an app needs a custom command, output
directory, or entrypoint.

When `Prisma.Project` creates its default database, Prisma injects
system-managed `DATABASE_URL` and `DATABASE_URL_POOLED` values into
Compute deployments. Leave those keys out of `env`. For a standalone
`Prisma.Postgres` database, create a `Prisma.Connection` and pass its
outputs explicitly as shown in [Connections](/prisma/data/connections).

`app.url` is the deployed endpoint.

## Static sites

Generic Vite apps work with `build: "auto"`. To deploy a directory that already
contains static files, set `build.type` to `"static"` and point `outdir` at it.
Alchemy packages the files with the HTTP entrypoint Prisma Compute requires;
the application does not need its own server file or runtime dependency:

```typescript
const site = yield* Prisma.Compute("web", {
  project,
  path: "./site",
  build: {
    type: "static",
    outdir: ".",
  },
});
```

Add `command` when the output directory needs to be built first:

```typescript
const site = yield* Prisma.Compute("web", {
  project,
  path: "./app",
  build: {
    type: "static",
    command: "bun run build",
    outdir: "dist",
    spa: true,
  },
  dev: { command: "bun run dev", port: 5173 },
});
```

Set `spa: true` for client-side routers so unmatched paths serve
`index.html`. Leave it disabled for static sites that should return `404` for
missing files. Directory indexes redirect to a trailing-slash URL so relative
asset links resolve correctly.

For static builds, `archiveIgnore` patterns are relative to `outdir`. The
configured index page must remain in the archive; excluding it rejects the
deployment.

## Effect-native apps

Pass `main` and an Effect body instead of a build, and the app is
bundled from your Stack file — same shape as an Effect-native
Cloudflare Worker or Lambda:

```typescript
export default Prisma.Compute(
  "api",
  { project, main: import.meta.filename },
  Effect.gen(function* () {
    const db = yield* Prisma.Connect(connection);
    const sql = yield* SQL.Postgres({ url: db.databaseUrl });

    return {
      fetch: Effect.gen(function* () {
        const users = yield* sql`SELECT * FROM users`;
        return yield* HttpServerResponse.json(users);
      }),
    };
  }).pipe(Effect.provide(Prisma.ConnectBinding)),
);
```

## Routing URLs

`Prisma.RoutingUrl` saves a hostname for an app before its DNS exists. Without `dns`, the deploy succeeds at once, and the resource reports the records still to publish:

```typescript
const url = yield* Prisma.RoutingUrl("api", {
  app,
  hostname: "api.example.com",
});
// url.status: "pending"
// url.records: the TXT record that proves ownership and the CNAME to the switchboard
// url.setupUrl: the Console page that shows what to do next
```

Prisma makes the RoutingUrl `active` once both records are published. It also creates the domain ownership the `TXT` record proves; destroying the RoutingUrl leaves that domain ownership in place.

Pass `dns` to publish both records through a [DNS adapter](/infrastructure-as-code/dns-adapters) in the same deploy, and to wait for the hostname to serve. Destroy removes them:

```typescript
const url = yield* Prisma.RoutingUrl("api", {
  app,
  hostname: "api.example.com",
  dns: Cloudflare.DNS.Adapter(),
});
```

The records are published DNS-only, even when the adapter proxies aliases, so Prisma can see the `CNAME`. `dns` needs `hostname` as a plain string. Nothing is published under `alchemy dev`.

- Removing `dns` removes the records it published. To publish them with another tool instead, publish them there first; copy them from your DNS host, because `records` is empty once the RoutingUrl is `active`.
- A hostname that serves from another host today stops serving there as soon as its `CNAME` is replaced, until Prisma can serve it. To move such a hostname, publish the records yourself.
- A create Prisma refuses leaves both records published until you change or remove the RoutingUrl.
- A record already published with the same value is treated as the RoutingUrl's own, and destroy removes it.
- A zone apex needs a DNS host that flattens a `CNAME` at the apex. At any other host, omit `dns` and publish an ALIAS or ANAME yourself.

With `dns`, the deploy waits for the hostname to serve, so `url.status` is `active` when it finishes. It waits up to about a minute for the records to appear at the hostname's nameservers before Prisma checks them, then up to 6 minutes for the RoutingUrl to become `active`. A certificate normally takes about 20 seconds, and Prisma looks at it again 3 minutes after ordering it.

- When the wait runs out, the deploy fails with `RoutingUrlNotActive`. Its message names the first condition not met and quotes Prisma's last sync error. Prisma keeps working on the hostname; redeploy to wait again.
- When the workspace has reached its hourly limit of new certificates, the deploy fails at once with `RoutingUrlCertificateLimitReached`, which says when the limit resets. Prisma continues on its own at that time, and a redeploy after then waits for the hostname.
- A deploy that failed while waiting has saved the RoutingUrl. The next deploy finds it and does not create another.

### How many hostnames you can add

A workspace can add about 10 custom hostnames an hour, because each one needs a new certificate. Every RoutingUrl a deploy or a test creates counts, also one created again after it was deleted. Count CI reruns and parallel jobs that deploy to the same workspace. A hostname that waits for the limit serves on its own once the limit resets.

A RoutingUrl is identified on its Branch by `logicalId`, which defaults to the resource's fully qualified name: `Prisma.RoutingUrl("Url", …)` declared inside a `Prisma.Website` named `Site` gets `Site/Url`. Without state, a RoutingUrl takes over a row on its own app that has its `logicalId`, or one with no `logicalId` and its hostname, such as the row Prisma made for a custom domain. A row with its `logicalId` on another app belongs to another stage or stack sharing the Branch, and is taken over only with `--adopt`. Changing the hostname of an `active` RoutingUrl fails before anything changes, until the workspace is shown to own the new hostname and every authoritative nameserver for it answers with either a `CNAME` to the regional switchboard or, with no `CNAME`, A or AAAA records that include a switchboard address. A `CNAME` to any other name does not pass, even when that name has the switchboard's addresses. Ownership is shown by a verified domain ownership that covers the hostname, or by its `TXT` record at every authoritative nameserver, which Prisma verifies when it saves the change. The error lists the records still missing, so publishing them and redeploying lets the change through. With `dns`, the new hostname's records are published in the same deploy, and the old hostname's records are removed only once the change is saved.

Any hostname passes with either form. A zone apex such as `example.com` cannot have a `CNAME`, so point it at the switchboard with an ALIAS, ANAME or flattened `CNAME`, which gives it the switchboard's addresses. When the check cannot query the nameservers from your machine, the change is refused, and the error's `switchboardDns` or `ownership` is `unknown`. The check does not see a RoutingUrl in another workspace that holds the new hostname; then the change goes through, and the new hostname stays `pending` with `heldBy` set.

Prisma records a custom domain as a RoutingUrl, and has done so for every custom domain since its backfill ran on 2026-11-17. To move a hostname from `Prisma.CustomDomain`, replace it with a `Prisma.RoutingUrl` for the same app and hostname in one deploy. The RoutingUrl takes over the row Prisma recorded, and the CustomDomain's delete leaves that row in place.

### Proving a wildcard once

Prisma creates the domain ownership for each RoutingUrl's exact hostname. To serve many hostnames under one domain without a `TXT` record for each, prove a wildcard once with `Prisma.DomainOwnership`:

```typescript
yield* Prisma.DomainOwnership("example.com", {
  project,
  domain: "*.example.com",
  dns: Cloudflare.DNS.Adapter(),
});
yield* Prisma.RoutingUrl("api", { app: api, hostname: "api.example.com" });
yield* Prisma.RoutingUrl("admin", { app: admin, hostname: "admin.example.com" });
```

A wildcard and its apex share one record name (`_prisma-verification.example.com`), so prove only one of them per zone. Without `dns`, publish the record yourself: the deploy fails with `PrismaDomainOwnershipRequired`, which names the record. Don't declare a `Prisma.DomainOwnership` for the exact hostname of a `Prisma.RoutingUrl`: it takes over the domain ownership Prisma created for the RoutingUrl, and deletes it on destroy.

## Custom domains (deprecated)

:::caution
Prisma removes the custom domain routes `Prisma.CustomDomain` uses about 2026-12-21. Use [`Prisma.RoutingUrl`](#routing-urls) instead; it takes over a custom domain's hostname in one deploy.
:::

Until then, an existing `Prisma.CustomDomain` keeps working. Its `dnsRecords` lists the DNS to publish and `status` tells whether it serves. Changing its hostname or app is rejected.

## Local dev

Under `alchemy dev`, `dev.command` runs your app locally (e.g.
`vite dev`) with the same env the deployed app would see — including
connection bindings, which resolve to the local
[dev database](/prisma/data/postgres#local-dev):

```typescript
const app = yield* Prisma.Compute("web", {
  project,
  path: ".",
  dev: { command: "bun run dev" },
  env: { DATABASE_URL: connection.databaseUrl },
});
```
