`Prisma.Compute` deploys an application onto Prisma's managed
runtime. One resource covers the whole path: optional build, artifact
upload, deployment, health check, and promotion — see
[Deployments](/prisma/compute/deployments) for the lifecycle.

## Framework apps

For frontend frameworks, prefer the [`Prisma.Website` family](/prisma/frontend/websites).
It provides framework-specific builds and native dev servers with the
same `rootDir`, `env`, `assets`, `dev`, and `domain` vocabulary as other
providers. Its output still runs on Bun in Compute, including static
sites. Use `Prisma.Compute` directly for custom builds, server apps,
and the Effect-native handlers below.

Point `path` at the app. With `build: "auto"`, alchemy detects the
framework, builds it, archives the output, and deploys the correct
server entrypoint:

```typescript
const app = yield* Prisma.Compute("api", {
  project,
  path: "./app",
  build: "auto",
  healthCheck: { path: "/api/health" },
  destroyOldDeployment: true,
});
```

The server must listen on `PORT` (injected at runtime). Auto-build
supports Bun, Next.js, Nuxt, Astro, TanStack Start, Vite, and NestJS. Generic
Vite projects are deployed as static SPAs. Use an
explicit build object when an app needs a custom command, output
directory, or entrypoint.

When `Prisma.Project` creates its default database, Prisma injects
system-managed `DATABASE_URL` and `DATABASE_URL_POOLED` values into
Compute deployments. Leave those keys out of `env`. For a standalone
`Prisma.Postgres` database, create a `Prisma.Connection` and pass its
outputs explicitly as shown in [Connections](/prisma/data/connections).

`app.url` is the deployed endpoint.

## Static sites

Generic Vite apps work with `build: "auto"`. To deploy a directory that already
contains static files, set `build.type` to `"static"` and point `outdir` at it.
Alchemy packages the files with the HTTP entrypoint Prisma Compute requires;
the application does not need its own server file or runtime dependency:

```typescript
const site = yield* Prisma.Compute("web", {
  project,
  path: "./site",
  build: {
    type: "static",
    outdir: ".",
  },
});
```

Add `command` when the output directory needs to be built first:

```typescript
const site = yield* Prisma.Compute("web", {
  project,
  path: "./app",
  build: {
    type: "static",
    command: "bun run build",
    outdir: "dist",
    spa: true,
  },
  dev: { command: "bun run dev", port: 5173 },
});
```

Set `spa: true` for client-side routers so unmatched paths serve
`index.html`. Leave it disabled for static sites that should return `404` for
missing files. Directory indexes redirect to a trailing-slash URL so relative
asset links resolve correctly.

For static builds, `archiveIgnore` patterns are relative to `outdir`. The
configured index page must remain in the archive; excluding it rejects the
deployment.

## Effect-native apps

Pass `main` and an Effect body instead of a build, and the app is
bundled from your Stack file — same shape as an Effect-native
Cloudflare Worker or Lambda:

```typescript
export default Prisma.Compute(
  "api",
  { project, main: import.meta.filename },
  Effect.gen(function* () {
    const db = yield* Prisma.Connect(connection);
    const sql = yield* SQL.Postgres({ url: db.databaseUrl });

    return {
      fetch: Effect.gen(function* () {
        const users = yield* sql`SELECT * FROM users`;
        return yield* HttpServerResponse.json(users);
      }),
    };
  }).pipe(Effect.provide(Prisma.ConnectBinding)),
);
```

## Routing URLs

`Prisma.RoutingUrl` saves a hostname for an app before its DNS exists. A hostname serves once a verified domain ownership covers it and its `CNAME` points at the regional switchboard. Declare the domain ownership with `Prisma.DomainOwnership` next to the RoutingUrl. With `dns` on both, the deploy publishes the `TXT` and the `CNAME` through a [DNS adapter](/infrastructure-as-code/dns-adapters):

```typescript
yield* Prisma.DomainOwnership("api-domain", {
  project,
  domain: "api.example.com",
  dns: Cloudflare.DNS.Adapter(),
});
const url = yield* Prisma.RoutingUrl("api", {
  app,
  hostname: "api.example.com",
  dns: Cloudflare.DNS.Adapter(),
});
// Prisma.DomainOwnership publishes TXT _prisma-verification.api.example.com
//   and creates the workspace's domain ownership
// Prisma.RoutingUrl publishes CNAME api.example.com -> switchboard.{region}.prisma.build
//   and saves the hostname
// The deploy ends with url.status "pending"; Prisma makes it "active" on its own
//   once the domain ownership is verified and the certificate is issued
```

Without `dns`, both are saved at once, and the records to publish are in the domain ownership's `recordName` and `recordValue` and the `CNAME` in `url.records`:

```typescript
const ownership = yield* Prisma.DomainOwnership("api-domain", {
  project,
  domain: "api.example.com",
});
const url = yield* Prisma.RoutingUrl("api", {
  app,
  hostname: "api.example.com",
});
// publish TXT ownership.recordName with value ownership.recordValue
// url.status: "pending"; "active" once the hostname has gone live, and back to "pending"
//   only when the hostname changes, the service is deleted, or ownership lapses
// url.state: what the hostname is doing now, such as "no_domain_ownership",
//   "not_verified", "waiting_for_dns", "certificate_failed", or "active" when it serves
// url.records: the TXT record that proves ownership and the CNAME to the switchboard
// url.setupUrl: the Console page that shows the live state and what to do next
```

The two resources are saved in either order. The deploy ends once the RoutingUrl is saved, before the hostname serves, so the hostname may not answer yet. After a first deploy that declares the domain ownership, `url.state` can be `no_domain_ownership`, `not_verified`, `waiting_for_dns` or a certificate state; none needs action, and the hostname serves a few minutes later. In `no_domain_ownership` with no domain ownership declared, the `TXT` in `records` is the one a domain ownership for the exact hostname would use, and publishing it does nothing until one exists; the deploy logs a warning. `status` and `state` are as of the deploy's last write or check. The Console page at `setupUrl`, or `GET /v1/urls/{id}`, shows them live, and its Check button, or `POST /v1/urls/{id}/check`, makes Prisma look at the DNS now.

A stack that should not manage a workspace-level resource, such as one deployed with a token limited to one project, can set `createDomainOwnership: true` on the RoutingUrl instead. Prisma then creates an `unverified` domain ownership for the exact hostname, unless a verified one already covers it, and leaves it when the RoutingUrl is destroyed. `dns` does not publish its `TXT`, so publish the `TXT` in `records` yourself. Don't combine it with a `Prisma.DomainOwnership` for the same exact hostname: when the RoutingUrl is saved first, that resource then needs `--adopt`. Prisma does not store the option, so a domain ownership deleted later is created again only by the next deploy that changes the RoutingUrl's props.

A RoutingUrl's `dns` publishes only the `CNAME`. It is published DNS-only, even when the adapter proxies aliases, so Prisma can see it. `dns` needs `hostname` as a plain string. Nothing is published under `alchemy dev`.

- Removing `dns` removes the `CNAME` it published. To publish it with another tool instead, publish it there first.
- A hostname that serves from another host today stops serving there as soon as its `CNAME` is replaced, until Prisma can serve it. To move such a hostname, publish the record yourself.
- A record already published with the same value is treated as the RoutingUrl's own, and destroy removes it.
- A zone apex needs a DNS host that flattens a `CNAME` at the apex. At any other host, omit `dns` and publish an ALIAS or ANAME yourself.
- Before Prisma first looks at a new hostname, the deploy waits up to 3 minutes for the `CNAME` at the hostname's authoritative nameservers. While it is still absent, the deploy fails with `RoutingUrlRecordsNotSeen`, and Prisma was not changed. A nameserver your machine cannot query does not raise it. Redeploy once the record appears; if it never does, check that the domain is delegated to this DNS host at its registrar.
- When that save leaves the RoutingUrl in `waiting_for_dns` with no custom domain, the deploy asks Prisma to check once.

A RoutingUrl is identified on its Branch by `logicalId`, which defaults to the resource's fully qualified name: `Prisma.RoutingUrl("Url", …)` declared inside a `Prisma.Website` named `Site` gets `Site.Url`. Without state, a RoutingUrl takes over a row on its own app that has its `logicalId`, or one with no `logicalId` and its hostname, such as the row Prisma made for a custom domain. A row with its `logicalId` on another app belongs to another stage or stack sharing the Branch, and is taken over only with `--adopt`.

Changing the hostname of an `active` RoutingUrl fails before anything changes, until the workspace is shown to own the new hostname and every authoritative nameserver for it answers with either a `CNAME` to the regional switchboard or, with no `CNAME`, A or AAAA records that include a switchboard address. A `CNAME` to any other name does not pass, even when that name has the switchboard's addresses. Ownership is shown by a verified domain ownership that covers the hostname, or by the `TXT` record of a covering domain ownership of any status at every authoritative nameserver, which Prisma verifies when it saves the change. With no covering domain ownership, the exact hostname's `TXT` counts only with `createDomainOwnership: true`; otherwise the error's `ownership` is `noDomainOwnership`. The check looks once and does not wait, so a hostname change made together with a new `Prisma.DomainOwnership` for the new hostname can be refused on the first deploy and pass on the next, once the domain ownership exists. The error lists the records still missing. With `dns`, the new hostname's `CNAME` is published in the same deploy, and the old hostname's is removed only once the change is saved.

Any hostname passes with either form. A zone apex such as `example.com` cannot have a `CNAME`, so point it at the switchboard with an ALIAS, ANAME or flattened `CNAME`, which gives it the switchboard's addresses. When the check cannot query the nameservers from your machine, the change is refused, and the error's `switchboardDns` or `ownership` is `unknown`. The check does not see a RoutingUrl in another workspace that holds the new hostname; then the change goes through, and the new hostname stays `pending` with `state: "in_use_elsewhere"` and `heldBy` set.

Prisma records a custom domain as a RoutingUrl, and has done so for every custom domain since its backfill ran on 2026-11-17. To move a hostname from `Prisma.CustomDomain`, replace it with a `Prisma.RoutingUrl` for the same app and hostname in one deploy. The RoutingUrl takes over the row Prisma recorded, and the CustomDomain's delete leaves that row in place.

### Certificates

A failed certificate shows as `state: "certificate_failed"` with Prisma's reason in `certificateFailureReason`. A deploy does not retry it. Retry it from the RoutingUrl's `setupUrl` in the Console or with one `POST /v1/urls/{id}/check`; a retry orders a new certificate, which counts toward the workspace's hourly limit. A RoutingUrl that holds a custom domain is never checked by a deploy; check it from the Console.

Prisma orders a certificate for each new hostname once its records are published, for each hostname change, and again when an order fails or is stuck. A workspace may order 10 an hour. A RoutingUrl created again after it was deleted counts again, so count CI reruns and parallel jobs that deploy to the same workspace. At the limit, the hostname stays `pending`, `customDomainSyncError` says when the limit resets, and Prisma then continues on its own.

### Domain ownership

A domain ownership is the workspace's record that it owns a domain, which is an exact hostname or a wildcard. It belongs to the workspace, not to a project. `Prisma.DomainOwnership` saves one and reports Prisma's `status`. Without `dns`, it does not wait for DNS. With `dns`, it publishes the `TXT` record first, waits up to 3 minutes for it at the authoritative nameservers, then saves the domain ownership and asks Prisma to verify; it never fails because the record is missing or Prisma has not verified it. Removing `dns` from a deployed domain ownership deletes the record, and a verified domain ownership becomes `expiring` at Prisma's next lookup of that record. A wildcard covers every hostname under it, so those hostnames need no `TXT` record of their own:

```typescript
yield* Prisma.DomainOwnership("example.com", {
  project,
  domain: "*.example.com",
  dns: Cloudflare.DNS.Adapter(),
});
yield* Prisma.RoutingUrl("api", { app: api, hostname: "api.example.com" });
yield* Prisma.RoutingUrl("admin", { app: admin, hostname: "admin.example.com" });
```

A wildcard and its apex share one record name (`_prisma-verification.example.com`), so prove only one of them per zone. `unverified` at the end of a deploy means Prisma has not seen the record yet; without `dns`, publish `recordName` with `recordValue`. Prisma looks again when Check is pressed on the workspace's Domains page or a RoutingUrl's `setupUrl`, when `POST /v1/domain-ownerships/{id}/verify` or `POST /v1/urls/{id}/check` is called, when a hostname it covers is created, updated or checked, and once 10 minutes after a lookup that did not find the record.

A domain ownership the stack did not create needs `--adopt`, or better `adopt(true)` on that one resource, since `--adopt` adopts everything unowned in the stack. Such rows come from the Console, from a RoutingUrl with `createDomainOwnership: true`, from Prisma's backfill of older custom domains, and from other stacks. Once two stacks have it, destroying either deletes it, and with `dns` its record, for both. Declare a shared one in one stack, with `RemovalPolicy.retain()` if it must outlive that stack. With `dns`, the refusal can name `Prisma.DomainVerification`, the resource that checks for an existing domain ownership of this domain or of the wildcard or apex that shares its record, before the record is published. Adopting in that last case makes the stack publish, and on destroy delete, the record the other domain ownership also uses. Adding `dns` to a deployed domain ownership does not check the wildcard or apex, so prove only one of the two per zone.

A domain ownership belongs to a workspace. Moving `project` to a project in another workspace fails the deploy and changes nothing. Either point `project` back, or remove the domain ownership from the stack and deploy, which deletes it from the old workspace unless it is retained, then declare it again.

## Custom domains (deprecated)

:::caution
Prisma removes the custom domain routes `Prisma.CustomDomain` uses about 2026-12-21. Use [`Prisma.RoutingUrl`](#routing-urls) instead; it takes over a custom domain's hostname in one deploy.
:::

Until then, an existing `Prisma.CustomDomain` keeps working. Its `dnsRecords` lists the DNS to publish and `status` tells whether it serves. Changing its hostname or app is rejected.

## Local dev

Under `alchemy dev`, `dev.command` runs your app locally (e.g.
`vite dev`) with the same env the deployed app would see — including
connection bindings, which resolve to the local
[dev database](/prisma/data/postgres#local-dev):

```typescript
const app = yield* Prisma.Compute("web", {
  project,
  path: ".",
  dev: { command: "bun run dev" },
  env: { DATABASE_URL: connection.databaseUrl },
});
```
