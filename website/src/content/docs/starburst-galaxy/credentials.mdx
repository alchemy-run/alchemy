Galaxy has three kinds of login, and Alchemy uses each for one job.

| Login | Who uses it | Where it comes from |
| --- | --- | --- |
| API client (client ID and secret) | Alchemy at deploy, and hosts through bindings | Galaxy's console; saved in a profile |
| Service account password | Trino clients: the CLI, JDBC, BI tools | `ServiceAccountPassword` in your Stack |
| User | People in Galaxy's console | Invitations or SCIM, outside Alchemy |

## Deploying

Alchemy calls Galaxy's API as the API client in your profile ([Setup](/starburst-galaxy/setup)), or in CI as `STARBURST_GALAXY_DOMAIN`, `STARBURST_GALAXY_CLIENT_ID` and `STARBURST_GALAXY_CLIENT_SECRET`. It exchanges the client ID and secret for an access token that lasts ten minutes, and gets a new one before it expires.

The client's role bounds the deploy: a Stack can only create what that role may create. `accountadmin` may manage everything; a narrower role works for a Stack that declares less.

Galaxy allows about 20 API calls every 10 seconds per account. When it answers 429, Alchemy waits as long as Galaxy says and retries, so a large deploy slows down instead of failing.

## Bindings

A binding lets a host (a Cloudflare Worker, a Lambda) call Galaxy while it runs: read a catalog's tables, run a SQL job, evaluate a data quality check.

```typescript title="src/Api.ts"
import * as Cloudflare from "@alchemy.run/cloudflare";
import * as StarburstGalaxy from "@alchemy.run/starburst-galaxy";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/http/HttpServerResponse";

const shop = StarburstGalaxy.Catalog.PostgresqlCatalog.lookup({ name: "shop" });

export default class Api extends Cloudflare.Worker<Api>()(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const listTables = yield* StarburstGalaxy.Discovery.ListCatalogSchemaTables(shop);
    return {
      fetch: Effect.gen(function* () {
        const tables = yield* listTables({ schemaName: "public" });
        return yield* HttpServerResponse.json(tables.map((table) => table.tableId));
      }).pipe(Effect.orDie),
    };
  }).pipe(Effect.provide(StarburstGalaxy.Discovery.ListCatalogSchemaTablesHttp)),
) {}
```

Galaxy can't create an API client or a token through its API, and it trusts no workload identity, so Alchemy can't give each host a login of its own. A host calls Galaxy as the API client that deployed it: Alchemy binds the account domain, client ID and client secret into the host (`STARBURST_GALAXY_DOMAIN`, `STARBURST_GALAXY_CLIENT_ID`, and the secret as a secret binding, `STARBURST_GALAXY_CLIENT_SECRET`), and the host exchanges them for its own access tokens.

So the deploying client's role is also every host's role. Deploy hosts from a profile whose API client holds a role with only the privileges the bindings need, separate from the client that manages your account.

## Trino clients

Queries go to a cluster's Trino endpoint (`cluster.trinoUri`), not to the API. Give each application a `ServiceAccount` with a role, and a `ServiceAccountPassword`:

```typescript
const reporter = yield* StarburstGalaxy.ServiceAccount.ServiceAccount("Reporter", {
  role: reporting.roleId,
});
const password = yield* StarburstGalaxy.ServiceAccount.ServiceAccountPassword("ReporterPassword", {
  serviceAccount: reporter.serviceAccountId,
});
```

The application logs in as `reporter.userName` with `password.trinoPassword`. The password is created once and kept in state; Galaxy never shows it again. A new `ServiceAccountPassword` (or a replaced one) gives a new password, and deleting it revokes the old one.
