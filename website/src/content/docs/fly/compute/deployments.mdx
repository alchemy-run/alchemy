title: Blue/green deployments
description: Deploy replacements, check readiness, and shut down old Fly processes.

Enable blue/green on your Service to prepare new Machines before retiring the old ones. Keep one Service declaration. Alchemy manages both versions.

```typescript title="api.ts"
import * as Fly from "alchemy/Fly";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export const app = Fly.App("App");

export default class Api extends Fly.Service<Api>()(
  "Api",
  {
    app,
    main: import.meta.url,
    deploy: { strategy: "bluegreen" },
  },
  Effect.succeed({
    fetch: Effect.succeed(HttpServerResponse.text("hello")),
  }),
) {}
```

The props configure the Machines. The Effect defines the application they run. `Fly.Machine` and Fly websites accept the same deployment policy.

The default is `rolling`. It updates Machines in place, one at a time. A single Machine can be unavailable during that update.

## Enable replacement deployments

Add the Service to your stack. A public App also needs an [IP assignment](/fly/networking).

```typescript title="alchemy.run.ts"
import * as Alchemy from "alchemy";
import * as Fly from "alchemy/Fly";
import * as Effect from "effect/Effect";
import Api, { app } from "./api.ts";

export default Alchemy.Stack(
  "Site",
  { providers: Fly.providers(), state: Alchemy.localState() },
  Effect.gen(function* () {
    yield* Fly.IpAssignment("PublicIp", { app, type: "shared_v4" });
    const api = yield* Api;
    return { url: api.url };
  }),
);
```

Deploy with the usual command. There is no separate promotion command.

```sh
alchemy deploy
```

For an always-running Service with `count: 1`, a code change temporarily runs two Machines. The App URL stays the same. The Machine ID changes. With more replicas, Alchemy prepares the replacement set before retiring the old set. The same process handles changes to `count`.

## Choose a readiness check

Services include a TCP check by default. Use an HTTP check when a listening port is not enough to prove the application is ready.

```typescript
const http: Fly.MachineService = {
  protocol: "tcp",
  internalPort: 3000,
  autostop: "off",
  ports: [
    { port: 80, handlers: ["http"], forceHttps: true },
    { port: 443, handlers: ["tls", "http"] },
  ],
  checks: [{
    type: "http",
    port: 3000,
    path: "/healthz",
    interval: "5s",
    timeout: "2s",
  }],
};
```

Pass `services: [http]` in the Service props. Implement `/healthz` in your handler and return success only when the application and its dependencies are ready. Alchemy does not create the endpoint for you.

Every published service needs a service check. Named top-level `checks` are useful for private workers, but do not replace checks on public services or publish a port.

Alchemy requires passing reports for the current instance of every candidate it starts. Missing, stale, warning, or failed reports do not count. Fly caps service-check intervals at 60 seconds. Named top-level checks can use longer intervals.

## Set the readiness deadline

Set `deploy.healthTimeout` in the Service props to allow more time for initialization and check reporting.

```typescript
const deploy: Fly.MachineDeploy = {
  strategy: "bluegreen",
  healthTimeout: "90 seconds",
};
```

The default is 60 seconds after a separate startup wait. The maximum is 300 seconds. Changing only this deadline does not create a new application generation.

## How replacement works

For an always-running single replica, deployment follows these steps.

1. Acquire a native lease on the old Machine before mutating it.
2. Start a replacement and wait for readiness. Keep it excluded from normal Fly Proxy traffic while the old Machine serves requests.
3. Record promotion intent and admit traffic to the replacement. Allow 10 seconds for routing propagation.
4. Check readiness again, exclude the old Machine from new proxy traffic, and allow another 10 seconds for propagation.
5. Stop the old Machine using its own shutdown policy. Wait for it to retire and verify deletion.

The traffic switch is not atomic. Both versions can receive requests during the overlap. Database changes and shared services must support both versions.

Excluding a Machine from proxy traffic is called cordoning. It does not stop private-network calls, queue consumers, or scheduled jobs. Replacement Machines also cost money while they overlap with the old ones. Alchemy does not add a coordinator Machine or deployment service.

## Keep idle capacity with stop or suspend

`count` is the number of provisioned Machines. It does not require every process to run continuously.

These Service props provision three Machines and let Fly stop idle capacity. They reuse the `http` service above.

```typescript
const props: Fly.ServiceProps = {
  app,
  main: import.meta.url,
  count: 3,
  deploy: { strategy: "bluegreen" },
  services: [{
    ...http,
    autostop: "stop",
    autostart: true,
    minMachinesRunning: 1,
  }],
};
```

Use `"suspend"` instead of `"stop"` to allow suspension. Fly's regional and per-service minimum-running rules still apply.

| Policy | Process behavior |
| --- | --- |
| `"off"` | Keep the desired replicas running. |
| `"stop"` | Shut down idle capacity. A later start boots a new process. |
| `"suspend"` | Pause and resume a Machine when supported. A resume can fall back to a cold start. |

During replacement, Alchemy starts and checks at least one candidate and any additional candidates needed for the running floor. Other idle candidates can stay unstarted. It restores the desired autostop policy before retiring the old Machines. If restoration starts a new instance, that instance must pass fresh checks.

Idle Machines remain in the resource outputs. Stopping or suspending them does not by itself trigger a new rollout. Alchemy does not restart an idle predecessor just to retire it.

Suspension is not SIGTERM shutdown. Do not rely on finalizers running when a Machine suspends. Replacing a suspended Machine creates a new process rather than transferring its memory snapshot.

## Set the shutdown deadline

Set `shutdown` in the Service props to give the old process time to finish work.

```typescript
const shutdown: Fly.MachineShutdown = {
  signal: "SIGTERM",
  timeout: "45 seconds",
};
```

Blue/green defaults to SIGTERM and 30 seconds. The maximum is 300 seconds. Durations must be positive and finite, with whole-millisecond precision. Managed Services support SIGTERM and SIGINT.

Retirement uses the old Machine's signal and timeout. Giving the new version a shorter timeout does not shorten the old version's window.

Managed Effect Services stop accepting HTTP requests and drain existing responses, including streamed bodies. Worker cleanup begins at the same time. Request scopes and shared dependencies stay alive until HTTP and worker cleanup settle.

HTTP draining gets 80% of the shutdown window. Remaining connections close after that. A hard exit at 90% bounds stuck finalizers. The first signal starts the deadline and later signals do not extend it. A hard exit does not mean all work finished.

Setting `shutdown` also enables graceful rolling scale-down and deletion. It does not make a single Machine continuously available during an in-place update. Omitting both policies preserves the existing rolling and runtime defaults.

:::caution[The first replacement]
An already-running process cannot gain a shutdown handler retroactively. Its first replacement may interrupt requests. Raw images and external website servers must implement their own shutdown handling.
:::

## Deploy a private worker

Set `services: []` to avoid publishing proxy ports. Add a named check that the worker actually serves.

```typescript
const workerProps: Fly.ServiceProps = {
  app,
  main: import.meta.url,
  services: [],
  deploy: { strategy: "bluegreen" },
  checks: {
    ready: { type: "http", port: 3000, path: "/ready" },
  },
};
```

A Service can return `fetch`, `run`, or both. In this example, `readiness` and `runJobs` are Effects defined by your application.

```typescript
import { readiness, runJobs } from "./jobs.ts";

const program = Effect.succeed({
  fetch: readiness,
  run: runJobs,
});
```

Pass `workerProps` and `program` to `Fly.Service`. A private `fetch` handler can serve the readiness endpoint without publishing it through Fly Proxy. A run-only program must start its own readiness server.

Acquire connections and start consumers inside `run`. The outer initialization Effect also runs during deployment evaluation.

Raw `Fly.Machine` images accept the same check and shutdown props, but own their signal handling. Use immutable image tags or digests. Repushing an unchanged tag does not declare a configuration change.

## Own the job drain with ordinary scopes

Alchemy cannot infer queue behavior from a health endpoint. Use ordinary Effect finalizers to stop acquiring jobs, then finish or checkpoint work already owned by the process.

```typescript title="jobs.ts"
import * as Effect from "effect/Effect";
import * as Scope from "effect/Scope";
import { QueueClient, Jobs } from "./queue.ts";

export const runJobs = Effect.scoped(Effect.gen(function* () {
  const client = yield* QueueClient.acquire;
  const workScope = yield* Scope.make();
  yield* Effect.addFinalizer((exit) => Scope.close(workScope, exit));

  const worker = yield* Jobs.start({ client, workScope });
  yield* Effect.addFinalizer(() =>
    worker.stopAcquiring.pipe(Effect.andThen(worker.awaitIdle)),
  );
  yield* Effect.never;
}));
```

`QueueClient` and `Jobs` are application code, not Alchemy APIs. Here, `QueueClient.acquire` registers connection cleanup and `Jobs.start` forks jobs into `workScope`. Finalizers run in reverse order. Stop and drain the worker first, close its work scope next, then release the client.

`stopAcquiring` must also account for a claim already in flight. Seeing no active jobs before closing that gate does not prove the drain is complete. Jobs in the worker's own closing scope may be interrupted, which is why this example gives them a separate work scope.

Give independent workers separate scopes so they can begin cleanup concurrently. Keep cleanup within the process deadline. If acquisition cannot be stopped, cancel the poller and finish, checkpoint, or release claims where possible.

Both generations can consume jobs before and during promotion. Queue leases, deduplication, and idempotency belong to the application. Blue/green does not provide exactly-once delivery or single-consumer execution.

## Retry a failed deployment

Before promotion, a definite readiness failure preserves the old generation. Alchemy removes only candidates it can prove are owned and unpromoted. Uncertain creation or cleanup returns an error rather than claiming rollback succeeded.

After promotion may have happened, Alchemy preserves replacements that might be serving traffic. Run the same command to finish the transition.

```sh
alchemy deploy
```

`rolloutPending` reports unfinished work. Healthy replacement outputs do not mean every predecessor was removed. `alchemy destroy` also discovers owned unfinished generations whose IDs were never saved. Keep Alchemy's ownership metadata intact.

A genuinely unreachable host may require force-deleting an owned, stateless predecessor after the replacement is ready. This cannot prove the old process drained. Transport failures, foreign leases, unclear ownership, and attached storage do not authorize that fallback. Failed retirement remains an error.

## Understand native lease limits

Alchemy acquires and renews native Machine leases for the targets it owns. It stops scheduling new mutations if it loses a lease. It cannot undo a request Fly already accepted.

Machine leases are not an App-wide deployment lock. A first deployment has no old Machine to lock. Older binaries and direct API writers can also overlap. Serialize deployments to the same stack and resource in CI.

LocalState outputs are cached observations, not a cross-process lock. State-store locking depends on the chosen backend. Ownership is checked again before deleting an old Machine.

Fly rejects exec requests while a native lease is held, even with the holder's nonce. Wait for the deployment to release its lease before using exec. Readiness checks do not need exec access.

App deletion uses a name rather than a leased App instance. If its outcome is unclear, inspect and reconcile the App before retrying or reusing that name. A delayed delete could still act on it.

## Treat secret versions as a floor

Service-bound secrets are prepared before candidate creation. `minSecretsVersion` is the oldest acceptable secret version, not a fixed snapshot. Candidates must not knowingly start below that floor.

Other Services, standalone `Fly.Secret` resources, and runtime writers can update the same App vault. Machine leases do not serialize those writes. Alchemy does not roll back the App's secret values.

An out-of-band secret update does not guarantee a Service rollout. Change a deployment input when rotation needs new Machines. Standalone Machines can set `minSecretsVersion` explicitly.

## Use stable outputs

The logical resource and App URL stay stable during an update. `machineId`, `machineIds`, private IPs, and physical names can change.

An explicit `name` is the base for generation-qualified names. `baseName` records that base. Changes to the App, region, or logical name keep their normal replacement behavior and may be disruptive.

## Check incompatible settings

Blue/green requires a persistent process with readiness checks. It rejects attached volumes, including `MountVolume` bindings, because both generations cannot safely share a Fly volume.

It also rejects explicit `skipLaunch`, auto-destroy or one-shot configuration, SIGKILL, and invalid durations or signals. Every published service needs a service check. Alchemy reports these errors rather than silently switching to rolling.

Use rolling updates for volume-backed workloads, or design a separate data migration. Stop and suspend are supported through the idle-capacity behavior described above.

## Forward policies through websites

Declare a website with the same policies, then yield it in your stack.

```typescript
const site = Fly.Website.Vite("Web", {
  rootDir: "./web",
  deploy: { strategy: "bluegreen" },
  shutdown: { timeout: "30 seconds" },
});
```

Framework websites and `StaticSite` forward `deploy`, `shutdown`, `checks`, and `services` to their hosted Service. Static HTML and server code changes feed into the build and image hash. Omitting the deployment policy still selects rolling.

Websites run external server programs rather than managed Effect handlers. The shutdown props configure Fly's stop request. They do not install signal handlers in the application. The generated Node serve entry does not add one either.

An external server must stop accepting work, drain or checkpoint active work, and exit within its budget. Passing a readiness check does not prove this behavior. Static assets served from Tigris have a separate lifetime from the origin process.

## Return to rolling updates

Change the deployment strategy back to rolling. Keep `shutdown` if you still want graceful scale-down and deletion.

```typescript
const deploy: Fly.MachineDeploy = { strategy: "rolling" };
const shutdown: Fly.MachineShutdown = { timeout: "30 seconds" };
```

Rolling updates change Machines in place. A shutdown policy does not remove the availability gap for a single Machine.
