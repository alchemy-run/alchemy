Alchemy AI models agentic processes in code. A **process** is prose that describes a piece of work, and everything it mentions is a real reference: a tool, an LLM, another process, a part of your business.

Those references connect the whole system. Processes use tools, tools use your infrastructure, and your Domain model holds the rules of the business. It is one declarative program that the compiler checks and Alchemy deploys.

The examples come from an issue board that looks after a GitHub repository, the same one the [tutorial](/ai/tutorial/part-1) builds.

## A process: a description of work

A **process** has two parts. The class is its name, which the rest of your program refers to:

```typescript title="src/Triage.process.ts"
export class Triage extends AI.Process<Triage>()("Triage", {}) {}
```

A **Layer** gives that name its prose, which the LLM reads as its instructions:

```typescript title="src/Triage.process.ts"
export const TriageLive = Triage.toLayer({
  description: "Say what kind of issue this is.",
})`
  Read the issue you are given and reply with one word:
  bug, feature or question.
`;
```

Everything in Alchemy AI is split this way. A tool, an LLM, the harness and the sandbox are each a name and a Layer that says how it is done. Code depends on the name, so any Layer can be swapped for another without changing the code that uses it.

A process is not an agent with an identity. It describes work, and it can run any number of times.

See [Processes](/ai/processes).

## Mentions: what a process uses

Prose mentions things with `${}`. The LLM reads the thing's name in the sentence, and the process may use it.

```typescript title="src/Triage.process.ts"
export const TriageLive = Triage.toLayer({
  description: "Say what kind of issue this is.",
})`
  Find the code the issue is about with ${AI.Grep} and ${AI.Read}.
  Reply with one word: bug, feature or question.
`;
```

A process can use only what it mentions. This `Triage` can search and read files, and it cannot edit one or run a command.

A mention is also a dependency. `TriageLive` needs a Layer for each tool, and a program that provides it without them does not compile.

## Sessions: a running process

A **session** is a running process: one conversation, with a key you choose.

```typescript
const triage = yield* Triage;

const reply = yield* triage.get("issue-42").prompt("The app crashes on the settings page.");
```

A session keeps its conversation indefinitely. Send it another message next week and it remembers everything so far. `prompt` waits for the answer, and `send` leaves a message without waiting.

A process has no inputs and no output. A session is told what to do in its messages, and it acts through what its process mentions.

## Tools: what a process can do

A **tool** is a function the LLM can call. Its class says what it takes, what it returns and how it can fail.

```typescript title="src/PostAnswer.tool.ts"
export class IssueClosed extends Schema.TaggedError<IssueClosed>()("IssueClosed", {
  issue: Schema.Number,
}) {}

export class PostAnswer extends AI.Tool<PostAnswer>()("post_answer", {
  description: "Post your answer on the issue as a comment.",
  parameters: Schema.Struct({ issue: Schema.Number, markdown: Schema.String }),
  success: Schema.Struct({ url: Schema.String }),
  failure: IssueClosed,
}) {}
```

The LLM reads a failure as the tool's result and can try something else.

A few tools are the same everywhere: run a command, read a file, edit one, search. Those are names (`AI.Bash`, `AI.Read`, `AI.Edit`, `AI.Grep`) that each harness implements its own way. An MCP server is mentioned like a tool and stands for every tool it offers.

See [Tools](/ai/tools), [Coding tools](/ai/coding-tools) and [MCP servers](/ai/mcp-servers).

## Models: which LLM runs it

A **model** is a name for an LLM. A process mentions the name, never the LLM behind it.

```typescript title="src/Models.ts"
export class Smart extends AI.Model<Smart>()("smart") {}
export class Fast extends AI.Model<Fast>()("fast") {}
```

Every session runs on the default model unless told otherwise. A process that mentions a model may hand work to it:

```typescript
`For anything you need to look up, start a ${Research} on ${Fast}.`
```

See [Models](/ai/models).

## Processes that use processes

A process can mention another. Its session may then **follow** it, reading that process's prose into its own conversation, or **start** it, as a session of its own.

```typescript title="src/Answering.process.ts"
export class Answering extends AI.Process<Answering>()("Answering", {}) {}

export const AnsweringLive = Answering.toLayer({
  description: "How to write an answer on an issue. Follow it before you post one.",
})`
  Keep the answer under two hundred words. Name each file you read.
`;
```

```typescript title="src/Triage.process.ts"
export const TriageLive = Triage.toLayer({
  description: "Answer one issue and say what kind of issue it is.",
})`
  Follow ${Answering}, then post your answer with ${PostAnswer}.
`;
```

`Triage` mentions the name `Answering`, not its prose, so `AnsweringLive` can change without `Triage` knowing.

Other systems have two concepts here: a **skill**, instructions read into the current conversation, and a **subagent**, a separate conversation with its own instructions. Here there is one. `Answering` is a process, and it is not a skill or a subagent by nature. The prose that mentions it says which to do:

```typescript
`Follow ${Answering}, then post your answer with ${PostAnswer}.`
```

```typescript
`Start ${Answering} to draft the answer, then post it with ${PostAnswer}.`
```

The first reads `Answering` into the same conversation. The second runs it as a session of its own. Processes that mention each other are how you model a team or an organization.

See [Processes that use processes](/ai/process-graphs).

## The Domain model: the business a process works on

A [Domain model](/domain) is your business in code: what can happen, what did happen, and the rules that decide. An issue board has issues that are reported, labeled and replied to.

```typescript title="src/Board/Board.model.ts"
export class Board extends Domain.Model("Board", {
  aggregates: [Issue],
  views: [IssueDetail],
}) {}
```

A process describes a business process over that model. Its prose mentions the model's commands and views, and a session reads and acts through them:

```typescript title="src/Triage.process.ts"
export const TriageLive = Triage.toLayer({
  description: "Say what kind of issue this is.",
})`
  Get the issue with ${Board.IssueDetail}. Then send ${Board.LabelIssue}:
  bug when something is broken, feature when something new is asked for,
  question otherwise.
`;
```

The model's rules hold whoever sends a command. A session cannot label an issue nobody reported, because the board rejects it. A session is started as someone, and every command it sends is sent as them:

```typescript
yield* assistant.start(customer.id, { as: CurrentActor.context(customer) });
```

The two work in both directions. A policy of the model decides when there is work for a process, and Domain can [prove](/domain/verifying-models) the model's rules hold whatever a session sends.

See [Processes and Domain models](/ai/domain).

## Layers: how each thing is done

A tool and a model get their Layers the same way a process does. A tool's Layer is its handler, an Effect that runs in your program:

```typescript title="src/PostAnswer.tool.ts"
export const PostAnswerLive = PostAnswer.make(
  Effect.gen(function* () {
    const comment = yield* GitHub.CreateIssueComment(yield* Repo);

    return Effect.fn(function* ({ issue, markdown }) {
      const posted = yield* comment({ issue_number: issue, body: markdown }).pipe(Effect.orDie);
      return { url: posted.html_url };
    });
  }),
).pipe(Layer.provide(GitHub.CreateIssueCommentHttp));
```

A model's Layer is the LLM behind its name:

```typescript title="src/Models.ts"
export const SmartLive = AICloudflare.Model(Smart, {
  model: "@cf/meta/llama-3.3-70b-instruct-fp8-fast",
});
```

A process that will only ever have one prose can skip the Layer and carry it on the class:

```typescript title="src/Answering.process.ts"
export class Answering extends AI.Process<Answering>()("Answering", {
  description: "How to write an answer on an issue. Follow it before you post one.",
})`
  Keep the answer under two hundred words. Name each file you read.
` {}
```

## The harness: what runs a session

Something has to run the loop: send the LLM the conversation and its tools, run the tools it asks for, and ask again until it answers. That program is an **agent harness**. Pi and OpenCode are harnesses, and so are Claude Code and Codex.

A process never names one. The harness is one more Layer, provided with the rest:

```typescript title="src/Layers.ts"
export const Live = TriageLive.pipe(
  Layer.provide(
    Layer.mergeAll(
      AnsweringLive,
      PostAnswerLive,
      SmartLive,
      AI.DefaultModel(Smart),
      Pi.HarnessLive,
    ),
  ),
);
```

Change `Pi.HarnessLive` for `OpenCode.HarnessLive` and the same processes run on OpenCode.

See [Choose a harness](/ai/harnesses).

## Sandboxes: where files and commands live

A session runs where your program runs, which on Cloudflare has no files and no shell. Tools that need either work in a **sandbox**: a Linux machine on E2B, Daytona, Modal, Boat or Archil, one for each session.

```typescript
const sandbox = yield* AI.Sandbox;
const result = yield* sandbox.exec(["npm", "test"]);
```

See [Sandboxes](/ai/sandboxes).

## A Durable Object: where a session lives

A session needs storage for its conversation and a way to wake up after an eviction. On Cloudflare that is a Durable Object you write: it yields the process, and its methods are what the rest of your app may ask of a session.

```typescript title="src/Agents.ts"
export default class Agents extends Cloudflare.DurableObject<Agents>()(
  "Agents",
  Effect.gen(function* () {
    const triage = yield* Triage;

    return Effect.succeed({
      start: (issue: number) =>
        triage
          .get(String(issue))
          .send(`The issue is ${issue}.`, { requestId: "start" })
          .pipe(Effect.orDie),
    });
  }).pipe(Effect.provide(Live)),
) {}
```

See [Where sessions run](/ai/hosting).

## One program, down to the infrastructure

Every reference above is typed, so the graph is checked from end to end. `Triage` mentions `PostAnswer`. `PostAnswerLive` uses `GitHub.CreateIssueComment` on `Repo`. The Durable Object provides them, and the Worker binds the Durable Object.

Alchemy deploys that graph. The binding in `PostAnswerLive` is also what gives the Worker its GitHub token and the repository to comment on. A process can do what its tools can do, and a tool can do what its bindings allow.

So a process says what the work is, and Layers say how it is done. The same process runs on another harness, another LLM or another sandbox platform by changing a Layer.
