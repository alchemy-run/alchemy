Effect already emits traces, metrics, and logs. Every alchemy
runtime ships with the OTLP exporter built in. The exporter is a
Layer, wired to resources through the binding infrastructure. With
alchemy the receiving end is code too. Datasets, ingest tokens,
monitors, notifiers, and alarms live in the same Stack as the
Workers and Functions they observe. A threshold change is a diff in
the PR that you can review, revert, and trace with `git blame`.

## OTel everywhere

Provide a telemetry Layer on the Function/Worker and the built-in
exporter ships Effect's traces, metrics, and logs. Without one,
nothing is exported:

```typescript
Alchemy.Telemetry.layerOtlp({ url: "https://collector.example.com" })
```

Any OTLP/HTTP endpoint works. Swap the layer to ship somewhere else,
and the code emitting the signals stays the same. See
[Telemetry](/infrastructure-as-effects/telemetry) for the mechanics,
passing an API key as a `Config.Redacted` header, and how buffered
telemetry is flushed.

## Provision the receiving end

The endpoint the exporter targets is a resource. You declare one
[Axiom](/axiom) `Dataset` per OTEL signal. Each one exposes its
OTLP endpoints as outputs:

```typescript
// src/observability.ts
import * as Axiom from "alchemy/Axiom";

export const Traces = Axiom.Dataset("Traces", {
  name: "app-traces",
  kind: "otel:traces:v1",
});
export const Logs = Axiom.Dataset("Logs", {
  name: "app-logs",
  kind: "otel:logs:v1",
});
```

Each dataset's `otelTracesEndpoint`, `otelLogsEndpoint`, and
`otelMetricsEndpoint` attributes are [Outputs](/infrastructure-as-code/outputs).
You wire these references into whatever runs the exporter.

## Bind the datasets to the runtime

Mint a least-privilege ingest token, then provide `Axiom.Telemetry`
on the Worker. It is a binding layer that wires the datasets and
token in one line:

```typescript
// src/observability.ts
export const Ingest = Axiom.ApiToken("Ingest", {
  name: "prod-ingest",
  datasetCapabilities: {
    "app-traces": { ingest: ["create"] },
    "app-logs": { ingest: ["create"] },
  },
});

// src/worker.ts — in the Worker's constructor Effect:
import { Ingest, Logs, Traces } from "./observability.ts";

Effect.provide(
  Layer.mergeAll(
    Cloudflare.R2.ReadWriteBucketBinding,
    Axiom.Telemetry({ token: Ingest, traces: Traces, logs: Logs }),
  ),
)
```

Building the layer binds each dataset's OTLP endpoint and the
token's `Authorization` header onto the Worker. The bearer travels
as a `secret_text` binding (see [Secrets](/environments/secrets)) and
never appears in plaintext. At runtime the built-in exporter ships
each signal to its dataset. The Worker contains no exporter code.

## Export from the platform

On Cloudflare you can skip the in-process exporter. An
`ObservabilityDestination` has Cloudflare push Workers Logs telemetry
(traces, logs, or metrics) to an OTLP collector:

```typescript
// in the Stack's generator
import * as Output from "alchemy/Output";
import * as Redacted from "effect/Redacted";
import { Ingest, Traces } from "./src/observability.ts";

const traces = yield* Traces;
const ingest = yield* Ingest;

yield* Cloudflare.Workers.ObservabilityDestination("TracesExport", {
  url: traces.otelTracesEndpoint,
  headers: {
    authorization: Output.map(ingest.token, (t) => `Bearer ${Redacted.value(t)}`),
    "x-axiom-dataset": traces.name,
  },
  logpushDataset: "opentelemetry-traces",
});
```

The `authorization` header is derived from the ingest token's
`Redacted` output. The `x-axiom-dataset` header tells Axiom's OTLP
endpoint which dataset receives the data.

Workers Traces are opt-in. Set
`observability: { traces: { enabled: true } }` on each Worker whose
traces you want to export.

Create one destination per signal (`opentelemetry-traces`,
`opentelemetry-logs`, `opentelemetry-metrics`). The endpoint URL and
headers update in place. Changing `name` or `logpushDataset` replaces
the destination. Cloudflare preflights the `url` with a `POST` on
create (skippable with `skipPreflightCheck`) and on every update, so
the collector must answer `2xx`. The
[Axiom observability guide](/cloudflare/observability/axiom-observability)
covers the details.

## Alerts in code

Monitors and notifiers are resources too. A `Notifier` is an alert
destination. A `Monitor` is a scheduled APL query that fires it:

```typescript
const slack = yield* Axiom.Notifier("ops-slack", {
  name: "ops-channel",
  properties: {
    slack: { slackUrl: process.env.SLACK_WEBHOOK_URL! },
  },
});

yield* Axiom.Monitor("error-rate", {
  name: "High error rate",
  type: "Threshold",
  aplQuery: `
    ['app-traces']
    | where status >= 500
    | summarize count() by bin_auto(_time)
  `,
  operator: "Above",
  threshold: 100,
  intervalMinutes: 5,
  rangeMinutes: 5,
  notifierIds: [slack.id],
});
```

Notifiers cover Slack, email, PagerDuty, Opsgenie, Discord, Teams,
and custom webhooks. Monitors come in `Threshold`, `MatchEvent`, and
`AnomalyDetection` flavors. Raising the threshold is a one-line diff.
The same notifier is reused across every monitor in the stack.

## CloudWatch alarms and dashboards

AWS works the same way. Alarms reference metrics by name and fire
SNS topics. Dashboards are structured documents. You declare both
next to the resources they observe:

```typescript
import * as AWS from "alchemy/AWS";

const alerts = yield* AWS.SNS.Topic("Alerts");

const errors = yield* AWS.CloudWatch.Alarm("HighErrors", {
  MetricName: "Errors",
  Namespace: "AWS/Lambda",
  Statistic: "Sum",
  Period: 60,
  EvaluationPeriods: 1,
  Threshold: 1,
  ComparisonOperator: "GreaterThanOrEqualToThreshold",
  AlarmActions: [alerts.topicArn],
});

yield* AWS.CloudWatch.Dashboard("ApiHealth", {
  DashboardBody: {
    widgets: [
      {
        type: "metric",
        width: 12,
        properties: {
          title: "Lambda errors",
          view: "timeSeries",
          stat: "Sum",
          metrics: [["AWS/Lambda", "Errors", "FunctionName", "api"]],
        },
      },
      {
        type: "alarm",
        width: 12,
        properties: {
          title: "Alarms",
          alarms: [errors.alarmArn],
        },
      },
    ],
  },
});
```

`AWS.CloudWatch.CompositeAlarm` combines alarm states with AND/OR
into a higher-level alert. Alchemy generates alarm names from the
app, stage, and logical ID unless you set `name`, so reference them
through the `alarmName` output:

```typescript
import * as Output from "alchemy/Output";

yield* AWS.CloudWatch.CompositeAlarm("HighSeverity", {
  AlarmRule: Output.interpolate`ALARM("${errors.alarmName}")`,
});
```

Stacks are per-stage, so `prod`, `staging`, and `pr-42` each get
their own dashboards and alarms.
