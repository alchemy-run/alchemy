This page explains how observability fits into an Alchemy stack. Read
it before you choose where your traces, logs, and alerts go. The setup
steps live on the linked guides.

## How signals leave your code

Effect already emits traces, logs, and metrics. Every Alchemy runtime
exports them once you provide an exporter layer, and the exporter is
a layer like any other:

```typescript
Effect.provide(
  Layer.mergeAll(
    Cloudflare.R2.ReadWriteBucketBinding,
    Alchemy.Telemetry.layerOtlp({ url: "https://collector.example.com" }),
  ),
);
```

Your handlers never call an SDK. To ship somewhere else, you swap the
layer, and the code that emits the signals stays the same. See
[Telemetry](/infrastructure-as-effects/telemetry) for exporters,
multiple destinations, and flushing.

## The receiving end is a resource

The backend that receives the signals is part of the stack. An
[Axiom](/axiom) `Dataset` exposes its OTLP endpoints as
[Outputs](/infrastructure-as-code/outputs), and an `ApiToken` mints a
least-privilege ingest credential:

```typescript
export const Traces = Axiom.Dataset("Traces", {
  name: "app-traces",
  kind: "otel:traces:v1", // exposes otelTracesEndpoint
});

export const Ingest = Axiom.ApiToken("Ingest", {
  name: "app-ingest",
  datasetCapabilities: { "app-traces": { ingest: ["create"] } },
});
```

The exporter binds to these outputs, so the endpoint and token never
appear in your code or in plaintext. The token travels as a secret
binding (see [Secrets](/environments/secrets)). The
[Axiom observability guide](/cloudflare/observability/axiom-observability)
walks through the full setup.

## Exporting from the platform

On Cloudflare, a `Cloudflare.Workers.ObservabilityDestination` has
Cloudflare push Workers Logs telemetry to an OTLP collector, so your
Worker ships no exporter code. In exchange, the ingest token lives in
Cloudflare's destination config, and each Worker opts in to traces
with `observability: { traces: { enabled: true } }`. See
[Let Cloudflare push it](/cloudflare/observability/axiom-observability#alternative-let-cloudflare-push-it)
for the setup.

## Alerts and dashboards are resources

Monitors, notifiers, alarms, and dashboards live in the same stack as
the runtimes they watch:

```typescript
yield* Axiom.Monitor("error-rate", {
  name: "High error rate",
  type: "Threshold",
  aplQuery: `['app-traces'] | where status >= 500 | summarize count() by bin_auto(_time)`,
  operator: "Above",
  threshold: 100, // raising it is a one-line diff
  intervalMinutes: 5,
  rangeMinutes: 5,
  notifierIds: [slack.id], // slack is an Axiom.Notifier
});
```

This has three effects:

- **Reviewable changes**: a threshold change is a diff in the pull
  request that you can review, revert, and trace with `git blame`.
- **A copy per stage**: `prod`, `staging`, and `pr-42` each get their
  own alarms and dashboards, because each stage deploys its own stack.
- **Generated names**: Alchemy names a CloudWatch alarm from the app,
  stage, and logical ID unless you set `name`, so you reference it
  through its `alarmName` output. See [CloudWatch › Alarms](/aws/observability/cloudwatch#alarms).

See [Monitors & Alerting](/axiom/guides/alerting) for Axiom and
[CloudWatch](/aws/observability/cloudwatch) for AWS alarms and
dashboards.
