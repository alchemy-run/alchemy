beta.77 redesigns the CLI. `alchemy login` becomes
**`alchemy profile`**, a dashboard for every connected account
whose every action is also a non-interactive subcommand; profiles
are stored as **a folder per profile with a file per provider**
instead of a central `profiles.json`; and `alchemy dev` gets a
plan/output widget you can flip with `←/→`. Outside the CLI,
**`Cloudflare.Telemetry()`** sends Effect spans to Workers
Observability with no OTLP setup, Workflows take cron schedules,
and AWS gains provisioned ElastiCache.

Here is the new CLI on a fresh machine, start to finish:

_`alchemy profile` → `alchemy dev` → `alchemy deploy` → `alchemy drift` → `alchemy destroy`._

:::caution
**Breaking changes**

- **`alchemy deploy` defaults to `live_$USER`**
  ([#1421](https://github.com/alchemy-run/alchemy/pull/1421)) —
  `plan`, `destroy`, `logs`, and `drift` follow; `alchemy dev`
  keeps `dev_$USER`. Pass `--stage dev_sam` to keep deploying to
  an old target. The stage env var is now `ALCHEMY_STAGE`, not
  `STAGE` ([#1433](https://github.com/alchemy-run/alchemy/pull/1433)).
- **Commands moved**
  ([#1234](https://github.com/alchemy-run/alchemy/pull/1234),
  [#1235](https://github.com/alchemy-run/alchemy/pull/1235)). The
  old names print a migration hint instead of running:

  | Old                          | New                                   |
  | ---------------------------- | ------------------------------------- |
  | `alchemy login`              | `alchemy profile`                     |
  | `alchemy login --configure`  | `alchemy profile edit`                |
  | `alchemy profile clear`      | `alchemy profile delete`              |
  | `alchemy deploy ./stack.ts`  | `alchemy deploy --config ./stack.ts`  |
  | `alchemy tail`               | `alchemy logs --follow`               |
  | `alchemy sync`               | `alchemy drift --repair`              |
  | `alchemy destroy --dry-run`  | `alchemy plan --destroy`              |
  | `alchemy aws` / `cloudflare` | `alchemy provider aws` / `cloudflare` |

- **The AWS `local` auth method is removed**
  ([#1480](https://github.com/alchemy-run/alchemy/pull/1480)) —
  `alchemy dev` wires the local emulator itself.
- **Custom auth providers** list `Interaction` instead of
  `CliKit` in `StackServices`
  ([#1430](https://github.com/alchemy-run/alchemy/pull/1430)). See
  [Custom Auth Providers](/environments/custom-auth-provider).
- **distilled operations are `verbNoun`**
  ([#1517](https://github.com/alchemy-run/alchemy/pull/1517)) —
  `railway.serviceCreate` is now `railway.createService`. Only
  affects code that calls a distilled client directly.
:::

## `alchemy profile`

A profile is a set of connected provider accounts — Cloudflare via
OAuth, AWS via SSO, a pasted token for Neon. That is unchanged.
What changed is how you manage them
([#1234](https://github.com/alchemy-run/alchemy/pull/1234),
[#1235](https://github.com/alchemy-run/alchemy/pull/1235),
[#1547](https://github.com/alchemy-run/alchemy/pull/1547)).
`alchemy profile` opens a dashboard: profiles are tabs, each
connected provider is a row, and each action is a key:

```text
◆ default   work

❯ default · active

  Cloudflare  oauth  ✓ configured
    accountId  2b29022c…
    expires    in 59m
  AWS         sso    ✓ configured
    ssoProfile my-org

←/→ switch profile · ↑/↓ focus provider · e edit · r refresh · n new · q quit
```

`e` opens the edit menu — Space cycles a provider through
add / re-configure / remove, Enter runs the queued flows. `r`
refreshes credentials in place; `n`, `R`, `d` create, rename, and
delete profiles.

Every key is also a subcommand, and the subcommands never prompt:

```sh
alchemy profile create work
alchemy profile edit --profile work --add cloudflare     # runs the OAuth flow
alchemy profile refresh --provider cloudflare
alchemy profile rename work staging
alchemy profile delete staging --yes
```

For agents and CI, token-shaped methods are configured entirely
from flags. `--set` takes a literal, an environment variable, or
stdin, so secrets never touch shell history:

```sh
alchemy profile edit --add cloudflare --method stored \
  --set apiToken=env:CLOUDFLARE_API_TOKEN \
  --set accountId=0123456789abcdef0123456789abcdef

op read op://vault/neon/key | alchemy profile edit --add neon --method stored --set apiKey=-
```

Under the hood, the central `profiles.json` and the separate
`credentials/` tree are gone. A profile is a directory and each
provider is one file holding its method, config, and credentials
together. Existing installs migrate on first run, with the old
layout backed up to `~/.alchemy/.profiles-v0-<timestamp>/`
([#1429](https://github.com/alchemy-run/alchemy/pull/1429)):

```text
~/.alchemy/profiles/
├─ default/
│  ├─ cloudflare.json   # method: oauth, accountId, tokens, scopes
│  └─ aws.json          # method: sso, ssoProfile
└─ work/
   └─ cloudflare.json   # method: stored, apiToken, accountId
```

Only `profile` commands log in. `deploy`, `plan`, and `dev` never
open a wizard — a missing credential fails with the exact
`alchemy profile edit --add …` to run. Explicit provider
environment variables (`CLOUDFLARE_API_TOKEN`, `AWS_ACCESS_KEY_ID`,
…) take precedence over the profile, per provider, and the CLI
logs which ones it used
([#1520](https://github.com/alchemy-run/alchemy/pull/1520)).

Docs: [profile](/cli/profile) · [Profiles](/environments/profiles)
· [CI](/environments/ci).

## `alchemy dev` and `alchemy drift`

The plan view is one component everywhere
([#1458](https://github.com/alchemy-run/alchemy/pull/1458),
[#1492](https://github.com/alchemy-run/alchemy/pull/1492)). In
`alchemy dev`, logs render above it in normal scrollback and the
widget at the bottom shows either the stack's output or the last
applied plan — `←/→` flips, `↑/↓` scrolls, `p` hides it:

![alchemy dev with the plan open](/blog/beta-77/dev-plan.png)

Reloads follow the import graph from your entrypoint — sibling
`infra/` and `src/` trees included — and only fire when a file's
contents actually change; the CLI names the files that caused it
([#1461](https://github.com/alchemy-run/alchemy/pull/1461),
[#1477](https://github.com/alchemy-run/alchemy/pull/1477)).

`alchemy drift` re-reads the cloud and diffs it against what was
deployed. Drifted attributes render inline; `--repair` puts them
back:

![alchemy drift showing a renamed KV namespace](/blog/beta-77/drift.png)

Without a TTY — CI, a pipe, a coding agent — the same commands
print plain append-only lines, build output streams as it
happens, and exit codes are `0` done / `1` failed or declined /
`130` cancelled
([#1423](https://github.com/alchemy-run/alchemy/pull/1423),
[#1426](https://github.com/alchemy-run/alchemy/pull/1426)). Slow
shutdowns show progress, and a second Ctrl+C force-quits
([#1427](https://github.com/alchemy-run/alchemy/pull/1427)):

```text
^C
Shutting down — waiting for cleanup to finish (Ctrl+C again to force quit)
Still shutting down (5s)
```

Every run also writes a debug log under `~/.alchemy/logs` — the
first thing to attach to a bug report.

Docs: [CLI](/cli) · [dev](/cli/dev) · [drift](/cli/drift).

## `Cloudflare.Telemetry()`

Effect spans from a Worker now land in
[Workers Observability](https://developers.cloudflare.com/workers/observability/)
([#1444](https://github.com/alchemy-run/alchemy/pull/1444)).
Provide the Layer on the Worker and your `Effect.withSpan` frames
show up in the Cloudflare dashboard, nested under the platform's
own spans:

```typescript
export default Cloudflare.Worker(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    return {
      fetch: Effect.gen(function* () {
        const user = yield* kv.get("user:1").pipe(Effect.withSpan("load.user"));
        return yield* respond(user);
      }).pipe(Effect.withSpan("handle")),
    };
  }).pipe(Effect.provide(Cloudflare.Telemetry())),
);
```

```text
http.server GET
└─ handle
   ├─ load.user
   │  └─ kv_get
   └─ respond
```

Cloudflare owns sampling and export, so there is no OTLP endpoint
and nothing to flush. It composes with `Axiom.Telemetry` for the
same waterfall in both. The Worker's compatibility date must be
`2026-07-28` or later.

Docs: [Native Workers tracing](/cloudflare/observability/workers-tracing).

## Workflows: cron schedules

Cloudflare Workflows take wrangler-compatible `schedules`, so a
cron expression creates instances natively — no Cron Trigger
Worker calling `workflow.create()`
([#1491](https://github.com/alchemy-run/alchemy/pull/1491)):

```typescript
export default class Hourly extends Cloudflare.Workflow<Hourly>()(
  "Hourly",
  { schedules: ["0 * * * *"] },
  Effect.gen(function* () {
    return Effect.fn(function* () {
      const event = yield* Cloudflare.Workflows.WorkflowEvent;
      return event.schedule?.cron;
    });
  }),
) {}
```

## Provisioned ElastiCache

`AWS.ElastiCache` adds `SubnetGroup`, `ReplicationGroup` (Valkey
and Redis OSS) and `CacheCluster` (Memcached) alongside the
serverless cache, with `Connect*` bindings that publish the
endpoint to a Lambda and attach it to the cache's VPC
([#1422](https://github.com/alchemy-run/alchemy/pull/1422)).
Thanks [Henning Pokriefke](https://github.com/henningpokriefke)!

```typescript
const cache = yield* AWS.ElastiCache.ReplicationGroup("Cache", {
  engine: "valkey",
  nodeType: "cache.t4g.micro",
  subnetGroupName: subnetGroup.subnetGroupName,
  securityGroupIds: [sg.groupId],
  replicasPerNodeGroup: 1,
  automaticFailoverEnabled: true,
});

// inside the Lambda: endpoint env + VPC attachment
const conn = yield* AWS.ElastiCache.ConnectReplicationGroup(cache, {
  subnetIds: vpc.privateSubnetIds,
  securityGroupIds: [sg.groupId],
});
```

## Railway: private services, pre-deploy, local contexts

Three additions to `Railway.Service`, all from
[Dallen Pyrah](https://github.com/dallenpyrah) — thanks!
([#1439](https://github.com/alchemy-run/alchemy/pull/1439),
[#1438](https://github.com/alchemy-run/alchemy/pull/1438),
[#1440](https://github.com/alchemy-run/alchemy/pull/1440))

```typescript
const worker = yield* Railway.Service("Worker", {
  project,
  context: "./worker",                    // build from a local directory
  preDeploy: { command: "bun migrate" },  // runs between build and start
  publicDomain: false,                    // {name}.railway.internal only
});
```
