fixes.

It moves Alchemy to **Effect 4.1**. Alchemy Domain's deploys now **replay
history** into new and changed views, and one Domain model can be served
**over HTTP, MCP or the CLI**, so people and agents reach it however they
prefer. GCP gets **Cloud Run sidecars with typed RPC** and **connects to AWS
without keys**. Custom domains work with **any DNS provider**, **AWS state
uses DynamoDB** and plans 270× faster, and **Alchemist** exposes the whole
CLI as a programmatic API.

:::caution

  -  queue,
  -  (records) =>
  -    records.pipe(Stream.runForEach((record) => Effect.log(record.body))),
  +  queue,
  +  Effect.fn(function* (event) {
  +    for (const record of event.Records) yield* Effect.log(record.body);
  +  }),
  );

## Effect 4.1

Alchemy now runs on Effect 4.1
([#2754](https://github.com/alchemy-run/alchemy/pull/2754)):

```sh
bun add effect@^4.1.0 @effect/platform-node@^4.1.0
```

Effect 4.1 deletes `effect/Crypto`. Its `SecureRandom` and `Digest` services
replace it, and the platform layer provides them, so `StackServices` changes
with it:

```diff lang="typescript"
export type StackServices =
  | FileSystem
-  | Crypto
+  | Digest
+  | SecureRandom
  | Path
```

([#2790](https://github.com/alchemy-run/alchemy/pull/2790)).

### Deploys replay history into views

A Domain view or projection is a fold over events. Until now, one added in a
later deploy only saw events from then on, and changing a view's `evolve`
left its stored state stale. Now the deploy replays the history for you
([#2725](https://github.com/alchemy-run/alchemy/pull/2725),
[#2875](https://github.com/alchemy-run/alchemy/pull/2875)).

Add a view, and the deploy feeds it every event its sources recorded before
it existed, in the order they were recorded:

```typescript
// deploy 1
class Bank extends Domain.Model("Bank", { aggregates: [Account] }) {}

// deploy 2: AccountSummary folds every earlier event, with no script
class Bank extends Domain.Model("Bank", {
  aggregates: [Account],
  views: [AccountSummary],
}) {}
```

Change a view by bumping its `version`, and the deploy recomputes it:

```typescript
export class AccountSummary extends Domain.View("AccountSummary", {
  from: [Account],
  key: Account,
  state: Schema.Struct({ net: Schema.Number }),
  initial: { net: 0 },
  evolve: {
    MoneyDeposited: (v, e) => ({ net: v.net + e.amount }),
    // new: applied to every past withdrawal
    MoneyWithdrawn: (v, e) => ({ net: v.net - e.amount }),
  },
  version: 1,
}) {}
```

The deploy picks the cheapest correct way to do it. A view keyed by the one
aggregate it reads is rebuilt in place: each key re-reads its own
aggregate's events the first time it's touched, so the deploy waits for
nothing. Any other view is rebuilt from the history in new storage, and the
deploy waits and reports progress:

```sh
[DomainBackfillRun] Backfilling view:Deposits reading history 41% (1,690/4,096 subtrees, 410,211 instances) (48s) ...
[DomainBackfillRun] Backfilled view:Deposits (112.4s)
```

Views and projections that read a rebuilt view are rebuilt too, and reads
stay correct while the new code rolls out. A view keyed by its aggregate can
also skip the backfill when it's added, and fill each key on first read:

```typescript
export const BankLive = Bank.layer(BankHandlers, {
  lazy: ["AccountSummary"],
});
```

On Cloudflare the replay runs as Durable Objects, not on the deploying
machine. It is safe to interrupt and re-run, and a view over 100,000
accounts and a million events rebuilt in 58 seconds.

Docs: [Consumers added later receive the history](/domain/model#consumers-added-later-receive-the-history) ·
[Change a view: bump its version](/domain/model#change-a-view-bump-its-version) ·
[History at scale](/domain/backfill).

### Serve a Domain model over HTTP, MCP or the CLI

A `Domain.Api` names the parts of a model a client may reach
([#2820](https://github.com/alchemy-run/alchemy/pull/2820)):

```typescript
export class BankApi extends Domain.Api("BankApi", {
  model: Bank,
  commands: ["DepositMoney", "WithdrawMoney"],
  views: ["AccountSummary"],
}) {}
```

The same Api can now be served to whoever needs it, through the same
middleware and rejections, so an agent can do exactly what a signed-in
client can and no more.

As an HTTP JSON API with an OpenAPI document, with live reads as
Server-Sent Events, for partners, scripts and browsers
([#2587](https://github.com/alchemy-run/alchemy/pull/2587)):

```typescript
const BankHttp = DomainHttp.toHttpApi(BankApi);

export const BankHttpLive = HttpApiBuilder.layer(BankHttp.api, {
  openapiPath: "/openapi.json",
}).pipe(Layer.provide(BankHttp.layer), Layer.provide(BankLive));
```

As an MCP server for agents, or as Effect AI tools for an agent inside your
app ([#2586](https://github.com/alchemy-run/alchemy/pull/2586)):

```typescript
export const BankMcp = DomainAi.toMcp(BankApi).pipe(
  Layer.provide(
    McpServer.layerHttp({ name: "bank", version: "1.0.0", path: "/mcp" }),
  ),
  Layer.provide(BankLive),
);
```

As a command-line tool, for people and agents in a terminal
([#2588](https://github.com/alchemy-run/alchemy/pull/2588)):

```sh
$ bank deposit-money --target a-1 --amount 1000
{ "reply": { "balance": 1000 }, "stream": "Account/a-1", "version": 1 }

$ bank withdraw-money --target a-1 --amount 5000   # exit code 1
{ "_tag": "InsufficientFunds", "balance": 1000, "requested": 5000 }
```

And as Foldkit commands and subscriptions for a web app
([#2700](https://github.com/alchemy-run/alchemy/pull/2700)).

Docs: [HTTP API](/domain/http-api) · [MCP](/domain/mcp) · [CLI](/domain/cli) ·
[Foldkit](/domain/foldkit).

### Show a command's outcome before the server answers

`Aggregate.predict` runs an aggregate's own `decide` and `evolve` on the
client. A UI shows the outcome at once, with the same events and state the
server will produce, or the same rejection
([#2568](https://github.com/alchemy-run/alchemy/pull/2568)):

```typescript
const outcome = Account.predict(state, new Deposit({ amount: 30 }), {
  id: "a-1",
  now,
  version: 3,
});

switch (outcome._tag) {
  case "Accepted": // outcome.events, outcome.state
  case "Rejected": // outcome.rejection, the instance the server returns
  case "Unpredictable": // only the server can tell; outcome.cause says why
}
```

When the server answers, `snapshot` gives a view's state with the cursor it
is valid at. The page renders it, then follows the view live from that
cursor, with no gap and no duplicate
([#2567](https://github.com/alchemy-run/alchemy/pull/2567),
[#2579](https://github.com/alchemy-run/alchemy/pull/2579)):

```typescript
const { state, cursor } = yield* api.AccountSummary.snapshot("a-1", {
  atLeast: { stream: receipt.stream, version: receipt.version },
});
render(state);

yield* api.AccountSummary.events("a-1", { after: cursor }).pipe(
  Stream.runForEach((frame) =>
    Domain.Read.isCaughtUp(frame) ? markLive() : apply(frame),
  ),
);
```

Docs: [Optimistic updates](/domain/optimistic-updates) ·
[Render a snapshot, then follow it](/domain/view#render-a-snapshot-then-follow-it).

## GCP

### Cloud Run sidecars with typed RPC

`GCP.Run.Container` runs your own Effect program, or any image, as a sidecar
of a Cloud Run service. `bindContainer` adds it to the revision, starts it
first, and hands back a typed client over `localhost`
([#2652](https://github.com/alchemy-run/alchemy/pull/2652)):

```typescript
export class Worker extends GCP.Run.Container<Worker>()(
  "Worker",
  {
    main: import.meta.url,
    port: 3000,
    startupProbe: { httpGet: { path: "/health" } },
  },
  Effect.gen(function* () {
    return {
      greet: (name: string) => Effect.succeed(`hello ${name}`),
      count: () => Stream.make(1, 2, 3),
      fetch: Effect.succeed(HttpServerResponse.text("ok")),
    };
  }),
) {}

export default class Api extends GCP.Run.Service<Api>()(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const worker = yield* GCP.Run.bindContainer(Worker);
    return {
      fetch: worker.greet("sam").pipe(Effect.map(HttpServerResponse.text)),
    };
  }),
) {}
```

Sidecars can bind other sidecars, and each binding orders startup through
`dependsOn`. `bindPort` binds a raw port on an image like Redis or nginx, and
an image-only service can list Containers in its template
([#2657](https://github.com/alchemy-run/alchemy/pull/2657)). Every container
takes `startupProbe`, `livenessProbe` and `dependsOn`
([#2644](https://github.com/alchemy-run/alchemy/pull/2644)):

```text
revision
├── start Static  → TCP :80
├── start Worker (dependsOn Static) → GET :3000/health
├── start Api    (dependsOn Worker) → GET :8080/health
└── Ready → traffic to Api
```

Docs: [Sidecars](/gcp/compute/sidecars).

### Call private Cloud Run services

`InvokeService` calls the methods of a private Cloud Run service, signed with
the caller's ID token, with types taken from the service class
([#2653](https://github.com/alchemy-run/alchemy/pull/2653)):

```typescript
export default class Quotes extends GCP.Run.Service<Quotes>()(
  "Quotes",
  { main: import.meta.url }, // the IAM invoker check stays on
  Effect.gen(function* () {
    return {
      quote: (symbol: string) => Effect.succeed({ symbol, price: 42 }),
      ticks: (symbol: string) => Stream.make(41, 42, 43),
    };
  }),
) {}

// in another service
const quotes = yield* GCP.Run.InvokeService(Quotes);
const { price } = yield* quotes.quote("GOOG");
```

Pass an Effect RPC `schema` or an HttpApi `api` to `InvokeService` or
`bindContainer` for a client with typed errors, and serve it with
`ServeRpc` or `ServeHttpApi`
([#2654](https://github.com/alchemy-run/alchemy/pull/2654)):

```typescript
const tasks = yield* GCP.Run.InvokeService(TaskBackend, { schema: TaskRpcs });
// Effect<Task, TaskNotFound | …>
const task = yield* tasks.getTask({ id: "t1" });
```

A service that returns methods but turns off the invoker check fails to
deploy, so RPC methods are never public by accident.

Docs: [Call it from another service](/gcp/apis/effect-rpc#call-it-from-another-service) ·
[Run it as a sidecar](/gcp/apis/effect-rpc#run-it-as-a-sidecar).

### Connect AWS and GCP without keys

A GCP binding on a Lambda, ECS task, EC2 instance or App Runner service no
longer creates a service account key. The host's IAM role impersonates the
service account through workload identity federation
([#2648](https://github.com/alchemy-run/alchemy/pull/2648)). Your code
doesn't change:

```typescript
export default Worker.make(
  { main: import.meta.url, functionUrl: true },
  Effect.gen(function* () {
    const publish = yield* GCP.PubSub.Publish(yield* Events);
    return {
      fetch: publish({ body: { messages: [{ data: btoa("hello") }] } }).pipe(
        Effect.as(HttpServerResponse.text("published")),
      ),
    };
  }).pipe(Effect.provide(GCP.PubSub.PublishHttp)),
);
```

```diff lang="text"
WorkerServiceAccount         GCP.IAM.ServiceAccount
-WorkerServiceAccountKey      GCP.IAM.ServiceAccountKey
+AwsWorkloadIdentityPool      GCP.IAM.WorkloadIdentityPool
+AwsWorkloadIdentityProvider  GCP.IAM.WorkloadIdentityProvider
+WorkerWorkloadIdentityUser   GCP.IAM.Member
```

The other direction works the same way: Cloud Run and Cloud Functions assume
their AWS role with a Google ID token, with no IAM user or access key
([#2645](https://github.com/alchemy-run/alchemy/pull/2645)).
`WorkloadIdentityPool` and `WorkloadIdentityProvider` are resources too, for
keyless CI from GitHub Actions or any OIDC issuer
([#2130](https://github.com/alchemy-run/alchemy/pull/2130)).

Docs: [GCP federated identity](/gcp/security/federated-identity) ·
[AWS federated identity](/aws/security/federated-identity).

### Migrations on Cloud SQL, AlloyDB and Spanner

Every GCP SQL database applies `migrations` on deploy, like D1, Neon,
PlanetScale, Turso, RDS and DSQL
([#2651](https://github.com/alchemy-run/alchemy/pull/2651)):

```typescript
const db = yield* GCP.SQL.Database("App", {
  instance: instance.instanceName,
  migrations: "./migrations",
  migrationsUser: user.userName,
  migrationsPassword: password.text,
});
```

Cloud SQL runs them over its data API by default, which needs no network
route, or through the Cloud SQL connector. Spanner resumes a failed
migration at the statement that failed. `GCP.SQL.Instance` can now be
private-IP only, with SSL mode and backup retention in the stack
([#2642](https://github.com/alchemy-run/alchemy/pull/2642)), and Pub/Sub
subscriptions write straight into BigQuery
([#2213](https://github.com/alchemy-run/alchemy/pull/2213)). Thanks
[Lucas Duailibe](https://github.com/duailibe)!

Docs: [Cloud SQL](/gcp/data/cloud-sql).

### Sign in with gcloud

A GCP profile signs in through a named gcloud configuration, the way an AWS
profile uses `aws sso login`
([#2635](https://github.com/alchemy-run/alchemy/pull/2635),
[#2680](https://github.com/alchemy-run/alchemy/pull/2680)):

```sh
gcloud auth login --configuration=work
alchemy profile edit --add GCP --method gcloud --set configuration=work
```

`alchemy profile edit --add GCP` lists your configurations, or creates one
and opens the browser. Each run asks gcloud for a fresh token, and nothing is
copied into the profile. Signed in as yourself, you can also create projects
without an organization or folder
([#2616](https://github.com/alchemy-run/alchemy/pull/2616)).

Docs: [GCP credentials](/gcp/setup#credentials).

## Custom domains with any DNS provider

A custom domain's DNS no longer has to live with the platform that serves
it. `domain.dns` names the DNS provider that holds the records, on every
platform ([#1888](https://github.com/alchemy-run/alchemy/pull/1888)):

```typescript
yield* AWS.Lambda.Function("Api", {
  main: "./src/handler.ts",
  domain: {
    name: "api.example.com",
    dns: Cloudflare.DNS.Adapter(),
  },
});

yield* Cloudflare.Worker("Web", {
  main: "./src/web.ts",
  domain: {
    name: "app.example.com",
    zoneId: saasZone.zoneId,
    cnameTarget: fallback.origin,
    dns: AWS.Route53.Adapter(),
  },
});

yield* Fly.Website.Vite("Docs", {
  domain: {
    name: "docs.example.com",
    dns: Hetzner.DNS.Adapter(),
  },
});
```

Alchemy publishes whatever the platform asks for: certificate validation
records, ACME challenges, verification TXTs and aliases. Cloudflare, Route
53 and Hetzner adapters ship today, and an adapter for another DNS provider
is three functions. Thanks [Dan Myles](https://github.com/dan-myles) and
[bjorntechTobbe](https://github.com/bjorntechTobbe)!

Docs: [DNS adapters](/infrastructure-as-code/dns-adapters).

## AWS state now uses DynamoDB and plans 270× faster

`AWS.state()` keeps state in one on-demand DynamoDB table per account and
region, and a deploy loads the stage with one `Query`
([#2683](https://github.com/alchemy-run/alchemy/pull/2683),
[#2691](https://github.com/alchemy-run/alchemy/pull/2691)):

| | S3 | DynamoDB |
| --- | ---: | ---: |
| plan, 250 resources | 21.6 s | 0.08 s |
| unchanged redeploy, 1,000 resources | 195 s | 0.5 s |
| destroy, 1,000 resources | 162 s | 12.5 s |

Existing stages move with one command. Older Alchemy versions are fenced
out of the S3 copy, and nothing in S3 is deleted:

```sh
$ alchemy state migrate
my-app/prod: migrated (42 records)

$ alchemy state migrate --rollback   # back to S3, before downgrading
```

Docs: [AWS state store](/state-store#aws-state-store) ·
[Migrating from S3](/state-store#migrating-from-the-s3-store).

## Lambda aliases, streaming and partial batch failures

`alias` publishes a version on each deploy and routes every event source,
URL and integration through it, so a rollback is one `update-alias` call
([#2504](https://github.com/alchemy-run/alchemy/pull/2504)):

```typescript
export default class Api extends AWS.Lambda.Function<Api>()(
  "Api",
  { main: import.meta.url, alias: "live", functionUrl: true },
  Effect.gen(function* () {
    yield* AWS.SQS.consumeQueueMessages(jobs, processJob); // → api:live
    return { fetch: handleHttp }; // URL on qualifier "live"
  }),
) {}
```

SQS, Kinesis and DynamoDB Streams handlers receive the Lambda event and can
return its batch response, so only the failed records are retried
([#2508](https://github.com/alchemy-run/alchemy/pull/2508)):

```typescript
yield* AWS.SQS.consumeQueueMessages(
  queue,
  Effect.fn(function* (event) {
    const failed = yield* Effect.filter(event.Records, (record) =>
      handle(record.body).pipe(
        Effect.as(false),
        Effect.catchCause(() => Effect.succeed(true)),
      ),
    );
    return {
      batchItemFailures: failed.map((r) => ({ itemIdentifier: r.messageId })),
    };
  }),
);
```

A `RESPONSE_STREAM` Function URL streams an Effect response body instead of
buffering it ([#2502](https://github.com/alchemy-run/alchemy/pull/2502)), and
a handler that runs past its `timeout` is interrupted, so finalizers run and
telemetry flushes before Lambda kills the sandbox
([#2682](https://github.com/alchemy-run/alchemy/pull/2682)):

```typescript
timeout: Duration.seconds(30), // handler interrupted at 30 s
timeoutMargin: Duration.seconds(2), // Lambda configured for 32 s
```

Docs: [Lambda](/aws/compute/lambda).

## Alchemist: the Alchemy CLI as a programmatic API

The `alchemy` CLI is now a thin layer over `alchemy/Alchemist`. Everything
it does (plan, apply, drift, nuke, logs, state) is one call you can make from
your own program, and every step is a typed event you can handle
([#2765](https://github.com/alchemy-run/alchemy/pull/2765)):

```typescript
import * as Alchemist from "alchemy/Alchemist";

const program = Effect.gen(function* () {
  const plan = yield* Alchemist.plan({
    stack: Stack,
    operation: "deploy",
    stage: "prod",
  });
  if (Alchemist.hasChanges(plan)) yield* Alchemist.apply(plan);

  const scan = yield* Alchemist.Drift.scan({ stack: Stack, stage: "prod" });
  if (Alchemist.Drift.hasDrift(scan)) yield* Alchemist.Drift.execute(scan);
}).pipe(
  Alchemist.onEvent((event) => Effect.log(event.type)),
  Effect.provide(Alchemist.layer()),
  Effect.scoped,
);
```

Build your own CLI, a deploy bot or a CI step on the same API the `alchemy`
command uses. Every run also writes one NDJSON log under `.alchemy/log/`,
child processes and sidecars included. Thanks
[Rahul Mishra](https://github.com/BlankParticle)!

Docs: [CLI API](/cli/api).

## 95 bug fixes

Most of this release is fixes, many found by new test suites rather than by
users. About 900 provider failures that were a plain `Error` are now tagged
errors you can catch ([#2711](https://github.com/alchemy-run/alchemy/pull/2711)),
and ECR images hash only what `.dockerignore` keeps, so hashing a large repo
dropped from 344 s to 8 s
([#2351](https://github.com/alchemy-run/alchemy/pull/2351)).

### Workflows wake on time

Wake-ups scheduled inside a Durable Object alarm inherited its retry
backoff, so workflow sleeps ran later on every hop: four one-second sleeps
took over 45 s, and now take about 4 s
([#2916](https://github.com/alchemy-run/alchemy/pull/2916)). The fix came
with one 28-case conformance suite that every engine now runs, on Durable
Objects, Cloudflare Workflows and Lambda durable functions. The suite found
12 of the 15 engine bugs fixed in this release, including:

- A repeated or late signal hung for three minutes, then died.
- An interrupt sent right after start was dropped, or stopped the run without
  running its compensations.
- `Activity.retry` saw attempt 1 on every retry.
- `Activity.raceAll` hung forever on the two engines that can't support it;
  it now fails at once and points to the Durable Object engine.

### Drift only reports real changes

`alchemy drift` now sees every setting that Lambda, DynamoDB, S3, SQS,
EventBridge, Step Functions, WAF, ELB, ECS and EC2 networking manage, so a
change made in the console shows up
([#2661](https://github.com/alchemy-run/alchemy/pull/2661),
[#2705](https://github.com/alchemy-run/alchemy/pull/2705)). Untouched
resources no longer show up as drifted
([#2496](https://github.com/alchemy-run/alchemy/pull/2496),
[#2169](https://github.com/alchemy-run/alchemy/pull/2169),
[#2647](https://github.com/alchemy-run/alchemy/pull/2647)):

```diff lang="sh"
$ alchemy deploy && alchemy drift
-[Api] drifted
-[Db] drifted
+Plan: no changes
```

`--repair` recreates deleted resources in dependency order
([#2495](https://github.com/alchemy-run/alchemy/pull/2495)), and EC2 creates
are idempotent, so a retry never launches a second instance
([#2598](https://github.com/alchemy-run/alchemy/pull/2598)). Thanks
[DivMode](https://github.com/DivMode),
[Gjermund Garaba](https://github.com/gjermundgaraba) and
[Ahmed Hesham](https://github.com/ahmedhesham6)!

### Deploys never take over a resource they don't own

- A resource in a dependency cycle checks ownership before it's created, so
  it can't overwrite a Worker or Lambda someone else owns
  ([#2195](https://github.com/alchemy-run/alchemy/pull/2195),
  [#2620](https://github.com/alchemy-run/alchemy/pull/2620)).
- A replacement is refused before it touches anything when its new name
  belongs to someone else ([#2200](https://github.com/alchemy-run/alchemy/pull/2200)).
- Recovering an interrupted create never deletes a same-named resource by
  guessing ([#2199](https://github.com/alchemy-run/alchemy/pull/2199),
  [#2534](https://github.com/alchemy-run/alchemy/pull/2534)).
- A ref to a resource in the same stack is a dependency, so destroy no longer
  races it ([#2913](https://github.com/alchemy-run/alchemy/pull/2913)).
- `alchemy destroy` plans from state without running your program, so a dev
  stage tears down without cloud credentials
  ([#2491](https://github.com/alchemy-run/alchemy/pull/2491)).

Thanks [Nacho Vazquez](https://github.com/NachoVazquez)!

## Also in this release

**Alchemy Domain**

- Views, projections and policies can be keyed by a Schema value instead of an aggregate ([#2554](https://github.com/alchemy-run/alchemy/pull/2554)), and a scheduled command can be cancelled with `unschedule` ([#2547](https://github.com/alchemy-run/alchemy/pull/2547)).
- External system calls are checked against their schemas, and an operation can declare several errors ([#2548](https://github.com/alchemy-run/alchemy/pull/2548), [#2553](https://github.com/alchemy-run/alchemy/pull/2553)).
- Stories print every step on failure, fail on events no step asserts, type-check against the last command, and move the clock with `Story.advance` ([#2475](https://github.com/alchemy-run/alchemy/pull/2475), [#2551](https://github.com/alchemy-run/alchemy/pull/2551), [#2559](https://github.com/alchemy-run/alchemy/pull/2559), [#2629](https://github.com/alchemy-run/alchemy/pull/2629)). [Docs](/domain/story).
- Each model owns its data, and models and workflow engines can stay in a Cloudflare jurisdiction ([#2560](https://github.com/alchemy-run/alchemy/pull/2560), [#2601](https://github.com/alchemy-run/alchemy/pull/2601)).

**Cloudflare**

- The Cloudflare state store takes your account, Worker name and domain ([#2385](https://github.com/alchemy-run/alchemy/pull/2385)). [Docs](/state-store#cloudflare-state-store).
- `codeUpdateStrategy` sets how running Durable Objects move onto new code ([#2863](https://github.com/alchemy-run/alchemy/pull/2863)). [Docs](/cloudflare/compute/code-updates).
- Workers import any file through `rules` ([#2792](https://github.com/alchemy-run/alchemy/pull/2792)), and Flagship flags evaluate locally in `alchemy dev` ([#2746](https://github.com/alchemy-run/alchemy/pull/2746)).
- `consumeNotifications` handles Cloudflare alerts in code, and Effect logs reach Workers Logs at their own level ([#2519](https://github.com/alchemy-run/alchemy/pull/2519)).
- Workflows, Queues and R2 buckets take a `jurisdiction` ([#2734](https://github.com/alchemy-run/alchemy/pull/2734), [#2538](https://github.com/alchemy-run/alchemy/pull/2538), [#2758](https://github.com/alchemy-run/alchemy/pull/2758)), and Email Routing takes subdomains and subaddressing ([#2762](https://github.com/alchemy-run/alchemy/pull/2762)).

- `EventBridge.Endpoint` global endpoints, regional NAT gateways, and Auto Scaling by instance attributes ([#2507](https://github.com/alchemy-run/alchemy/pull/2507), [#2498](https://github.com/alchemy-run/alchemy/pull/2498), [#2817](https://github.com/alchemy-run/alchemy/pull/2817)).
