---
title: Build & push images
description: Build or mirror a Docker image, publish it to a registry, and pass an immutable reference to a container platform.
---

Named `Docker.Image` resources build Dockerfiles and named `Docker.RemoteImage`
resources resolve existing images. Both accept `publish` and return `ref`: a local
image ID when publication is omitted, or an immutable
`registry/repository@sha256:…` reference when published.

Called without an ID, these helpers return plain image descriptors instead.
A consuming resource, such as Cloudflare Container, registers the child image
resource and manages its lifecycle.

Building and pulling need a Docker daemon. Reusing an already-published image
only needs registry access; it does not require a daemon or builder.
See [Setup](/docker/setup) for Docker prerequisites.

## Build from a Dockerfile

```typescript
import * as Alchemy from "alchemy";
import * as Docker from "alchemy/Docker";
import * as Effect from "effect/Effect";

export default Alchemy.Stack(
  "MyImages",
  { providers: Docker.providers(), state: Alchemy.localState() },
  Effect.gen(function* () {
    const image = yield* Docker.Image("App", {
      build: {
        context: "./app",
        dockerfile: "Dockerfile",
        args: { NODE_ENV: "production" },
      },
    });
    return { ref: image.ref };
  }),
);
```

`build.context` is the filesystem context. `dockerContext`, at the resource's
outer level, selects a Docker daemon. The build also accepts a multi-stage
`target`, `platform`, and `cacheFrom`/`cacheTo` settings.

## Publish to a registry

```typescript
const image = yield* Docker.Image("App", {
  build: { context: "./app", platform: "linux/amd64" },
  publish: {
    repository: "ghcr.io/acme/app",
    tags: ["production"],
  },
});
```

`publish.repository` is the complete registry/repository path, without a tag or
digest. Alchemy maintains an input-hash tag; optional `tags` are additional aliases.
`image.ref` always uses the resolved digest, so moving an alias does not change an
already-deployed consumer.

Authentication comes from a registered integration or your Docker configuration,
including credential helpers. To supply credentials explicitly:

```typescript
publish: {
  repository: "ghcr.io/acme/app",
  credentials: {
    username: "octocat",
    password: Config.Redacted("GITHUB_TOKEN"),
  },
}
```

Import `Config` from `effect/Config` when using this form. Credentials stay out of
command arguments, and publication does not modify your global Docker login.

## When it rebuilds

Planning hashes the Dockerfile and effective build inputs; it never builds or
pushes. Filesystem hashing honors Docker ignore rules. Generated files, build
arguments, target, platform, and build options contribute to the hash.

For published builds, Alchemy checks the input-hash tag first. A hit returns the
registry digest without invoking Docker. A miss builds and publishes. Layer-cache
settings are separate: by default, published builds import the repository's
`:buildcache` tag and export inline cache metadata.

:::caution
Pin base images and downloaded dependencies when reproducibility matters.
A mutable base tag or network download can change without changing local inputs.
Use `build.extraHash` to explicitly invalidate those dependencies. Changing
`cacheFrom` or `cacheTo` does not invalidate the finished-image hash.
:::

Published images are retained on destroy because other deployments may use them.
Local builds remove their owned tags rather than force-deleting shared images.
In `alchemy dev`, image resources build or pull locally without publishing.

## Inline and generated contexts

```typescript
const image = yield* Docker.Image("Static", {
  build: {
    dockerfile: Docker.Dockerfile.inline`
      FROM nginx:alpine
      COPY index.html /usr/share/nginx/html/index.html
    `,
    files: [{ path: "index.html", content: "Hello from Alchemy" }],
    platform: "linux/amd64",
  },
  publish: { repository: "ghcr.io/acme/static" },
});
```

Inline Dockerfiles use a generated context. Supply additional files through
`build.files`; use a Dockerfile path and `build.context` for an existing directory.

## Mirror remote images

```typescript
const mirrored = yield* Docker.RemoteImage("Nginx", {
  source: "docker.io/library/nginx:alpine",
  platform: "linux/amd64",
  publish: { repository: "ghcr.io/acme/nginx" },
});
```

Mutable source tags are resolved against the registry before deciding whether a
mirror is current. Use a digest in `source` to pin the input. An image already in
the destination repository is resolved without pulling or pushing it through Docker.
Remote images and published manifests are retained on destroy.

## Let a Cloudflare Container own its image

```typescript
const application = yield* Cloudflare.Container("Web", {
  image: Docker.Image({ context: "./web" }),
}).Application;
```

`Docker.Image({ … })` is plain data, not a resource or an Effect. Build options
are at the top level of this shorthand. Cloudflare creates the real
`Web/Image` child resource and supplies its default platform and publication
repository. No extra image name or `yield*` is needed.

To use an existing image:

```typescript
const application = yield* Cloudflare.Container("Proxy", {
  image: Docker.RemoteImage({ source: "nginx:alpine" }),
}).Application;
```

This descriptor creates a child `Docker.RemoteImage`. Both shorthand forms
accept `publish` overrides and `dockerContext`. They do nothing when called on
their own; the consuming container registers the managed resource.

## Share a named image in Cloudflare

```typescript
import * as Cloudflare from "alchemy/Cloudflare";
import * as Layer from "effect/Layer";

export default Alchemy.Stack(
  "Web",
  {
    providers: Layer.mergeAll(Docker.providers(), Cloudflare.providers()),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const image = yield* Docker.Image("WebImage", {
      build: { context: "./web", platform: "linux/amd64" },
      publish: {
        repository: yield* Cloudflare.containerRepository("web"),
      },
    });
    const application = yield* Cloudflare.Container("Web", {
      image: image.ref,
    }).Application;
    return { applicationId: application.applicationId };
  }),
);
```

`Cloudflare.containerRepository` supplies the managed registry's account prefix.
`Cloudflare.providers()` supplies its registry authentication integration; tokens
are requested only when needed. A Durable Object and Worker provide the request
entrypoint to the application; see [Cloudflare Containers](/cloudflare/compute/containers).

Docker's build and publication resources are independent of that application.
Other platforms can consume their registry references without duplicating the
image lifecycle.

## Effect-native Cloudflare programs

A Container declared with `main` bundles a program and creates a child
`Docker.Image` automatically. Use `baseImage` for its execution environment,
`bundle` for JavaScript bundler options, and `publish` for the shared Docker
publication configuration:

```typescript
export default MyContainer.make(
  {
    main: import.meta.url,
    baseImage: "oven/bun:1",
    bundle: { output: { minify: true } },
    publish: {
      repository: Cloudflare.containerRepository("my-program"),
    },
  },
  implementation,
);
```

The program's runtime bindings remain Cloudflare-specific. Its generated
Dockerfile and bundled files use the same hashing, build, publication, and reuse
implementation as a standalone `Docker.Image`. Legacy `context`/`dockerfile`
Container builds also delegate to a child image; prefer an explicit `Docker.Image`
when sharing a Dockerfile-based artifact.
