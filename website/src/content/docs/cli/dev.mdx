```sh
alchemy dev [options]
```

Run your stack in development mode with hot reloading. Resources are deployed to the cloud while Workers run in the local dev runtime; file changes trigger automatic rebuilds and hot reloads.

## How it works

`dev` watches the stack's imports through `alchemy/bin/exec`. Node reloads the stack in the exec process; Bun starts a fresh exec process after each stack change. The supervisor and local provider sidecar survive these reloads.

`--yes` and dev mode are implied, so approval prompts never appear.

A failed apply keeps dev alive so healthy resources keep serving — fix the error and save to redeploy.

## Repeated invocations

One supervisor owns each **canonical stack entrypoint path and resolved stage** in your local Alchemy home (`~/.alchemy`, or `$ALCHEMY_HOME`). Relative paths and symlinks to the same entrypoint share ownership. Different entrypoints or stages remain independent, even if their stack declarations use the same name.

Running the same invocation again prints the owner's PID and exits successfully without starting another exec process or sidecar. The session may still be starting; this message does not assert that its resources are healthy. The original terminal retains control: stop it with Ctrl+C before starting a replacement.

A repeated invocation with a different working directory, profile selection, environment-file selection, `--force`, or include/exclude filters fails with a conflict message. Profile selection records whether `--profile` was explicit and, when inherited, the shell's `$ALCHEMY_PROFILE`. Explicit overrides have their own precedence with stack secret providers. Explicit `--env-file .env` also counts as a different selection because it gives dotenv values precedence over process environment variables.

Filter order and duplicate filters preserve the same selection. Ownership records store only option metadata; environment-file contents and credentials remain private. Changes to environment-file contents are outside the ownership check.

Ownership is released after child cleanup. A later invocation can recover a record whose owner PID is known to have exited. An unreadable or corrupt record, or uncertain PID liveness, stops the invocation with an error.

Metadata updates use a short-lived lock with automatic age-based recovery disabled. An abrupt exit during a metadata update can leave that lock behind. The timeout error identifies its directory; after stopping other Alchemy processes, remove that directory and retry.

## Flags

| Option              | Description                                                        |
| ------------------- | ------------------------------------------------------------------ |
| `--stage <name>`    | Stage to use for dev (defaults to `$ALCHEMY_STAGE` or `dev_$USER`) |
| `--force`           | Force updates for resources that would otherwise no-op             |
| `--profile <name>`  | Auth profile to use (defaults to `$ALCHEMY_PROFILE` or `default`) |
| `--env-file <path>` | Load environment variables from a file                             |
| `--config, -c <file>`            | Stack file to run (defaults to `alchemy.run.ts`)                   |

`alchemy deploy` defaults to `live_$USER`. Using a different default
here means a bare `alchemy dev` will not replace a stage you deployed.
Pass `--stage` (or `$ALCHEMY_STAGE`) to run local emulation against a specific
stage — including one you also deploy.

Tear the default local-dev stage down with
`alchemy destroy --stage dev_$USER`.

## Examples

```sh
# Start dev mode (stage dev_$USER)
alchemy dev

# Emulate the prod program locally (replaces that stage's local/live mode)
alchemy dev --stage prod
```
