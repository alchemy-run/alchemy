Every Alchemy runtime ships with OpenTelemetry export built in.
Each fetch, queue message, cron fire, RPC call, Durable Object call,
Workflow run, and Lambda invocation is wrapped in the machinery to
export the traces, logs, and metrics that Effect already emits —
`Effect.withSpan` and `Effect.fn` spans, `Effect.log` records, and
`Metric` updates. There is no exporter to write and no SDK to
initialize.

## Configure with env vars

Telemetry is on by default and configures itself from the standard
OpenTelemetry environment variables. Set an endpoint on the
Function/Worker and it starts exporting:

```typescript
const worker = yield* Cloudflare.Worker("Api", {
  main: "./src/worker.ts",
  env: {
    OTEL_EXPORTER_OTLP_ENDPOINT: "https://collector.example.com",
    OTEL_EXPORTER_OTLP_HEADERS: "x-api-key=...",
  },
});
```

Without an endpoint, telemetry resolves to an empty Layer — Effect's
default tracer is a no-op, so all instrumentation stays free until
you point it somewhere.

The full set of recognized variables:

| Variable | Meaning |
| --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Base OTLP/HTTP URL; `/v1/{traces,logs,metrics}` is appended per signal |
| `OTEL_EXPORTER_OTLP_{TRACES,LOGS,METRICS}_ENDPOINT` | Per-signal URL, used as-is (takes precedence over the base) |
| `OTEL_EXPORTER_OTLP_HEADERS` | Headers in `k=v,k2=v2` form (e.g. auth tokens) |
| `OTEL_EXPORTER_OTLP_{TRACES,LOGS,METRICS}_HEADERS` | Per-signal headers (take precedence) |
| `OTEL_SERVICE_NAME` | The `service.name` resource attribute |
| `OTEL_SDK_DISABLED` | `true` disables telemetry even when endpoints are set |

Each signal resolves independently — set only a traces endpoint and
only traces export. Per-signal variables matter for backends like
[Axiom](/axiom) that route by dataset: each signal gets its own URL
and its own `X-Axiom-Dataset` header (see the
[tutorial](/cloudflare/tutorial/part-6) for the full wiring).

## Service identity

The exported `service.name` defaults to `OTEL_SERVICE_NAME`, then
the deployed Function/Worker's physical name, then the stack name.
Every signal also carries `alchemy.stack` and `alchemy.stage`
resource attributes, so one collector can receive every stage and
still tell them apart.

## Per-event scope and flushing

On the per-event runtimes — Worker fetch/queue/cron/RPC, Durable
Object calls, Workflow runs, Lambda invocations — the exporters are
built into each event's request scope and buffered telemetry is
flushed when that scope closes:

- On Cloudflare, the flush is registered with `ctx.waitUntil`, so it
  happens after the response is sent and never adds latency.
- On Lambda, the flush settles inline before the invocation returns —
  the response isn't released until the invoke completes anyway.

This per-event lifecycle is what makes export work on workerd, where
timers and fetches are pinned to the request that created them: a
process-global batching exporter would be killed the moment its
creating request ended.

Server runtimes — Cloudflare Containers, ECS Tasks, EC2 hosts,
Lambda microVMs — are long-lived processes, so they build the
exporters once at startup instead: telemetry batches on the standard
export intervals and the final flush runs at graceful shutdown.

## HTTP request spans

Fetch handlers get an `http.server` root span automatically, carrying
the method, URL, status, and headers. Incoming `traceparent` headers
are honored, so a trace that starts in one service continues through
your Worker or Lambda — and outgoing requests made with Effect's
`HttpClient` propagate the context onward.

Everything you instrument nests under that root:

```typescript
const object = yield* bucket
  .get(key)
  .pipe(Effect.withSpan("bucket.get", { attributes: { key } }));
```

## Override the exporter in code

The telemetry configuration is itself a value you can provide on the
Function/Worker's init Effect:

```typescript
import * as Alchemy from "alchemy";

// configure the built-in OTLP exporter explicitly:
Effect.provide(Alchemy.Telemetry.otlp({
  baseUrl: "https://api.honeycomb.io",
  headers: { "x-honeycomb-team": "..." },
}))

// install any custom exporter Layer:
Effect.provide(Alchemy.Telemetry.layer(myExporterLayer))

// force-disable, ignoring OTEL_* env vars:
Effect.provide(Alchemy.Telemetry.disabled)
```

`Telemetry.layer` accepts any Layer that provides a `Tracer`,
loggers, or metric exporters — Effect's
`effect/unstable/observability` modules (`OtlpTracer`, `OtlpLogger`,
`OtlpMetrics`, protobuf serialization) compose here directly. The
Layer is built per event into the event's request scope, so a custom
exporter gets the same flush-on-close behavior as the built-in one.

:::caution
A custom Layer for per-event runtimes should disable or greatly
lengthen its periodic export intervals (e.g.
`exportInterval: "1 hour"`). An interval export that fires mid-event
races the scope close — the close interrupts the in-flight batch and
drops it. The built-in defaults already handle this; the flush on
scope close delivers everything.
:::
