title: Effectful Websites
description: Website constructs accept the same Effect program as a Worker or Lambda Function — one deploy serves your framework app and an effect-native API from a single origin, on Cloudflare and AWS alike.
---

Every `Website` construct — `Cloudflare.Website.*` and `AWS.Website.*` —
accepts the same third argument as a Worker or Lambda Function: an
[Effectful Constructor](/infrastructure-as-effects/functions-and-servers).
One deploy then serves your framework app **and** your effect-native API
from a single origin:

```typescript
export default class Site extends Website.Vite<Site>()(
  "Site",
  { main: import.meta.url },
  Effect.gen(function* () {
    const users = yield* KV.ReadWriteNamespace(yield* Users); // binding
    return {
      fetch: Effect.gen(function* () {
        /* your API */
      }),
    };
  }).pipe(Effect.provide(KV.ReadWriteNamespaceBinding)),
) {}
```

The program works exactly like a Worker's or Lambda's: the init Effect
runs at plan time to collect [Bindings](/infrastructure-as-effects/binding)
(env vars and native bindings on Cloudflare, env vars and IAM on AWS)
onto the site's server, and runs again inside the deployed
runtime to serve requests. The framework's own build ships unchanged —
alchemy never rewrites or scans it. HTTP delivery is **your mount**: one
framework-native file that calls `mount(Site)` from `alchemy/Serve` and
composes `site.fetch` with the framework's own handler.

## The two files: backend and mount

The program must live in a **dedicated module whose default export is
the class**, anchored by `main: import.meta.url` — identical to
`Cloudflare.Worker`. The deployed bundle re-imports the program by path,
so it cannot live inline in `alchemy.run.ts`.

```typescript
// src/backend.ts — the class + program
import * as KV from "alchemy/Cloudflare/KV";
import * as Website from "alchemy/Cloudflare/Website";
import * as Effect from "effect/Effect";
import { HttpServerRequest } from "effect/unstable/http/HttpServerRequest";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export const Users = KV.Namespace("Users");

export default class Site extends Website.Vite<Site>()(
  "Site",
  {
    main: import.meta.url,
    assets: { notFoundHandling: "single-page-application" },
    server: { entry: "./server.ts" },
  },
  Effect.gen(function* () {
    const users = yield* KV.ReadWriteNamespace(yield* Users);
    return {
      fetch: Effect.gen(function* () {
        const request = yield* HttpServerRequest;
        const url = new URL(request.url, "http://localhost");
        if (url.pathname === "/api/user") {
          const value = yield* users.get("current").pipe(Effect.orDie);
          return yield* HttpServerResponse.json({ value });
        }
        // the effect owns /api/* — unknown paths get its own 404
        return yield* HttpServerResponse.json(
          { error: "not found" },
          { status: 404 },
        );
      }),
    };
  }).pipe(Effect.provide(KV.ReadWriteNamespaceBinding)),
) {}
```

The second file is **the mount** — your server entry (or the
framework's hook), where HTTP composition is ordinary code you own:

```typescript
// src/server.ts — the mount (Vite / TanStack Start server entry)
import framework from "@tanstack/react-start/server-entry";
import { mount } from "alchemy/Serve";
import Site from "./backend.ts";

const site = mount(Site);

export default {
  fetch: async (request: Request, env: unknown, ctx: ExecutionContext) =>
    (await site.fetch(request, env, ctx)) ?? framework.fetch(request, env, ctx),
};
```

`site.fetch` resolves the `Response` for paths the mount claims and
`undefined` for everything else — decline, not error — so `??` composes
the framework as the fallback. Gates, custom routes, and dispatch order
are plain statements around it. `env` and `ctx` are whatever your host
provides: pass them through on Cloudflare (finalizers ride
`ctx.waitUntil`); omit them on AWS and in dev servers (env resolves from
`process.env`, and the request scope settles inline).

```typescript
// alchemy.run.ts — deploy it like any resource
import Site from "./src/backend.ts";

const site = yield* Site;
```

:::tip[Prefer narrow subpath imports in site modules]
A `src/backend.ts` module is re-imported inside the framework's server
graph. The provider barrels (`alchemy/Cloudflare`, `alchemy/AWS`) are
fully supported there — the host-only engine machinery is invisible to
bundlers by construction — but the **service-level subpaths** keep the
compiled graph to the slice you actually use, which means smaller server
bundles and faster dev compiles:

```typescript
import * as KV from "alchemy/Cloudflare/KV"; // ✅ leanest
import * as Website from "alchemy/Cloudflare/Website"; // ✅
import { Bucket, GetObject } from "alchemy/AWS/S3"; // ✅
import { mount } from "alchemy/Serve"; // ✅

import * as Cloudflare from "alchemy/Cloudflare"; // ✅ works — just heavier
```
:::

## Routing semantics

**Routing is the mount's code.** The mount's claim decides who serves
each path — in your entry, where you can read it:

```
request → your mount code (gates, custom routes — plain statements)
  ├─ path inside the mount's routes? ─ yes ─► Effect fetch (authoritative — even its 404s)
  └─ no ─► site.fetch resolves undefined ─► framework fetch (SSR / framework routes)
```

`mount(Site, { routes })` (default `["/api/*"]`) declares the URL space
the Effect `fetch` owns. Globs: `*` matches any run of characters
including `/`, and a leading `!` marks an exclusion — **exclusions
win**. Inside the claim the Effect fetch is **authoritative**: whatever
it returns is the response, and an `HttpRouter` miss (a `RouteNotFound`
failure) renders as the effect's *own* 404 — never delegation, no
response sniffing. Outside the claim `site.fetch` resolves `undefined`
without invoking the effect, and your `??` fallback serves.

To hand a path inside the claim back to the framework, carve it out with
an exclusion glob:

```typescript
// the effect owns /api/*, except /api/auth/* stays the framework's
const site = mount(Site, { routes: ["/api/*", "!/api/auth/*"] });
```

`routes: ["/*"]` claims every request for the Effect fetch — the
framework then serves only the paths you exclude.

One deploy-time note: the platform's asset layer runs **in front of**
the server, so alchemy compiles the default `/api/*` claim into the
platform's edge ordering (Cloudflare `assets.runWorkerFirst`; the
CloudFront router on AWS) — a static file can never shadow an API path,
even under SPA fallback. If your mount claims paths beyond `/api/*`,
mirror them in `assets: { runWorkerFirst: [...] }` on Cloudflare.

## Calling the backend

Hand-rolled `fetch` routing is optional. Any other function-valued key
on the impl shape — beside `fetch` and the platform handlers (`queue`,
`scheduled`, ...) — is an **RPC method**, served automatically at the
reserved wire path `POST /api/__rpc/<method>`:

```typescript
// src/backend.ts
Effect.gen(function* () {
  const users = yield* KV.ReadWriteNamespace(yield* Users);
  return {
    get: () => users.get("current"),
    save: (value: string) => users.put("current", value),
  };
}).pipe(Effect.provide(KV.ReadWriteNamespaceBinding));
```

Methods return `Effect` (or a plain value/Promise); arguments and
results cross the wire as plain JSON. The `/api/__rpc` path is
**reserved** — user routes must not claim it, and the default `/api/*`
mount claim already covers it. A backend of methods alone needs no
`fetch` handler at all.

### In the browser: the type-only form

```typescript
// a client component — note the TYPE-ONLY backend import
import { createClient } from "alchemy/Client";
import type Backend from "../src/backend.ts";

const backend = createClient<typeof Backend>();

await backend.save("hello"); // POST /api/__rpc/save  ["hello"]
const value = await backend.get(); // fully typed from the backend
```

The backend is imported **as a type only**, so zero backend bytes reach
the client bundle — the proxy POSTs to the page's own origin. Never
value-import the backend module from client-bundled code: a value
import would pull the backend program into the browser bundle.

### On the server: the value form

SSR seams — a TanStack/SvelteKit `load`, Astro frontmatter on a
non-prerendered page, a Next server component — import the backend as a
**value** and pass the class:

```typescript
import { createClient } from "alchemy/Client";
import Backend from "../src/backend.ts";

export const load = async () => {
  const backend = createClient(Backend);
  return { value: await backend.get() }; // direct dispatch — no HTTP
};
```

Same call shape, different transport: on the server, calls dispatch
**directly into the backend's effects in-process** — there is no HTTP
round-trip against your own origin once you're already on it.

### Self-authorizing methods

Browser calls are same-origin fetches, so session cookies ride along by
default. Each RPC call runs with `HttpServerRequest` in context —
exactly like `fetch` — so a method authorizes itself by reading the
caller's headers/cookies:

```typescript
save: (value: string) =>
  Effect.gen(function* () {
    const request = yield* HttpServerRequest;
    if (request.cookies.session === undefined) {
      return yield* Effect.fail(new Unauthorized());
    }
    return yield* users.put("current", value);
  }),
```

### Per-request identity on the server

The in-process form has no ambient request — hand the incoming
request's headers over so methods see the caller's cookies:

```typescript
const backend = createClient(Backend, { headers: request.headers });
```

For a shared, module-scope client, pass a **thunk** instead — it is
resolved fresh on every call, so the client stays per-request-correct
with a framework's ambient accessor (TanStack Start's
`getRequestHeaders`, Next's `headers`):

```typescript
import { getRequestHeaders } from "@tanstack/react-start/server";

export const backend = createClient(Backend, { headers: getRequestHeaders });
```

### Typed failures

A method's typed failure crosses the wire as a 400
`{"error": {"_tag", ...props}}` envelope and rejects as an `RpcError`
**structurally** re-carrying the failure's `_tag` + props (the
backend's error class never ships to the client); defects are sanitized
server-side to a message-only `RpcDefectError` — no stacks or
internals. On the in-process path the rejection is the real failure
instance. Either way, switching on `_tag` works in both worlds:

```typescript
try {
  await backend.save(draft);
} catch (error) {
  if (error instanceof RpcError && error._tag === "Unauthorized") {
    // redirect to login
  }
}
```

### Effect mode

`createEffectClient` is the same bridge with methods returning
`Effect` — the method's typed failure rides the failure channel
(decoded structurally on the wire path), so `Effect.catchTag` works on
backend failure tags:

```typescript
import { createEffectClient } from "alchemy/Client";
import type Backend from "../src/backend.ts";

const backend = createEffectClient<typeof Backend>();

const value = yield* backend.get().pipe(
  Effect.catchTag("KVError", () => Effect.succeed(null)),
);
```

### Prerendered pages

A prerendered page builds in a world with no deployed backend: the
value form fails with the typed `RpcPrerenderError` instead of
dispatching. Keep prerendered/static pages backend-free — make the page
dynamic, or move the call into client code, where it becomes a wire
call against the deployed site.

## Per-framework mounts

The mount is the same `mount(Site)` everywhere — what differs per
framework is **which file you own** to compose it in. Same file, both
clouds:

| Framework | Your mount file |
| --- | --- |
| StaticSite | none — the program **is** the server (the Worker in front of the assets on Cloudflare; the server Lambda on AWS) |
| Vite SPA | none — no framework server exists; the program serves `/api/*` directly |
| Vite / TanStack Start | `src/server.ts` (the server entry — `server: { entry }` on plain Vite; Start's own convention) |
| SvelteKit | `src/hooks.server.ts` (the `handle` hook) |
| Next.js | `app/api/[[...slug]]/route.ts` (an optional catch-all route file) |
| Nuxt | `server/middleware/alchemy.ts` (a Nitro middleware) |
| Astro | `src/fetch.ts` (Astro 7's native fetch entrypoint) |
| Waku | `src/middleware/mount.ts` (a Waku middleware — compose `site.fetch(request) ?? next()`) |

```typescript
// Next.js — app/api/[[...slug]]/route.ts (both clouds)
import { mount } from "alchemy/Serve";
import Site from "../../../src/backend.ts";

const site = mount(Site);
export const dynamic = "force-dynamic";

const handler = async (req: Request): Promise<Response> =>
  (await site.fetch(req)) ?? new Response("Not Found", { status: 404 });
export { handler as GET, handler as POST, handler as PUT,
         handler as PATCH, handler as DELETE, handler as HEAD,
         handler as OPTIONS };
```

```typescript
// SvelteKit — src/hooks.server.ts (both clouds)
import { mount } from "alchemy/Serve";
import Site from "./backend.ts";

const site = mount(Site);

export const handle = async ({ event, resolve }) =>
  (await site.fetch(event.request, event.platform?.env, event.platform?.ctx)) ??
  resolve(event);
```

For any other fetch-shaped server entry, the composition is the same
two lines:

```typescript
// src/server.ts (TanStack Start shown)
import framework from "@tanstack/react-start/server-entry";
import { mount } from "alchemy/Serve";
import Site from "./backend.ts";

const site = mount(Site);
export default {
  fetch: async (req: Request, env: unknown, ctx: ExecutionContext) =>
    (await site.fetch(req, env, ctx)) ?? framework.fetch(req, env, ctx),
};
```

## Beyond fetch

The mount delivers HTTP; everything else the program registers —
Durable Object and Workflow classes, queue consumers, cron `scheduled`
handlers — is the **platform surface**, and alchemy delivers it through
a generated entry that wraps the framework bundle *additively*: the
framework handler (with your mount inside) serves all HTTP verbatim,
and the wrapper adds the class exports and listener dispatch next to
it. Everything the wrapper emits derives from the program's `yield*`
registrations at plan time — nothing is scanned out of build output,
and you never hand-write a DO or Workflow export.

On Cloudflare that generated entry is the deployed Worker's entry. On
AWS it is the single Lambda's handler: HTTP-shaped events route to the
framework handler and SQS batches / schedule events dispatch through
the program's registered listeners — **one Lambda**, no sibling
functions. The effectful `StaticSite` (and the Vite SPA) are the
degenerate case where there is no framework server at all: the program
*is* the entry.

## Async work

The request/response leg is only half of a backend: a method can
**enqueue** work, and a queue consumer **on the same class** processes it
in the background. Producer, consumer, and the queue itself are all
declared by the one program — the same init Effect that collects
bindings at plan time deploys the queue, grants the send capability, and
registers the consumer.

Declare the queue next to the class, like any other resource:

```typescript
// src/backend.ts
import { Queue } from "alchemy/Cloudflare/Queues";

export const Jobs = Queue("Jobs");
```

The producer side is a capability binding like any other — expose it as
an RPC method:

```typescript
const jobs = yield* WriteQueue(yield* Jobs);
return {
  enqueue: (message: string) =>
    jobs.send(message, { contentType: "text" }).pipe(Effect.orDie),
};
```

The consumer registers in the same init Effect, on the same class —
`consumeQueueMessages` wires both halves in one call: at plan time it
yields the `Queues.Consumer` resource that points the queue at the
site's Worker, and at runtime it registers the `queue` event listener:

```typescript
yield* consumeQueueMessages<string>(
  yield* Jobs,
  { batchSize: 5, maxRetries: 2 },
  (stream) =>
    Stream.runForEach(stream, (msg) =>
      recordProcessed(String(msg.body)), // e.g. bump a counter in KV
    ),
);
```

Provide `Queues.EventSourceLive` alongside the producer's
`WriteQueueBinding` on the program, and delivery follows the
[Beyond fetch](#beyond-fetch) mechanics — the batch dispatches on the
same Worker that served the enqueue.

AWS is symmetric — `AWS.SQS.consumeQueueMessages` with the
`Lambda.QueueEventSource` layer, and `SQS.SendMessage` (provided by
`SQS.SendMessageHttp`) as the producer capability:

```typescript
import { consumeQueueMessages, Queue, SendMessage } from "alchemy/AWS/SQS";

const send = yield* SendMessage(yield* Jobs);
yield* consumeQueueMessages(yield* Jobs, (records) =>
  Stream.runForEach(records, (record) => recordProcessed(record.body)),
);
return {
  enqueue: (message: string) =>
    send({ MessageBody: message }).pipe(Effect.orDie),
};
```

On AWS the consumer rides the site's own Lambda — the generated
single-handler entry dispatches SQS batches through the registered
consumer, and the event-source mapping and its IAM target that same
function, so `recordProcessed` above writes to the same DynamoDB table
the fetch side reads.

Because the consumer runs asynchronously, the frontend observes the
catch-up by polling a read method — a `processed()` RPC method that
returns whatever state the consumer writes (the counter above) — over
the same typed bridge:

```typescript
// client code — same type-only createClient bridge
await backend.enqueue("hello queue");
// poll until the consumer's write lands
const { count, last } = await backend.processed();
```

## Dev mode

`alchemy dev` runs each framework's own dev server (full HMR) with your
mount running natively inside it — the same file, the same routing
semantics as production:

- **Cloudflare** — bindings resolve against the local simulators. The
  program's platform surface runs locally too: Durable Objects,
  Workflows, and queue consumers are hosted in a local platform worker
  (workerd) next to the dev server, so DO round-trips, workflow runs,
  and queue produce→consume all work offline. The site's identity stays
  `dev:`-prefixed; nothing touches the real cloud unless a resource is
  piped through `Alchemy.remote()`.
- **AWS** — the program runs in the local Lambda emulator; a local
  queue (not piped through `Alchemy.remote()`) delivers batches to the
  emulated consumer. Capability resources piped through
  `Alchemy.remote()` hit the real cloud with your ambient credentials.

## Migrating from two workers

Before effectful Websites, a fullstack app was typically a Website plus
a separate API Worker, wired together with routes or a service binding:

```typescript
// before: two resources, two origins (or manual route wiring)
const api = yield* Api; // a Cloudflare.Worker serving /api/*
const site = yield* Cloudflare.Website.Vite("Site", {
  env: { API_URL: api.url },
});
```

Move the API Worker's Effect program into the Website's third argument
and delete the separate Worker:

```diff lang="typescript"
-export default class Api extends Cloudflare.Worker<Api>()(
-  "Api",
-  { main: import.meta.url },
+export default class Site extends Website.Vite<Site>()(
+  "Site",
+  { main: import.meta.url, server: { entry: "./server.ts" } },
   Effect.gen(function* () {
     const users = yield* KV.ReadWriteNamespace(yield* Users);
     return { fetch: /* unchanged */ };
   }).pipe(Effect.provide(KV.ReadWriteNamespaceBinding)),
 ) {}
```

The API now serves same-origin — no CORS, no second deploy, no
`API_URL` plumbing — and the frontend calls it through the typed
[`createClient`](/providers/client/createclient) bridge (or plain
`fetch("/api/…")` against the effect `fetch`). Bindings, RPC methods,
and (on Cloudflare) Durable Objects and event handlers move over
unchanged.
