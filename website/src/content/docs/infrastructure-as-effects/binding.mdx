A **Binding** connects a [Resource](/infrastructure-as-code/resource)
to a [Runtime](/infrastructure-as-effects/runtime) such as a Worker,
Lambda Function, Container, or Server. Inside the Runtime's
constructor, you yield the resource and get back a typed client:

```typescript
import * as AWS from "alchemy/AWS";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export const Jobs = AWS.DynamoDB.Table("Jobs", { partitionKey: "pk" });

export default AWS.Lambda.Function(
  "Api",
  { main: import.meta.url, functionUrl: true },
  Effect.gen(function* () {
    const getItem = yield* AWS.DynamoDB.GetItem(Jobs);

    return {
      fetch: Effect.gen(function* () {
        const job = yield* getItem({ Key: { pk: { S: "job-1" } } });
        return yield* HttpServerResponse.json(job.Item);
      }),
    };
  }).pipe(Effect.provide(AWS.DynamoDB.GetItemHttp)),
);
```

`yield* GetItem(Jobs)` is the binding. `getItem` is the client.
`GetItemHttp` is the implementation.

A Function that reads a table needs three things: permission to call
the API, the table's name at runtime, and a client to call it with. In
traditional IaC those live in three places. A policy sits in the
infrastructure code. An environment variable carries the name between
the two. An SDK call in the handler reads it back:

```typescript
// infrastructure: grant access and pass the name
policy: { Action: ["dynamodb:GetItem"], Resource: [table.arn] },
environment: { JOBS_TABLE: table.name },
```

```typescript
// handler: hope the two above agree
const client = new DynamoDBClient();
await client.send(
  new GetItemCommand({ TableName: process.env.JOBS_TABLE, Key }),
);
```

Nothing checks that they agree. If you rename the table, widen the
policy, or forget the env var, you find out at runtime. The binding
covers all three. The sections below follow what that one line
produces.

## Permissions

At deploy time the binding attaches an IAM statement to the Function's
role. It grants the one action the client can make, on the one table
it was bound to:

```json
{
  "Effect": "Allow",
  "Action": ["dynamodb:GetItem"],
  "Resource": ["arn:aws:dynamodb:us-east-1:123456789012:table/Jobs-a1b2c3"]
}
```

Least privilege follows from the shape. If you also bind `PutItem`, the role
gains a second statement for `dynamodb:PutItem` and nothing else:

```typescript
const getItem = yield* AWS.DynamoDB.GetItem(Jobs);
const putItem = yield* AWS.DynamoDB.PutItem(Jobs);
```

Bind several tables at once and the statement lists each of their ARNs:

```typescript
const batchGet = yield* AWS.DynamoDB.BatchGetItem(Jobs, Audit);
```

## Configuration

The client needs the table's physical name. The binding serializes the
`Jobs.tableName` [Output](/infrastructure-as-code/outputs) into the
Function's environment:

```sh
Jobs_tableName=Jobs-a1b2c3
```

`getItem` reads it back and fills in `TableName` on every request. You
never touch `process.env`, and the name can't drift from the policy.
Both come from the same `Jobs` declaration.

## The client

`getItem` is the DynamoDB operation with the table already filled in.
It returns an `Effect` with a typed error channel, so retries, timeouts,
and error handling compose onto it:

```typescript
const job = yield* getItem({ Key: { pk: { S: "job-1" } } }).pipe(
  Effect.retry({ times: 3, schedule: Schedule.exponential("100 millis") }),
  Effect.timeout("5 seconds"),
  Effect.catchTag("ResourceNotFoundException", () => Effect.succeed(undefined)),
);
```

## A contract and a Layer

`GetItem` names the capability. `GetItemHttp` decides how it's
satisfied. Cloudflare shows why that split matters. A Worker binds an
R2 bucket with the same shape:

```typescript
import * as Cloudflare from "alchemy/Cloudflare";

export const Uploads = Cloudflare.R2.Bucket("Uploads");

export default Cloudflare.Worker(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const bucket = yield* Cloudflare.R2.ReadWriteBucket(Uploads);

    return {
      fetch: Effect.gen(function* () {
        yield* bucket.put("hello.txt", "world");
        return HttpServerResponse.text("ok");
      }),
    };
  }).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)),
);
```

Cloudflare has no IAM. `ReadWriteBucketBinding` registers a native
`r2_bucket` binding on the Worker. The access level is in the name:
`ReadBucket`, `WriteBucket`, or `ReadWriteBucket`.

The contract is a `Binding.Service`. It names the capability and the
client it returns. It says nothing about the platform:

```typescript
export interface ReadWriteBucket extends Binding.Service<
  ReadWriteBucket,
  "Cloudflare.R2.ReadWriteBucket",
  (bucket: Bucket) => Effect.Effect<ReadWriteBucketClient>
> {}
```

So a different Layer can satisfy the same contract. Swap the
Layer and `bucket` calls R2 over HTTP with a scoped API token minted at
deploy time:

```diff lang="typescript"
-  }).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)),
+  }).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketHttp)),
```

The handler doesn't change. Cloudflare capabilities ship up to three
implementations of the same contract:

- `*Binding` (e.g. `ReadWriteBucketBinding`): registers a native binding
  on the Worker and calls it at runtime.
- `*Http` (e.g. `ReadWriteBucketHttp`): mints a scoped API token at
  deploy time and calls the Cloudflare HTTP API with it.
- `*Local` (e.g. `ReadWriteBucketLocal`): calls the HTTP API with the
  credentials the CLI is already deploying with. It registers nothing on
  a host, so it suits [Actions](/infrastructure-as-code/action#binding-resources)
  and other deploy-time code.

`*Local` Layers exist only for Cloudflare capabilities with an HTTP data
plane, such as D1, KV, R2, and Queues. AWS bindings have no `*Local`
variant.

A Layer that needs a platform the host can't supply is a compile error:

```typescript
export default AWS.Lambda.Function(
  "Api",
  { main: import.meta.url },
  handler.pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)),
  // ✗ Type error: the Layer requires `WorkerEnvironment` and `Worker`,
  //   which a Lambda Function can't provide
);
```

[Layers](/infrastructure-as-effects/layers) takes this split one level
up, so your own services can carry their bindings with them.

## Plan-time invokes

A binding can also run before anything is deployed. Terraform calls
this a data source. Pulumi calls it an invoke. Call it directly and
you get back an [Output](/infrastructure-as-code/outputs) to pass into
resource props:

```typescript
// Output<ec2.Image | undefined>
const image = AWS.EC2.getAmi({ owners: ["amazon"], name: ["al2023-ami-2023.*"] });

// a helper built on it. Output<string>, fails when nothing matches
imageId: AWS.EC2.amazonLinux2023(),
```

`getAmi` is `GetAmi.execute`. Any binding whose client takes no
arguments has an `.execute(...)` that runs it at plan time and returns
an `Output`. The call is hostless, so no IAM or environment is
attached. Its implementation Layer must be registered on the Stack.
The cloud `providers()` Layers include the plan-executable ones. A
failure fails the plan.

The same capability bound inside a Function with
`yield* AWS.EC2.GetAmi(...)` still grants its IAM and runs at runtime.
One contract covers both phases.

## Event Sources and Sinks

An [Event Source](/infrastructure-as-effects/event-sources) is a
Binding that runs an Effect or `Stream` in the background whenever
something happens on the resource:

```typescript
yield* AWS.SQS.consumeQueueMessages(Inbound, (records) =>
  Stream.runForEach(records, (record) => Effect.log(record.body)),
);
```

A [Sink](/infrastructure-as-effects/sinks) is the converse. It is a
Binding you sink a `Stream` into:

```typescript
const sink = yield* AWS.SQS.QueueSink(Outbound);
```

Both generate their permissions and configuration the same way.

## How it works under the hood

A binding declaration says nothing about how it is implemented. The
Layer you provide decides that:

```typescript
Effect.provide(Cloudflare.R2.ReadWriteBucketHttp)
```

Inside that Layer, the deploy-time work sits behind a guard. The
**Construction phase** runs twice. The guard tells the two runs
apart:

```typescript
if (!globalThis.__ALCHEMY_RUNTIME__) {
  // deploy time only: register IAM / native bindings / env on the host
  yield* host.bind`${resource}`(/* … */);
}
// always: return the typed runtime client
```

When Alchemy bundles the Runtime, it defines that global as `true`, so
the bundler drops the whole branch. Only the client ships:

```typescript
// folded into every bundle as a rolldown define
"globalThis.__ALCHEMY_RUNTIME__": "true"
```

The Resource Provider is the code that creates the bucket or the
table. The binding never imports it. Declaring a resource only records
a requirement for its Provider. The Stack satisfies that requirement
once:

```typescript
export default Alchemy.Stack(
  "MyApp",
  { providers: Cloudflare.providers(), state: Cloudflare.state() },
  Effect.gen(function* () {
    yield* Api;
  }),
);
```

This lets you declare resources and bindings inside runtime code with
little to no effect on bundle size. The heavy infrastructure code stays
at the Stack. The guard erases the rest.
[Phases](/infrastructure-as-effects/phases#the-__alchemy_runtime__-guard)
covers the guard in depth.

The granularity pays off twice. Every binding has its own Layer. Each
Layer carries exactly one client and registers exactly one grant. If
you provide the two you use, you get two clients in the bundle and two
statements on the role, and nothing more:

```typescript
Effect.provide(
  Layer.mergeAll(
    AWS.DynamoDB.GetItemHttp, // ships getItem, grants dynamodb:GetItem
    AWS.DynamoDB.PutItemHttp, // ships putItem, grants dynamodb:PutItem
  ),
)
```

The same choice that keeps the bundle small keeps the permissions and
environment minimal.
