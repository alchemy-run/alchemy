Infrastructure as Effects is Alchemy's model for building
applications. The code that runs inside a Worker or Lambda Function
and the infrastructure it runs on are one Effect program. A Worker is
a [Resource](/infrastructure-as-code/resource) that carries its own
code, and the resources it uses are wired in as typed values:

```typescript
import * as Cloudflare from "alchemy/Cloudflare";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export const Uploads = Cloudflare.R2.Bucket("Uploads");

export default Cloudflare.Worker(
  "Api",
  { main: import.meta.url },
  Effect.gen(function* () {
    const bucket = yield* Cloudflare.R2.ReadWriteBucket(Uploads);

    return {
      fetch: Effect.gen(function* () {
        const obj = yield* bucket.get("hello.txt");
        return obj
          ? HttpServerResponse.text(yield* obj.text())
          : HttpServerResponse.text("Not found", { status: 404 });
      }),
    };
  }).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)),
);
```

Traditional IaC splits this in two. One program declares the bucket,
the Worker, and the permission between them. Another program runs
inside the Worker and reaches for the bucket through an environment
variable:

```typescript
// infrastructure
const bucket = new R2Bucket("uploads");
new Worker("api", { script: "src/api.ts", bindings: { BUCKET: bucket } });

// src/api.ts
export default {
  async fetch(request, env) {
    const obj = await env.BUCKET.get("hello.txt");
  },
};
```

The two agree by convention. `BUCKET` is typed twice, the permission
lives in one file and the call in another, and nothing tells you when
they drift. In Alchemy there is one program, and `bucket` is a value
the handler closes over.

Everything in this section is in that one Worker. Let's take it
apart.

## Runtimes carry their code

`Cloudflare.Worker("Api", props, effect)` is a **Runtime**: a Resource
that carries the code it runs. The props are the cloud configuration. The Effect is the code
that runs inside it. One deploy ships both, and the Effect always has
the same shape: bind what you need, then return what you expose.

[Runtime](/infrastructure-as-effects/runtime)
covers that shape, the `fetch` and RPC interface it returns, and the
three ways to declare one.

## Bindings wire resources in

`yield* Cloudflare.R2.ReadWriteBucket(Uploads)` is a Binding. It hands
back `bucket`, a typed client, and generates the permission and
configuration the client needs. On Cloudflare that is a native
`r2_bucket` binding. On AWS it is an IAM statement scoped to one
resource, plus the resource's name in the Function's environment:

```typescript
const getItem = yield* AWS.DynamoDB.GetItem(Jobs);
// → { Action: ["dynamodb:GetItem"], Resource: [Jobs.tableArn] }
// → Jobs_tableName=Jobs-a1b2c3
```

There is no `env.BUCKET`. The binding is the SDK.
[Bindings](/infrastructure-as-effects/binding) follows one binding
through everything it produces.

Some bindings run your Function instead of being called from it. An
[Event Source](/infrastructure-as-effects/event-sources) triggers on a
resource and hands you the messages as an Effect `Stream`. A
[Sink](/infrastructure-as-effects/sinks) is the write side, a resource
you run a `Stream` into:

```typescript
yield* AWS.SQS.consumeQueueMessages(Inbound, (records) =>
  records.pipe(Stream.map(transform), Stream.run(outboundSink)),
);
```

## Two phases, one program

The Worker's Effect runs in two phases. The outer Effect is the
**Construction phase**. It runs at deploy time, where
`ReadWriteBucket(Uploads)` records the binding, and again at cold
start, where the same line builds the live client. The inner `fetch`
Effect is the **Runtime phase**. It runs per request, only inside the
deployed Worker:

```typescript
Effect.gen(function* () {
  // Construction: deploy time and cold start
  const bucket = yield* Cloudflare.R2.ReadWriteBucket(Uploads);

  return {
    // Runtime: per request, inside the deployed Worker
    fetch: Effect.gen(function* () {
      const obj = yield* bucket.get("hello.txt");
    }),
  };
});
```

Both phases are one program, so `bucket` is a value the handler closes
over rather than something looked up at request time.
[Phases](/infrastructure-as-effects/phases) explains exactly what runs
when.

## Layers package it all

A binding is a contract plus an implementation Layer. `ReadWriteBucket`
names the capability. `ReadWriteBucketBinding` decides how it's
satisfied, and can be swapped for `ReadWriteBucketHttp` without touching
the handler.

The same split works one level up. Put resources and bindings inside a
`Layer.effect` behind your own service, and consumers see only the
service:

```typescript
export const JobServiceKV = Layer.effect(
  JobService,
  Effect.gen(function* () {
    const kv = yield* Cloudflare.KV.ReadWriteNamespace(Cloudflare.KV.Namespace("Jobs"));
    return { getJob: (id: string) => kv.get<Job>(id, "json") };
  }),
);
```

Provide `JobServiceKV` to a Worker and the namespace is created, bound,
and hidden behind `JobService`.
[Layers](/infrastructure-as-effects/layers) builds one from scratch,
and [Circular Bindings](/infrastructure-as-effects/circular-bindings)
uses the split to let two Workers call each other.

## Built into every Runtime

[Telemetry](/infrastructure-as-effects/telemetry) is a Layer too.
Provide an exporter alongside your bindings and every request, queue
batch, and cron fire exports the traces and logs Effect already emits.
[Custom Runtime](/infrastructure-as-effects/custom-runtime) brings the
whole model to a compute target Alchemy doesn't ship.

Effect style is optional. Bindings also work as plain props on an
`async fetch` handler with a typed env via `InferEnv`. See
[Effect handlers vs async handlers](/infrastructure-as-effects/runtime#effect-handlers-vs-async-handlers).
