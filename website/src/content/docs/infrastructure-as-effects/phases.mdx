This page covers when your code runs at deploy time and when it runs in
the deployed [runtime](/infrastructure-as-effects/runtime). Read it
before you put I/O, `Config` lookups, or cleanup in a Worker, Lambda
Function, or Container.

## Construction vs runtime

A runtime's code is an Effect that returns an Effect. The outer Effect is the
**Construction phase**, and the handlers it returns are the **Runtime
phase**:

```typescript
Cloudflare.Worker(
  "Worker",
  { main: import.meta.url },
  Effect.gen(function* () {
    // ─── Construction phase ───
    // runs at deploy time and once per cold start
    const bucket = yield* Cloudflare.R2.ReadWriteBucket(Bucket);

    return {
      // ─── Runtime phase ───
      // runs per request, only inside the deployed Worker
      fetch: Effect.gen(function* () {
        const obj = yield* bucket.get("key");
        return HttpServerResponse.text(yield* obj.text());
      }),
    };
  }).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)),
);
```

Construction sets up `bucket` once, and the handler closure captures
it. Each request then runs with everything already wired up.

`Alchemy.RuntimeContext` exists only in the Runtime phase. An Effect
that requires `RuntimeContext` type-checks only inside the handler
closure. [Layers](/infrastructure-as-effects/layers#the-types-hold-the-boundary)
uses this to keep whole services honest about where they can run.

- **At deploy time**, the constructor runs to discover bindings.
  Alchemy needs to know which resources the handler uses so it can wire
  permissions, env vars, and references.
- **At cold start**, the constructor runs again inside the deployed
  Worker. The same binding calls now return live clients backed by the
  deployed resource.
- **The handler body** runs only in the deployed runtime. It never runs
  at deploy time, so per-request work there doesn't slow down deploys.

### What this means for constructor code

A `Config` lookup in the constructor is captured at deploy time and
bound onto the runtime as a secret. At runtime the same lookup reads
the value back from the runtime's environment. See
[Secrets](/environments/secrets).

Every other Effect in the constructor also runs during `alchemy deploy`,
`alchemy plan`, and `alchemy dev`. One-shot I/O there, such as fetching
a value to cache for every request, must succeed in the deploy process
too. If it can't, move it into the handler.

## Instance scope vs request scope

The constructor runs once per instance, such as a Worker isolate, a
Lambda sandbox, or a server process. Each event runs the handler in a
fresh `Scope`. Build things at instance scope, and use things at
request scope:

```typescript
Effect.gen(function* () {
  // instance scope: runs once, reused by every event
  const secret = yield* fetchSecret;
  // ✓ one-shot I/O producing a plain value

  const conn = yield* acquireConnection;
  // ✗ disposable. The instance scope may never close, so the
  //   connection may never be released

  return {
    fetch: Effect.gen(function* () {
      // request scope: runs per event, closed when the event settles
      const conn = yield* acquireConnection;
      // ✓ acquired per event, released when the event settles
    }),
  };
});
```

For the inline and class
[forms of a runtime](/infrastructure-as-effects/runtime#three-ways-to-declare-a-runtime),
the types enforce this.
Their constructor has no `Scope` in its services, so
`Effect.acquireRelease` or `Effect.addFinalizer` there is a type error,
while the same code type-checks inside `fetch`. The `.make` of a Tag
declared with an explicit shape, such as
`Cloudflare.Worker<Api, {}>()("Api")`, skips this check, so follow the
rule yourself there.

Anything shared across calls within one event is memoized on the
request scope. For example, `Drizzle.Postgres` opens one pool per
event and closes it when the event settles, as the
[SQL connection lifecycle](/sql/effect-sql/lifecycle) describes.

### Finalizers

A finalizer added inside a handler runs when the event settles:

```typescript
fetch: Effect.gen(function* () {
  // workerd: runs after the response, through ctx.waitUntil
  // Lambda: runs before the response leaves, so keep it cheap
  yield* Effect.addFinalizer(() => flushMetrics.pipe(Effect.ignore));
  return HttpServerResponse.text("ok");
}),
```

Instance finalizers are best effort, so design your code to need no
instance-level cleanup:

- **workerd**: they never run, because isolates are frozen or evicted
  without a teardown hook.
- **Lambda**: they get a 500 ms `SIGTERM` window at spin-down, skipped
  on hard failures.
- **Servers**: they run on graceful process exit.

## `ALCHEMY_PHASE`

Alchemy exposes the current phase as the `ALCHEMY_PHASE` environment
variable or config key:

- `plan`: the default. Set during `alchemy deploy`, `alchemy plan`, and
  `alchemy dev`.
- `runtime`: set by runtime providers in the deployed environment of a
  Worker, Lambda Function, or Container.

Alchemy reads it to decide whether a `Config` lookup in the constructor
is captured as a binding (`plan`) or read back from the environment
(`runtime`). Bindings use the build-time
[`__ALCHEMY_RUNTIME__` guard](#the-__alchemy_runtime__-guard) instead.

## `ALCHEMY_DEV`

`alchemy dev` runs at deploy time, so `ALCHEMY_PHASE` is `plan` there
too. To check for `alchemy dev` specifically, read the `ALCHEMY_DEV`
config key:

```typescript
import { ALCHEMY_DEV } from "alchemy";

Effect.gen(function* () {
  // `alchemy dev` sets ALCHEMY_DEV=true. Every other entrypoint
  // leaves it unset, so it defaults to false.
  if (yield* ALCHEMY_DEV) {
    // local-dev-only behavior
  }
});
```

## The `__ALCHEMY_RUNTIME__` guard

A binding's implementation layer does two things in the Construction
phase. It registers deploy-time wiring on the host, and it returns a
typed client. The wiring sits behind a guard:

```typescript
if (!globalThis.__ALCHEMY_RUNTIME__) {
  // deploy time only: register IAM, native bindings, or env on the host
  yield* host.bind`${resource}`(/* … */);
}
// both phases: return the typed runtime client
```

When Alchemy bundles a runtime, it defines the global as `true`, so
the bundler removes the whole branch as dead code:

```typescript
// Bundle/Bundle.ts, folded into every bundle as a rolldown define
"globalThis.__ALCHEMY_RUNTIME__": "true"
```

At deploy time the global is unset, so `bind()` records what the
runtime needs. In the bundle only the client ships. This is how you
call `bucket.get(...)` in a Worker without bundling AWS or Cloudflare
provisioning code.

Plan-time lookups need no guard. Constructing an
[`Output.fromEffect`](/infrastructure-as-code/outputs#fromeffect) Output
is inert, so helpers built on it, such as `AWS.EC2.amazonLinux2023()`,
are safe in composition code that re-runs inside a deployed Function,
Worker, or Instance bundle. See
[Bindings › Plan-time invokes](/infrastructure-as-effects/binding#plan-time-invokes).
