Every alchemy program runs in two phases. Plantime builds the plan,
and runtime serves requests. [Runtime](/infrastructure-as-effects/runtime)
resources such as Workers, Lambdas, and Containers express both in a
single program by returning an Effect from inside an Effect. Earlier
pages named the two halves the Construction phase and the Runtime
phase. This page defines when each one runs.

## Construction vs Runtime

```typescript
Cloudflare.Worker(
  "Worker",
  { main: import.meta.url },
  Effect.gen(function* () {
    // ─── Construction phase ───
    const bucket = yield* Cloudflare.R2.ReadWriteBucket(Bucket);

    return {
      // ─── Runtime phase ───
      fetch: Effect.gen(function* () {
        const obj = yield* bucket.get("key");
        return HttpServerResponse.text(yield* obj.text());
      }),
    };
  }).pipe(Effect.provide(Cloudflare.R2.ReadWriteBucketBinding)),
);
```

| Phase        | Code   | When it runs                          |
| ------------ | ------ | ------------------------------------- |
| Construction | outer  | At plantime and at cold start         |
| Runtime | inner  | Only inside a deployed handler        |

Construction sets up the `bucket` value once, and the runtime closure
captures it. The constructor runs at most once per cold start. The
runtime body runs per request with everything already wired up.
Each phase has its own `Scope`, and the two lifetimes differ.
[Instance scope vs request scope](/infrastructure-as-effects/runtime#instance-scope-vs-request-scope)
covers where cleanup can and cannot happen.

`Alchemy.RuntimeContext` is available only in the Runtime phase.
Any Effect whose requirements include `RuntimeContext` can only
execute inside the runtime closure. The type system rejects it
everywhere else.
[Layers](/infrastructure-as-effects/layers#the-types-hold-the-boundary)
builds on this split to keep whole services honest about where they
can run.

- At **plantime**, the constructor runs to discover bindings. Alchemy needs
  to know which resources the handler will use so it can wire
  permissions, env vars, and references.
- At **runtime cold start**, the constructor runs again inside the
  deployed Worker. There, the same `bind()` calls return live SDK
  clients backed by the deployed resource.
- The **runtime body** only runs in the deployed handler. It never
  executes at plantime, so you can put real per-request work there
  without affecting deploy speed.

### What this means for constructor code

A `Config` lookup in the constructor is captured at plantime and bound
onto the Runtime as a secret. At runtime the same lookup reads the
value back from the Runtime's environment. See
[Secrets](/environments/secrets).

Any other Effect in the constructor also runs during `alchemy deploy`,
`alchemy plan`, and `alchemy dev`. One-shot I/O there, such as fetching
a value to cache for every request, must succeed in the deploy process
too. If it can't, move it into the handler.

## `ALCHEMY_PHASE`

Alchemy exposes the current phase as the `ALCHEMY_PHASE` environment
variable or config key:

| Value     | Context                                                              |
| --------- | ------------------------------------------------------------------- |
| `plan`    | Default. Running `alchemy deploy`, `alchemy plan`, or `alchemy dev`. |
| `runtime` | Running inside a deployed Worker or Lambda Function.                 |

Runtime providers set `ALCHEMY_PHASE=runtime` in the deployed
environment. Alchemy reads it to decide whether a `Config` lookup in
the constructor is captured as a binding (`plan`) or read back from the
environment (`runtime`). [Bindings](/infrastructure-as-effects/binding)
instead check `globalThis.__ALCHEMY_RUNTIME__`, which the bundler folds
to `true` at build time, so their deploy-only code is removed from the
bundle ([see below](#the-__alchemy_runtime__-guard)).

## `ALCHEMY_DEV`

`alchemy dev` is a plantime phase, so `ALCHEMY_PHASE` is `plan`
during local development, the same as a regular deploy. To check
whether you're running under `alchemy dev` specifically, read the
`ALCHEMY_DEV` config key. The CLI sets `ALCHEMY_DEV=true` on the dev
process. Every other entrypoint leaves it unset, so it defaults to
`false`.

```typescript
import { ALCHEMY_DEV } from "alchemy";

Effect.gen(function* () {
  if (yield* ALCHEMY_DEV) {
    // local-dev-only behavior
  }
});
```

## The `__ALCHEMY_RUNTIME__` guard

A binding's contract is a `Binding.Service`. The guarded setup
Effect lives in the implementation Layer you provide, not in the
contract. That setup Effect does two things, and the phase decides
how much of it runs:

| Work                    | Phase | Job                                                      |
| ----------------------- | ----- | -------------------------------------------------------- |
| typed client            | both  | The lightweight typed SDK that ships with the bundle.    |
| `host.bind(...)` wiring  | plan | Deploy-time registration of IAM / env / native bindings. |

The deploy-time wiring is fenced behind `if (!globalThis.__ALCHEMY_RUNTIME__)`.
At plantime the guard is open, so calling `bind()` records what the
function will need. At runtime the global flag is set, so the guard is
skipped and `bind()` returns only the typed client. The runtime bundle
stays small because the planning branch never executes.

The implementation Layer you provided decides which wiring the
guard protects
([Bindings](/infrastructure-as-effects/binding#a-contract-and-a-layer)).

The guard also lets you write `bucket.get(...)` inside a Worker
without bundling AWS or Cloudflare provisioning code. The
provisioning lives behind the guard and stays off the runtime path.

## Why this matters

The Construction/Runtime split lets you write code that:

1. **Resolves infrastructure references at deploy time.** Bindings
   know which bucket ARN, queue URL, etc. to inject.
2. **Initializes SDK clients once at cold start.** This does not
   happen on every request.
3. **Handles requests with a pre-configured context.** The `bucket`
   variable in the runtime body already knows which resource to
   talk to.
