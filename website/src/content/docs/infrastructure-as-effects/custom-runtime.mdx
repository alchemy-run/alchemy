title: Custom Runtime
description: Implement your own Runtime resource on the Platform type. A custom runtime is a Provider that provisions the compute and bundles the runtime Effect.
---

Worker, Lambda, and Container cover the common cases. This guide
shows how to bring the [Runtime](/infrastructure-as-effects/runtime)
model to a new compute target. A custom runtime is a
[Provider](/infrastructure-as-code/provider) with two jobs. It
provisions the compute infrastructure, and it bundles and uploads the
runtime Effect.

This guide uses `AWS.ECS.Task` as its example
([`AWS/ECS/Task.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/AWS/ECS/Task.ts)).
It bundles an inline Effect program, builds a Docker image, and
registers a Fargate task definition. Every built-in runtime follows
the same two-part shape, including `Cloudflare.Worker`,
`AWS.Lambda.Function`, and `AWS.EC2.Instance`.

## The two halves

A runtime resource splits into a **constructor** and a **provider**:

```typescript
// 1. The constructor — what users call. Built on `Platform`.
export const Task: Platform<Task, TaskServices, TaskShape, TaskRuntimeContext> =
  Platform("AWS.ECS.Task", {
    createRuntimeContext: createContainerRuntimeContext("AWS.ECS.Task"),
  });

// 2. The provider — the lifecycle Layer. Ordinary `Provider.effect`.
export const TaskProvider = () =>
  Provider.effect(Task, Effect.gen(function* () { /* ... */ }));
```

`Platform` handles the Effect plumbing. It runs the user's constructor
Effect, collects handlers, and wires [Bindings](/infrastructure-as-effects/binding).
The provider only has to do what every provider does, which is
reconcile cloud state.

## Declare the Resource

The Resource contract is a plain `Resource` declaration. The fourth
type parameter is the **Binding Contract**. It is the data shape that
upstream capabilities attach to this host:

```typescript
export interface TaskBindingContract {
  env?: Record<string, any>;
  policyStatements?: PolicyStatement[];
  volumes?: ecs.Volume[];
  mountPoints?: ecs.MountPoint[];
}

export interface Task extends Resource<
  "AWS.ECS.Task",
  TaskProps, // main | context | image, cpu, memory, port, env, ...
  {
    taskDefinitionArn: string;
    imageUri: string;
    taskRoleArn: string;
    // ...
    code: { hash: string };
  },
  TaskBindingContract,
  Providers
> {}
```

For the Task, the contract is env vars and IAM statements, plus the
volumes and mount points a binding such as `AWS.EFS.Mount` requests.
The fifth type parameter, `Providers`, is the provider set a Stack
must supply to deploy the resource. A Cloudflare
Worker accepts `{ bindings: Worker.Binding[] }`. Your contract is
whatever your platform needs from a binding.

## The `Platform` type

`Platform` takes four main type parameters. Two more, `BaseShape` and
`InlineProps`, have defaults:

```typescript
export interface Platform<
  Resource extends ResourceLike<string, PlatformProps>,
  Services,
  MainShape,
  RuntimeContext extends BaseRuntimeContext,
  BaseShape = {},
  InlineProps extends Resource["Props"] = Resource["Props"],
> extends Effect.Effect<Resource & RuntimeContext, never, Resource> { /* ... */ }
```

| Parameter        | ECS Task instantiation                                  | Meaning                                                        |
| ---------------- | ------------------------------------------------------- | -------------------------------------------------------------- |
| `Resource`       | `Task`                                                  | The Resource contract above                                     |
| `Services`       | `Credentials \| Region \| ServerHost \| AWSEnvironment` | Services the runtime provides to the user's constructor Effect        |
| `MainShape`      | `TaskShape`                                             | What the constructor Effect may return: `{ fetch?, run? }`     |
| `RuntimeContext` | `TaskRuntimeContext extends HostRuntimeContext`         | The mutable context that collects handlers, env, and exports   |

The value-level factory takes the type string and a
`createRuntimeContext` hook. It also takes an optional `onCreate`
hook. `Cloudflare.Worker` uses it to register child resources for
async bindings:

```typescript
import { Platform, type Main } from "alchemy";

export type TaskShape =
  | void
  | (Exclude<Main<TaskServices>, void> & {
      // runs to completion when the container starts, then the container exits
      run?: Effect.Effect<
        void,
        never,
        TaskServices | PlatformServices | RuntimeContext | Scope
      >;
    });

export const Task: Platform<Task, TaskServices, TaskShape, TaskRuntimeContext> =
  Platform("AWS.ECS.Task", {
    createRuntimeContext: createContainerRuntimeContext("AWS.ECS.Task") as (
      id: string,
    ) => TaskRuntimeContext,
  });
```

`Main<TaskServices>` allows a `fetch` handler. The Task adds a one-shot
`run` entry for tasks that do a job and exit.

## The RuntimeContext

`createRuntimeContext(id)` returns the object that accumulates
everything the constructor Effect registers. Its contract is
`BaseRuntimeContext` from `alchemy/RuntimeContext`:

```typescript
export interface BaseRuntimeContext {
  Type: string;
  id: string;
  env: Record<string, any>;
  get<T>(key: string): Effect.Effect<T | undefined>;
  set(id: string, output: Output): Effect.Effect<string>;
  exports?: Effect.Effect<Record<string, any>>;
  serve?<Req = never>(
    handler: HttpEffect<Req>,
    options?: { shape?: Record<string, unknown> },
  ): Effect.Effect<void, never, Req>;
}
```

- **`set`** is called during plan when a binding or config lookup
  captures an `Output`. Store the value under an env key.
- **`get`** is called at runtime inside the deployed artifact. Read
  the same key back from the environment.
- **`serve`** receives the user's `fetch` handler and RPC shape.
  Register it however your platform serves HTTP.
- **`exports`** resolves to whatever the bundled entrypoint needs
  to run. For hosts, that is a single `program` Effect.

Server-style platforms can reuse `createHostRuntimeContext` in
[`Server/Process.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Server/Process.ts).
`AWS.EC2.Instance` uses it directly, through the alias
`createEc2HostRuntimeContext`. It folds `run` (background loops) and
`serve` (HTTP handlers) into one list of runners:

```typescript
run: (effect) => Effect.sync(() => {
  runners.push(effect);
}),
serve: (handler) => Effect.sync(() => {
  runners.push(Http.serve(handler));
}),
exports: Effect.sync(() => ({
  program: Effect.all(runners, { concurrency: "unbounded" }),
})),
```

This is a simplified view. The real `program` also coordinates
graceful HTTP shutdown on hosts that manage it.

Container platforms such as `AWS.ECS.Task` use
`createContainerRuntimeContext`, which wraps `createHostRuntimeContext`.
It registers a returned `run` as a one-shot runner, so the container
exits when `run` completes. It boots the HTTP server only when the
constructor returns a `fetch` handler.

After it runs the constructor Effect, `Platform` hands any returned `fetch`
handler to `serve`, along with the whole returned shape. It then folds the context back onto the resource's
Props, so everything the constructor recorded reaches your provider:

```typescript
// inside Platform (Platform.ts) — what your provider receives as `news`
instance.Props = {
  ...props,
  env: { ...props?.env, ...runtimeContext.env },
  exports: runtimeContext.exports ? yield* runtimeContext.exports : undefined,
};
```

## Implement the Provider

The provider is a standard lifecycle Layer with `reconcile` and `delete`,
plus optional `diff`/`read`/`list`. The
[Custom Provider](/infrastructure-as-code/custom-provider) guide covers the
contract in depth. The runtime-specific part is that `reconcile`
also bundles and ships the handler:

```typescript
reconcile: Effect.fn(function* ({ id, news, bindings, output, session }) {
  // 1. Observe/ensure the supporting infrastructure (idempotent helpers).
  const taskRoleArn = output?.taskRoleArn
    ?? (yield* createTaskRoleIfNotExists({ id, roleName: taskRoleName }));

  // 2. Apply the Binding Contract data (IAM policy, env, volumes).
  const { env: bindingEnv, volumes: bindingVolumes, mountPoints: bindingMountPoints } =
    yield* attachTaskBindings({
      roleName: taskRoleName,
      policyName: taskPolicyName,
      bindings,
    });

  // 3. Bundle the runtime Effect into an image and push it.
  const resolved = yield* imageSource.resolve({
    id,
    source: news,
    repositoryName,
    tags,
    bootstrap: makeBunBootstrap(news.handler ?? "default"),
    session,
    // ...
  });

  // 4. Register a task definition revision that runs the image.
  const taskDefinition = yield* registerTaskDefinitionRevision({
    props: { ...news, env: { ...bindingEnv, ...alchemyEnv, ...news.env } },
    imageUri: resolved.imageUri,
    taskRoleArn,
    bindingVolumes,
    bindingMountPoints,
    // ...
  });

  return { taskDefinitionArn: taskDefinition.taskDefinitionArn!, /* ... */ };
}),
```

`imageSource.resolve` builds the image from whichever source the props
declare (`main`, `context`, or `image`). For `main`, it bundles the
program with the generated entrypoint that `bootstrap` returns (see
[Bundle the handler](#bundle-the-handler)).

Each step is independently idempotent. The same observe → ensure →
sync flow works for greenfield creates, updates, and adoption. Don't
branch on `output === undefined`. See
[Providers › reconcile](/infrastructure-as-code/provider#reconcile).

`delete` tears down everything reconcile created: the task
definition, ECR repository, log group, and IAM roles. It treats
"already gone" as success.

## Bundle the handler

`alchemy/Bundle` wraps rolldown. `Bundle.build` takes input/output
options and returns every emitted file plus a content hash:

```typescript
import * as Bundle from "alchemy/Bundle";

const bundleOutput = yield* Bundle.build(
  { input: entry, cwd, platform: "node", external: ["bun", "bun:*"] },
  { format: "esm", entryFileNames: "index.mjs" },
);
// bundleOutput.files — entry + chunks; bundleOutput.hash — sha256
```

Ship every file in `files`, including the chunks. Dynamic imports split
into chunks, and a missing chunk crashes the artifact at boot. Use
`hash` as the immutable artifact version. The Task hashes the bundle
together with its generated Dockerfile and target platform, and tags
the image `${repositoryUri}:${codeHash}`.

The user's `main` module exports the platform class. It does not export
a runnable program, so the bundle needs a generated entrypoint.
`Bundle.virtualEntryPlugin` wraps `main` in one. Keep that generated
entry to a three-line shim that imports only your bootstrap module and
the user's `main`:

```typescript
const virtualEntryPlugin = yield* Bundle.virtualEntryPlugin;

yield* Bundle.build({
  input: realMain,
  plugins: [virtualEntryPlugin((importPath) => `
import { bootstrap } from "alchemy/Runtime/Bootstrap/Ecs";
import { ${handler} as entrypoint } from ${JSON.stringify(importPath)};

await bootstrap(entrypoint);
`)],
}, { format: "esm", entryFileNames: "index.mjs" });
```

This is the Task's `makeBunBootstrap(handler)` from
[`AWS/ECR/ImageSource.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/AWS/ECR/ImageSource.ts).
The generated entry is a virtual module with no location on disk. Under
an isolated install (pnpm, or bun with `--linker=isolated`), no
directory can resolve both alchemy's own dependencies and the user's,
so a bootstrap written inline in the template dies at boot with
`Cannot find module`. `Bundle.build` turns an unresolved bare import
from a generated entry into a build error for this reason. The shim
avoids the problem. `alchemy` is a direct dependency of the user's
project, so `alchemy/Runtime/Bootstrap/Ecs` resolves, and the bootstrap
module is a real file whose own imports resolve normally.

The bootstrap module is the one place the Effect world meets the
process entrypoint. It composes helpers from
`alchemy/Runtime/Bootstrap/Process` with your platform's Layers.
[`Runtime/Bootstrap/Ecs.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Runtime/Bootstrap/Ecs.ts)
is the reference:

```typescript
import {
  entrypointLayer,
  resolveProgram,
  runProcess,
  stackFromEnv,
} from "alchemy/Runtime/Bootstrap/Process";

export const bootstrap = (entrypoint: unknown): Promise<void> => {
  const program = resolveProgram("program", { telemetry: true }).pipe(
    Effect.provide(
      entrypointLayer(entrypoint).pipe(
        Layer.provideMerge(stackFromEnv),
        Layer.provideMerge(Credentials.fromChain()),
        Layer.provideMerge(Region.fromEnv()),
        Layer.provideMerge(Endpoint.fromEnv()), // AWS_ENDPOINT_URL override, if set
        Layer.provideMerge(BunHttpServer()),
        Layer.provideMerge(platform), // Bun services, HTTP client, logger
        // ...plus a ConfigProvider over process.env
      ),
    ),
    Effect.scoped,
  );

  return runProcess("Task", program);
};
```

- **`entrypointLayer`** turns the user's default export into a Layer
  that provides the platform instance.
- **`resolveProgram("program")`** reads `RuntimeContext.exports` from
  that instance and returns an Effect that runs its `program`.
- **`stackFromEnv`** provides the `Stack` from the
  `ALCHEMY_STACK_NAME` and `ALCHEMY_STAGE` your provider ships.
- **`runProcess`** runs the program as the process entry. It exits
  with code 1 on failure.

For the Task, the platform Layers include a Bun HTTP server bound to
`PORT`. That server serves the `{ fetch }` handler and keeps `host.run`
loops alive. Your platform provides whatever its host needs.

Long-lived hosts build telemetry exporters once per process.
`resolveProgram("program", { telemetry: true })` wraps the program in
`provideProcessTelemetry(self.RuntimeContext)`, so exporters batch on
their intervals and flush when the root scope closes on graceful
shutdown. See [Telemetry](/infrastructure-as-effects/telemetry) for
how exporters are configured.

A runtime published outside alchemy can't add files under
`alchemy/Runtime/Bootstrap`. Ship your own bootstrap module in your
package, resolvable from the user's project, that composes the same
helpers. Point the shim at it.

## Honor the phase split

The same constructor Effect runs twice. It runs at plantime to record
bindings, and at cold start inside the artifact to build live clients.
See [Phases](/infrastructure-as-effects/phases). Two mechanisms keep
the two runs separate. `Bundle.build` wires the first one automatically:

```typescript
// Bundle.ts — folded into every bundle via rolldown transform.define
const ALCHEMY_DEFINE = {
  "globalThis.__ALCHEMY_RUNTIME__": "true",
};
```

Every `if (!globalThis.__ALCHEMY_RUNTIME__)` guard in a
`Binding.Service` becomes `if (!true)` in the bundle. The bundler
removes it as dead code, so provisioning code never ships.

The second mechanism is the `ALCHEMY_PHASE` config key. Your provider
must set it to `"runtime"` in the shipped environment:

```typescript
const alchemyEnv = {
  ALCHEMY_STACK_NAME: stack.name,
  ALCHEMY_STAGE: stack.stage,
  ALCHEMY_PHASE: "runtime",
};
```

`Platform` installs a `ConfigProvider` interceptor keyed on this
phase. At `plan` it captures every config lookup into the
RuntimeContext via `ctx.set`. At `runtime` the same lookup resolves
through `ctx.get`, which reads back the env var your provider shipped.
Because of this round-trip, `set`/`get` must agree on how values are
encoded. The host context packs values with `packEnvValue` on `set`
and unpacks them with `unpackEnvValue` on `get`. A string stays as-is
unless it would parse as JSON (such as `"123"` or `"null"`). Other
values become JSON, and `Redacted` values get a marker.
Both come from `alchemy/RuntimeContext`.

## Bindings flow through the host

When the user writes `yield* AWS.S3.GetObject(bucket)` in the constructor
Effect, the capability calls ``host.bind`${bucket}`(data)`` with
data matching your Binding Contract. The engine collects those and
hands them to `reconcile` as the `bindings` argument:

```typescript
const attachTaskBindings = Effect.fn(function* ({ roleName, policyName, bindings }) {
  const activeBindings = bindings.filter((binding) => binding.action !== "delete");

  const env = activeBindings
    .map((binding) => binding?.data?.env)
    .reduce((acc, value) => ({ ...acc, ...value }), {});

  const policyStatements = activeBindings.flatMap(
    (binding) => binding?.data?.policyStatements ?? [],
  );

  // volumes and mountPoints are collected the same way (deduplicated)

  if (policyStatements.length > 0) {
    yield* iam.putRolePolicy({
      RoleName: roleName,
      PolicyName: policyName,
      PolicyDocument: JSON.stringify({
        Version: "2012-10-17",
        Statement: policyStatements,
      }),
    });
  } else {
    yield* iam
      .deleteRolePolicy({ RoleName: roleName, PolicyName: policyName })
      .pipe(Effect.catchTag("NoSuchEntityException", () => Effect.void));
  }

  return { env, volumes, mountPoints }; // merged into the task definition
});
```

Your provider decides what the contract data means. Here IAM
policies attach to the task role, env vars land in the container
definition, and volumes and mount points are added to the task
definition. A binding removed from code arrives with
`action: "delete"`. `attachTaskBindings` skips those and rewrites the
whole policy from the rest, deleting it when no statements remain, so
removed permissions go away.

## What users get

The finished runtime reads like any other Function. It has
infrastructure props, a constructor Effect, and a `{ fetch }` handler:

```typescript
import * as AWS from "alchemy/AWS";
import { ServerHost } from "alchemy/Server";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export default class ApiTask extends AWS.ECS.Task<ApiTask>()(
  "ApiTask",
  { main: import.meta.filename, cpu: 256, memory: 512, port: 3000 },
  Effect.gen(function* () {
    const host = yield* ServerHost;
    yield* host.run(pollLoop); // long-running background work

    return {
      fetch: Effect.gen(function* () {
        return HttpServerResponse.text("hello from ecs task");
      }),
    };
  }),
) {}
```

Everything on this page sits behind that surface. `Platform` runs
the constructor Effect and collects `host.run` and `fetch` into
`exports.program`. The provider bundles that program into an image
and reconciles the task definition around it.
