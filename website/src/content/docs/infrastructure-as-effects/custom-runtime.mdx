This guide brings the [runtime](/infrastructure-as-effects/runtime)
model to a new compute target. A custom runtime is a
[provider](/infrastructure-as-code/provider) with two jobs. It
provisions the compute, and it bundles and uploads the runtime Effect.

The example is `AWS.ECS.Task`
([`AWS/ECS/Task.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/AWS/ECS/Task.ts)).
It bundles an inline Effect program, builds a Docker image, and
registers a Fargate task definition. `Cloudflare.Worker`,
`AWS.Lambda.Function`, and `AWS.EC2.Instance` follow the same shape.

## What users get

The finished runtime reads like any other Function. It has
infrastructure props, a constructor Effect, and a `{ fetch }` handler:

```typescript
import * as AWS from "alchemy/AWS";
import { ServerHost } from "alchemy/Server";
import * as Effect from "effect/Effect";
import * as HttpServerResponse from "effect/unstable/http/HttpServerResponse";

export default class ApiTask extends AWS.ECS.Task<ApiTask>()(
  "ApiTask",
  { main: import.meta.filename, cpu: 256, memory: 512, port: 3000 },
  Effect.gen(function* () {
    const host = yield* ServerHost;
    yield* host.run(pollLoop); // long-running background work

    return {
      fetch: Effect.gen(function* () {
        return HttpServerResponse.text("hello from ecs task");
      }),
    };
  }),
) {}
```

`Platform` runs the constructor Effect and collects `host.run` and
`fetch` into `exports.program`. The provider bundles that program into
an image and reconciles the task definition around it. The rest of this
guide builds both halves.

## The two halves

A runtime resource splits into a constructor and a provider:

```typescript
// 1. The constructor, which users call. Built on `Platform`.
export const Task: Platform<Task, TaskServices, TaskShape, TaskRuntimeContext> =
  Platform("AWS.ECS.Task", {
    createRuntimeContext: createContainerRuntimeContext("AWS.ECS.Task"),
  });

// 2. The provider, an ordinary `Provider.effect` lifecycle layer.
export const TaskProvider = () =>
  Provider.effect(Task, Effect.gen(function* () { /* ... */ }));
```

`Platform` runs the user's constructor Effect, collects handlers, and
wires [bindings](/infrastructure-as-effects/binding). The provider only
reconciles cloud state, like every provider.

## Declare the resource

The resource contract is a plain `Resource` declaration. The fourth
type parameter is the **binding contract**, the data shape that
bindings attach to this host:

```typescript
export interface TaskBindingContract {
  env?: Record<string, any>;
  policyStatements?: PolicyStatement[];
  // requested by bindings such as AWS.EFS.Mount
  volumes?: ecs.Volume[];
  mountPoints?: ecs.MountPoint[];
}

export interface Task extends Resource<
  "AWS.ECS.Task",
  TaskProps, // main | context | image, cpu, memory, port, env, ...
  {
    taskDefinitionArn: string;
    imageUri: string;
    taskRoleArn: string;
    // ...
    code: { hash: string };
  },
  TaskBindingContract,
  Providers // the provider set a stack must supply to deploy it
> {}
```

Your contract is whatever your platform needs from a binding. A
Cloudflare Worker accepts `{ bindings: Worker.Binding[] }`.

## Declare the Platform

`Platform` takes the resource type string and a `createRuntimeContext`
hook. An optional `onCreate` hook registers child resources, as
`Cloudflare.Worker` does for async bindings. The type parameters are
documented on `Platform` in
[`Platform.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Platform.ts):

```typescript
import { Platform, type Main } from "alchemy";

// what the constructor Effect may return
export type TaskShape =
  | void
  | (Exclude<Main<TaskServices>, void> & { // Main allows a fetch handler
      // runs to completion when the container starts, then the container exits
      run?: Effect.Effect<
        void,
        never,
        TaskServices | PlatformServices | RuntimeContext | Scope
      >;
    });

export const Task: Platform<Task, TaskServices, TaskShape, TaskRuntimeContext> =
  Platform("AWS.ECS.Task", {
    createRuntimeContext: createContainerRuntimeContext("AWS.ECS.Task") as (
      id: string,
    ) => TaskRuntimeContext,
  });
```

## The RuntimeContext

`createRuntimeContext(id)` returns the object that collects everything
the constructor Effect registers. It implements `BaseRuntimeContext`
from
[`alchemy/RuntimeContext`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/RuntimeContext.ts),
which stores captured values with `set` at deploy time, reads them back
with `get` at runtime, takes the `fetch` handler through `serve`, and
resolves `exports` to what the bundled entrypoint runs.

Server-style platforms can reuse `createHostRuntimeContext` from
[`Server/Process.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Server/Process.ts).
`AWS.EC2.Instance` uses it directly, through the alias
`createEc2HostRuntimeContext`. It folds background loops and HTTP
handlers into one list of runners:

```typescript
// simplified: the real program also coordinates graceful HTTP shutdown
run: (effect) => Effect.sync(() => {
  runners.push(effect);
}),
serve: (handler) => Effect.sync(() => {
  runners.push(Http.serve(handler));
}),
exports: Effect.sync(() => ({
  program: Effect.all(runners, { concurrency: "unbounded" }),
})),
```

Container platforms such as `AWS.ECS.Task` use
`createContainerRuntimeContext`, which wraps `createHostRuntimeContext`.
It registers a returned `run` as a one-shot runner, so the container
exits when `run` completes. It boots the HTTP server only when the
constructor returns a `fetch` handler.

After the constructor Effect runs, `Platform` hands any `fetch` handler
and the returned shape to `serve`. It then folds the context back onto
the resource's props, which your provider receives as `news`:

```typescript
// inside Platform (Platform.ts)
instance.Props = {
  ...props,
  env: { ...props?.env, ...runtimeContext.env },
  exports: runtimeContext.exports ? yield* runtimeContext.exports : undefined,
};
```

## Implement the provider

The provider is a standard lifecycle layer with `reconcile` and
`delete`, plus optional `diff`, `read`, and `list`. See
[Custom Provider](/infrastructure-as-code/custom-provider) for the
contract. The runtime-specific part is that `reconcile` also bundles
and ships the handler:

```typescript
reconcile: Effect.fn(function* ({ id, news, bindings, output, session }) {
  // 1. Observe/ensure the supporting infrastructure (idempotent helpers).
  const taskRoleArn = output?.taskRoleArn
    ?? (yield* createTaskRoleIfNotExists({ id, roleName: taskRoleName }));

  // 2. Apply the binding contract data (IAM policy, env, volumes).
  const { env: bindingEnv, volumes: bindingVolumes, mountPoints: bindingMountPoints } =
    yield* attachTaskBindings({
      roleName: taskRoleName,
      policyName: taskPolicyName,
      bindings,
    });

  // 3. Bundle the runtime Effect into an image and push it.
  //    Builds from whichever source the props declare: main, context, or image.
  const resolved = yield* imageSource.resolve({
    id,
    source: news,
    repositoryName,
    tags,
    bootstrap: makeBunBootstrap(news.handler ?? "default"),
    session,
    // ...
  });

  // 4. Register a task definition revision that runs the image.
  const taskDefinition = yield* registerTaskDefinitionRevision({
    props: { ...news, env: { ...bindingEnv, ...alchemyEnv, ...news.env } },
    imageUri: resolved.imageUri,
    taskRoleArn,
    bindingVolumes,
    bindingMountPoints,
    // ...
  });

  return { taskDefinitionArn: taskDefinition.taskDefinitionArn!, /* ... */ };
}),
```

Each step is independently idempotent, so the same flow handles
greenfield creates, updates, and adoption. Don't branch on
`output === undefined`. See
[Provider contract › reconcile](/infrastructure-as-code/provider#reconcile).

### Apply bindings

When a user writes `yield* AWS.S3.GetObject(bucket)` in the
constructor, the capability calls ``host.bind`${bucket}`(data)`` with
data matching your binding contract. The engine collects those calls
and passes them to `reconcile` as `bindings`:

```typescript
const attachTaskBindings = Effect.fn(function* ({ roleName, policyName, bindings }) {
  // a binding removed from code arrives with action: "delete"
  const activeBindings = bindings.filter((binding) => binding.action !== "delete");

  const env = activeBindings
    .map((binding) => binding?.data?.env)
    .reduce((acc, value) => ({ ...acc, ...value }), {});

  const policyStatements = activeBindings.flatMap(
    (binding) => binding?.data?.policyStatements ?? [],
  );

  // volumes and mountPoints are collected the same way (deduplicated)

  if (policyStatements.length > 0) {
    // rewrite the whole policy from the active bindings
    yield* iam.putRolePolicy({
      RoleName: roleName,
      PolicyName: policyName,
      PolicyDocument: JSON.stringify({
        Version: "2012-10-17",
        Statement: policyStatements,
      }),
    });
  } else {
    // no statements left, so removed permissions go away
    yield* iam
      .deleteRolePolicy({ RoleName: roleName, PolicyName: policyName })
      .pipe(Effect.catchTag("NoSuchEntityException", () => Effect.void));
  }

  return { env, volumes, mountPoints }; // merged into the task definition
});
```

Your provider decides what the contract data means. Here IAM
statements attach to the task role, env vars land in the container
definition, and volumes and mount points join the task definition.

### Implement delete

`delete` tears down everything `reconcile` created, including the task
definition, ECR repository, log group, and IAM roles. It treats
"already gone" as success.

## Bundle the handler

`alchemy/Bundle` wraps rolldown. `Bundle.build` takes input and output
options and returns every emitted file plus a content hash:

```typescript
import * as Bundle from "alchemy/Bundle";

const bundleOutput = yield* Bundle.build(
  { input: entry, cwd, platform: "node", external: ["bun", "bun:*"] },
  { format: "esm", entryFileNames: "index.mjs" },
);
// bundleOutput.files: entry + chunks. bundleOutput.hash: sha256
```

Ship every file in `files`, because a missing dynamic-import chunk
crashes the artifact at boot. Use `hash` as the immutable artifact
version. The Task hashes the bundle with its generated Dockerfile and
target platform, and tags the image `${repositoryUri}:${codeHash}`.

The user's `main` module exports the platform class, not a runnable
program, so the bundle needs a generated entrypoint.
`Bundle.virtualEntryPlugin` wraps `main` in one. Keep it to a
three-line shim that imports only your bootstrap module and the user's
`main`:

```typescript
const virtualEntryPlugin = yield* Bundle.virtualEntryPlugin;

yield* Bundle.build({
  input: realMain,
  plugins: [virtualEntryPlugin((importPath) => `
import { bootstrap } from "alchemy/Runtime/Bootstrap/Ecs";
import { ${handler} as entrypoint } from ${JSON.stringify(importPath)};

await bootstrap(entrypoint);
`)],
}, { format: "esm", entryFileNames: "index.mjs" });
```

This is the Task's `makeBunBootstrap(handler)` from
[`AWS/ECR/ImageSource.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/AWS/ECR/ImageSource.ts).
The generated entry is a virtual module with no location on disk, so
under an isolated install (pnpm, or bun with `--linker=isolated`) an
inline bootstrap dies at boot with `Cannot find module`. `Bundle.build`
turns an unresolved bare import from a generated entry into a build
error for this reason.

The shim avoids the problem. `alchemy` is a direct dependency of the
user's project, so `alchemy/Runtime/Bootstrap/Ecs` resolves, and the
bootstrap module is a real file whose own imports resolve normally.

### Write the bootstrap module

The bootstrap module is where the Effect program meets the process
entrypoint. It composes the helpers in
[`Runtime/Bootstrap/Process.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Runtime/Bootstrap/Process.ts)
with your platform's layers.
[`Runtime/Bootstrap/Ecs.ts`](https://github.com/alchemy-run/alchemy/blob/main/packages/alchemy/src/Runtime/Bootstrap/Ecs.ts)
is the reference:

```typescript
import {
  entrypointLayer,
  resolveProgram,
  runProcess,
  stackFromEnv,
} from "alchemy/Runtime/Bootstrap/Process";

export const bootstrap = (entrypoint: unknown): Promise<void> => {
  // runs RuntimeContext.exports.program. With telemetry: true, exporters are
  // built once per process and flush when the root scope closes
  const program = resolveProgram("program", { telemetry: true }).pipe(
    Effect.provide(
      // the user's default export as a layer providing the platform instance
      entrypointLayer(entrypoint).pipe(
        Layer.provideMerge(stackFromEnv), // ALCHEMY_STACK_NAME + ALCHEMY_STAGE
        Layer.provideMerge(Credentials.fromChain()),
        Layer.provideMerge(Region.fromEnv()),
        Layer.provideMerge(Endpoint.fromEnv()), // AWS_ENDPOINT_URL override, if set
        Layer.provideMerge(BunHttpServer()), // serves fetch on PORT, keeps host.run alive
        Layer.provideMerge(platform), // Bun services, HTTP client, logger
        // ...plus a ConfigProvider over process.env
      ),
    ),
    Effect.scoped,
  );

  // exits with code 1 on failure
  return runProcess("Task", program);
};
```

Your platform provides whatever its host needs. See
[Telemetry](/infrastructure-as-effects/telemetry) for how exporters are
configured. A runtime published outside Alchemy can't add files under
`alchemy/Runtime/Bootstrap`, so ship your own bootstrap module in your
package and point the shim at it.

## Honor the phase split

The same constructor Effect runs at deploy time to record bindings and
at cold start to build live clients (see
[Phases](/infrastructure-as-effects/phases)). `Bundle.build` already
folds the
[`__ALCHEMY_RUNTIME__` guard](/infrastructure-as-effects/phases#the-__alchemy_runtime__-guard)
into every bundle, so provisioning code never ships.

Your provider must set `ALCHEMY_PHASE` to `"runtime"` in the shipped
environment:

```typescript
const alchemyEnv = {
  ALCHEMY_STACK_NAME: stack.name,
  ALCHEMY_STAGE: stack.stage,
  ALCHEMY_PHASE: "runtime",
};
```

`Platform` installs a `ConfigProvider` keyed on this phase. At `plan`
it captures every config lookup through `ctx.set`, and at `runtime` the
same lookup resolves through `ctx.get` from the env var you shipped. So
`set` and `get` must agree on encoding, which the host context does
with `packEnvValue` and `unpackEnvValue` from `alchemy/RuntimeContext`.
