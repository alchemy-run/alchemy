You have a host with the bundled tokens, and a rule the tokens cannot
express: anyone with a `write` token may push, but `main` should only
move for an admin. By the end of this part that rule is enforced, and
you have replaced your first block.

## What Auth decides

`Git.Auth` is two functions. `authenticate` turns request headers into
an actor: `admin`, `token`, `user`, or `anonymous`. `authorize` answers
yes or no for an actor, a repository, and an action. Actions are git's
own facts: `Fetch`, `Push` with the refs it wants to move, `ReadRepo`,
`CreateRepo`, `MergePull`, and so on.

`Git.AuthTokens` is one implementation of that. Yours can wrap it.

## Wrap the bundled tokens

Keep the token model and add one rule on top:

```typescript
// src/auth.ts
import * as Git from "alchemy/Git";
import * as Effect from "effect/Effect";
import * as Layer from "effect/Layer";

export const ProtectedMain: Layer.Layer<Git.Auth> = Layer.effect(
  Git.Auth,
  Effect.gen(function* () {
    const base = yield* Git.Auth;
    return {
      authenticate: base.authenticate,
      authorize: (input) =>
        input.action._tag === "Push" &&
        input.action.updates.some((u) => u.ref === "refs/heads/main") &&
        input.actor.kind !== "admin"
          ? Effect.succeed(false)
          : base.authorize(input),
    };
  }),
).pipe(Layer.provide(Git.AuthTokens));
```

`yield* Git.Auth` inside the Layer is the bundled implementation,
provided by the last line. Everything that isn't a push to `main`
defers to it.

## Provide it

```diff lang="typescript"
// src/git.ts
+import { ProtectedMain } from "./auth.ts";

const GitLive = Git.ServerLive.pipe(
  Layer.provide(Git.ReposDurableObject),
  Layer.provide(Git.RegistryDurableObject),
  Layer.provide(Git.BlobStoreR2(GitObjects)),
  Layer.provide(Git.HasherInline),
-  Layer.provide(Git.AuthTokens),
+  Layer.provide(ProtectedMain),

```

```sh
bun alchemy deploy
```

## Try it

Push a branch with the `write` token from Part 2, then push `main`:

```sh
git push origin HEAD:feature
git push origin main
```

The branch lands. The push to `main` is refused in-band with the ref
named, the way git reports any rejected ref. Push `main` with the admin
secret in the password field and it moves.

`Push` carries its `updates` twice. At the ref advertisement the list
is empty and the question is whether this caller may push at all. At
commit it is exact, which is when the rule above sees `refs/heads/main`.

## Your users as actors

Tokens are for git clients. Your application has users, and they can
be the actors too. Resolve a session in `authenticate` and rule on it
in `authorize`. Anything you don't recognize falls through to the
tokens:

```typescript
export const AuthSessions: Layer.Layer<Git.Auth> = Layer.effect(
  Git.Auth,
  Effect.gen(function* () {
    const base = yield* Git.Auth;
    const sessions = yield* Sessions; // yours, e.g. Better Auth

    return {
      authenticate: (headers) =>
        Effect.gen(function* () {
          const session = yield* sessions.fromHeaders(headers);
          if (session) {
            return { kind: "user", id: session.userId, name: session.name };
          }
          return yield* base.authenticate(headers);
        }),
      authorize: ({ actor, repo, action }) =>
        actor.kind === "user"
          ? Effect.succeed(
              action._tag === "CreateRepo"
                ? action.owner === actor.id
                : repo !== null && isMember(actor.id, repo.owner),
            )
          : base.authorize({ actor, repo, action }),
    };
  }),
).pipe(Layer.provide(Git.AuthTokens));
```

`isMember` is your policy over your data. The host asks `MergePull`
and `Push` with the refs that move. It never asks what a team is.

A `git` client can only send HTTP Basic, so `git push` keeps using
tokens. Your `authorize` decides who may `ManageTokens`, so a
signed-in user mints their own over the REST plane and puts it in
their remote.
