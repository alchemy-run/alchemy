---
title: Auth
description: The engine holds no users and no credentials. Your HTTP layer says who is calling, through Caller and Authenticate, and Policy answers what they may do, inside the repository with git's own facts.
---

Authentication happens outside the engine, in the HTTP layer you own.
The engine asks one pure question per action. Three services carry
that split:

| Service | Answers | Runs |
| --- | --- | --- |
| `Git.Caller` | who is calling a REST endpoint | provided by your `HttpApi` middleware |
| `Git.Authenticate` | who is calling the wire, raw, and GitHub routes | at the Worker, per request |
| `Git.Policy` | may they do this | where the facts are, inside the repository's Durable Object |

Shipped: `PolicyOwners`, `AuthenticateSecret`, and `Authenticated`, the
default middleware that bridges `Authenticate` into `Caller` so one
implementation serves every plane.

## Principal

The identity your authentication resolved:

```typescript
interface Principal {
  readonly id: string;
  readonly name?: string;
}
```

Repositories are owned by a principal's id. Owner names are lowercased,
so `Git.owns(principal, repo)` compares `repo.owner` with
`principal.id.toLowerCase()`.

## Caller

What an `HttpApi` middleware provides to every REST handler: a principal,
or anonymous. No middleware at all is anonymous too, which the policy
confines to public reads.

```typescript
class Caller extends Context.Service<
  Caller,
  { readonly principal: Principal | undefined }
>()("alchemy/Git/Caller") {}
```

Your middleware declares it provides `Caller` and is applied to the API
that carries the git groups:

```typescript
export class Session extends HttpApiMiddleware.Service<
  Session,
  { provides: Git.Caller }
>()("app/Session", { error: Git.Unauthorized }) {}

export const AppApi = Git.Api.add(Me).middleware(Session);
```

A session cookie is the usual source. [Part 3](/git/tutorial/part-3)
implements it over Better Auth.

## Authenticate

A `git` client can only send HTTP Basic with the credential in the
password field, so the wire routes cannot sit behind an `HttpApi`
middleware. They, the raw blob and file reads, and the GitHub facade
resolve the caller through `Authenticate`:

```typescript
class Authenticate extends Context.Service<
  Authenticate,
  (headers: Headers) => Effect<Principal | undefined>
>()("alchemy/Git/Authenticate") {}
```

`undefined` is anonymous, never a failure. `Git.parseBasic`,
`Git.parseBearer`, and `Git.parseSecret` read the header for you. An
API key verified by Better Auth:

```typescript
const AuthenticateLive = Layer.succeed(
  Git.Authenticate,
  Effect.fn(function* (headers) {
    const key = Git.parseSecret(headers);
    if (key === undefined) return undefined;
    const verified = yield* auth.api.verifyApiKey({ body: { key } });
    return verified.valid && verified.key
      ? { id: verified.key.referenceId }
      : undefined;
  }),
);
```

`AuthenticateSecret` is the shipped starter: one secret from `Config`,
one principal.

```typescript
Layer.provide(Git.AuthenticateSecret({ principal: { id: "acme" } }))
```

When browsers and git clients should authenticate the same way,
`Git.Authenticated` is an `HttpApi` middleware over `Authenticate`, and
`ServerLive` applies it. Provide one `Authenticate` and every plane
agrees.

## Policy

```typescript
interface PolicyShape {
  authorize(input: {
    principal: Principal | undefined;
    repo: RepoContext | null;
    action: GitAction;
  }): Effect<boolean>;
}
```

`repo` is `null` for registry-level actions. `action` is one of git's
own facts, not a role: `Fetch`, `Push` with the parsed ref updates,
`ReadRepo`, `UpdateRepo`, `DeleteRepo`, `CreateRepo` with its owner,
`ListRepos`, `Maintain`, `CreatePull`, `UpdatePull`, `MergePull`.

A denial for anonymous is `401` with `WWW-Authenticate`, so git
prompts. A denial for a principal is `403` naming the action, except
on reads of a private repository, which answer `401` to anyone the
policy does not admit so the repository's existence is not confirmed.

`Push` carries its `updates` twice. At the ref advertisement the list
is empty and the question is whether this caller may push at all. At
commit it is exact, so a rule can look at which refs move and to what:

```typescript
export const ProtectedMain = Layer.succeed(Git.Policy, {
  authorize: ({ principal, repo, action }) =>
    Effect.succeed(
      principal === undefined
        ? repo !== null && repo.public && Git.isReadAction(action)
        : repo === null
          ? true
          : action._tag === "Push"
            ? action.updates.every((u) =>
                u.ref === "refs/heads/main" ? Git.owns(principal, repo) : true,
              )
            : Git.owns(principal, repo) ||
              (repo.public && Git.isReadAction(action)),
    ),
});
```

`Git.PolicyOwners` is the default: anonymous reads public, a principal
may create and list, and owns what it owns. A policy may be a
`Layer.effect` that reads your own data, as the team rule in
[Part 4](/git/tutorial/part-4) does.

## What the engine keeps

The Worker resolves the principal once, strips any inbound
`x-git-principal` header, and forwards the resolved one to the Durable
Object, which trusts it because only the Worker can reach it. The push
pipeline's internal hash route authenticates with a deploy-time random
secret no user holds. There is no tokens table and no admin key.
Credentials are your authentication's, and only your authentication
ever sees them.
