---
title: Auth
description: Apply your request middleware to Git route layers and use pre-receive hooks to control ref updates.
---

Authentication belongs to your application. Apply native `HttpRouter.middleware`
to the public route layers you want it to protect:

```typescript
const PublicRoutes = Layer.mergeAll(AppApiLive, Git.ApiLive).pipe(
  Layer.provide(Authentication.layer),
);
```

`Authentication` may provide your own `Session` service to handlers. It resolves
users from your identity system and authorizes the request before the Git handler
runs. [Part 4](/git/tutorial/part-4#authorize-the-identified-user) shows the complete Better
Auth implementation; [Getting Started](/git/getting-started) uses a shared secret.

| Component | Decides | Runs |
| --- | --- | --- |
| Application middleware | Who may call a route | Before its handler |
| `Git.Hooks` | Which refs may move | After parsing a push, before changing refs |

## Git credentials and public repositories

Git sends HTTP Basic with the credential in the password field.
`HttpApiBuilder.securityDecode(HttpApiSecurity.basic)` reads it. Return a 401
with `WWW-Authenticate: Basic realm="git"` when credentials are needed.

`Git.isRead(request)` recognizes REST reads, upload-pack, and fetch advertisements.
Receive-pack advertisements are writes. Resolve `owner` and `repo` from
`HttpRouter.params`, and consult `Git.RegistryStore` to allow anonymous access
only when your policy permits it, such as reads of a public repository.

## Application API schemas

Router middleware and API schemas are independent. If a typed client should decode
an application-specific authentication error, declare that error on its endpoint
or through a client API middleware schema. Applying router middleware does not
implicitly change `Git.Api`'s error contract.

## Hooks

```typescript
interface HooksShape {
  preReceive(input: {
    repo: RepoMetaData;
    updates: ReadonlyArray<{ ref: string; oldOid: string; newOid: string }>;
  }): Effect<ReadonlyArray<{ ref: string; reason: string }>>;
}
```

`preReceive` runs on `git push`, on the REST ref writes, and on a pull
request merge, with the parsed updates: `oldOid` is all zeros for a
create, `newOid` all zeros for a delete. It returns the refs to refuse
with a reason; an empty array accepts. A push with any refused ref is
rejected as a whole, and git reports the reason per ref. REST and a
merge answer a typed `403`, `HookRejected`. It runs in the Worker,
inside the request, so whatever your middleware provided is in
context:

```typescript
export const ProtectedMain = Layer.succeed(Git.Hooks, {
  preReceive: ({ repo, updates }) =>
    Effect.gen(function* () {
      const session = yield* Effect.serviceOption(Session);
      const user = Option.isSome(session) ? session.value.user : null;
      return updates.flatMap((update) =>
        update.ref === "refs/heads/main" && user?.id !== repo.owner
          ? [{ ref: update.ref, reason: "only the owner moves main" }]
          : [],
      );
    }),
});
```

`Git.Hooks` is optional; without it every update is accepted, and
`Git.HooksNone` says so explicitly. A hook may be a `Layer.effect` that
reads your own data. Who may write to a repository at all is the
middleware's question. [Part 6](/git/tutorial/part-6) implements and tests a
rule that prevents deleting `main`. A hook that must see the commit a merge
writes, or react after a push, decorates `Git.RepoStore` instead; [Repository](/git/blocks/repositories)
shows it.

## Internal hashing

Mount `Git.InternalApiLive` beside the protected public route layer. Its handler
checks its own internal secret; user credentials do not authorize internal hashing.
