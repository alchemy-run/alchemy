---
title: Building blocks
description: The layer graph behind a git host — what each block does, and how to replace one.
---

A git host is five decisions: where refs live, where names resolve,
where bytes go, who may do what, and what verifies a push. Each is a
[Layer](/infrastructure-as-effects/layers), and you make all five in
one graph:

```typescript
const GitLive = Git.ServerLive.pipe(
  Layer.provide(Git.ReposDurableObject),    // refs, objects, pull requests
  Layer.provide(Git.RegistryDurableObject), // owner/name -> repoId
  Layer.provide(Git.HasherInline),          // push verification
  Layer.provide(Git.BlobStoreR2(GitObjects)), // bulk bytes
  Layer.provide(Git.AuthTokens),            // access control
);
```

One graph, one `Effect.provide`. Never a chain of `Effect.provide`
calls — build the graph with `Layer.*` and provide it once.

## `Git.Server`

The top-level block: a `Context.Service` exposing the composed HTTP
handler for all three planes — the git smart-HTTP wire, the typed REST
API at `/api/v1`, and the [GitHub-compatible
facade](/git/github-api) at `/api/v3`.

```typescript
Effect.gen(function* () {
  const git = yield* Git.Server;
  return { fetch: git.fetch };
});
```

It is deliberately not a Worker. You construct the Worker, so you
choose the name, the domain, the compatibility date, and what else runs
alongside it.

## `Git.ReposDurableObject`

One Durable Object per repository, keyed by an internal id. It owns
everything that must be consistent: refs, the object index, loose
object bytes, tokens, the commit graph, and pull requests — all in the
DO's SQLite.

Refs live here because a git push is a compare-and-swap: the ref moved
from the value the client expected, or the push is rejected. A single
Durable Object gives that serialization for free, without a lock
service. The wire protocol itself runs inside the DO, so a push's ref
update is one `transactionSync`.

## `Git.RegistryDurableObject`

A singleton mapping `owner/name` to a repository id, enforcing
uniqueness and serving listings. Listings render from denormalized
columns so that listing a thousand repositories does not wake a
thousand Durable Objects.

The Worker caches resolutions in-isolate for a minute. A stale hit
fails safe: each repo DO stores its own `owner/name` and rejects
mismatched requests.

## `Git.BlobStore`

Bulk, immutable, content-addressed bytes: compacted packs, clone
bundles, oversize objects, and spilled push bodies. The contract is
exactly what the pack plane needs — ranged reads, whole-object writes,
multipart writes of unknown length, delete, and prefix listing.

Two implementations ship:

```typescript
Layer.provide(Git.BlobStoreR2(GitObjects))
```

```typescript
Layer.provide(
  Git.BlobStoreS3({ bucket: "my-git-objects", region: "us-east-1" }),
)
```

`BlobStoreS3` speaks SigV4 over Effect's `HttpClient`, so it runs
unchanged inside a Worker — compute on Cloudflare, bytes in S3, if
that is where your data has to live. R2 remains the default for
Cloudflare-hosted deployments: no egress fees and no cross-internet
hop on the serving path.

The package owns no bucket. You pass yours, and the one provided layer
serves both places bytes are touched — the Worker streaming clone
bundles, and the Durable Object reading and writing objects. See
[Storage & maintenance](/git/storage).

## `Git.Hasher`

Every object a push sends has to be inflated and hashed before a ref
moves. That is CPU, and where it runs is a layer.

```typescript
Layer.provide(Git.HasherInline)
```

The default hashes in the Worker that receives the push. It costs
nothing extra and is the right answer for the small pushes that make up
almost all of a repository's life.

```typescript
import * as GitLambda from "alchemy/Git/Lambda";

Layer.provide(GitLambda.HasherLambda(GitLambda.HasherFunction)),
Layer.provide(AWS.Lambda.InvokeFunctionHttp),
```

A Lambda hashes each 4 MiB chunk of a large push in its own invocation,
all of them at once. The Worker binds the function cross-cloud: Alchemy
mints an IAM identity for it and signs each call with an assumed role,
so nothing about your Worker changes except the layer. The stack that
declares it needs both provider sets. If a chunk cannot be hashed
there — a throttle, a cold start that runs out of time — the Worker
hashes it inline; a push never fails because its hasher did.

```typescript
import * as GitLoader from "alchemy/Git/WorkerLoader";

Layer.provide(GitLoader.HasherWorkerLoader()),
```

Four dynamically loaded Workers, each in its own isolate and its own
memory, hash a large push four chunks at a time. Nothing leaves
Cloudflare and nothing needs credentials; the hasher module is bundled
into your Worker at build time. The runtime allows four concurrent
loaded workers per request, so a push wider than that hashes in waves.

`Git.HasherSelf` fans out through the Worker's own service binding. On
Cloudflare that runs on the same thread as the caller, so it buys
nothing there; it is the shape a hasher on another host takes.

### Choosing a hasher

Measured on one client pushing a 40 MiB, 15.6k-object, delta-heavy
pack (`loose`) and a 44 MiB pack of whole blobs (`synthetic`), with
GitHub on a fresh repository from the same client for scale. Cloudflare
timings vary run to run by about a fifth.

| layer | parallelism | memory | leaves Cloudflare | extra cost | loose push | synthetic push |
| --- | --- | --- | --- | --- | --- | --- |
| `HasherInline` | none | the Worker's | no | none | 9.9–13.5 s | 8.8 s |
| `HasherWorkerLoader` | 4 isolates | 128 MB each | no | none | 5.9–7.2 s | 4.8–6.4 s |
| `HasherLambda` | one Lambda per 4 MiB chunk | 3 GB each | yes | Lambda-seconds, egress | 6.8–7.9 s | 6.3–6.7 s |
| GitHub | | | | | 3.3 s | 4.6 s |

The loader numbers include the later push-path work every layer
shares — deltas resolved as hasher jobs, delta-resolved blobs promoted
into a resolved pack, and a commit that no longer rewrites every staged
row — so the Lambda row would move down with it. Best runs are the
honest server-side comparison; the spread is the client's uplink.

Incremental pushes are 0.2–0.4 s on every layer (GitHub: 1.2 s); the
choice only matters for pushes of tens of megabytes. Start with
`HasherWorkerLoader` when large pushes matter and you want to stay on
Cloudflare; reach for `HasherLambda` when a push is wider than four
chunks and you already run AWS.

## `Git.AuthTokens`

The bundled access-control plugin: a deployer admin secret plus
per-repository scoped tokens. It is the smallest thing that makes a
fresh deployment secure, and it is meant to be replaced once you have
users. [Authentication](/git/auth) covers both halves.

## Replacing a block

Every block is a `Layer` producing a `Context.Service`, so swapping one
is swapping a line. To move bytes to S3, change the `BlobStore` line —
nothing else in the graph knows or cares.

Blocks are also required, not optional: omit one and the graph fails to
compile rather than failing at runtime. A missing `BlobStore` is a type
error at build time, not a 500 on your first clone.
