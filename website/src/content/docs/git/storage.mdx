---
title: Storage & maintenance
description: Where git objects live, how they are compacted, and the background jobs that keep a repository small.
---

Git objects move through three homes over their life, and the moves
happen on their own. Nothing here needs operating — this page explains
what the service is doing so the numbers make sense when you look.

## Where objects live

**Freshly pushed objects** land in the repository's Durable Object,
stored pre-deflated in SQLite. Small objects stay inline; oversize ones
go straight to blob storage with only their index kept locally.

**Compacted objects** live in real packfiles in blob storage. A
background job rewrites accumulated loose objects into an immutable
pack and drops the local copies, which is what keeps a busy
repository's Durable Object small.

**Clone bundles** are precomputed full-clone packs, keyed by a
snapshot of the repository's refs.

Because objects are stored already deflated, serving a pack is
concatenation plus a checksum rather than a recompression pass.

## Clone bundles

When a full clone arrives and a bundle matching the current refs
exists, the Durable Object answers with a reference to it and the
**Worker** streams the bytes. No pack byte passes through the DO, so
concurrent clones scale with Workers and object storage instead of
with one single-threaded object.

Refs move, and the bundle goes stale. That clone is served
dynamically and a new bundle is scheduled. Incremental fetches always
take the dynamic path — they are small by construction.

## Background jobs

Maintenance runs on Durable Object alarms, scheduled by the work
itself rather than a cron you configure:

- **Compaction** — triggered by a post-push size check. Rewrites loose
  objects into an immutable pack.
- **Bundling** — cuts a fresh clone bundle after refs move.
- **Purge** — drains a deleted repository's objects and blobs, then
  releases its name.

Jobs are idempotent and resumable: an interrupted run picks up where
it stopped on the next alarm, and re-issuing a delete re-arms a purge
whose alarm was lost.

## Choosing a store

R2 is the default for Cloudflare-hosted deployments — no egress fees,
and no cross-internet hop on the serving path:

```typescript
const GitObjects = Cloudflare.R2.Bucket("GitObjects");

Layer.provide(Git.BlobStoreR2(GitObjects))
```

S3 is available when data has to live in AWS:

```typescript
Layer.provide(
  Git.BlobStoreS3({ bucket: "my-git-objects", region: "us-east-1" }),
)
```

`BlobStoreS3` signs requests with SigV4 over Effect's `HttpClient`, so
it runs unchanged inside a Worker and inside the Durable Object —
compute on Cloudflare, bytes in S3. Credentials resolve through
`Config` at deploy time and bind to the Worker as secrets. Scope the
IAM policy to the bucket: `GetObject`, `PutObject`, `DeleteObject`,
`ListBucket`, and `AbortMultipartUpload`.

Expect higher serving latency than R2 — every read crosses the public
internet. Read coalescing keeps the request count low, but the hop is
real.

## Bringing your own

`Git.BlobStore` is a contract, not a class. Implement ranged reads,
whole-object writes, multipart writes, delete, and prefix listing, and
any object store works:

```typescript
const BlobStoreMine: Layer.Layer<Git.BlobStore> = Layer.effect(
  Git.BlobStore,
  Effect.gen(function* () {
    // return an object satisfying Git.BlobStoreShape
  }),
);
```

Multipart parts must be uniform in size except the last — the
intersection of R2's and S3's rules, and what any implementation
should assume.

## What to watch

A repository reports its object breakdown — loose, packed, offloaded,
and total bytes — plus timing for the last push, split into ingest,
staging, connectivity checking, and finalization. When a push feels
slow, that split says which phase to look at. Fetch a repository
directly for live numbers; listings report zeros by design.
