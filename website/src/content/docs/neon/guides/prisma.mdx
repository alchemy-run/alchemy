---
title: Prisma ORM with Neon
description: Manage your Prisma schema as a resource — alchemy regenerates migration SQL on deploy and Neon applies it transactionally on the project or branch.
---

Prisma gives you a typed data model in `schema.prisma`; alchemy's
`Prisma.Schema` resource turns it into a deploy-driven migration
pipeline. On every deploy the schema is diffed against the last
snapshot, pending SQL is regenerated, and `Neon.Project` /
`Neon.Branch` apply it transactionally — the deploy owns the whole
flow from schema change to migrated branch.

## Register the Prisma provider

`Prisma.Schema` ships in its own `providers()` layer — merge it
next to Neon's in your stack config:

```typescript
// alchemy.run.ts
import * as Neon from "alchemy/Neon";
import * as Prisma from "alchemy/Prisma";
import * as Layer from "effect/Layer";

providers: Layer.mergeAll(Prisma.providers(), Neon.providers()),
```

It's a build-time provider — it owns the migrations directory on
disk, not anything in a cloud account. It needs `prisma` and
`@prisma/client` installed (optional peers of `alchemy`).

## Declare the schema resource

Point `Prisma.Schema` at your schema file:

```typescript
import * as Prisma from "alchemy/Prisma";

const schema = yield* Prisma.Schema("app-schema", {
  schema: "./prisma/schema.prisma",
  // Workers need the workerd client runtime; the resource injects the
  // generator when the schema declares none.
  generateClient: { runtime: "workerd" },
});
```

`./prisma/schema.prisma` is an ordinary Prisma schema with a
`postgresql` datasource — on Prisma 7 the datasource block carries
no `url`, because the diff runs offline and the runtime connection
comes from a driver adapter. On deploy the provider runs
`prisma migrate diff` from the latest `snapshot.prisma` under `out`
(default `./prisma/migrations`) to the current schema and — only
when the diff would emit SQL — writes a new
`{timestamp}_migration/` directory containing `migration.sql` and
`snapshot.prisma`, then reruns `prisma generate` (injecting the
client generator when the schema has none, and an
[effect/Schema generator](/prisma/migrations#effect-schemas) for
your models alongside it). Migration files are meant to be checked
in, and removing the resource from the stack never deletes them.

## Feed `migrationsDir` from the schema

Wire the schema's `out` output into the Neon resource's
`migrationsDir`:

```typescript
import * as Neon from "alchemy/Neon";

const project = yield* Neon.Project("app-db", {
  region: "aws-us-east-1",
});

const branch = yield* Neon.Branch("app-branch", {
  project,
  migrationsDir: schema.out,
});
```

Because `Neon.Branch` depends on `schema.out`, the engine orders
them for you: `Prisma.Schema` regenerates pending migration SQL
first, then `Neon.Branch` scans the directory and applies any new
files transactionally, recording each in the `neon_migrations`
tracking table so it runs exactly once. The same prop works on
`Neon.Project` if you migrate the default branch directly — see
[Migrations](/neon/data/migrations) for the tracking and hashing
details.

## Iterate

Change `prisma/schema.prisma` — add a model, a field — and
redeploy:

```sh
bun alchemy deploy
```

The provider diffs the schema against the last snapshot, writes a
new migration directory with just the delta SQL, and the branch
applies it. When nothing changed, no migration is written and the
Neon resource isn't touched.

## Connect at runtime

The branch's outputs carry everything a client needs:
`connectionUri` / `pooledConnectionUri` plus the parsed `origin` /
`pooledOrigin` shapes (see [Connections](/neon/data/connections)). On
Cloudflare, front the **direct** origin with Hyperdrive:

```typescript
const hyperdrive = yield* Cloudflare.Hyperdrive.Connection("app-hyperdrive", {
  origin: branch.origin, //    direct — Hyperdrive does the pooling
  dev: branch.pooledOrigin, // local dev bypasses Hyperdrive
});
```

Inside the Worker, `postgres` from `alchemy/Prisma/Postgres` takes
your generated `PrismaClient` class and Hyperdrive's connection
string, and returns a client whose queries you `yield*` directly:

```typescript
import { postgres } from "alchemy/Prisma/Postgres";
import { PrismaClient } from "./generated/client.ts";

const hd = yield* Cloudflare.Hyperdrive.Connect(Hyperdrive);
const prisma = yield* postgres(PrismaClient, hd.connectionString);
```

To reach Neon directly over WebSockets — skipping Hyperdrive —
use `neon` from `alchemy/Prisma/Neon` with the branch's connection
URI bound into the Worker's env instead; it drives Neon's
serverless driver via `@prisma/adapter-neon`. The
[Add Prisma ORM](/cloudflare/data/prisma) guide walks through the
whole Worker side: binding the connection, the `nodejs_compat`
flag for the pg adapter, and the install commands.
