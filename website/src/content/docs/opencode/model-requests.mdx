OpenCode asks a model provider for every answer. Running it in a sandbox would normally mean putting a provider key there, next to code the model writes and runs. A harness doesn't. OpenCode in the sandbox is configured with one provider, and that provider is a **bridge** on the sandbox's own loopback address. The harness in your Durable Object answers each request with the model's Layer.

## What is in the sandbox

Two programs: OpenCode's server, and the bridge. Both listen only on `127.0.0.1`. The bridge speaks the OpenAI chat completions format to OpenCode, and holds each request until it is answered.

There is no provider key in the sandbox, and nothing there knows your runtime's address.

## How the harness reaches it

The harness uses the one thing every sandbox platform has: running a command in the sandbox. One command follows the bridge and prints each waiting request. Another sends a reply. Both are started by the harness, so the sandbox needs no public port and accepts no inbound connection.

## How a request is answered

The harness turns the request into an Effect AI prompt and runs it on the `AI.Model` the prompt chose. That is the Layer you provided: Workers AI, an AI Gateway, or any other provider. The tools OpenCode offered are passed through, and tool calls go back to OpenCode, which runs them itself.

```typescript
const reply = yield* harness.session("pr-142").prompt("Fix the failing test.", { model: Smart });
```

Logging, caching, rate limits and spend caps on your gateway apply to OpenCode's requests, because they are your runtime's requests.

## Calls to your tools

Your tools travel the same way. OpenCode sees them as tools of an MCP server the bridge serves, calls one, and the bridge holds the call until the harness has run the handler in the Durable Object. See [Tools](/opencode/tools).

## When the Durable Object is evicted

A request waits in the bridge until a harness answers it. A prompt whose Durable Object is evicted midway stops being answered, and nothing wakes the object by itself. Run prompts from the object's alarm with a `requestId`, so the job is delivered again and the retried prompt joins the one still running. See [Sessions & prompts](/opencode/sessions#prompts-take-minutes).
