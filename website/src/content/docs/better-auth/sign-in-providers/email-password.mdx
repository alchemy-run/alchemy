Start with the [shared Auth service and browser client](/better-auth/sign-in-providers),
which already enables `emailAndPassword` at `/api/auth`.

Email/password needs no OAuth application, client ID, client secret, or
`/api/auth/callback/email-password` registration; email delivery is a separate integration.

## Configure real email delivery

This example sends through [Resend's email API](https://resend.com/docs/api-reference/emails/send-email).
In the Resend dashboard, add a domain, publish its requested DNS records, and wait for domain verification.

Create an API key with sending access to that domain and store it as secret
`RESEND_API_KEY`; set `AUTH_EMAIL_FROM` to a sender on the verified domain, such as `Auth <auth@example.com>`.

Use a real verified sender for external recipients, not a sandbox sender with restricted
recipients; configure these server-side values through [Configuration](/better-auth/guides/configuration).

Start the basic email/password tutorial with `alchemy dev` before adding this mail
configuration; Alchemy allocates an available port and prints the URL.

Set `AUTH_BASE_URL` to that printed origin locally, without a trailing slash or path.
For production, use your real origin, such as `https://auth.example.com`.

Verification links go through `/api/auth/verify-email`; reset links go through
`/api/auth/reset-password/<token>` before returning to your application page.

## Import the mail transport APIs

Add these imports to `src/auth.ts`, retaining the shared setup's existing imports,
exported `authOptions`, and `Auth` class.

```typescript
import * as Config from "effect/Config";
import * as HttpClient from "effect/unstable/http/HttpClient";
import * as HttpClientRequest from "effect/unstable/http/HttpClientRequest";
import * as HttpClientResponse from "effect/unstable/http/HttpClientResponse";
```

## Configure verification and recovery

Replace `const makeAuth = BetterAuth(authOptions)` with this complete Resend integration:

```typescript
const makeAuth = Effect.gen(function* () {
  const baseURL = yield* Config.String("AUTH_BASE_URL");
  const from = yield* Config.String("AUTH_EMAIL_FROM");
  const apiKey = yield* Config.Redacted("RESEND_API_KEY");
  const http = yield* HttpClient.HttpClient;

  const sendMail = (to: string, subject: string, text: string) =>
    Effect.gen(function* () {
      const response = yield* http.execute(
        HttpClientRequest.post("https://api.resend.com/emails").pipe(
          HttpClientRequest.bearerToken(apiKey),
          HttpClientRequest.bodyJsonUnsafe({ from, to: [to], subject, text }),
        ),
      );
      yield* HttpClientResponse.filterStatusOk(response);
      yield* response.text;
    }).pipe(
      Effect.timeout("10 seconds"),
      Effect.mapError(() => new Error("Email delivery failed")),
      Effect.scoped,
      Effect.runPromise,
    );

  return yield* BetterAuth({
    ...authOptions,
    baseURL,
    emailAndPassword: {
      ...authOptions.emailAndPassword,
      requireEmailVerification: true,
      revokeSessionsOnPasswordReset: true,
      sendResetPassword: ({ user, url }) =>
        sendMail(user.email, "Reset your password", `Reset your password: ${url}`),
    },
    emailVerification: {
      sendOnSignUp: true,
      autoSignInAfterVerification: false,
      sendVerificationEmail: ({ user, url }) =>
        sendMail(user.email, "Verify your email", `Verify your email: ${url}`),
    },
  });
});
```

Config is evaluated when `Auth.layer` is constructed; the HTTP bearer-token helper
accepts the redacted API key directly, so no manual secret unwrapping is needed.

The Promise bridge is confined to Better Auth's upstream mail hooks, and each send
performs its own bounded HTTP request; no connection or in-flight request is retained between Worker events.

The hooks send Better Auth's generated URLs unchanged as plain text.
Never print verification/reset links or log mail bodies, request headers, API keys, or passwords.

## Provide HTTP from the host

In the host module, compose the mail HTTP client into the Auth layer and use
`authLayer` where the Worker previously provided `Auth.layer`.

```typescript
import * as Layer from "effect/Layer";
import * as FetchHttpClient from "effect/unstable/http/FetchHttpClient";
import { Auth } from "./auth.ts";

const authLayer = Auth.layer.pipe(Layer.provide(FetchHttpClient.layer));
```

Keep the host's existing `CloudflareD1(AuthDb)` and runtime provision unchanged.
Alchemy still supplies the stable auth signing secret and supported database migrations automatically.

## Register a user

Call this from the registration form with its name, email, and password fields;
render the returned message as text.

```typescript
import { authClient } from "./client.ts";

export async function signUp(name: string, email: string, password: string) {
  try {
    const { error } = await authClient.signUp.email({
      name,
      email,
      password,
      callbackURL: "/sign-in",
    });
    if (error) return "Could not register. Check your details and try again.";
    return "Check your inbox to verify your email, then sign in.";
  } catch {
    return "Could not reach the server. Try again.";
  }
}
```

Verification is required before a session is issued; successful registration is not
successful authentication, and this configuration asks the user to sign in after verifying.

Better Auth's default password length range is 8–128 characters.
Keep server-side validation authoritative and do not persist password fields in browser storage.

## Sign in

Use `authClient` from the same-origin `src/client.ts`, not a server-side Auth instance.
Only redirect after a successful response containing a user.

```typescript
import { authClient } from "./client.ts";

export async function signIn(email: string, password: string) {
  try {
    const { data, error } = await authClient.signIn.email({ email, password });
    if (error?.code === "EMAIL_NOT_VERIFIED") return "Verify your email first.";
    if (error) return "Could not sign in. Check your email and password.";
    if (!data?.user) return "Sign-in did not finish. Try again.";
    window.location.assign("/account");
  } catch {
    return "Could not reach the server. Try again.";
  }
}
```

Check the session on `/account` and enforce it on the server as shown in
[Result handling](/better-auth/sign-in-providers#handle-the-returned-result).

## Resend a verification message

Offer a resend action on the sign-in page without revealing whether an address is registered.
Keep rate limiting enabled and apply an appropriate resend cooldown in the UI.

```typescript
import { authClient } from "./client.ts";

export async function resendVerification(email: string) {
  try {
    const { error } = await authClient.sendVerificationEmail({
      email,
      callbackURL: "/sign-in",
    });
    if (error) return "Could not request verification. Try again later.";
    return "If this address needs verification, check its inbox.";
  } catch {
    return "Could not reach the server. Try again.";
  }
}
```

Handle expired or invalid verification links on `/sign-in` with a fixed message and a
resend action; do not display raw query-string error descriptions.

## Request a password reset

Create a `/reset-password` page containing your new-password form.
The `redirectTo` below is an application destination, not a provider callback URI.

```typescript
import { authClient } from "./client.ts";

export async function requestReset(email: string) {
  try {
    const { error } = await authClient.requestPasswordReset({
      email,
      redirectTo: "/reset-password",
    });
    if (error) return "Could not request a reset. Try again later.";
    return "If this email has an account, check its inbox for a reset link.";
  } catch {
    return "Could not reach the server. Try again.";
  }
}
```

A successful request must not disclose whether the account exists.
The mail transport reports delivery failures without including sensitive request content; monitor delivery status without recording the reset link.

## Submit the new password

Read the reset token on the reset page, remove it from the address bar, and retain
it only in the page's memory until submission.

```typescript
import { authClient } from "./client.ts";

const query = new URLSearchParams(window.location.search);
const token = query.get("token");
const invalidLink = query.has("error") || !token;
window.history.replaceState(null, "", window.location.pathname);

export async function resetPassword(newPassword: string) {
  if (invalidLink || !token) return "Request a new reset link.";
  try {
    const { error } = await authClient.resetPassword({ token, newPassword });
    if (error) return "Could not reset your password. Request a new link.";
    window.location.assign("/sign-in");
  } catch {
    return "Could not reach the server. Try again.";
  }
}
```

Serve this page without third-party analytics and with `Referrer-Policy: no-referrer`;
configure access-log redaction for token-bearing auth URLs as well.

Reset tokens are single-use, and the configuration above revokes existing sessions
on reset; a reload after removing the token requires reopening the email link.

## Keep account ownership explicit

Retain the shared `disableImplicitLinking: true` policy when adding social providers.
An existing email/password user signs in first, then explicitly links the provider instead of creating a second account or merging by email.

Password recovery can also establish a password for an existing social-only account,
so email ownership and real delivery are security boundaries, not optional UI features.

Never manually mark an address verified to unblock sign-in, disable verification in
production to work around mail failures, or enable different-email linking to hide an account collision.
