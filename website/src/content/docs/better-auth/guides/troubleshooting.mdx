---
title: Troubleshooting
description: Diagnose Better Auth configuration, session, migration, and provider failures without exposing credentials.
---

Start with the failing HTTP status and literal error code. Do not treat a deployment failure, unavailable database, or failed session lookup as a signed-out user.

## Check the public route

For the local tutorial, leave `bunx alchemy dev` running and paste its printed origin into another shell, without a trailing slash:

```sh
read -r BASE_URL
```

For a deployed application, use its actual origin instead, such as `https://auth.example.com` from [Part 6](/better-auth/tutorial/part-6). Check the same route in either environment:

```sh
curl --silent --show-error --output /dev/null \
  --write-out '%{http_code}\n' \
  "$BASE_URL/api/health"
```

A failed health request is not yet an authentication diagnosis. Check routing, deployment, and hostname configuration before changing auth options.

## Check the route mount

The tutorial routes exactly `/api/auth` and its child paths to `auth.fetch`; other paths go to the Effect HTTP API. If `/api/health` works but `/api/auth/get-session` returns `404`, compare the mount with `authOptions.basePath` in [Part 2](/better-auth/tutorial/part-2).

Do not put the application `Authentication` middleware in front of `/api/auth`. Sign-in and OAuth callbacks must work before a session exists.

## Interpret session responses

On `/api/auth/get-session`, a successful `null` response means there is no valid session. On the protected `/api/me` endpoint, the tutorial maps that result to typed `Unauthorized` with HTTP `401`.

`AuthenticationUnavailable` with HTTP `503` means session resolution failed. Preserve that distinction using [HTTP API middleware](/better-auth/guides/http-api-middleware), including its defect-handling boundary where needed.

## Inspect errors without dumping credentials

The wrapper's `BetterAuthApiError.status` is a string such as `"UNAUTHORIZED"`; `statusCode` is the numeric HTTP code. Match the numeric status and literal `body.code`, not a guess based on the message alone.

In the request Effect in `src/middleware.ts`, add this diagnostic to the session lookup. It logs only a fixed label, status, and code before preserving the tutorial's `503` mapping:

```typescript
const session = yield* auth.getSession().pipe(
  Effect.tapError((error) =>
    Effect.logWarning("Session lookup failed", {
      statusCode: error.statusCode,
      code: error.body?.code,
    }),
  ),
  Effect.mapError(() => new AuthenticationUnavailable()),
  Effect.catchDefect(() => Effect.fail(new AuthenticationUnavailable())),
);
```

The tutorial already imports `Effect` and declares `AuthenticationUnavailable` in that file. Do not log the whole error: its headers and cause may contain cookies or sensitive backend details.

## Inspect the deployed logs

For a deployment that uses the `prod` stage and `prod` profile:

```sh
bunx alchemy logs --stage prod --profile prod --since 10m --limit 50
```

Use the same stage, profile, and stack config as the deployment you are investigating. Review logs locally and redact credentials, cookie headers, request bodies, and personal data before sharing excerpts.

## Check the selected profile

```sh
bunx alchemy profile current
bunx alchemy profile show --profile prod
```

Profile output redacts credentials, but still contains account metadata. A profile named `prod` selects cloud authentication; it does not load production application settings or select the `prod` stage.

## Check configuration binding

Resolve an optional `AUTH_BASE_URL` override and any `Config.Redacted(...)` values while constructing the Auth layer. Resolving them only inside `fetch` does not register deploy-time bindings.

If using an explicit env file, supply it again on subsequent deployments:

```sh
bunx alchemy deploy --stage prod --profile prod --env-file .env.production
```

An explicit `--env-file` takes precedence over process values for keys in that file; without it, process values take precedence over `.env`. See [configuration](/better-auth/guides/configuration) for the complete service example.

## Resolve origin and callback errors

For `INVALID_ORIGIN`, compare the incoming origin with `baseURL` and `trustedOrigins`. For `INVALID_CALLBACK_URL` or a provider redirect mismatch, compare the configured callback URLs exactly, including scheme, hostname, port, and path.

Derive the GitHub callback from the actual origin rather than guessing a local URL. Paste the origin printed by Alchemy, or the deployed origin for production:

```sh
read -r BASE_URL
printf '%s/api/auth/callback/github\n' "$BASE_URL"
```

Register that exact result with the matching OAuth application. If the local origin changes, update the callback and any explicit `AUTH_BASE_URL` override.

The post-login `callbackURL` is a different URL: it is where the user goes after authentication. Follow [GitHub sign-in](/better-auth/sign-in-providers/github) rather than disabling CSRF or origin validation.

## Diagnose a missing session cookie

Use the [cookie-jar test](/better-auth/guides/testing) to check sign-in, session lookup, and `/api/me` against the same origin. Keep the hostname consistent: `localhost` and `127.0.0.1` are different cookie hosts.

For browser sign-in, call the client against the mounted `auth.fetch` route. Calling a server-side `auth.api.signInEmail()` and returning only its data does not forward `Set-Cookie` to the browser.

## Diagnose sessions lost after deployment

For a new application, the wrapper's signing secret is automatic and stable across deployments of the same resource. Check for a changed stage, auth `id`, resource namespace, lost state, replaced database, or changed cookie configuration before rotating anything.

If importing an existing installation, preserve its signing secret and follow [migrations](/better-auth/guides/migrations). A new secret can invalidate cookies and affect encrypted data; it is not a routine fix for a database error.

## Diagnose stale access after revocation

A valid cookie cache can outlive server-side session revocation. Bypass it on sensitive server authorization paths or leave cookie caching disabled, as described in [sessions](/better-auth/guides/sessions).

A cleared cookie jar proves browser sign-out, not that every previously copied credential has been invalidated. Better Auth's sign-out handler can still clear cookies when session deletion fails, so investigate storage errors separately.

## Resolve migration failures

`BetterAuthMigrationError` reports a deploy-time migration failure; inspect its underlying cause locally to distinguish connection, permissions, and schema problems. Do not set `migrate: false` merely to hide the failure and deploy against a missing schema.

An error saying the database layer does not support automatic migrations is literal: use a supported layer or manage the schema explicitly. Follow [migrations](/better-auth/guides/migrations) and the selected [database guide](/better-auth/databases); do not repeatedly retry an unsafe schema change.

## Resolve plugin type or schema failures

Keep `authOptions` declared with `satisfies BetterAuthProps`, and pair server plugins with their client plugins where required. If a new field is missing in the database, confirm that the plugin's schema change was applied to the database actually bound to this Worker.

Review the [plugin guide](/better-auth/guides/plugins) before adding casts or treating a missing endpoint as an authentication error.

## Resolve linking and freshness errors

`SESSION_NOT_FRESH` requires signing in again for the sensitive operation. `FAILED_TO_UNLINK_LAST_ACCOUNT` protects the user's remaining sign-in method; do not remove that protection just to make the request succeed.

For `LINKING_DIFFERENT_EMAILS_NOT_ALLOWED` or the OAuth callback error `email_does_not_match`, verify the identities being linked. Follow [account linking](/better-auth/guides/account-linking), not an email-based user merge.

## Resolve secondary-storage failures

The error `Secondary-storage rate limiting requires SecondaryStorage.increment.` means the configured store lacks the required atomic operation. A non-atomic read/update/write implementation is not a fix.

Check all five operations, seconds-based TTLs, and construction-time layer provisioning in [secondary storage](/better-auth/guides/secondary-storage). Do not convert storage outages to missing keys.
