## Check the public auth route

```sh
read -r BASE_URL
BASE_URL=${BASE_URL%/}
curl --silent --show-error --output /dev/null \
  --write-out '%{http_code}\n' \
  "$BASE_URL/api/auth/get-session"
```

Enter the origin of the existing application you are diagnosing, or the origin printed by its running `alchemy dev` process. These commands assume its Better Auth `basePath` is `/api/auth`; substitute the actual mount if yours differs.

An anonymous session lookup normally returns `200` with a `null` body, not an authentication denial. A `404` suggests a missing route or mismatched mount; a failed connection suggests routing, deployment, or hostname problems before authentication.

Keep Better Auth's sign-in and callback routes outside application authentication middleware. Mount `auth.fetch` on exactly the configured base path and its child paths, preserving its complete responses rather than rebuilding them from data.

## Log only safe diagnostic fields

```typescript
// session-diagnostics.ts
import type {
  BetterAuthInstance,
  BetterAuthProps,
} from "@alchemy.run/better-auth";
import * as Effect from "effect/Effect";
import * as Schema from "effect/Schema";

export class AuthenticationUnavailable extends Schema.TaggedError<AuthenticationUnavailable>()(
  "AuthenticationUnavailable", {}, { httpApiStatus: 503 },
) {}

export const getSessionWithDiagnostics = <O extends BetterAuthProps>(
  auth: BetterAuthInstance<O>,
) => auth.getSession().pipe(
  Effect.tapError((error) =>
    Effect.logWarning("Session lookup failed", {
      statusCode: error.statusCode,
      code: error.body?.code,
    }),
  ),
  Effect.mapError(() => new AuthenticationUnavailable()),
  Effect.catchDefect(() => Effect.fail(new AuthenticationUnavailable())),
);
```

This complete helper takes the instance returned by `BetterAuth` as its argument and returns a request-scoped Effect requiring the ambient HTTP request and Alchemy runtime context. Call it within a host request, not during layer construction; it intentionally does not create a second auth instance or database.

The helper preserves `null` as anonymous and maps lookup failures to a typed `503` error. A native HTTP API must declare `AuthenticationUnavailable` in its endpoint or middleware error schema; map only a successful `null` lookup to the application's `401` response.

`BetterAuthApiError.status` is a string such as `"UNAUTHORIZED"`; `statusCode` is numeric. Inspect that number and the literal `body.code`, not message guesses or the entire error, whose headers and cause may contain credentials.

Keep the catch around session resolution, not the downstream application handler. Otherwise a database or business-logic defect unrelated to authentication could be mislabeled as an authentication outage.

## Inspect the matching deployment

```sh
read -r STAGE
read -r PROFILE
bunx alchemy logs --stage "$STAGE" --profile "$PROFILE" --since 10m --limit 50
bunx alchemy profile show --profile "$PROFILE"
```

Enter the existing deployment's stage and profile, and run from its stack directory with the same config selection. Review output locally: profile output redacts credentials but still contains account metadata, and application logs may contain personal data.

A profile selects cloud authentication, not an application URL, stage, or env file. An explicit env file must be supplied again on subsequent deployments; it is not remembered merely because the previous command used it.

## Check construction-time configuration

Resolve `Config` values while constructing the Auth layer or Worker implementation, before returning `fetch`. Resolving provider credentials or an optional `AUTH_BASE_URL` only inside a request does not register deploy-time bindings.

When `AUTH_BASE_URL` is absent, request-origin detection allows Alchemy to select an available local port. An explicit override must match the actual origin and must be updated if that local origin changes.

`baseURL` does not provision DNS or attach a Worker domain. An explicit `--env-file` takes precedence over process values for keys in that file; without it, process values take precedence over `.env`.

## Resolve origin and callback errors

```sh
printf '%s/api/auth/callback/github\n' "$BASE_URL"
```

For GitHub, register this result as the authorization callback in the OAuth App whose credentials the server uses. The `BASE_URL` read above must be that environment's actual origin, not a guessed local port.

For `INVALID_ORIGIN`, compare the incoming origin with `baseURL` and `trustedOrigins`. For `INVALID_CALLBACK_URL` or a provider redirect mismatch, compare scheme, hostname, port, and path exactly.

The browser's post-login `callbackURL` is a separate destination after authentication. Use the intended exact origins and matching provider credentials rather than disabling CSRF or origin checks.

## Diagnose missing or stale cookies

Use a real cookie jar or browser against the mounted auth route, keeping the hostname consistent: `localhost` and `127.0.0.1` are different cookie hosts. Calling server-side `auth.api.signInEmail` and returning only its data does not forward `Set-Cookie` to the browser.

A valid cookie cache can outlive server-side revocation; bypass it on sensitive authorization paths or leave caching disabled. A cleared jar proves browser sign-out, not invalidation of copied credentials, especially because sign-out may still clear cookies after a deletion failure.

If sessions disappear after deployment, check the stage, auth `id`, resource namespace, local state, database identity, and cookie configuration. The wrapper's generated signing secret is stable for the same resource; rotating it is not a fix for a database error.

When moving an existing installation, preserve its signing identity and plan the database migration. A new secret can invalidate cookies and affect encrypted data even if the user rows were copied correctly.

## Resolve migration failures

`BetterAuthMigrationError` identifies a deploy-time failure; inspect its cause locally to distinguish connectivity, permissions, and unsafe schema changes. Do not set `migrate: false` merely to deploy against a missing schema or repeatedly force an unsafe change.

A layer without automatic migration support needs application-owned tooling or a supported database layer. Back up and rehearse existing-data changes, and remember that rolling back code does not undo schema changes.

## Resolve plugin and account errors

Pass plugin configuration inline to `BetterAuth` to preserve inference, and pair server plugins with their browser plugins where required. A missing database field means checking whether the schema change reached the database actually bound to this host, not adding a type cast.

`SESSION_NOT_FRESH` requires signing in again; `FAILED_TO_UNLINK_LAST_ACCOUNT` protects the remaining sign-in method. For `LINKING_DIFFERENT_EMAILS_NOT_ALLOWED` or `email_does_not_match`, verify the identities rather than weakening verification or merging users by email.

In Better Auth 1.7.5, unlink using the linked account row's `id` as the request's `accountId`. Its provider-side account identifier is not interchangeable with that local ID.

## Resolve secondary-storage failures

`Secondary-storage rate limiting requires SecondaryStorage.increment.` means the store lacks a required atomic operation. A non-atomic read/update/write sequence cannot fix it.

Verify all five operations: reads, expiring writes, idempotent deletion, atomic read-and-delete, and fixed-window increments. Supply the layer during Better Auth construction, use TTLs in seconds, and report outages as failures rather than missing keys.
