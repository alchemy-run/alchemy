Better Auth owns its schema — tables for users, sessions, accounts,
verifications, plus whatever your plugins add. With alchemy, applying
that schema is part of `alchemy deploy`, not a separate CLI step.

## How it works

When a stack containing `BetterAuth()` is evaluated, the package
registers an internal alchemy **Action** (`BetterAuth.Migrate`). Actions
run only during apply — never at plan, and the migration code is
dead-code-eliminated from deployed runtime bundles entirely.

The Action's input is a hash of:

- **the schema fingerprint** — derived from your options (plugins,
  additional fields, model renames, table indexes), so adding a plugin re-runs the
  migration on the next deploy;
- **the database identity** — a non-secret identifier from the layer
  (a D1 `databaseId`, a digest of the connection string, cluster ARNs),
  so pointing at a new database re-runs it too. Connection strings
  themselves are never persisted to state.

Unchanged input ⇒ the Action no-ops without touching the database.
`--force` re-runs it. Migrations are additive and idempotent
(`CREATE TABLE` / `ADD COLUMN` / `CREATE INDEX` on what's missing).
Existing data must satisfy new constraints. Unsafe changes fail with a
`BetterAuthMigrationError`; Alchemy does not rewrite account identities,
merge users, or convert legacy plugin data.

The host Function/Worker depends on the migration through its
environment, so first-deploy traffic cannot race the schema.

## Upgrading from 1.6 to 1.7.5 or newer

Upgrade directly to 1.7.5 or a later compatible 1.x release. The core
account schema is unchanged from 1.6: **do not add or backfill an `issuer`
column**. This guide assumes you have not applied the intermediate
1.7.0–1.7.2 issuer schema; if you have, follow the
[upstream cleanup instructions](https://better-auth.com/docs/guides/1-7-upgrade-guide#account-identity-keeps-the-provider-key)
first.

### Back up and check existing data

Back up the database and rehearse on a copy containing existing users,
accounts, and sessions. Keep the same auth secret. Check duplicate
`(providerId, accountId)` pairs using your configured table and column names.
Resolve account ownership explicitly rather than merging users by email.

Some integrations require manual preparation before the schema can be applied:

| Integration | Preparation |
| --- | --- |
| Microsoft / Microsoft Entra | Map old `sub` account IDs to verified `oid` values or a trusted directory export. Pause sign-in and linking until complete. |
| Custom OAuth / SSO identity mappings | Map existing subjects to the provider's verified immutable identifier. |
| Legacy OIDC / MCP provider | Move client registrations to `oauthClient` and handle legacy token tables. Generated migrations do not copy client records. |
| SCIM | Stop old provisioning and complete the upstream reprovisioning procedure. The new SCIM transaction requirements are not supported by D1. |
| Device Authorization | Resolve duplicate device/user codes. MySQL and SQL Server also require bounded strings. |

Follow the relevant sections of the
[Better Auth upgrade guide](https://better-auth.com/docs/guides/1-7-upgrade-guide)
for these data changes. Alchemy's dependency ordering delays the **new**
host deployment; it does not stop old application instances. Use a
maintenance window for incompatible changes, and do not assume an app
rollback reverses database changes.

### Upgrade packages together

Update `@alchemy.run/better-auth` to a release supporting Better Auth 1.7.5,
then align Better Auth and its synchronized plugins/adapters. Use the CLI
version matching your selected release; for 1.7.5:

```sh
npx auth@1.7.5 upgrade
```

The CLI requires Node.js 22.12 or newer. Review workspace catalogs and
package overrides manually. This command updates packages, not application
code or identity data.

### Apply the schema

For SQL layers with automatic migration support, the wrapper call stays the same:

```typescript
const auth = yield* BetterAuth({
  emailAndPassword: { enabled: true },
});
```

After any manual preparation, `alchemy deploy` applies the required schema
before updating the host. Ordinary email/password users upgrading directly
from 1.6 need no account-identity conversion.

Drizzle users continue to own schema migrations: regenerate and review the
auth schema, apply it through Drizzle's migration tooling, and include the
generated `authRelations` when constructing the database. See
[the Drizzle layer](/providers/betterauth/drizzle) for the configuration.
With `migrate: false`, apply your schema before deploying the new runtime.

The upstream CLI expects an exported upstream `betterAuth(...)` instance,
not an Effect-based Alchemy stack. Share the same plugins and schema options
with a separate CLI configuration when using `auth generate`. For Drizzle,
that configuration must use `@better-auth/drizzle-adapter/relations-v2`.
Run `npx auth@1.7.5 generate --config ./auth.cli.ts` without
`--adapter drizzle`: that flag bypasses the configured adapter's generator
and emits legacy relations instead of `authRelations`.

### Update application APIs

- Generic OAuth uses `signIn.social({ provider })` and `linkSocial()`;
  register `/api/auth/callback/:id` instead of `/api/auth/oauth2/callback/:id`.
- Account selectors use the local account row ID. Token/profile operations
  choose `{ accountId }` or `{ useAccountCookie: true }`, not `providerId`.
- Custom secondary storage must implement atomic `increment(key, ttl)` and
  `getAndDelete`. The TTL is required and must not be extended by subsequent
  increments. Custom rate-limit storage uses `consume` instead of `get`/`set`.
- Move `experimental.joins` to `advanced.database.joins`.

Review the upstream guide for plugin-specific changes, including SSO, MCP,
mobile clients, and proxy configuration.

### Verify the upgrade

Sign in as an existing user, create a new user, read an existing session,
and sign out. Exercise each configured social/SSO provider and account
link/list/refresh/unlink flow. Confirm existing user IDs are preserved and
no duplicate users were created. Repeat deployment to check that the
migration is a no-op once the schema is current.

## Per-layer transport

Each layer supplies its own deploy-time connection:

| Layer | Deploy-time migration path |
| --- | --- |
| `CloudflareD1` | D1 HTTP query API (or the local simulator under `alchemy dev`) |
| `Neon` | serverless driver against the same connection string |
| `AuroraDataApi` | RDS Data API with the stack's credentials |
| `CloudflareHyperdrive` | the **origin** URL you pass as `migrate` (Hyperdrive's own string is runtime-only) |
| `Postgres` / `MySQL` | the connection string (or a separate `migrate` source) |
| `SQLite` | the same local file |
| `Memory` / `Drizzle` | no migration — memory needs none; Drizzle schemas are user-owned |

## Opting out

```typescript
const auth = yield* BetterAuth({
  migrate: false,
  emailAndPassword: { enabled: true },
});
```

With `migrate: false` you own the schema — generate it with
`npx auth@1.7.5 generate --config ./auth.cli.ts` and apply it through your own migration
flow (for Drizzle users that is the default and only mode).

Multiple `BetterAuth` instances in one stack? Give each a distinct
`id` — it suffixes the migration Action and the auto-provisioned secret
so they don't collide.
